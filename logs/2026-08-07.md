## 저녁 체크업

**오늘 한 일 — 텍스트-앵커 : 청크별 정답 구절 라벨링 진행**
- 문단(문서) 하나당 청크를 직접 읽으면서 정답을 라벨링하는 방식으로 진행
- 질의마다 실제 문서 링크를 직접 열어보며 정답을 라벨링(수작업 대조)
- 중복 라벨링 체크: 동일 내용이 여러 청크에 있는 경우 중복 라벨링 허용
- 근거 청크 부족 문제 발견 : 특정 텍스트만으로는 답을 낼 수 없고 어디를 정답으로 태깅해야 하는지 애매한 케이스가 절반 수준

**오늘 한 일 — 큐폼 : 설계 스펙 확정**
- 큐폼 성격 재정의(D1) : 큐폼 = 슬롯 추출기 + 조건부 되묻기로 확정. 모든 질의에 추출기를 돌리며 진입/미진입 개념 자체가 없음
- 되묻기 규칙 : `sub_task`가 잡혔는데도 남은 조합 행이 2개 이상일 때만 되묻기 발동
- 착오송금 슬롯 5종 확정
- 조합 테이블 근거 표기 확정
- 종착점(outcome) 다중 부착 허용 : 정보 / 서류 / 서류;정보 3값으로 확정
- 착오송금 관통 스프린트 구현 완료

**논의사항 — 텍스트-앵커 : 기존 방식의 구조적 한계**
- 문제 : business_function(업무) 단위로 검색 범위를 고정해서 라벨링을 진행하다 보니, 실제 정답이 그 업무가 아닌 다른 업무의 청크에 있는 경우를 놓치는 사례가 발견됨(BF 밖에도 정답이 존재)
- 건의/결정 : BF를 고정하지 않고 전체 코퍼스를 대상으로 검색하도록 전환. 라벨링 단계에서 BF를 고정하지 않아도 평가에는 문제가 없음

**논의사항 — 큐폼**
- 첨부문서 태깅 : 큐폼 슬롯 값을 기반으로 첨부 후단 필터를 적용했을 때, 기존 22건(11서식) 통째 반환 대비 상황별 1~5서식으로 좁혀지는 실측 결과를 공유하며 첨부 태깅 방식 자체를 큐폼 슬롯 체계와 어떻게 연동할지 논의
- 되묻기 문구가 지금은 예시 제시형인데, 공공기관 톤에 맞는지 검수 필요
