## 저녁 체크업

**1. 큐폼 구조 변경 — 트리 → 테이블**
- 기존에는 트리 구조로 설계하려 했으나 한계 확인 → 테이블 구조로 전환. 경우의 수가 42개 정도로 크지 않아(열 데이터 42개, 행도 많지 않음) 테이블로 다뤄도 부담 없다고 판단
- 원래 트리를 고려한 이유는 "열 데이터가 필요 없는 부분이 많아서"였는데, 그 이점보다 트리 구조의 한계가 더 크다고 결론

**2. 라우팅 모델(6개 분류) ↔ 큐폼 연계 방식**
- 라우팅에서 나온 6개 업무 분류 결과를 큐폼에 가중치로만 반영할지 논의(하드 필터 아님, 기존 soft-boost 원칙 유지 방향)
- 큐폼 슬롯을 채우는 작업 자체는 LLM에 맡기는 게 낫다고 정리. 큐폼 작성이 필요한 질의인지 판단하는 라우팅 과정은 약 0.1초 수준으로 가벼움

**3. 큐폼 적용 범위 및 원칙 재확인**
- 모든 질의에 큐폼을 적용하지는 않을 것 — 신청서 필요/상황 묘사가 필요한 질의에만 큐폼을 넣어 정확도를 높이는 방향. 큐폼이 트리거된다는 것 자체가 "복잡한 질의"라는 의미이므로, 응답 시간이 길어져도 괜찮다고 판단
- 큐폼은 보조 장치이고 답변의 본체는 LLM — 큐폼 없이도 답변이 잘 되는 게 기본 전제, 큐폼은 정확도를 더 끌어올리는 역할
- 남은 결정 사항: 큐폼을 어느 정도까지 채워야 하는지 / 어떤 질의에 큐폼이 필요한지 기준 정교화. 멀티턴은 넣되 최소화하는 방향, UI 차원에서도 적용 가능하도록 고려

**4. 큐폼 문항 구성 원칙**
- 큐폼 문항 구성 시 business_function(bf)은 반드시 포함되어야 함
- 큐폼–텍스트앵커–첨부문서 흐름: 첨부문서 매칭은 큐폼이 나와야 가능한 구조(큐폼이 상황을 특정해야 첨부를 하나로 확정 가능)
