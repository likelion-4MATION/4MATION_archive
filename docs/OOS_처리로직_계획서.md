## 3. 2층 구조

```
사용자 질문
   │
   ├─[L-1] 룰 프리필터 (0콜)  ─── INVALID(의미없는 입력) · 명백한 CASUAL 정형구
   │
   ├─[L0] 게이트 분류 (LLM 1콜) ─── IN_SCOPE / OOS / 모호
   │        │
   │        ├── IN_SCOPE ──────────────────────► route=rag  (검색 → 생성 → checks)
   │        ├── 모호 ─────────────────────────► route=rag  (과차단 방지, 현행 유지)
   │        └── OOS ──┐
   │                  │
   └─[L1] OOS 세분류 (LLM 1콜) ─── 6대분류 + 하위
                      │
                      ├── DOMAIN_OOS ──────────► route=reject  (고정 거절)
                      ├── SCOPE_OOS ───────────► route=link    (타기관 안내 — 신규)
                      ├── HUMAN_HANDOFF ───────► route=handoff (신규)
                      ├── BUG_REPORT ──────────► route=handoff + 로깅
                      ├── CASUAL ──────────────► route=casual  (신규, 0콜 정형 응답)
                      └── INVALID/ADVERSARIAL ─► route=reject  (고정 거절 + 로깅)
```

### 3-1. 왜 2층인가
- **L0은 기존 로직을 그대로 쓴다.** 19/20 성적을 낸 게이트를 건드리지 않으므로 회귀 위험 최소
- **L1은 OOS로 판정된 것에만 돈다.** E2E 실측 기준 20문항 중 12건(60%)만 L1 진입 → 콜 증가는 문항당 평균 +0.6콜
- **단계적 배포 가능.** L1을 끄면 즉시 현행 동작으로 롤백
- **비용**: OOS 문항은 검색·생성을 생략하므로 L1 1콜을 더해도 rag 경로(4,956ms)보다 여전히 빠름

### 3-2. L0 판정 기준 (재정의 — 이것이 핵심 변경)
현행 프롬프트는 소관/비소관을 **기관 지식**으로 서술한다(id 19 실패 원인). 새 기준은 **코퍼스 존재 여부**로 바꾼다.

> **IN_SCOPE 정의**: 질문에 대한 답이 **크롤링 코퍼스(38페이지) 안에 있을 것으로 기대되는가.**
> 예보가 "처리하는 업무"인지가 아니라 **"우리 문서가 말하는 내용"인지**로 판정한다.

이 정의는 §4의 발견과 맞물려 중요한 결과를 낳는다 — **"예보 소관이 아니다"라는 답변 자체가 코퍼스에 있으면 IN_SCOPE에 가깝다.**

### ⚠️ 4-1. 즉시 수정이 필요한 불일치 1건
현행 `CLS_PROMPT`는 **"휴면예금은 서민금융진흥원"**이라고 서술한다. 그러나 코퍼스 원문(`DpsmIbamtExpln/selectScrn.do`)은 **"전국은행연합회 휴면계좌통합조회시스템(www.sleepmoney.or.kr)"**이라고 명시한다.
→ 분류기가 **코퍼스와 다른 기관을 파라메트릭 지식으로 말하고 있다.** id 19와 같은 계열의 오류이며, `trap id 10`(휴면예금 찾아주기)이 우연히 reject로 맞은 것이지 사유는 틀렸다.
→ **조치**: 안내처는 프롬프트가 아니라 **§5 안내 사전(referral registry)**에서만 가져온다. 사전 값은 코퍼스 원문에서만 채운다.

### 4-2. 정책 결론
> SCOPE_OOS는 **거절(reject)이 아니라 안내(link)** 로 처리한다.
> 응답 = ①예보 소관이 아님을 코퍼스 근거로 진술 + ②사전에 등록된 안내처 제시 + ③(가능하면) 예보가 대신 해줄 수 있는 인접 업무 안내.

③의 예: "보호한도 초과분" 질문 → 파산배당 안내 + **예보 개산지급금 제도**로 연결. 이건 순수 이관이 아니라 실제 소관 업무로의 회수다.

## 5. 택소노미 정의 및 라벨 판정 규칙

### 5-1. 6대분류 판정 기준 (배타적 정의)

| 클래스 | 한 줄 정의 | 판정 기준 (분류기가 볼 것) | route |
|---|---|---|---|
| **DOMAIN_OOS** | 예보 업무 영역 자체 밖 | 코퍼스에 **답도 안내처도 없음**. 질문의 주제가 예금보험·부실금융회사 정리 도메인 밖 | `reject` |
| **SCOPE_OOS** | 도메인은 걸치나 예보가 처리하지 않음 | 코퍼스가 **"예보 비소관"임을 명시하거나 안내처를 지목**함 | `link` |
| **HUMAN_HANDOFF** | 개인별 사안 — 문서로 답할 수 없음 | 특정 개인의 계좌·신청건·지급액·진행상태를 묻거나, 상담사 연결·민원을 명시 요청 | `handoff` |
| **BUG_REPORT** | 서비스 결함 신고 | 오답 지적, 사이트·신청시스템·인증 오류 호소 | `handoff` + 로깅 |
| **CASUAL** | 업무 무관 사교적 발화 | 인사·감사·작별·잡담·챗봇 자기소개 요구. **다른 라벨이 하나도 안 붙을 때만** | `casual` |
| **INVALID / ADVERSARIAL** | 처리 불가 또는 공격 | 의미 없는 입력, 프롬프트 인젝션, 내부정보 요구, 유해 요청 | `reject` + 로깅 |

### 5-2. DOMAIN_OOS vs SCOPE_OOS — 운영 가능한 경계

두 클래스의 구분은 실무에서 가장 헷갈리는 지점이므로 **단일 질문**으로 환원한다.

> **"우리 코퍼스가 이 주제에 대해 무슨 말이든 하고 있는가?"**
> - 한다(비소관이라고 말하든, 안내처를 지목하든) → **SCOPE_OOS** → link
> - 안 한다 → **DOMAIN_OOS** → reject

이 기준의 장점: 분류기가 **기관 지식을 동원할 필요가 없다**(P5). 그리고 link route의 안내 가능 여부와 **1:1로 대응**하므로, SCOPE_OOS 판정 = 안내 사전에 항목이 있다는 뜻이 된다.

**제시된 하위 항목 배치 검토:**
| 원안 하위 | 배치 | 비고 |
|---|---|---|
| DOMAIN_OOS > 타 기관 금융제도 | 유지 | 단 **외국 제도**(FDIC 등)를 별도 하위로 분리 권고 — 트랩 5건이 이 유형 |
| DOMAIN_OOS > 일반 금융 / 투자·보험·대출 / 생활·일반 상식 | 유지 | |
| SCOPE_OOS > 7개 항목 | 유지 | §4 대로 전부 link 대상 |
| SCOPE_OOS > 기타 타 기관 소관 업무 | **catch-all 금지** | 안내 사전에 항목이 없으면 SCOPE_OOS로 판정할 수 없다. 사전 미등록 건은 DOMAIN_OOS로 강등 |

### 5-3. 다중 라벨 충돌 시 우선순위

한 발화에 여러 라벨이 걸릴 수 있다("안녕하세요, 제 보험금 언제 나와요?" = CASUAL + HUMAN_HANDOFF).

```
INVALID/ADVERSARIAL  ▲ 최우선 (다른 무엇과 섞여도 이 라벨)
BUG_REPORT           │
HUMAN_HANDOFF        │
IN_SCOPE             │  ← 답변 가능한 질문이 섞여 있으면 답변을 우선
SCOPE_OOS            │
DOMAIN_OOS           │
CASUAL               ▼ 최후 (다른 라벨이 없을 때만)
```

**설계 의도**
- ADVERSARIAL 최우선: 인사말로 감싼 인젝션을 CASUAL로 흘리면 안 됨
- HUMAN_HANDOFF > IN_SCOPE: 사용자가 상담사를 **명시 요청**했으면 답변으로 갈음하지 않는다
- IN_SCOPE > SCOPE_OOS: 복합 질문("보호한도랑 워크아웃 알려줘")은 답할 수 있는 부분을 먼저 답하고 나머지를 안내
- CASUAL 최후: 인사 + 질문은 질문 처리

### 5-4. ⚠️ 택소노미에 없는 유형 — "구정보 확인형"
트랩 20문항 중 5문항(id 16~20)이 이 유형이며, **6대분류 어디에도 속하지 않는다.** 이들은 IN_SCOPE이고 rag로 가야 하며, 위험은 OOS 미차단이 아니라 **오정보 승인**이다(id 16 실측).
→ **OOS 처리 로직의 책임 밖으로 명시 선언**한다. 이 유형은 검색 개선(BF 부스팅)과 생성 프롬프트 규칙 4가 담당한다. OOS 분류기가 이걸 잡으려 하면 과차단이 생긴다.

## 6. 응답 정책

### 6-1. route 값 확장

| route | 신규 | 검색 | 생성 | checks | text 출처 |
|---|---|---|---|---|---|
| `rag` | — | O | O | O | LLM 생성 |
| `reject` | — | X | X | skip | 고정 문구 |
| `link` | **신규** | X | X | skip | **사전 조립**(템플릿 + 안내 사전) |
| `handoff` | **신규** | X | X | skip | 고정 문구 + 연결 경로 |
| `casual` | **신규** | X | X | skip | 고정 문구 |

**계약 영향**: 4필드 축소 없음(P1 준수). 단 `route` 값 도메인이 3값 → 6값으로 확장되므로 **`DECISIONS.md` 사람 서명 필요**. `app.py`는 `route` 값을 분기 없이 표시만 하므로 호환 예상되나 **재확인 필요**.

### 6-2. link route 응답 구성 (3부 구조)

```
[1] 소관 진술   — "○○은 예금보험공사 소관이 아닙니다."   ← 코퍼스 원문 근거
[2] 안내처      — 기관명 / URL / 전화번호                ← 안내 사전에서만 조립
[3] 인접 안내   — "다만 예보의 △△ 제도는 안내해 드릴 수 있습니다" (선택)
```

**절대 규칙**: [2]의 URL·전화번호는 **LLM이 생성하지 않는다.** 사전에 하드코딩된 값을 문자열 치환으로만 넣는다(P3).

### 6-3. 안내 사전 (referral registry) — 설계

- **저장 위치**: 코드 밖 데이터 파일(예: `chatbot/referrals.json`). 프롬프트에 넣지 않는다
- **필수 필드**: `키 / 기관명 / URL / 전화번호 / 코퍼스 근거 URL / 근거 원문 발췌`
- **채우기 규칙**: **코퍼스 원문에 실존하는 값만.** 원문에 없으면 항목을 만들지 않는다(그 주제는 DOMAIN_OOS로 강등)
- **초기 항목**(§4 표에서 확보 — 7개 하위 전부 채워짐)

### 6-4. ⚠️ answer_checks와의 충돌 — 반드시 처리할 것

`check_urls()`는 **sources 목록에 없는 URL을 플래그**한다(07-22 사람 확정, `allow_context_urls=False`). link route의 안내 URL(`ccrs.or.kr`, `sleepmoney.or.kr` 등)은 `sources`가 비어 있으므로 **전부 플래그된다.**

해결안 3가지:
| 안 | 내용 | 평가 |
|---|---|---|
| A | link route는 `checks`를 skip (현행 reject와 동일 처리) | **권고.** 모델 생성물이 아니므로 충실성 검증 대상이 아님. reject 선례와 일관 |
| B | 안내 사전 URL을 allowlist로 `check_urls`에 주입 | 사전 변경 시 검증기도 같이 바뀜 — 결합도 증가 |
| C | link 응답의 `sources`에 코퍼스 근거 문서를 채움 | 근거 추적성은 최선이나 sources 의미가 바뀜(계약 해석 변경) |

**동일 이슈**: `_is_rejection()` 정규식이 link/handoff/casual 응답 문구를 매칭하는지 확인 필요. 현행 패턴은 `확인되지 않는 | 안내된 내용이 아니 | 답변드리기 어렵 | 소관이? 아니`. link 문구에 "소관이 아닙니다"가 들어가면 매칭되어 citations 검사를 건너뛴다 — **의도한 동작이므로 유지**하되 문서화.

### 6-5. HUMAN_HANDOFF 응답
- 문서로 해결 불가함을 인정 + **고객상담센터 1588-0037**(코퍼스 실존) 안내
- 업무별 전용 번호가 코퍼스에 있으면 우선 사용: 파산재단 채무자 `02-758-1000`, ㈜케이알앤씨 `1899-0057`, 은닉재산 `02-758-0102~4`
- **주의**: 개인정보를 되묻지 않는다. 계좌번호·주민번호를 요구하는 응답 금지

### 6-6. BUG_REPORT 응답 + 로깅
- 응답: 접수 확인 + 상담센터 안내
- **로깅이 본질**: `_meta`에 `bug_report` 플래그 + 원문 질의를 남긴다
- ⚠️ **현재 세션 ID·대화 이력 식별자가 없다.** "챗봇 오답 신고"는 **직전 답변**을 가리키므로 최소 1턴 이전 컨텍스트가 필요 → **멀티턴 상태 설계 선행 필요**(§8-2)

### 6-7. INVALID / ADVERSARIAL 응답
- 고정 거절 문구. **공격 내용을 응답에 반향(echo)하지 않는다**
- 내부정보 요구(프롬프트 내용, API 키, 모델명) → 일절 노출 금지
- 로깅 필수

## 7. 리스크

### 7-1. 🔴 최우선 — 분류 실패 시 안전 기본값이 `"정상"`이다
현행 `classify()`는 JSON 파싱 2회 실패 시 `"정상"`을 반환한다(과차단 방지 의도, P4와 정합).
그러나 **프롬프트 인젝션은 분류기 자체가 공격 표면**이다. 인젝션으로 분류기 출력이 깨지면 → 기본값 `정상` → **rag 경로로 진입**한다. 공격자가 파싱을 깨는 것만으로 게이트를 우회할 수 있다.

**대응 방향(택1 필요, 사람 결정)**
| 안 | 내용 | 트레이드오프 |
|---|---|---|
| A | 기본값 유지 + **L-1 룰 프리필터**에서 인젝션 시그니처를 0콜로 선차단 | 룰 우회 가능하나 비용 0, 현행 성적 무영향 |
| B | 파싱 실패 시 기본값을 `모호`로 (여전히 rag이나 별도 플래그) | 실질 동일. 관측성만 개선 |
| C | 파싱 실패를 `reject`로 | 과차단 위험 — P4 위배 |

→ **A 권고.** 인젝션은 분류가 아니라 입력 위생 문제로 다룬다.

### 7-2. 🔴 분류 프롬프트의 파라메트릭 지식 오염
id 19(퇴직연금→근로복지공단), 휴면계좌(→서민금융진흥원) 두 건 모두 **프롬프트에 기관명을 서술한 것**이 원인이다.
**대응**: 분류 프롬프트에서 **기관명 서술을 전부 제거**하고, IN_SCOPE 판정은 §3-2 기준(코퍼스 존재 여부)으로만. 기관명은 §6-3 사전이 전담.

### 7-3. 🟡 L1 추가로 인한 콜·지연 증가
- OOS 문항당 +1콜. E2E 분포(OOS 60%) 기준 20문항 실행 시 +12콜
- `CALL_BUDGET=70` 내 신규 트랩셋 평가가 들어가면 예산 초과 가능 → **평가 세션 예산 재산정 필요**
- 완화: L-1 룰이 CASUAL·INVALID를 걷어내면 L1 진입률이 떨어짐

### 7-4. 🟡 SCOPE_OOS 과확장
"기타 타 기관 소관 업무"를 catch-all로 쓰면 사전에 없는 주제까지 link로 가서 **빈 안내**가 나간다.
**대응**: §5-2 대로 사전 미등록 = DOMAIN_OOS 강등. 사전 조회 실패 시 자동 fallback을 코드 레벨에서 강제.

### 7-5. 🟡 라벨 경계의 주관성
DOMAIN_OOS ↔ SCOPE_OOS, HUMAN_HANDOFF ↔ BUG_REPORT는 사람 간에도 이견이 난다.
**대응**: 트랩셋 라벨링 시 **2인 독립 라벨 + 불일치 건 협의**. 불일치율을 리포트에 기록(현행 trapset은 라벨 검수 자체가 미완 §1-4).

### 7-6. 🟢 계약 변경 승인
`route` 값 3→6 확장은 `DECISIONS.md` 서명 사안. `app.py` 호환 재확인 필요.
