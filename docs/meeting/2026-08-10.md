### 텍스트-앵커 — 검수 및 버전 관리 (v1 → v2 → v3)
- `gt_final.jsonl`(1,651건, 지난주 `judge_label.py` 산출물)에 대한 라벨링 수정 작업 진행
- **문제 1 — 파싱 실패로 인한 누락**: 14건이 라벨링 도중 파싱 실패로 누락된 것을 확인 → 재수집으로 해결
- **문제 2 — span만 보수적으로 폐기되는 구조**: `answerable=true`이고 `gt_chunk_id`도 존재하는데 `gt_anchor_span`이 `null`인 케이스 다수 발견. 정답 청크까지는 골랐지만 뽑아낸 스팬 텍스트가 정확한 부분문자열로 존재하지 않으면(패러프레이즈·요약 인용, 줄바꿈·특수문자 처리 어긋남 등) span만 null로 버리는 구조였음을 확인 — `answerable=true` 857건 중 **359건(41.9%)**이 이 케이스로 span이 null, 온전한 건 498건(58.1%)뿐. `gt_chunk_id`는 신뢰할 수 있으므로 같은 본문 안에서 스팬을 다시 추출하는 것이 가능하다는 방향 확인
- 1차 전수 검수 진행: `message.txt` 지침 기반으로 6단계 판정 체계(OK/FIX/WRONG_CHUNK/MULTI/CORPUS_NO_ANSWER/NO_SPAN) 적용, MULTI는 `gt_alt_evidence` 필드로 기존 스키마를 깨지 않고 확장 → `gt_final_v2.jsonl` 산출
- 재검수 및 Multi-Gold 개선 진행: **"Gold Evidence Operational Definition"** 프롬프트를 새로 정립 — 하나의 span만으로 질문의 핵심 판단(대상 여부·Yes/No·수치/조건 확인 등)이 가능하면 단일 Gold, 서로 다른 필수 사실을 결합해야만 판단 가능하면 Multi-Gold로 명확히 구분하는 기준 확립. "코퍼스 사실 → 질문의 핵심 판단"이면 Gold, "코퍼스 사실 → 외부 추론 → 판단"이면 NO_SPAN/CORPUS_NO_ANSWER로 판정하는 경계 원칙 확정 → `gt_final_v3.jsonl` 산출
- `eval_anchor.py` 수정: RAG 중복 정답 처리 방식 개선 — `gt_chunk_id` 단일값 비교 대신 `gt_chunk_ids`(리스트/집합)를 받아 여러 정답 청크 중 하나만 검색돼도 정답으로 인정하도록 `rank_of` 로직 변경
- 수정된 `eval_anchor.py`로 검색 평가 실행 → `eval_anchor_v3_report.md` 산출

## 4. 이슈 정리

## 이슈 1. 텍스트-앵커 — span 폐기 구조로 인한 대량 null 발생

**문제**
`judge_label.py`가 정답 청크(`gt_chunk_id`)는 정확히 찾아도, 뽑아낸 스팬이 원문과 정확히 일치하는 부분문자열이 아니면(패러프레이즈·요약 인용, 줄바꿈/특수문자 처리 문제 등) span 전체를 보수적으로 null 처리하는 구조였음. 그 결과 `answerable=true` 857건 중 41.9%(359건)가 span 없이 남음.

**건의/조치**
`gt_chunk_id`는 신뢰하되, 같은 청크 본문 안에서 스팬을 재추출하는 방식으로 1차 전수 검수(`gt_final_v2.jsonl`)를 진행. 이어서 Multi-Gold 판정 기준(Gold Evidence Operational Definition)까지 정립해 재검수(`gt_final_v3.jsonl`) 완료.

## 이슈 2. eval_anchor.py — 중복 정답 처리 미비

**문제**
기존 `eval_anchor.py`는 정답을 단일 `gt_chunk_id`로만 비교해, 같은 내용이 여러 청크에 정당하게 중복 존재하는 경우 검색기가 다른 쪽 정답 청크를 반환해도 오답으로 처리되는 구조적 문제가 있었음.

**건의/조치**
`rank_of` 로직을 `gt_chunk_ids`(리스트/집합) 기준으로 수정해 여러 정답 청크 중 하나만 걸려도 정답으로 인정하도록 개선. 개선된 스크립트로 평가를 재실행해 `eval_anchor_v3_report.md` 산출.

## 이슈 3. 청크 단위 vs 문서 단위 평가의 거품 정량 확인

**문제**
기존 문서 단위(hit@k) 평가가 실제 검색 성능을 얼마나 과대평가하고 있었는지 수치로 확인되지 않은 상태였음.

**건의/조치**
`eval_anchor_v3_report.md`로 청크 단위(recall@10=0.611)와 문서 단위(recall@10=0.918)를 나란히 산출 — **+0.308의 거품**을 정량적으로 확인. 이 수치를 앞으로 성능 개선 실험의 기준선(baseline)으로 사용.

## 이슈 4. 큐폼 — 순수 의도 표현(G14) sub_task 미추출

**문제**
"착오송금 반환 신청하려고요" 같은 의도 표현이 `sub_task` 추출 규칙에서 채널어(온라인/방문 등)를 필수로 요구하는 `and` 규칙에 걸리지 않아 `sub_task=None`으로 빠지고, 결과적으로 되묻기가 발동해야 할 상황에서 발동하지 않는 문제가 확인됨.

**건의/조치**
`_SUBTASK_RULES`에 의도 표현("~하려고요/하려는데/할래요") 전용 `and` 규칙을 1줄 추가하고, 450셋 발동률을 재측정하는 것을 트랙 A의 최우선 작업(A1)으로 지정.
