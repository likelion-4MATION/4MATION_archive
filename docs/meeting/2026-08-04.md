## 2. 실제 진행 내용

### 오전
- 라우터 평가셋 제작(1150건) — 업무가 비슷한 것들을 구분하는 모호 케이스 분류 기준 및 답변 형식(사용자에게 재확인) 논의
- 라우팅 성능 기준 정리 — 정확도는 높게, 틀린 케이스의 신뢰도는 낮게 나오는 것이 바람직하다는 방향 확립
- 누락/오탐 처리 원칙 정리 — 누락은 수기 태깅 수정, 오탐은 중복 라벨·캡 완화로 대응(라벨의 청크 단위화는 청크 실험이 불가능해져 제외)
- 라우터 평가셋 스키마 설계(`router_testset_v3_update.html`, 규남님)
- 라우팅 모델 설계 확정 — A안(이진 직접 분류) vs B안(6업무 다중분류+MSP 임계) 비교 후 B안 채택
- `1150_테스트셋_생성계획서.md` 기반 담당자별 테스트셋 분담 생성 착수(D1~D3, D4~D6, G4, OOS 4개 파트)

### 오후
- 1150건 평가셋으로 라우팅 모델 학습 불가 확인 — 기존 400건도 검색 평가셋 특성상 학습 불가한 문제와 동일선상에서 재발견
- 해결방안 도출: ① 1150건 중 D5 업무가 실제 청크 내 존재하는지 확인(존재 확인) ② 1150건을 우리 업무 6개 기준으로 재분류 ③ 400건에 없는 소관 질문을 1150건에서 찾아 테스트셋 확장
- 해결방안 반영 및 산출: `testset_natural_450.jsonl`(400건 재검사 후 50건 추가, 유상님), `router_testset_v3_1.jsonl`(라우팅 의도 재분류·검증, 현욱님)
- OOS 경계 모호 사례 조사(규남님) — 퇴직연금, 연금저축·사고보험금, 불법행위 신고, 채무조정 안내, 상호금융·우체국예금 등 소관 경계가 불명확한 케이스 정리
- 라우팅 모델 파인튜닝 파이프라인 코드 작성(`train_router_electra.ipynb`, 경은님) — ELECTRA discriminator 계열 4개 후보 모두 `AutoModelForSequenceClassification` 호환이라 동일 코드에서 `MODEL_CANDIDATES` 키만 교체하면 되도록 구성
- 각자 환경에서 배정된 후보 모델(KR-electra/Kcelectra·finance-kcelectra-base/Koelectra/Dialog-Koelectra) 파인튜닝 실행 시작

### 주요 논의 및 결정사항
1. **라우팅 모델 아키텍처 확정**: A안은 음성(OOS) 데이터 300~500건 신규 작성이 필요하고, 소수 기관 음성만 학습 시 "소관밖" 대신 "그 기관 토픽"을 학습해버려 여권·전기요금 등 첫 대면 질의를 통과시키는 함정이 있음. B안(6업무 다중분류 + MSP 임계)은 음성 데이터 없이 기존 `testset_natural_400` 재사용이 가능해 이 문제를 우회함 → **B안 채택**
2. **오채점/오탐 처리 원칙**: 오채점(정답인데 틀렸다고 판정)은 parent-child 구조 또는 중복 라벨링으로, 오탐(틀렸는데 맞다고 판정)은 추후 Qform 도입 후 더 정밀한 분류로 해소하는 방향으로 역할 분담
3. **1150건 평가셋의 한계 확인**: 1150건 자체가 검색 평가셋 성격이라 학습에 바로 쓸 수 없음을 확인 → 400건 재검사 + 50건 추가로 학습셋(`testset_natural_450`) 확정
4. **OOS 경계 모호 사례 반영 필요성 확인**: CLS_PROMPT에 퇴직연금·연금저축·사고보험금·불법행위신고(부실관련자 한정) 등이 명시되어 있지 않아 오분류 재발 위험 존재
5. **ELECTRA 후보 4개 모델 역할 분담**: KR-electra(유상), Kcelectra·finance-kcelectra-base(규남), Koelectra(경은), Dialog-Koelectra(현욱) — 각자 환경에서 파인튜닝 후 정확도·AUROC 비교 예정

## 3. 논의사항
- 오채점은 parent-child 구조 혹은 중복 라벨링으로, 오탐은 Qform 도입 후 더 정밀한 분류로 해결 예정(둘 다 오늘은 방향만 확정, 실행은 추후)
- 청크별 태그로 테스트셋을 구성할 경우 이후 청킹 단위(사이즈)를 바꾸는 실험 자체가 불가능해지는 구조적 문제 발견 → 앵커-텍스트 기반 해결 방안 제시, 구체화는 추후 진행
- 채무조정 안내 업무는 명칭 자체가 신용회복위원회·법원과 겹치고 콘텐츠도 안내·연결 위주라 "빚 줄여주세요"류 생성답변에 대한 실측 스팟체크 필요
- 상호금융(새마을금고·신협 등)·우체국예금은 소관 밖일 가능성이 있으나 CLS_PROMPT에 언급 자체가 없어 corpus 검증 후 반영 여부 결정 필요
