## 2. 실제 진행 내용

### 텍스트-앵커 — 현황 정리 및 수작업 라벨링
- 전체 학습·평가 대상 2,115건 중 **450건(testset_natural)만 gt_docs 보유**, 나머지 1,665건(router_trainset_v2.jsonl)은 gt_docs가 아예 없는 상태임을 재확인
- 문단(문서) 하나당 청크를 직접 읽으면서 정답을 라벨링하는 방식으로 진행 — 이 라벨이 채워지면 evaluation에서 hit 여부를 산출할 수 있는 상태가 됨
- 450건은 기존 스키마에 맞춰 텍스트-앵커 형태로 변환하고 evaluation 세팅까지 함께 진행
- **중복 라벨링 체크**: 동일 내용이 여러 청크에 있는 경우 중복 라벨 허용
- **근거 청크 부족 문제 발견**: 상속포기·소멸시효 등 일부 질문은 특정 텍스트 한 조각만 봐서는 답을 낼 수 없고, 문서 전체 맥락을 이해해야 정답 스팬을 특정할 수 있는 케이스로 확인됨 — 어디를 정답으로 태깅해야 하는지 애매한 채로 남음

### 텍스트-앵커 — 기존 방식의 구조적 한계 발견
- **문제**: business_function(업무) 단위로 검색 범위를 고정해서 라벨링을 진행하다 보니, 실제 정답이 그 업무가 아닌 **다른 업무의 청크에 있는 경우**를 놓치는 사례가 발견됨(BF 밖에도 정답이 존재)
- **건의/결정**: BF를 고정하지 않고 전체 코퍼스를 대상으로 검색하도록 전환. 실제 서빙 단계에서는 하드필터가 아니라 **소프트부스트(soft boost)** 방식을 쓰기 때문에, 라벨링 단계에서 BF를 고정하지 않아도 평가에는 문제가 없음(업무가 6대로 분류돼 있다고 해서 검색 후보까지 6개로 딱 나눠 가둘 필요는 없다는 결론)

### 텍스트-앵커 — 해결 방법: judge_label.py 도입
- LLM에게 **전체 청크 + 테스트셋(질문)**을 함께 제공하고, "코퍼스 청크의 실제 내용만으로 판단해서 정답 라벨을 붙여라"는 지시를 내리는 방식으로 전환
- 핵심 규칙: **'골드 업무'는 참고 힌트일 뿐**이며, 정답 청크는 다른 업무 태그를 가질 수 있음(크로스도메인 허용) — 내용이 실제로 맞으면 업무 태그가 달라도 그 청크를 정답으로 선택
- 이 방식의 장점: 이후 청크 개수나 내용이 바뀌어도 LLM이 그때마다 다시 앵커를 만들어줄 수 있어 재청킹에 대한 내구성이 생김
- 적용 대상: `router_trainset_v2.jsonl`(1,665건)의 앵커 라벨을 **HCX API**로 태깅하는 작업 착수

### 큐폼 — 설계스펙 rev.3 확정 (`QFORM_ARCH_설계스펙.md`)
- **큐폼 성격 재정의(D1)**: 기존 기획서 v1의 "객관식 폼 + 게이트" 전제를 폐기. 큐폼 = **슬롯 추출기 + 조건부 되묻기**로 확정. 모든 질의에 추출기를 돌리며 진입/미진입 개념 자체가 없음
- **되묻기 규칙(D2)**: `sub_task`가 잡혔는데도 남은 조합 행이 2개 이상일 때만 되묻기 발동. `sub_task`가 비어 있으면(null) 되묻지 않고 기존 검색 경로로 바로 보내 오발동을 방지
- **착오송금 슬롯 5종 확정**: `party`(송금인/수취인, 되묻지 않음) · `sub_task`(1순위 되묻기) · `qualification`(본인/대리인, 2순위) · `subject`(대리인일 때만 3순위) · `method`(다중 허용, 되묻지 않음)
- **조합 테이블 근거 표기 확정**: `source_doc_id`(조인용, 문서 단위, 재청킹 불변) + `evidence_chunks_v0`(검증용, 청크 단위) **병기**. 문서 단위로 승격하지 않는 이유는 14행 중 9행이 동일 문서(`MsdrprPossDcmntGudn`)로 수렴해, 승격하면 행별 구별력이 사라지기 때문
- **종착점(outcome) 다중부착 허용(D4)**: 정보/서류/서류;정보 3값으로 확정 — 법인·비법인단체·군복무자·국외거주 등은 추가서류가 전부 외부기관 발급이라 양식파일(서류)과 발급처 안내(정보)가 동시에 필요한 케이스가 존재
- **평가셋 450건으로 통일**: 기획서 v1의 "400셋" 표기는 stale로 확인, 450건 기준으로 정정

### 큐폼 — 착오송금 관통 스프린트 구현 완료 (`QformSprintDemo_결과공유.md`)
- **T1 조합 테이블 검증**: 14행, 유상 태깅 스키마 허용값 위반 0건, 근거 앵커 39개 중 미실재 0, 문서 참조 23개 중 미실재 0
- **T2 결정론 슬롯 추출기(LLM 호출 0)**: 착오송금 84건 기준 `sub_task` 88%·`party` 76%·`qualification` 39%·`subject` 39%·`method` 35% 커버, 수기 20문항 `sub_task` 정확도 100%(오추출 0)
- **T3 조건부 되묻기 시뮬레이션**: 평균 0.93턴(최대 2턴), 450셋 전체 발동률 **1.3%**(6/450) — 오발동이 거의 없는 것으로 확인(단문 위주 450셋 특성상 정상)
- **B 통합(첨부 후단 필터)**: 기존에는 구비서류 문서 검색 시 첨부 11서식(24파일)이 통째로 반환됐는데, 큐폼 슬롯으로 조합 조인 필터를 적용하면 상황별로 **1~5서식**으로 좁혀지는 것을 확인(예: "미성년자 착오송금 반환 서류" → 4건, "신청 철회" → 1건)
- **지킨 계약**: 검색·생성 로직은 무변경, `answer()` 반환 4필드도 무변경(`qform`은 메타에만 기록), `gt_docs`를 조합 테이블에 넣지 않아 어느 문서를 반환할지는 여전히 검색이 결정
- **미착수**: `app.py`에서의 E2E 배선(`extract → 되묻기 → answer(qform)` 실제 연결)은 아직 안 됨

### 첨부문서 태깅 논의
- 큐폼 슬롯 값을 기반으로 첨부 후단 필터를 적용했을 때, 기존 22건(11서식) 통째 반환 대비 상황별 1~5서식으로 좁혀지는 실측 결과를 공유하며 첨부 태깅 방식 자체를 큐폼 슬롯 체계와 어떻게 연동할지 논의
- 오라클 실험(450셋 business_function을 완벽한 S1로 가정해 부스트 적용) 결과가 나오기 전까지는, 메타데이터 부스트(③) 투자 여부를 보류하기로 함 — 조합 테이블 구조상(14행 중 12행이 단일 문서로 수렴) 오라클 실험이 +1pp 수준에 그칠 가능성이 높다고 사전 예측

## 3. 논의사항
- 텍스트-앵커: 근거 청크가 부족해 문맥 전체를 봐야 정답을 특정할 수 있는 케이스(상속포기, 소멸시효 등)의 라벨링 원칙 미정
- 큐폼: 다중 의도 질의(예: "대리인이고 수수료 환급도 되나요") 처리 방식 미정 — 슬롯 추출기가 `sub_task`를 2개 뽑는 것 자체는 가능하나 답변 병합 방식은 미결(R2)
- 큐폼: 유상 태깅 `verified` 좌표가 아직 0/26 — 사람 검증 전 상태이며, confidence med/low 2건(지분신고서·손해담보약정서)이 우선 검토 대상
- 큐폼: 되묻기 문구가 지금은 예시 제시형인데, 공공기관 톤에 맞는지 검수 필요

## 4. 이슈 정리

## 이슈 1. 텍스트-앵커 — business_function 고정 검색의 구조적 한계

**문제**
정답 라벨링 시 업무(business_function) 단위로 검색 범위를 고정해왔는데, 실제 정답이 해당 업무가 아닌 다른 업무의 청크에 존재하는 경우(BF 밖 정답)를 놓치는 문제가 발견됨.

**건의/조치**
BF를 고정하지 않고 전체 코퍼스를 대상으로 검색하도록 라벨링 방식을 전환. 실제 서빙 단계는 하드필터가 아닌 소프트부스트 방식이라, 라벨링 단계에서 BF를 고정하지 않아도 평가상 문제가 없음을 확인.

## 이슈 2. 텍스트-앵커 — 근거 청크 부족(맥락 의존형 질문)

**문제**
상속포기, 소멸시효 등 일부 질문은 특정 텍스트 한 조각만으로는 답이 나오지 않고, 문서 전체 맥락을 이해해야 정답 스팬을 특정할 수 있어 어디를 태깅해야 할지 애매함.

**건의/조치**
현재는 미해결 상태로 남김 — 별도 처리 원칙(문맥 의존형 질문에 대한 앵커 범위 확장 규칙 등) 정립 필요.

## 이슈 3. 텍스트-앵커 재작업 반복 문제 → judge_label.py 도입

**문제**
수작업(문단·청크를 직접 읽으며 라벨링)은 청크 구조가 바뀌면 다시 처음부터 라벨링해야 해 재작업 비용이 크고, 업무 단위 스코프 고정으로 인한 누락(이슈 1)도 반복될 위험이 있음.

**건의/조치**
`judge_label.py`로 전환 — LLM에게 전체 청크와 테스트셋을 함께 제공하고 코퍼스 실제 내용만으로 판단하게 함. 골드 업무는 참고 힌트로만 쓰고 크로스도메인 정답을 허용하는 규칙을 명시. 청크가 바뀌어도 같은 방식으로 재생성 가능해 재청킹 내구성을 확보. `router_trainset_v2.jsonl`(1,665건) 대상으로 HCX API 태깅 착수.

## 이슈 4. 큐폼 — 기획서 v1 전제(게이트·순차형 폼)의 무효화

**문제**
기획서 v1은 객관식 폼과 게이트(상황설정형 질의만 큐폼 진입) 구조를 전제로 설계됐으나, 실제 구현 과정에서 이 전제가 큐폼의 실사용 방식과 맞지 않음이 드러남.

**건의/조치**
설계스펙 rev.3에서 게이트를 폐기(D1)하고, 모든 질의에 결정론 슬롯 추출기를 돌리되 `sub_task`가 잡히고도 조합이 안 좁혀질 때만 되묻는 구조로 재설계. 이 변경으로 되묻기 발동률을 1.3% 수준으로 낮게 유지하며 오발동을 방지함.
