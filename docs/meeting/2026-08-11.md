## 2. 실제 진행 내용

### 텍스트-앵커 — 문제 재정의
기존 GT(`gt_final_v3.jsonl`)를 다시 들여다보며 다음 문제들을 확인함.
- **reason 누락 시 응답 불가**: `answerable=true`이고 span도 붙었는데 `reason`이 없으면 이후 단계에서 답을 만들지 못하는 케이스 발견
- **긍정형 질문에 부정형 답변이 정답인 경우**: 예) "착오송금 반환지원 대상 기간이 지나면 방법이 없나요?" → 실제로는 "없는 게 맞는" 정답인데, 코퍼스에 "없다"는 문장이 직접 명시되어 있지 않으면 시스템이 답을 못 만드는 문제
- **answerable 판정 기준이 "span 존재 여부"에만 의존**: 코퍼스에 명시적 span이 없으면 무조건 `answerable=false`로 처리되어, 실제로는 여러 청크를 조합하면 답할 수 있는 문항까지 걸러지는 문제
- **복수정답 vs 멀티청크 구분 필요**: 한 질문의 답이 두 개의 청크에 **각각 독립적으로** 존재하는 경우(복수정답, `or`)와, 두 개 이상의 청크를 **합쳐야만** 답이 도출되는 경우(멀티청크, `and`)가 구분되지 않고 있었음

### 텍스트-앵커 — GT 스키마 재설계 (2축 분리)
- **축 1 — 근거 강도 `evidence_type`**: `direct`(코퍼스에 답 문장이 그대로 있음) / `inferable`(명시적 사실들을 조합하면 안전하게 도출 가능) / `none`(조합해도 결정 불가)
- **축 2 — 복수정답 관계 `chunk_relation`**: `single`(단일 정답) / `and`(멀티청크, 전부 모아야 완성) / `or`(복수정답, 하나만 맞아도 정답)
- 핵심 원칙: "문장 그대로 없다"는 이유만으로 `false` 처리하지 않고, 명시적 사실 조합으로 안전하게 도출되면 `inferable`로 포함시키기로 함(오탐 방지를 위해 "그럴듯한 추측" 수준은 여전히 제외)
- `false`는 **(a) 소관밖**(타 기관 소관·금융 무관) 또는 **(b) 소관내인데 근거 전무**(통계·소요기간 등) 두 경우로만 한정
- 유상님이 이 기준을 정리해 `labeling_spec_multichunk.md`로 확정 — 판정 순서(소관밖 → direct → inferable → false → 관계 판정)와 축별 조합 예시표까지 포함

### 텍스트-앵커 — 평가 코드 재편 (`eval_anchor_v3.py`)
- 기존 평가 `eval_enchor.py` 코드와 관련 문서를 재편하여 검색능력평가 로직을 수정
- 기존 GT의 `gt_chunk_id`(단일값) 대신 `gt_chunk_ids`(리스트) + `chunk_relation`을 함께 읽어 판정하도록 변경
  - `single`/`or` 관계는 **ANY**(하나라도 top-k에 있으면 적중)
  - `and` 관계는 **ALL**(정답 청크 전부가 top-k에 있어야 적중)
- Recall 지표를 문항 평균 기준(Macro Recall)과 전체 gold occurrence 기준(Micro Recall)으로 나누어 함께 산출하도록 개선 — 문항당 정답 청크 개수가 다른 경우의 왜곡을 방지
- 오류 분석 섹션 추가: 미적중 문항의 원인(정분류 내 랭킹 문제 vs 오분류로 다른 업무 혼입)과 업무 간 혼입 흐름까지 자동 집계
- 기존 문서 단위(`parent_doc_id`) 평가와 나란히 비교해 거품(percentage point)도 함께 리포트

### 텍스트-앵커 — 재라벨링 (v3 → v3_q2 → v7)
- `answerable=false` 판정 문항 중 100개를 뽑아 멀티청크(`and`) 전환이 필요한 비율을 탐색. 별도로 질문 자체에 **지시대명사·주어가 손실**된 케이스(예: 앞 문맥 없이 "그거 되나요?" 식으로 주어가 빠진 질문)를 발견해 62건 수정 → `gt_final_v3_q2.jsonl` 산출
- `gt_final_v3_q2.jsonl`을 넘겨받아 새 라벨링 지침(`labeling_spec_multichunk.md`) 기준으로 HCX 기반 전체 재라벨링 진행 → `gt_relabeled_v7.jsonl` 산출

### 큐폼 — ver2 → ver3 전환 (`Qform_v2_v3_변경요약.md`)
> 한 줄 요약: **ver2는 E2E를 관통시켰고, ver3는 대화의 막다른 길을 닫았다.** 검색·생성 로직은 그대로 두고 전이 규칙(`qform_flow`·`qform_state`·`qform_extract`)과 렌더(`app.py`)만 수정 — 450셋 회귀 측정 대상 아님.

**ver2에서 끊겼던 5가지를 ver3에서 해결**
| 증상 | 해결 |
|---|---|
| 답변 턴이 끝나면 슬롯이 리셋 | **슬롯 이월** 추가 |
| 슬롯 못 채우면 같은 질문 반복 | `asked` 이력 추가 |
| 되묻기를 타이핑으로 답해야 함 | **선택지 버튼** 렌더 |
| reject가 고정 문구로 끝남 | 복구 칩 재노출 |
| 첫 화면이 빈 입력창 | 예시 질의 칩 6개 |

- **슬롯 이월**: 새 추출값이 이월값을 항상 덮고(정정 자동 처리), 업무(`bf`)가 바뀌면 이월을 금지해 새마을금고·우체국처럼 업무별 정반대 답이 나오는 사고를 차단. `qform_config.py`로 대화 정책 파라미터(SLOT_CARRYOVER 등) 외부화 — 향후 관리자 콘솔이 읽을 자리 마련
- **되묻기 선택지 버튼**: 조합 테이블 생존 행을 버튼으로 렌더 → 슬롯 오추출이 구조적으로 0이 되고 시연이 결정론적으로 바뀜(HCX 비결정성 회피)
- **슬롯 칩 수정**: 채워진 슬롯을 클릭해 해제·재선택 가능, 판정만 하고 자동 재생성하지 않는 구조("조용히 반영 금지" 원칙)
- **후속 질문 추천**: 조합 테이블 잔여 축에서 결정론적으로 생성, 클릭 시 재검색 없이 후단 필터만 재적용(착오송금 업무에서만 발동, 다른 업무는 조합 테이블 미비로 정상적으로 비어 있음)
- **정의형 질의 예외**: "~가 뭔가요" 패턴은 되묻기를 건너뛰고 직행(단, 450셋 교집합 0으로 실제 하니스에서는 검증 공백 상태 — 수동 워크스루로만 확인)
- **무변경 확인**: `rag.py`·`eval.py`·`chain.py`·`chunks.jsonl`·`qform_combos_msdr.csv` 전부 diff 0줄 유지

## 4. 이슈 정리

## 이슈 1. GT — answerable=false 판정이 span 존재 여부에만 의존

**문제**
코퍼스에 질문에 답하는 문장이 그대로(direct) 없으면 무조건 `answerable=false`로 처리되어, 여러 청크의 사실을 조합하면 안전하게 답을 도출할 수 있는 문항(예: 긍정형 질문에 대한 부정형 정답)까지 걸러지는 문제가 있었음.

**건의/조치**
`evidence_type`을 `direct`/`inferable`/`none` 3단계로 나누고, "명시적 사실 조합으로 안전하게 도출 가능"하면 `inferable`로 `answerable=true` 처리하도록 기준 변경. `labeling_spec_multichunk.md`로 판정 순서와 예시를 명문화.

## 이슈 2. GT — 복수정답(or)과 멀티청크(and)의 미구분

**문제**
"정답이 여러 청크에 있다"는 상황을 하나로 뭉뚱그려 다뤄서, 독립적으로 각각 정답인 경우(or)와 전부 모아야 완성되는 경우(and)를 구분하지 못해 채점 기준이 불명확했음.

**건의/조치**
`chunk_relation` 필드를 `single`/`and`/`or`로 신설. `eval_anchor_v3.py`에서 `and`는 ALL, `or`는 ANY 조건으로 적중을 판정하도록 반영.

## 이슈 3. GT — 질문 자체의 지시대명사·주어 손실

**문제**
일부 질문이 앞 문맥 없이 지시대명사만 남아 있거나 주어가 빠져 있어, 질문만으로는 무엇을 묻는지 특정할 수 없는 케이스가 있었음.

**건의/조치**
경은님이 62건을 식별해 수정 → `gt_final_v3_q2.jsonl` 산출, 이후 유상님의 v7 재라벨링에 반영.
