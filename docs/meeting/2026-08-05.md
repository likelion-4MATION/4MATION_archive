## 2. 실제 진행 내용

### 라우팅 모델 파라미터 튜닝 결과 비교
- 4개 후보 모델(KR-electra, Kcelectra, finance-kcelectra, MOAI/kakaobank) 각자 진행한 파인튜닝 결과 비교
- **MOAI(임베딩 기반 모델)이 성능 압도적 우위**로 확인 — 답변 속도는 kcelectra 계열 대비 약 4배 느리지만 기각할 정도는 아니라고 판단, 채택 방향으로 정리

### 테스트셋 채점 기준 이슈
- **G6 문제**: 테스트셋 내 G6은 원래 저신뢰 OOS로 라벨링된 애매한 케이스인데, 이를 채점에 포함시키면 ROC 수치가 대폭 낮아지는 것을 확인 → **G6은 채점 대상에서 제외**하기로 결정(저신뢰 라벨은 애초에 채점시키지 않는 원칙 확립)
- **학습셋/테스트셋 규모 불균형**: 기존 학습셋 450건 대비 테스트셋 1150건으로 규모 차이가 커 파라미터 튜닝만으로는 성능 향상에 한계가 있음을 확인

### 학습셋 재설계
- 신규 학습셋을 **1700건(6개 업무) + 700건(OOS)** 구성으로 재설계
- 단, **OOS 700건은 최종적으로 학습셋에서 기각** — OOS를 학습에 포함하면 향후 새로운 유형의 OOS 질문이 들어왔을 때 오히려 분류를 못 하는(일반화 실패) 위험이 있다고 판단
- 신규 학습셋(1700건)에 대한 라벨 검증 — 현욱님 진행

### Parent-Child 문제 재검토 및 해법 확정
- **문제 재정의**: 한 문서 안에 여러 청크가 있을 때, 정답이 문서 단위로 라벨링되어 있어 실제 답변과 무관한 청크가 검색돼도 정답 처리되는 문제
- **검토했던 대안**
  - 라벨링을 청크 단위로 전환 → 청킹 파라미터 실험 시 청크가 재생성될 때마다 다시 라벨링해야 하는 문제가 그대로 남아 기각
  - 검색 결과 대신 문서 전체를 LLM에 전달 → 문서가 최대 3만자에 달해 LLM 처리 시간·토큰 비용 문제로 현실적으로 불가하여 기각
- **최종 채택: 앵커-텍스트 방식**
  - 청크마다 정답 구절(텍스트) 자체를 라벨로 저장
  - 청크 사이즈가 바뀌어도 재청킹 결과에서 해당 구절을 따라가며 정답을 자동 매칭 → 파라미터 실험 시 재라벨링 불필요
  - 동일 구절이 여러 위치에 있는 경우 앵커-텍스트를 여러 개(중복 라벨)로 두어 대응 → 이 방식으로 **오탐 문제도 함께 해결 가능**
  - 모델은 그대로 사용하고 **바꿔야 하는 건 테스트셋뿐** → 정확도만 충분히 나오면 구조적으로 문제 없음
  - **한계점**: 원문 사이트가 동적으로 변경되면 정답 구절 자체가 사라질 수 있어 이에 대한 별도 대응 방법이 필요(미해결)

### 큐폼 관련 논의
- 복잡한 질의(본인/대리인 여부, 상황, 업무 종류 등 분기가 많은 질의) 대응을 위해 멀티턴 대화로 큐폼 항목을 채우는 구조를 재확인
- 임베딩 검색으로 문서를 반환할 때도 여러 후보 대신 **큐폼으로 상황을 특정한 뒤 문서 하나를 확정**하는 방식으로 정리
- 큐폼을 다 채울 필요 없는 질의(개념 설명, 단순 정보성 질문)는 LLM이 판단해 큐폼 없이 바로 응답하는 방향 유지

### 주요 논의 및 결정사항
1. 라우팅 모델은 **MOAI(임베딩 기반)** 채택 방향으로 정리 — 속도보다 정확도 우위를 우선
2. 테스트셋 채점 시 **G6(저신뢰 OOS)는 채점 대상에서 제외**하는 원칙 확립
3. 학습셋을 1700건+700건(OOS)로 재설계하되, **OOS는 학습셋에서 최종 기각**(일반화 실패 위험)
4. Parent-Child 문제는 청크 단위 재라벨링·문서 전체 전달 방식을 모두 기각하고 **앵커-텍스트 방식**으로 최종 확정
5. 큐폼은 임베딩 검색 결과를 문서 1개로 확정하는 역할까지 담당하도록 범위 정리

## 3. 논의사항
- 앵커-텍스트 방식의 한계(원문 사이트 동적 변경 시 정답 구절 소실)에 대한 대응 방법 미정
- 민원 처리 관련 질의(상담원 연결 요청, 오류·버그 신고 등)를 **OOS로 분류할지 큐폼으로 처리할지** 미정 → 라우팅의 OOS 영역을 넓혀야 하는지 여부와 연결되는 문제로 추가 논의 필요
- 큐폼과 테스트셋(앵커-텍스트) 작업을 함께 보면서 방향성을 조율할 담당자가 아직 지정되지 않음

## 4. 이슈 정리

## 이슈 1. 테스트셋 내 저신뢰 라벨(G6)로 인한 성능 지표 왜곡

**문제**
G6은 원래 OOS로 라벨링된 애매한(저신뢰) 케이스인데, 이를 그대로 채점에 포함시키면 AUROC 등 성능 지표가 대폭 낮아지는 왜곡이 발생함.

**건의/조치**
G6을 테스트에서 제외하고 결과를 재확인 — 저신뢰 라벨은 채점에 사용하지 않는 원칙으로 정리.

## 이슈 2. 학습셋·테스트셋 규모 불균형

**문제**
학습셋 450건 대비 테스트셋 1150건으로 규모 차이가 커, 파라미터 튜닝만으로는 성능 향상에 한계가 있음.

**건의/조치**
학습셋을 1700건(6개 업무) 규모로 신규 구축. OOS 700건은 별도 검토했으나 일반화 실패 위험으로 학습셋에서 기각.

## 이슈 3. Parent-Child(문서 단위 라벨링 vs 청크 단위 응답) 문제

**문제**
정답이 문서 단위로 라벨링되어 있어 실제 답변 근거가 아닌 청크가 검색돼도 정답 처리되는 문제. 청크 단위로 라벨을 전환하면 파라미터 실험(청킹 사이즈 변경) 시마다 재라벨링이 필요해지는 문제가 반복됨. 문서 전체를 LLM에 전달하는 방식은 최대 3만자 분량의 문서로 인해 시간·비용 문제로 불가.

**건의/조치**
앵커-텍스트 방식 채택 — 청크마다 정답 구절 자체를 라벨로 저장해 청킹 파라미터가 바뀌어도 구절을 따라가며 자동 매칭. 동일 구절 다수 위치 시 중복 라벨로 대응. 신규 학습셋 1700건에 앵커-텍스트를 추가해 약 2000건 규모로 임베딩 예정. 단, 원문 사이트가 동적으로 변경될 경우 정답 구절이 사라질 수 있는 한계는 별도 대응 방법 필요.

## 이슈 4. 큐폼 적용 범위(민원·오류신고 처리 방식) 미정

**문제**
상담원 연결 요청, 오류·버그 신고 등 민원성 질의를 OOS로 분류할지, 큐폼으로 처리할지 결정되지 않음. 이는 현재 라우팅에서 OOS 영역을 어디까지 넓혀야 하는지와 직결되는 문제.

**건의/조치**
추가 논의 필요 — 결론 미도출, 다음 논의 안건으로 이월.
