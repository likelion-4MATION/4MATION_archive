## 0. 한 줄 요약

GT 검수가 여러 번 반복되고도 수렴하지 않은 이유는 라벨러 품질이 아니라 **"정답의 정의"가 매 사이클 바뀌었고, 라벨 재현성을 한 번도 측정하지 않았기 때문**이다. 오늘 측정으로 불일치의 95%가 **"근거를 몇 개까지 기록하나"라는 단일 미정 규칙**에서 나온다는 것이 확인됐다. 이 자유도를 제거하면 라벨링을 1회로 종결할 수 있다.

## 2. 왜 여러 번 검수해도 수렴하지 않았나 — 근본 원인 5가지

### 원인 ① 정답의 정의가 사이클마다 바뀌었다

| 사이클 | 평가 단위 | 정답의 정의 |
|---|---|---|
| 문서 기준 1차 | 문서 | `gt_docs` 단일 |
| 문서 기준 2차 | 문서 | `gt_docs` + **허용집합**(복수정답 도입) |
| 청크 기준 1차 | 청크 | `gt_chunk_ids` |
| 청크 기준 2차 | 청크 | + `evidence_type` × `chunk_relation` 두 축 |
| 오늘 | 청크 | + `unanswerable` 재판정 |

정의가 바뀌면 이전 검수 결과는 자동으로 무효가 된다. **"검수했는데 또 달라진다"가 아니라, 고정된 대상을 검수한 적이 없다.** 신뢰성이 성립하지 않은 게 아니라 신뢰성을 논할 기준선이 없었다.

> 문서 기준 사이클(1~2차)은 `changelog_testset_eval.md` 기록. 청크 기준 이후 담당자별 검수 회차는 별도 확인 필요.

### 원인 ② 결정은 내렸는데 데이터에 반영되지 않았다

`GT구축_전체정리.md` **D4**: "**`answerable=false` 출구 필수** — 강제선택 시 fallback 재생산". 규칙7("빈 배열 금지, 최선 앵커 강제")이 오배정 66%를 만든 걸 진단하고 폐기한 결정이다.

그런데 현재 GT는 **1,276건 전부 `answerable=true`**이고, 오늘 표본에서 23%가 답이 없는 질문으로 판정됐다. **규칙7을 폐기했는데 결과물은 규칙7이 만든 것과 같다.**

같은 패턴이 여러 곳에 있다 (→ §5 부록).

### 원인 ③ 검증 장치가 검증하지 못하는 것을 검증했다

| 장치 | 확인하는 것 | 놓치는 것 | 측정 결과 |
|---|---|---|---|
| `span_verbatim_ok` | 문장이 청크 안에 있나 | **질문에 답하나** | `has_span` 계층도 일치 7/25 |
| `confidence` | (자기 보고) | 실제 정확도와 **역상관** | `conf=0.0`이 가장 정확 13/25 |
| 검수 트리거<br>`span_verbatim_ok=false OR cross_domain` | 의심 구간 선별 | 통과 구간의 안전성 | 통과 구간이 안전하지 않음 |

전형 사례:
```
train4-UNCL-050  "이미 몇 년 지난 미수령금인데 신청 기한이 있나요?"
  gold span = "'16.10월부터 전국 지급대행점 어디에서든 미수령금을 통합 신청할 수..."
  → verbatim 통과. 기한에 대한 답은 아님.
```
**문자열 일치는 의미 적합성의 대리 지표가 될 수 없다.**

### 원인 ④ GT가 검색기에 종속됐다 (순환성)

`GT구축_전체정리.md` **D3**: "judge 후보 = **코퍼스 전수/BM25 광역**". 그런데 실제 라벨링은 컨텍스트 초과(40003) 회피로 `bm25 --cand-k 60`을 썼다.

**BM25 상위 60에 못 들어온 청크는 정답이 될 수 없다.** 그리고 그 GT로 그 검색기를 평가한다. §1-4의 복합명사 구멍(`송금인` 토큰 0건)을 함께 보면, BM25가 구조적으로 못 잡는 어휘의 정답은 GT에서 지워졌을 가능성이 있다.

오늘 파일럿은 **215청크 전수**(6.3만 토큰, 한 프롬프트에 들어감)를 제시했고, `cross_domain` 계층에서 재라벨이 명백히 더 나은 근거를 찾은 사례들이 나왔다.

### 원인 ⑤ 재현성을 한 번도 측정하지 않았다

오늘 처음 2회 교차를 돌렸다. 이 숫자가 없으면 "검수했다"가 무슨 뜻인지 정의되지 않는다. **지금까지의 검수는 각각 1회짜리 판정이었고 서로 비교 가능한 형태가 아니었다.**

## 3. 방법론 카드

각 카드: **원리 / 유도 이유 / 장점 / 한계 / 판정**

### M1. 청크 단위 평가 (문서 → 청크)

**원리** — 정답 판정을 `parent_doc_id` 일치에서 `chunk_id` 일치로 조인다.

**유도 이유** — 실제 파이프라인은 LLM에 개별 청크를 넘기므로, 정답 문서의 엉뚱한 청크가 잡혀도 크레딧되면 false positive다. 측정: recall@10이 문서 단위 0.945 → 청크 단위 0.645, **거품 +0.300**.

**장점** — 생성 단계가 실제로 받는 것을 측정한다. 0.645는 하락이 아니라 정직한 출발선.

**한계** — 형제 청크(평균 8.2개, 최대 37개)를 단일 정답으로 강제하면, 동등하게 옳은 형제를 골라도 오답 처리된다. §1-1의 210건이 이 피해자다. **`or` 관계 없이는 청크 단위 평가가 과소평가를 만든다.**
또한 `#순번`은 `CHUNK_SIZE`/`OVERLAP`에 종속돼 재청킹 시 전부 어긋난다 — QFORM 스펙 §3-2가 "`#순번`으로 조인 금지"라고 명시한 것과 **정면 충돌**한다.

**판정** — **유지.** 단 `or`/`alt_evidence` 필수 + `corpus_hash` 고정이 전제.

---

### M2. gold BF 주입 (오라클 평가)

**원리** — 평가 시 `classify_query_bf`(질의 분류기)를 건너뛰고 GT의 업무 값을 직접 주입한다.

```python
# eval_anchor_v3.py L295~300
pool = searcher.hybrid_soft(question, len(chunks), bf=gold_bf, boost=rag.BF_BOOST)
```

**유도 이유** — 검색 실패의 원인이 분류기 오류인지 순위 매기기 오류인지 분리하기 위해. 라우터는 별도 테스트셋(`router_trainset_v1.jsonl`, 1,665건)에서 평가한다.

**장점** — 검색기만 떼어내 본다. "라우터가 완벽할 때의 상한"을 준다. QFORM 스펙 §6의 오라클 실험 규율과 같은 도구다.

**한계** — 세 가지.
1. **주입하는 필드가 틀렸다.** `item["business_function"]`은 *질문이 속한 업무*이고, 답이 있는 업무는 `answer_bf`다. 다른 게 183건(14.3%). 그 183건에서 부스트가 **정답이 없는 업무 쪽으로** 걸린다 — 부스트를 안 거는 것보다 나쁘다.
2. **그리드서치가 이 어긋난 설정 위에서 돌았다.** `BF_BOOST=0.12`는 정상 86%와 어긋난 14%의 절충점일 수 있다.
3. **완벽한 라우터도 이 문제를 못 푼다.** 라우터 학습셋 라벨이 `business_function`이다(`answer_bf`가 아니다). 라우터가 100% 맞아도 14.3%는 부스트가 반대 방향으로 걸린다.

**판정** — **진단용으로 유지, 배포 성능으로 보고 금지.** 보고 시 `none`/`gold`/`answer`/`router` 4모드를 나란히 제시한다.

---

### M3. 소프트 부스트 (`BF_BOOST` / `FACET_BOOST`)

**원리** — 전체 코퍼스 가중 RRF 후, 질의 업무와 같은 태그를 가진 청크에 상수를 가산한다. 하드 필터와 달리 타 업무를 배제하지 않아 분류 오류 시 정답이 후보에 살아남는다(graceful degradation).

**유도 이유** — 업무 신호를 반영하되 오분류 위험을 흡수하기 위해. `BF_MODE="soft"` 채택(2026-07-22).

**장점** — 오분류가 치명적이지 않다. 파라미터 하나로 강도 조절.

**한계**
- **`business_function`은 청크당 1개 태그인데 실제 업무는 겹친다.** 예금보험금 문서 안에 미수령금 내용이 있고 구비서류는 두 업무가 공유한다. 분할이 아닌 것을 분할로 취급하는 구조라, 키우면 겹침 구간이 깨지고 줄이면 정상 구간을 잃는다. `BF_SHARED_DOCS`에 문서 하나가 하드코딩된 것이 이 한계의 예외처리 흔적이다.
- **`FACET_BOOST`는 주석과 다르게 동작한다.** 주석은 "업무 내부 형제문서 구분"이라 적혀 있으나, `sub_category`는 문서 단위 값이라(측정: 27개 다청크 문서 전부에서 형제가 동일) **형제 청크 전원에게 같은 부스트가 들어간다.** 형제 구분을 원리적으로 수행하지 못한다.
- **레버 크기가 24배 커졌는데 문서 결론은 갱신되지 않았다.**

| | 문서 작성 시점 | 현재 코드 | 변화 |
|---|---:|---:|---|
| `BF_BOOST` | 0.005 | **0.12** | 24배 |
| `FACET_BOOST` | 0.03 | 0.02 | 0.67배 |
| BF / facet 비율 | 1/6 | **6배** | 36배 역전 |

`GT구축_전체정리.md`의 "업무 필터는 가장 약한 레버 → **필터 OFF 논쟁 무의미**"는 BF가 facet의 1/6이던 시절 결론이다. 현재 0.12는 RRF 최대 기여(0.333)의 36%로 지배적 레버다. **재측정 대상.**

**판정** — **재측정 필요.** 전체 평균이 아니라 `same-domain`(1,093건) / `cross-domain`(183건) 층별로. 층별로 반대 방향이면 답은 "조건부 부스트"다.

### M4. 리랭커 (cross-encoder 재정렬)

**원리** — 검색 후보 top-N을 (질문, 청크) 쌍으로 다시 채점해 순서를 갈아엎는다.

**유도 이유** — `GT구축_전체정리.md` §4의 병목 진단: "크로스도메인 0.497 — dense가 타업무 정답 못 끌어옴 → **리랭커 신호**".

**장점** — 질문-문서 상호작용을 직접 모델링한다. 학습 없이 즉시 적용 가능.

**한계**
- **측정 결과 베이스라인보다 나빴다** (Hit@1 0.366 → 0.264).
- **후보 안에 있는 것만 올릴 수 있다.** 어휘 불일치로 후보에 아예 못 들어온 정답은 손댈 수 없다. cross-domain 병목의 처방으로는 간접적이다.
- **순수 재정렬은 베이스라인의 튜닝된 신호를 전부 폐기한다.** alpha·rrf_k·boost·facet·cap 5축 그리드서치 결과와 gold BF 주입을 버리고 리랭커 단독으로 경쟁하게 만든다.
- **1,005 ms/query.** 배포에서 CPU 추론이면 더 느리다.
- **현재 GT로는 우열 판정이 불가능하다.** gold 일치율 28%, 답 없는 질문 23%가 분모에 섞여 있다.

**판정** — **보류.** 라벨 수정 후 재측정. 단독 재정렬이 아니라 융합(M5)으로.

---

### M5. 리랭커 융합 (순위 RRF 스윕)

**원리** — 베이스라인 순위와 리랭커 순위를 가중 결합한다.
```
fused = alpha/(k + rank_base) + (1-alpha)/(k + rank_rerank)
```
`alpha=1`이 베이스라인, `alpha=0`이 순수 리랭커.

**유도 이유** — M4의 "튜닝된 신호 폐기" 문제를 해소하고, 리랭커의 기여를 **연속적으로** 측정하기 위해.

**장점** — `alpha` 곡선 모양이 곧 진단이다. 1.0에서 단조 감소면 리랭커가 순수 노이즈, 중간에 봉우리가 생기면 보조 신호로 가치 있음. 리랭커 점수를 디스크에 캐시하면 융합 파라미터 스윕은 GPU 없이 초 단위로 반복 가능하다. 오프라인 검증: `alpha=1.0`이 rrf/score 양쪽 모드에서 베이스라인 순서를 정확히 재현하고 `MacroR@50`이 불변임을 확인.

**한계** — 리랭커가 애초에 정보를 안 주면 어떤 `alpha`에서도 이득이 없다. 그리고 M4와 같은 GT 신뢰도 문제를 공유한다.

**판정** — **M4의 올바른 측정 방식으로 채택.** 실행은 라벨 수정 후.

---

### M6. 전수 코퍼스 제시 라벨링

**원리** — 후보를 좁히지 않고 코퍼스 215청크 전체(6.3만 토큰)를 프롬프트에 넣고 고르게 한다.

**유도 이유** — 원인 ④(순환성) 차단. 후보를 BM25로 좁히면 GT가 검색기 성능에 갇힌다. 코퍼스가 작아서 전수가 물리적으로 가능하다.

**장점**
- GT가 어떤 검색기에도 종속되지 않는다.
- 업무 경계를 넘는 정답(`cross_domain`)을 자연스럽게 찾는다.
- "후보에 정답이 없어서 억지로 하나 고르는" 실패 모드가 원천 제거된다.

**한계**
- 코퍼스가 커지면 불가능해진다. 그때는 종속성을 감수할지 명시적으로 판단해야 한다.
- 토큰 비용이 배치 수에 비례한다 — 비용의 대부분이 **코퍼스 재전송**이다. 실측: 100문항 × 2패스 = 35.6만 토큰. 질문 1,276개 전부는 5만 토큰뿐이므로, 배치를 잘게 쪼갤수록 낭비가 커진다.

| 배치 크기 | 호출 수(2회) | 입력 토큰(추정) |
|---|---:|---:|
| 30문항 | 86 | ~5.6M |
| 100문항 | 26 | ~1.7M |
| 300문항 | 10 | ~0.7M |

**판정** — **채택.** 배치 100~300문항. 출력 품질이 배치 크기의 제약이다(문항당 약 90토큰 × 배치).

### M7. 2회 교차 + 재현성 지표

**원리** — 청크 제시 순서와 질문 순서를 바꿔 독립 2회 라벨링하고, 일치율을 측정한다.

**유도 이유** — 원인 ⑤. "검수했다"를 숫자로 정의하기 위해.

**장점** — 라벨 신뢰도를 처음으로 정량화했다. 그리고 **불일치 유형 분해가 기준의 결함을 정확히 지목한다** — 오늘 95%가 단일 미정 규칙에서 나온다는 걸 이 방법 없이는 알 수 없었다.

**한계** — 비용 2배. 그리고 2회가 일치해도 **둘 다 틀릴 수 있다**(재현성 ≠ 정확도).

**판정** — **교정 라운드에만 사용.** 기준이 자유도를 제거했음을 확인하는 용도. 목표 달성 후 전수는 1회.

> **1회 종결의 근거**: gold 보유 77건 중 교집합 존재가 94%(72건)다. 즉 두 패스가 갈린 실체는 "맞나 틀리나"가 아니라 "여러 정답 중 어느 걸 골랐나"였다. **복수정답을 모두 기록하면 재현율이 52% → 94%로 올라간다.** 자유도를 없애면 2회를 돌릴 필요가 없다.

### M8. 기계 검증 게이트

**원리** — LLM이 뽑은 인용문이 해당 청크 본문의 부분문자열인지(공백 정규화 후) 프로그램이 확인하고, 실패한 라벨은 **파일에 남기지 않는다**.

**유도 이유** — HCX 라벨의 `span` 빈 값 595건(46.6%)이 구조적으로 생기지 않게.

**장점** — 오늘 파일럿에서 266개 인용 전부 통과. **"근거 없는 라벨"이 원천 차단된다.** 사후 검수 대상이 아니라 생성 게이트다.

**한계** — **의미 적합성을 보증하지 않는다.** `has_span` 계층조차 재라벨 일치가 7/25였다. 게이트는 최소 조건이고, 정확도는 판정 규칙(M14)과 재현성(M7)으로 담보해야 한다.

**판정** — **필수.** 단 이것을 "검증 완료"로 읽지 않는다.

### M9. HyDE

**원리** — 질문에 대한 가상 답변을 생성하고, 그 답변을 임베딩해 유사 청크를 검색한다. 질문 어휘가 아니라 **답변 어휘**로 검색한다.

#### M9-a. HyDE를 라벨링에 쓰는 안 — **기각**

**유도 이유** — 생성 답변과 가장 유사한 청크를 gold로 삼으면 더 정확할 것이라는 기대.

**한계 (기각 사유)**
1. **D2 위반 (순환성).** D2는 "GT는 LLM judge(추출)로 생성 → 임베딩과 독립 → 순환성 차단"이다. HyDE는 임베딩 검색으로 GT를 만들고 그 GT로 임베딩 검색을 평가한다. 임베딩이 못 끌어오는 청크는 gold가 될 수 없어, 그 검색기의 약점이 GT에서 지워진다. §1-4의 복합명사 구멍과 같은 종류의 문제를 더 강하게 만든다.
2. **D4 위반 (강제 충전 재발).** 표본의 23%가 답이 없는 질문이다. HyDE는 답이 없어도 그럴듯한 답변을 생성하고, **유창한 환각 답변은 반드시 무언가와 높은 유사도를 낸다.**
   ```
   "고령자를 위한 예금보험금 신청 도움 서비스가 있나요?"
   → "예금보험공사는 고령자를 위해 창구 안내와 대리인 신청을 지원합니다"(환각)
   → 대리인 서류 청크와 높은 유사도 → gold 확정
   ```
   규칙7이 만든 오배정을 기계적으로 재생산한다.
3. **측정된 병목을 건드리지 않는다.** 불일치 95%가 "몇 개까지 기록하나"였다. HyDE는 후보 선택 방식을 바꾸는 기법인데, 오늘 파일럿은 후보 제한이 애초에 없었다(전수 215).

#### M9-b. HyDE를 검색에 쓰는 안 — **채택 후보**

**유도 이유** — cross-domain 실패의 메커니즘이 **어휘 불일치**다. 질문은 "미수령금 소멸시효", 정답 청크는 "예금보험금청구권은 「예금자보호법」제31조제7항의 규정에 의하여". 질문 어휘와 문서 어휘가 겹치지 않는다.

**장점** — HyDE는 이 vocabulary gap을 메우는 표준 처방이다. 그리고 **리랭커보다 직접적이다** — 리랭커는 후보에 있는 것만 올리는데 HyDE는 후보 자체를 바꾼다. M4가 베이스라인을 못 넘은 이유 중 하나가 "후보에 없는 걸 만들어낼 수 없음"일 수 있다.

**한계** — 생성 지연·비용이 질의당 추가된다. 환각 답변이 엉뚱한 문서로 끌고 갈 위험(검색에서는 치명적이지 않으나 정밀도를 떨어뜨림). 그리고 M10과 목적이 겹친다(둘 다 어휘 확장).

**판정** — **검색 쪽 후보로 채택, 리랭커와 같은 자리에서 경쟁 측정.** 라벨 수정 후 `hit@5`/`hit@10`, cross-domain 층 중심으로.

#### M9-c. 역방향 (청크 → 질문 생성) — **주지표 금지, 별도 셋만**

**장점** — `answerable`이 구조적으로 보장된다. 오늘 23% 답없음의 근본 원인("질문 먼저, 근거 나중")을 원천 해소한다.

**한계** — `changelog_testset_eval.md` §4가 이미 기록한 함정: "faq 1.000 — 정답 페이지에서 추출 → **누수, 상한 아티팩트**. 자연어화 시 페이지 문장 복붙 금지". 질문이 코퍼스 어휘로 오염돼 지표가 부풀려진다.

**판정** — 기존 질문셋(실사용 어휘)은 유지. 코퍼스 커버리지 측정용 **별도 셋**으로만, 주지표에 섞지 않는다.

### M10. 계층 키워드 텍스트 앵커 + 큐폼 슬롯

**원리** — 업무 분류를 6개 플랫 태그에서 계층 경로로 확장하고(`착오송금 → 송금인 → 법인 → 대리인`), 각 노드에 **유사 표면형 묶음**을 달아 청크 **본문**에서 매칭시킨다. 매칭 가중치가 누적된 청크/문장이 위로 올라온다. 메타데이터와 크롤링 파이프라인은 건드리지 않는다.

**유도 이유** — 형제 청크 문제와 `cross_domain` 부스트 역방향 문제를 한 번에 다루기 위해. 그리고 큐폼이 받은 슬롯 값을 검색 신호로 재사용하기 위해.

**장점**
1. **형제 구분 정보가 본문에 실재한다.** 다청크 문서에서 형제 대비 고유 토큰 3개 이상인 청크가 **96%**다. 메타데이터로는 0/27이지만 텍스트로는 갈린다.
2. **축 용어의 판별력이 측정됐다.** `절차` 19문서 중 14, `법인` 12중 10, `전화` 10중 9, `자격`·`단체` 5중 5.
3. **BM25가 못 잡는 구멍을 정확히 메운다.** `송금인` 토큰 0건 / 원문 21청크, `미성년` 0건 / 16청크. 복합명사에 묻힌 21·16청크가 표면형 묶음으로 살아난다. **질의측만 손대면 되고 파이프라인 무손상이다.**
4. **큐폼 슬롯은 추측이 아니라 사용자 입력이다.** 현재 `classify_query_bf`의 추측 오류가 183건에서 부스트를 반대로 걸고 있는데, 신호가 사용자 입력으로 바뀌면 그 오류원이 사라진다. M3의 "부스트를 키우면 겹침 구간이 깨진다"는 제약도 함께 완화된다.
5. **QFORM 스펙 §1이 이미 채택한 (나) 노선의 구현이다.** "슬롯 값을 쿼리 직렬화 + 소프트부스트 입력으로 흘려 정문서를 생성 window 안으로 끌어올린다."
6. 결정론적이라 재현 가능하고, 관리자 콘솔에서 편집 가능한 자산이 된다.

**한계**
1. **수동 큐레이션 유지 비용.** 현재 `BF_QUERY_KEYWORDS`도 이미 6업무 × 십수 개다. 계층으로 내려가면 표면이 곱셈으로 늘어난다.
2. **가중치를 튜닝할 대상이 GT다.** 지금 GT는 gold 일치율 28%다. 신뢰할 수 없는 정답에 가중치를 맞추면 **오라벨에 과적합**된다.
3. **가중치 방향을 틀리기 쉽다.** 상위 노드(`착오송금`)는 이미 BF 부스트가 문서 선택을 하고 있어서, 거기 더 주면 형제가 똑같이 올라가 아무것도 안 갈린다. **깊을수록(희소할수록) 가중치가 커야 한다** — 본질은 수동 큐레이션된 IDF다. 측정이 이를 뒷받침한다: `법인`(24청크)은 12문서 중 10에서 판별력, `서류`(41청크)는 12문서 중 4뿐이다.
4. **문장 단위로 내려가면 집계 방식이 결과를 좌우한다.** max / top-3 합 / 길이 정규화 합에 따라 짧은 청크 편향이 생긴다. 현재 채점 단위는 청크다.
5. 4/27 문서에는 고유 토큰 0인 청크가 있다 — 텍스트로도 못 가르는 진짜 중복. 이건 라벨의 `or`로 흡수해야 한다.

**판정** — **채택, 단계적으로.**
- 1단계: 청크 단위 가중 합으로 시작. 문장 단위는 **근거 하이라이트**(사용자에게 보여줄 문장)로 분리 — 그 대상이 GT의 `sentence` 필드와 동일하므로 라벨이 그대로 검증 재료가 된다.
- 2단계: 가중치 튜닝은 라벨 수정 후.
- **GT 없이 지금 검증 가능한 것**: 용어 클러스터가 새로 커버하는 청크 수. 코퍼스만으로 셀 수 있다.
- 우선 축: 측정상 판별력이 높은 **채널**(온라인/방문/우편/전화)과 **인적유형**(본인/대리인/법인/단체). 복합명사 구멍은 `송금인`·`미성년`·`수취인`.

### M11. 순위 캐시 오프라인 스윕

**원리** — RRF는 **순위만** 쓰고 점수는 쓰지 않는다. 질의별 dense·sparse 순위 배열(각 215)을 한 번 캐시하면 `alpha`·`rrf_k`·`boost`·`FACET_BOOST`·`BF_DOC_CAP` 전부 GPU·검색 없이 손실 없이 재계산된다.

```python
rrf[idx] += alpha / (rrf_k + rank + 1)   # rank만 들어감
if 같은 업무: rrf[idx] += boost           # 순수 가산
```

**유도 이유** — 5축 그리드서치를 매 조합마다 1,276번 검색을 반복하며 돌고 있었다.

**장점** — 캐시 생성 1회 약 10분(파일 1~2MB), 이후 전체 그리드서치가 CPU 수십 초. 층별 분해·조건부 부스트 실험·리랭커 융합까지 같은 캐시로. 손실 없이 정확히 동일한 결과.

**한계** — 코퍼스나 임베딩 모델이 바뀌면 캐시 무효. 청크 순서 변경에도 무효.

**판정** — **채택.** 파라미터 실험의 기본 인프라.

---

### M12. 청크 메타데이터 재태깅 — **기각**

**원리** — `person_type`·`channel`·`doc_type` 같은 축을 청크마다 새로 붙인다.

**유도 이유(초기 오판)** — 형제 청크를 구분하는 메타데이터 필드가 0/27이므로 새 라벨이 필요하다고 판단했다.

**기각 사유** — **크롤링 파이프라인이 망가진다.** 청크 메타는 `chunk.py`가 결정론적으로 생성하며, 임의 재태깅은 재수집·재청킹 사이클과 충돌한다. 그리고 **불필요하다** — 구분 정보가 이미 본문에 있고(고유 토큰 96%), M10이 파이프라인을 건드리지 않고 같은 목적을 달성한다.

**판정** — **기각.** M10으로 대체.

---

### M13. 청킹 재설계 — **이번 사이클 밖**

**유도 이유** — 형제 청크 평균 8.2, 최대 37. 같은 내용이 여러 청크에 흩어져 있다.

**한계** — `chunk_id = doc#순번`이 `CHUNK_SIZE`/`OVERLAP`에 종속돼, 청킹을 바꾸면 **GT 전체가 무효**가 된다(QFORM 스펙 §3-2가 명시). `corpus_hash`가 바뀌므로 라벨 작업을 다시 해야 한다.

**판정** — **보류.** 라벨 확정 후 별도 사이클. 라벨 쪽에서는 `or` 규칙으로 상당 부분 흡수된다.

### M14. 단독 충분성 규칙 + `partial` 폐지

**원리** — 정답 판정을 단 하나의 이진 테스트로 정의한다.

> **이 청크 하나만 사용자에게 보여주면, 사용자가 질문에 대한 답을 얻는가?**

통과한 청크를 **전부** 기록한다(개수가 판단 대상이 아니게 된다). 보조·맥락 청크는 기록하지 않는다.

**유도 이유** — 불일치 37건 중 35건(③ 14 + ④ 21)이 "몇 개까지 기록하나"에서 나왔다. 그리고 남은 경계 불일치 5건이 전부 `partial` 판정에서 나왔다.

**장점** — 재현율을 52% → 94%(교집합 기준)로 끌어올리는 단일 레버다. `partial`을 없애 3지를 2지로 줄이면 경계 판정의 자유도도 사라진다.

**한계** — "핵심 요구를 충족한다"의 판단이 여전히 사람/모델 몫이다. 규칙이 아니라 **판정 예시집**으로 보강해야 한다. 그리고 여러 청크를 합쳐야 답이 되는 경우(`composite`)를 어디까지 허용할지는 미결(→ §6).

**판정** — **채택.** 기준 문서의 §1로 승격.

## 4. 라벨링 기준 (요약)

전체 규격은 별도 문서로 확정하되, 골격은 다음과 같다.

**판정** — `verdict` 3지

| 값 | 정의 | gold | 채점 |
|---|---|---|---|
| `single` | 단독으로 답하는 청크가 1개 이상 | 그 청크들 **전부** | OR |
| `composite` | 단독 충분 청크는 없으나 정확히 2개 조합으로 완성 | 필수 2개 | AND |
| `none` | 위 둘 다 아님 | `[]` | 분모 제외 |

**`none`의 두 갈래** (거절·에스컬레이션 평가 자산)

| `none_reason` | 정의 | 표본 예시 |
|---|---|---|
| `out_of_scope` | 예보 소관이 아님 | 법률 상담, 개인회생 병행, 계좌 정지 |
| `not_documented` | 소관인데 웹사이트에 서술 없음 | 우편 접수, 이의제기 창구, 교육자료, 고령자 지원 |

**인용문** — 글자 그대로, 완결 문장, **15자 이상**(현 GT에 단어 하나짜리 117건).

**절차** — 후보 전수 215청크 · 업무를 후보 제한에 쓰지 않음 · 기존 HCX 라벨 비공개(확인 편향 차단).

**게이트** (실패 = 폐기·재질의)

| # | 검사 |
|---|---|
| G1 | `chunk_id`가 코퍼스에 존재 |
| G2 | `sentence`가 해당 청크 본문의 부분문자열(공백 정규화) |
| G3 | `sentence` 길이 ≥ 15자 |
| G4 | `verdict=none` ⟺ `gold == []` |
| G5 | `verdict=composite` ⟹ `len(gold) == 2` |
| G6 | `corpus_hash` 일치 |
| G7 | 질문 중복 없음 |

**스키마** — 15필드 → 6필드. 나머지는 파생.

```json
{
  "id": "...", "question": "...",
  "verdict": "single",
  "gold": [{"chunk_id": "...", "sentence": "본문에서 글자 그대로"}],
  "none_reason": null,
  "corpus_hash": "sha256:..."
}
```

파생: `answerable` ← `verdict != "none"` · `chunk_relation` ← verdict + gold 개수 · `gt_chunk_ids` · `gt_anchor_span` ← `gold[0].sentence` · `gt_alt_evidence` ← `gold[1:]` · `answer_bf` ← `gold[0]`의 청크 업무 · `cross_domain` ← `answer_bf != business_function` · `evidence_type` ← verdict.

폐기: `confidence`(정확도와 역상관) · `reason`(검증 불가) · `multi_chunk`(중복) · `gt_chunk_id`(중복).

**지표**
- **주지표: `hit@5` / `hit@10`** — LLM에 5개 vs 10개 청크를 넘길 때의 탐색 시간 트레이드오프 측정
- 보조: `hit@1` · `MRR@10` · `recall@10`
- `composite`는 별도 집계(AND 채점)
- **doc-level 병기** — chunk-level만 낮으면 형제 청크 문제라는 진단이 자동으로 나옴
- 지표에는 항상 4개 동봉: **분모 정의 · 코퍼스 버전 · 라벨 버전 · 재현성 수치**

**확정 조건 (라벨링 1회 종결)**
1. 위 기준으로 표본 100건 2회 교차 (교정 라운드)
2. 목표: 집합 완전일치 ≥ 90%, verdict 일치 ≥ 95%
3. 달성 → 전수 **1회**로 확정 / 미달 → 불일치 유형을 다시 분해해 **규칙을 보강**(라벨을 더 만들지 않는다)
4. 전수 라벨 게이트 100% 통과 + 계측치 동봉

> **종료 조건은 "달라지는 게 없을 때까지"가 아니다.** 그건 도달 불가능하다. "교정 라운드에서 목표 재현성을 달성했고 전수 라벨이 게이트를 100% 통과했다"가 종료 조건이다.
