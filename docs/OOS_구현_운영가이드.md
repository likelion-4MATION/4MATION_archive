# OOS 구현·운영 가이드

## 적용 범위

새 대화 입력은 먼저 보수적으로 절 단위로 나뉘고, 모든 절이 기존 6-BF 라우터를 통과한다.
BF로 판정된 절만 Qform과 범위 제한 RAG로 들어가며, 나머지는 OOS 정책으로 처리된다.
뒤 절은 세션의 `unit_queue`에 순서대로 보관한다.

이번 구현은 BF/OOS 라우터의 임계값과 판정 경계를 변경하지 않는다. 현재 경계 문제를 별도
작업에서 수정하더라도 `chatbot/router_adapter.py`가 기존 라우터 결과를 그대로 받아 쓴다.

## OOS 안전 규칙

- 판정 출력은 `action`, `row_id`만 허용하는 엄격한 JSON이다.
- 우선순위는 챗봇 답변 오류 신고, 등록 안내처, 일상 대화, 명백한 원거리 OOS, 유선 상담 순이다.
- 파싱 실패, 타임아웃, 라우터 장애, 모호한 금융 인접 질문은 유선 상담 안내로 닫는다.
- OOS 경로에서는 RAG 검색과 답변 생성을 호출하지 않는다.
- 기관명·URL·전화번호·운영시간은 게시·활성·검증 완료된 운영 레지스트리 값만 보여 준다.
- 원거리 OOS 고정 응답에는 유선 상담 안내를 붙이지 않는다.

## 운영 데이터

관리자 콘솔의 `⑧ OOS 안내처`에서 안내처와 유선 상담 정보를 관리한다. 안내처 게시 조건은
필수 필드, 정상/반례 트리거 검증, 게시 행 간 충돌 없음, 활성 상태, 링크 상태 `정상`이다.
행 ID는 만든 뒤 화면에서 바꿀 수 없고, 변경할 때마다 버전과 감사 스냅샷이 남는다.

초기 데이터에는 실제 기관명이나 연락처를 임의로 넣지 않았다. 관리자가 공식 근거로 확인한
값을 게시해야 사용자에게 노출된다. 게시 정보가 없으면 유선 상담 버튼도 연락처를 만들지 않고
“게시된 정보 없음”으로 안내한다.

`⑨ 오류 신고함`에서는 상태, 담당자, 메모, 중복 기준 신고를 관리한다. 저장 시 주민번호,
카드번호, 전화번호, 계좌번호, 이메일, 인증번호, 비밀번호를 마스킹하고 비밀키 계열 필드는
제외한다. 원본 시각은 UTC로 저장하며 화면은 한국시간으로 표시한다. 신고는 생성 30일 후
자동 삭제된다.

SQLite 파일은 `admin/data/oos.sqlite3`이며 Git에 포함하지 않는다.

## 실행과 확인

리포지토리 루트에서 챗봇과 관리자 콘솔을 각각 실행한다.

```bash
# 터미널 1 — 관리자
source .venv/bin/activate
cd admin
python -m uvicorn main:app --host 127.0.0.1 --port 8600

# 터미널 2 — 리포지토리 루트에서 챗봇
source .venv/bin/activate
python -m streamlit run chatbot/app.py \
  --server.address 127.0.0.1 --server.port 8501
```

공통 의존성 설치와 인덱스 생성은 [RUNBOOK](./RUNBOOK.md#0-공통-준비)을 따른다.

OOS 단위 테스트:

```bash
python -m pytest tests/test_oos.py -q
```

운영 점검 순서는 다음과 같다.

1. 안내처를 초안으로 저장하고 정상 예시와 반례의 미리보기를 확인한다.
2. 공식 URL을 직접 확인한 뒤 링크 상태를 `정상`, 상태를 `published`, 활성을 켜서 저장한다.
3. 챗봇에서 정상 예시를 입력해 레지스트리의 고정 응답만 노출되는지 확인한다.
4. 챗봇 상단 신고 버튼과 “챗봇 답변이 틀렸다” 문장으로 각각 신고를 만든다.
5. 신고함에서 마스킹, 검색 근거·점수, 라우팅 기록, 30일 삭제 시각을 확인한다.
