# 앵커 텍스트 정답 라벨링 — 파이프라인 문서

> **상태**: 설계(제안) · 미착수
> **레이어**: 평가 / 정답(GT) 라벨링 — `testset*.jsonl`, `eval_TF.py`
> **원칙**: 청킹·인덱싱 파이프라인 **무수정**. 정답을 청크가 아니라 **내용(앵커 텍스트)** 에 건다.
> **한 줄**: 정답을 청크 경계가 아니라 안정적 내용 스팬에 라벨 → 재청킹해도 라벨이 안 깨진다.

---

## 0. 왜 앵커 텍스트인가 (결정 흐름 요약)

```
[시작]  문서 단위 정답 체크 + 청크 단위 반환
          └→ 같은 문서 안의 '다른 청크'가 정답으로 계산됨 (오탐)
          └→ 정확도(hit@k) 상한 과대추정  ── 문제
                     │
[후보1]  청크 단위로 정답까지 라벨링
          └→ 오탐은 잡히나, 관리자 UI 재청킹 시 chunk_id 변동 → 라벨 전량 재작업  ── 취약
                     │
[채택]   앵커 텍스트 방식
          └→ 정답을 '내용 스팬'에 건다(청크 ID 무관) → 재청킹해도 라벨 그대로
```

현재 `eval_TF.py`는 `chunk["parent_doc_id"] in gt`로 적중을 판정한다(문서 단위). 정답 문서의 **정답 스팬이 없는 청크**가 top-k에 들어와도 적중으로 세어 `hit@k`를 부풀린다(H12 "self-referential → 상한 추정"과 같은 방향). 앵커 방식은 이 오탐과 재청킹 취약성을 동시에 해소한다.

---

## 1. 파이프라인 개요

정답 라벨을 "이 청크"가 아니라 "이 내용이 든 곳"으로 표현하고, 평가 시 top-k 청크가 그 내용을 **포함**하는지로 적중을 판정한다.

```
① 앵커 선정      정답을 유일하게 특정하는 최소 내용 스팬 추출
② 라벨 스키마     testset에 gt_anchors 추가 (gt_docs 병존)
③ 중복 라벨 처리  한 정답이 여러 곳(FAQ 등)에 정당히 존재 → 앵커 리스트로 명시
④ 정규화         라벨·청크 텍스트 공백/특수문자 정규화 규칙 통일
⑤ 평가 판정      top-k 청크 중 하나라도 앵커 포함 시 적중
⑥ 재청킹 검증     청크 파라미터를 바꿔 재청킹 후 앵커 잔존·판정 불변 확인
```

**청킹·인덱싱·검색은 건드리지 않는다.** 바뀌는 것은 `testset`의 라벨 필드와 `eval_TF.py`의 "적중" 판정부뿐.

---

## 2. 단계별 정의

### ① 앵커 선정
- 정답을 **유일하게 특정하는 최소 스팬**. 짧고 변별력 있게(문장 전체보다 핵심 구절).
- 표 청크처럼 긴 직렬화 텍스트에서는 정답 행을 특정하는 구절을 앵커로.

### ② 라벨 스키마 (초안)
```jsonc
{
  "question": "...",
  "business_function": "...",
  "gt_docs": ["kdic-...-selectScrn"],                 // 기존 유지(병존)
  "gt_anchors": ["착오송금 반환요구에 대한 이의 제기서 양식"]  // 신규: 정답 내용 스팬(1+개)
}
```
- `gt_docs` 병존 → 점진 전환. 판정은 `앵커 포함` 단독 또는 `앵커 포함 AND doc 일치` 선택 가능.

### ③ 중복 라벨 처리 — FAQ 중복 (필수)
- FAQ/게시판은 **cross-topic**이라 같은 정답 내용이 여러 문서·청크에 정당히 존재(예: 정산금·지급대행점·Fast-Track이 두 문서에 중복 → 이미 `gt_docs` **이중 라벨** 운용 중).
- 앵커도 같은 원리로 **리스트로 명시**: 정답이 N군데면 앵커 N개(또는 한 앵커가 N군데 등장). top-k에 **어느 하나라도** 포함되면 적중.
- **의도된 중복(라벨로 명시)** 과 **비의도 중복(유일성 검증에서 걸러 더 변별적 스팬으로 교체)** 을 구분 — §5 R1 참조.

### ④ 정규화
- 라벨 앵커와 청크 텍스트를 **동일 규칙**으로 정규화(공백 제거·줄바꿈 정리). 검색 분류기(`classify_query_bf`의 `replace(" ","")`)와 정규화 철학을 맞춰 포함 판정 안정화.

### ⑤ 평가 판정
- `hit@k = ∃ chunk ∈ topk : gt_anchor ⊂ normalize(chunk.text)` (앵커 리스트면 OR).
- 지표 정의(`hit@1/hit@3/MRR`)는 유지, **"적중"의 기준만** 문서 일치 → 앵커 포함으로 교체.
- **전환 효과 정량화**: 같은 평가셋에서 문서단위 판정과 앵커 판정을 나란히 산출 → 두 `hit@k` 차이 = 그동안 있던 오탐 규모. 채택 근거로 직접 제시.

### ⑥ 재청킹 견고성 검증
- 청크 크기·오버랩·표 규칙을 바꿔 재청킹 후, 앵커가 여전히 **어느 한 청크에 온전히** 잔존하고 판정이 불변인지 확인. 관리자 UI 청킹 조절 시나리오의 회귀 테스트.

## 3. 스케일 계획 — 1705 → 2155

| 단계 | 규모 | 내용 |
|---|---|---|
| 앵커 방식 완성 | — | §1~⑥ 파이프라인·판정 확정 |
| 학습셋 전환 | **1705건** | 기존 1705 학습셋을 앵커(gt_anchors) 기준으로 재라벨 |
| 통합 평가 | **총 2155건** | 전환분 + 추가분(450) 합산 규모로 테스트 |

- 전환은 **1회성**이며 재청킹에도 재사용 → 청크 재라벨링 대비 총비용 낮음.
- 통합 후 앵커 판정 기준으로 `eval_TF` 지표 재산출 → 문서단위 대비 델타 리포트.

> **확인 필요**: 총 2155의 구성(추가분 450건이 기존 `testset_natural_400`을 포함하는지, 신규인지) 명시 → §5 R5.

## 5. 고려할 점 (열린 이슈)

| # | 이슈 | 방향 |
|---|---|---|
| R1 | **의도된 중복 vs 비의도 중복** — 앵커가 여러 곳 등장 시, 정당한 FAQ 중복인가 변별력 부족인가 | 정당 중복은 라벨 리스트로 명시 / 비의도는 유일성 검증에서 더 변별적 스팬으로 교체 |
| R2 | **판정 엄격도** — 완전포함(엄격) vs 정규화 후 부분포함(완화) | 법·돈 도메인이라 완전포함으로 시작, 표 청크 긴 직렬화로 과빡빡하면 완화 검토 |
| R3 | **앵커 포함성** — 앵커가 청크 경계에 잘려 두 청크로 분할 | 앵커 축소 / 정규화 통일 / **표 무분할·오버랩 규칙과의 상호작용** 점검 |
| R4 | **앵커 최소성 ↔ 변별력** — 너무 짧으면 오적중, 너무 길면 잘림 | 정답 특정 최소 스팬 가이드 정립 |
| R5 | **2155 구성 확정** — 추가분 450건의 출처(기존 400 포함 여부) | 통합 전 명시 |
| R6 | **정답 첨부 정밀도(파생 과제)** — 표 청크가 여러 서식을 합집합으로 반환 | 별도 검토(앵커-토큰 관련도 정렬) — 본 문서 범위 밖, 파생으로 기록 |

## 7. 한 줄 요약

> 문서 단위 정답은 오탐으로 정확도를 부풀리고 청크 단위 정답은 재청킹마다 깨진다. **정답을 앵커 텍스트에 걸면** 오탐도 잡고 재청킹에도 라벨이 살아남는다. FAQ처럼 정당한 중복은 라벨 리스트로 명시하고, 1705 학습셋을 앵커 기준으로 전환해 총 2155건으로 평가한다. 청킹은 손대지 않고 판정 기준만 "앵커 포함"으로 바꾼다.
