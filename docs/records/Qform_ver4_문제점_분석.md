## 1. 🔴 조합 테이블의 근거 청크 ID가 곧 전부 끊어진다

### 확인된 사실

`qform_combos_msdr.csv`의 `evidence_chunks_v0` 컬럼은 `MsdrprPossDcmntGudn-selectScrn#01` ~ `#19`를 참조한다. 그런데 코퍼스가 이미 바뀌었다.

| 기준 | 총 청크 | `MsdrprPossDcmntGudn` | `MsdrprAttnMttr` |
|---|---:|---|---|
| `origin/Qform_ver3` | 215 | **20개** (#00~#19) | 8개 (#00~#07) |
| `origin/dev` | 215 | 20개 | 8개 |
| **로컬 `feature/anc` (커밋 `e7e898f`)** | **181** | **2개 (#00, #01)** | **3개 (#00~#02)** |

커밋 `e7e898f` "표 원자성 수정 코퍼스 반영"으로 **재청킹이 이미 완료**되어 있다. 이것이 dev에 머지되는 순간 조합 테이블의 근거가 무너진다.

### 피해 범위 — MSDR 14행 중 11행

| combo | 참조 청크 | 현행(181) 존재 여부 |
|---|---|---|

| C03 | #02·#03·#04·#05 | ❌ 전무 |
| C04 | #05 | ❌ |
| C05 | #05·#06 | ❌ |
| C06 | #06·#07·#08 | ❌ |
| C07 | #08·#09 | ❌ |
| C08 | #09·#10·#11 | ❌ |
| C09 | #11·#12 | ❌ |

**C03~C12 10행은 근거가 하나도 안 남고, C02는 절반이 날아간다.**

### 왜 문서가 이걸 못 봤나

ver4 §8은 "동결 파일 8종이 스프린트 시작 시점과 해시 동일"을 성과로 든다. 그런데 **동결은 자기 브랜치 안에서만 성립한다.** 코퍼스는 다른 트랙(`feature/anc`)에서 재청킹되고 있었고, ver4 문서 어디에도 이 의존성이 언급되지 않는다.

§8의 "원문에 없는 결론을 만들지 않는다 / 검증 스크립트가 창작을 잡아낸다"는 원칙도 **근거 ID가 dangling이면 무력화**된다. `verify_combos.py`가 무엇을 대조하고 있는지 재확인이 필요하다 — 존재하지 않는 청크를 참조해도 통과한다면 그 검증은 지금 아무것도 보증하지 않는다.

### 더 큰 위험 — DPIN 9행

ver4가 신설한 `qform_combos_dpin.csv` 9행도 같은 방식으로 근거 청크를 박았을 가능성이 높다. **215 기준으로 박았다면 폭탄이 2배**가 되고, 181 기준으로 박았다면 MSDR과 DPIN이 서로 다른 코퍼스를 참조하는 상태가 된다. 어느 쪽인지 **즉시 확인 필요**(§10 Q1).

### 조치

1. DPIN 9행의 기준 코퍼스 확인
2. 재청킹 머지 전에 **구 청크 ID → 신 청크 ID 매핑표** 작성 (텍스트 대조로 자동 생성 가능)
3. `verify_combos.py`에 **"참조 청크가 현행 코퍼스에 실존하는가"** 검사 추가 — 지금 이 검사가 없다면 그것이 가장 시급하다
4. 근거를 청크 ID가 아니라 **`(doc_id, 텍스트 스니펫)` 쌍**으로 바꾸는 것 검토. 청킹은 앞으로도 바뀐다

```bash
# 확인
git show origin/Qform_ver3:crawler/data/chunks.jsonl | wc -l          # 215
wc -l crawler/data/chunks.jsonl                                       # 181
git log --oneline -1 -- crawler/data/chunks.jsonl                     # e7e898f
```

## 2. 🔴 §6 진단이 부정확하다 — 막는 건 한 곳이 아니다

### 서술과 코드의 차이

ver4 §6:
> `verify_qform_e2e.py`의 **한 케이스**가 "예금보험금은 어떻게 신청하나요?"를 **소관 밖 질문으로 하드코딩**해 두고 "되묻기가 안 나와야 한다"를 단언한다.

실제 코드(AC5):
```python
# ── AC5. 소관밖·타업무 — 큐폼 미개입 ───────────────────────
OUT_Q = ["예금보호한도가 얼마인가요?", "채무조정 신청하려면 어떻게 해요?",
         "은닉재산 신고하면 포상금 얼마나 받나요?", "예금보험금은 어떻게 신청하나요?",
         "가지급금이 뭔가요?", "오늘 날씨 어때?"]
...
    if ev[0]["kind"] != "answer" or sent_q != qq or any(sent_qform.values()):
```

**세 가지가 다르다.**

1. **"소관 밖"이 아니다.** 테스트 이름은 "소관밖·**타업무**"이고, 주석은 "슬롯이 전부 None 이면 attachments 후단 필터가 통과 모드로 동작 — **타 업무 서식 유지**"다. 이 리스트에는 소관 밖(오늘 날씨)과 **소관 안 타업무 5건**이 섞여 있다. 코드가 단언하는 것은 소관 여부가 아니라 **큐폼 개입 여부**다.
2. **단언이 3중 조건이다.** `되묻기 미발동 AND 검색 쿼리 무변형 AND 슬롯 전부 None`. 스코프를 켜면 **①이 아니라 ③에서 먼저 깨진다**(슬롯이 채워지므로). ver4는 "되묻기가 안 나와야 한다"만 언급해 실패 지점을 잘못 지목했다.
3. **한 케이스가 아니다.**

### 스코프 상수에 묶인 곳 — 최소 3개 AC

| AC | 묶인 방식 | 스코프 ON 시 |
|---|---|---|
| **AC4** | `NO_ASK = ["예금보험공사가 뭐하는 곳인가요", "**가지급금이 뭔가요?**", "안녕하세요"]` — 예금보험금 도메인 용어가 "되묻기 미발동" 기대군에 있음 | ver4 §3-5가 `보험금신청` 규칙을, §3-6이 DPIN 되묻기 문구 8행을 추가했다. `가지급금`에서 `sub_task=제도안내`가 잡히면 **동반 실패 위험** |
| **AC5** | `OUT_Q`에 예금보험금 4문항 | 슬롯 채워짐 → `any(sent_qform.values())`에서 실패 |
| **AC6** | `v1_path()` 안에 `business_function="착오송금 반환 신청"` 하드코딩 + `MS_DOCS`가 착오송금 3개 문서로 고정 | v1 재현 경로 자체가 착오송금 전용. 확장 시 비교 기준이 성립 안 함 |
| (AC7) | `QSET["E"]`에 동일 5문항 | 무크래시 검사라 실패는 안 하나 의미가 사라짐 |

### 이 진단이 §6의 결론을 바꾼다

ver4는 "동결을 깨지 않기 위해 스코프를 되돌렸다"고 판단했고, 그 판단 자체는 규율로서 옳다. 다만 **프레이밍이 하나 빠졌다.**

AC5가 단언하는 것은 "예금보험금은 소관 밖이다"가 아니라 **"큐폼이 개입하지 않는다"**다. 스코프를 넓히면 개입하는 것이 **정상 동작**이므로, 그 케이스를 갱신하는 것은 **방어선을 여는 것이 아니라 회귀 테스트를 확장에 맞춰 갱신하는 것**이다. 이 둘은 성격이 완전히 다르다.

보강 근거: 예금보험금은 코퍼스에 **4페이지·42청크**가 있는 명백한 소관 업무다. 우리 OOS 계획서의 IN_SCOPE 정의("코퍼스에 답이 있는가")를 적용하면 AC5의 그 항목은 **애초에 오라벨**로 판정된다 — 스코프 확장 때문에 틀려진 게 아니다.

§6 말미의 "다음 확장 때도 같은 자리에서 걸린다"는 경고는 맞다. **다만 자리가 여러 개**이므로, 다음 스프린트 1순위(§7)를 "e2e 하니스 **케이스** 개정"이 아니라 **"AC4·AC5·AC6의 스코프 의존 제거"**로 다시 써야 한다.

```bash
git show origin/Qform_ver3:chatbot/verify_qform_e2e.py | grep -n "OUT_Q\|NO_ASK\|business_function=\|MS_DOCS"
```

## 3. 🟠 `party`는 독립 슬롯이 아니다 — 수정 방향이 반대다

### 조합 테이블이 보여주는 것

`qform_combos_msdr.csv`의 `party` 컬럼:

| sub_task | party | 행 |
|---|---|---|
| 제도안내 | (빈칸) | C01 |
| 반환신청·신청철회·매입계약해제·수령계좌변경·대리인변경 | 송금인 | C02~C12 |
| 이의제기·이체수수료환급 | 수취인 | C13, C14 |

**`sub_task`를 알면 `party`가 100% 결정된다.** 예외가 없다. ver3 코드의 유도 로직은 이 사실을 정확히 반영한 것이고, 주석도 그렇게 적혀 있다.

```python
# sub_task → party (정의상 확정). 제도안내는 양쪽이라 None.
if out["sub_task"] in _SUBTASK_PARTY:
    out["party"] = _SUBTASK_PARTY[out["sub_task"]]
```

### 그래서 §3-5 ②의 진단이 틀렸다

ver4는 이를 "오발동 원인 ②: `party`가 `sub_task`에서 자동 유도됨 → 예금보험금에서 쓰지 않기로 한 축이 자동으로 박힘"으로 보고 **유도 로직을 제거**했다.

증상 해소는 맞다. 그러나 진짜 문제는 유도가 아니라 **`party`가 애초에 조합 테이블의 독립 축이 아니라는 것**이다. 올바른 조치는 둘 중 하나다.

- (a) `party`를 **파생 컬럼으로 강등** — 테이블에서 빼고 `sub_task`에서 계산해 표시용으로만 씀
- (b) 스코프별로 유도 매핑을 갈아끼움 — 착오송금은 유도, 예금보험금은 미사용

ver4는 (a)도 (b)도 아닌 **유도 자체를 제거**했다. 그 결과 착오송금에서 "정의상 확정"인 정보를 이제 안 쓰게 된다.

### ver4 문서 내부 모순

§3-5는 "②의 부산물 — `party` 유도로 채워지던 **30건은 원래 아무 일도 안 하고 있었다.** 제거해도 동작이 하나도 안 바뀌었다"고 한다.

이건 유도가 **틀렸다**는 증거가 아니라, **`party`가 좁힘에 기여하지 않는다**는 증거다. 조합 테이블에서 `sub_task`가 이미 같은 정보를 담고 있으니 당연하다.

그런데 §1-4는 여전히 `party`를 **5종 슬롯 중 하나**로 유지하고 소개한다. 문서가 "이 축은 아무 일도 안 한다"를 §3-5에서 실측해 놓고 §1-4에서는 핵심 슬롯으로 제시하는 상태다.

### 조치
- `party`를 슬롯 목록에서 파생 필드로 재분류하거나, 조합 테이블에서 컬럼 제거
- §1-4 슬롯 표를 5종 → 4종 + 파생 1로 정정

## 4. 🟠 `subject` 축에 두 의미가 섞여 있다 — 문구만 고쳤다

### 정규화 위반

| combo | qualification | subject | 문제 |
|---|---|---|---|
| C02 | 본인 | **본인** | 두 컬럼이 같은 값 |
| C03 | 대리인 | **대리인** | 두 컬럼이 같은 값 |
| C04~C08 | 대리인 | 법인 / 비법인단체 / 미성년자 / 군복무자 / 국외거주 | 피대리인 유형 (정상) |
| C09~C11 | 본인;대리인 | **공통** | 세 번째 의미 |

`subject`는 "피대리인 유형"으로 정의된 축인데, 실제 값에는 **① 피대리인 유형 ② `qualification`의 복제 ③ 무관 표식(`공통`)** 세 가지가 섞여 있다.

`qform_prompts.csv`에도 그대로 번져 있다.

```csv
subject,반환신청,누구를 대리해서 신청하시나요?,법인,법인을 대리하는 경우,...
subject,반환신청,누구를 대리해서 신청하시나요?,대리인,대리인,...      ← phrase 형식이 다름
subject,반환신청,누구를 대리해서 신청하시나요?,본인,본인,...          ← 질문과 값이 안 맞음
```

### 이것이 §3-6 버그의 진짜 원인이다

ver4 §3-6:
> 되묻기 문구 CSV에 예금보험금 8행 추가. "본인 자격인데 `…를 대리하는 경우`로 나오는" 버그 해소

버그의 원인은 문구 CSV의 행 부족이 아니라 **`subject` 슬롯 하나가 두 의미를 겸하는 스키마 오염**이다. "누구를 대리해서 신청하시나요?"라는 질문에 `본인`이라는 값이 붙어 있으니 문구가 어긋나는 게 당연하다.

ver4는 **문구를 고치고 스키마는 그대로 뒀다.** 그리고 §3-2에서 DPIN `subject` 값 풀을 새로 정의했다(미성년자·군복무자·사망 예금자·국외거주). **같은 오염이 DPIN으로 전이됐는지 확인 필요**(§10 Q2).

### 조치
- `subject`를 "피대리인 유형"으로 좁히고, `qualification=본인`인 행은 `subject`를 `*`(무관)로
- `공통`을 `*`로 통일 — 값 언어와 무관 표식을 섞지 않는다
- DPIN 9행에 같은 오염이 있는지 점검

## 5. 🟠 쿼리 부스트는 구조적으로 효과가 없을 수 있다

### 근거

`qform_combos_msdr.csv`의 `source_doc_id`를 보면 **대리인 6종(C03~C08)이 전부 같은 문서 하나**를 가리킨다.

```
C03 대리인       → MsdrprPossDcmntGudn
C04 법인         → MsdrprPossDcmntGudn
C05 비법인단체   → MsdrprPossDcmntGudn
C06 미성년자     → MsdrprPossDcmntGudn
C07 군복무자     → MsdrprPossDcmntGudn
C08 국외거주     → MsdrprPossDcmntGudn
C09~C12          → MsdrprPossDcmntGudn
```

슬롯을 아무리 정확히 채워도 **가리키는 문서가 같으면 검색 결과가 바뀔 수 없다.** 쿼리를 강화해도 같은 문서가 나온다.

### 이건 이미 지적된 것이다

우리 08-06 문서 §5-c:
> 현욱의 날카로운 발견: 대리인 7종이 **문서 하나**에 다 있음 → S5는 검색 hit@3을 안 움직이고 **④ 답변 필터에서만 값어치**

즉 현욱 본인이 ver3 이전에 이미 발견한 사실이다. 그런데 ver4 §7-3은 이걸 **"검색 갈림 이슈 해소 → 쿼리 부스트 기본값 재검토"**라는 해결 가능한 버그로 다루고 3순위에 배치했다.

**이슈 해소로 풀릴 문제가 아니다.** 착오송금 도메인에서 슬롯이 문서를 가르지 못하는 것은 데이터 구조의 결과이고, 부스트를 켜면 개선이 아니라 **잡음**이 된다.

### 노선 논쟁에 미치는 영향

현욱 기획서의 핵심 주장은 "(나) 노선 — 큐폼은 답을 결정하지 않고 **검색 입력을 강화**한다"였다. 그 메커니즘이 쿼리 부스트다.

- ver4 §4-2: 쿼리 부스트 **OFF 유지**
- 위 구조상 착오송금에서는 켜도 효과 기대가 어려움
- 현재 큐폼이 실제로 하는 일은 **첨부 좁힘(④ 답변 필터)뿐**

역설적으로 **현재 구현은 우리가 08-06에 재프레이밍했던 층위(④ B-1 콘텐츠)에 정확히 있고, 현욱이 주장한 (나) 노선의 층위는 비어 있다.**

이건 실패가 아니다. 다만 **"큐폼은 검색을 강화한다"는 문장을 발표에서 쓰면 안 된다.** ver4 §5가 "성능 향상은 주장하지 않는다"고 이미 캐비앗을 걸어 둔 것과 같은 이유인데, 노선 서술에는 그 캐비앗이 안 걸려 있다.

### 조치
- 예금보험금 도메인은 문서가 갈리는지 먼저 확인 — **갈리면 부스트가 여기서 값어치를 낸다**. 착오송금이 아니라 DPIN에서 오라클 실험을 하는 게 맞다
- §7-3의 우선순위와 문제 정의를 "이슈 해소"에서 "**도메인별 부스트 유효성 판정**"으로 재작성

## 6. 🟠 소스 부재를 "구분 없음"으로 처리했다

C13(이의제기)·C14(이체수수료환급)의 `qualification`이 **빈칸**이다. 빈칸은 이 테이블에서 "무관"으로 해석되므로, **본인이든 대리인이든 같은 서류를 제시**하게 된다.

그런데 원문(`MsdrAddrsePossDcmntGudn`)에 수취인의 대리인 케이스가 없는 것은 **"구분이 없어서"가 아니라 "소스에 없어서"**다. 두 상태는 다르다.

우리 `QFORM_DECISIONS_HOLES.md` **H13**이 정확히 같은 유형(법인 예금보험금 서류 소스 부재)을 다루면서 **low-confidence 표시 + 문의 안내**로 처리하기로 했다. 조합 테이블에는 그 장치가 없다.

ver4 §8 "원문에 없는 결론을 만들지 않는다"와 어긋난다 — 빈칸이 곧 "모든 자격에 동일"이라는 **결론**을 만들고 있다.

### 조치
- 조합 테이블에 `confidence` 또는 `source_status` 컬럼 추가 (`확인됨` / `소스부재-추정`)
- 우리 H13·H15와 축을 맞춤

## 8. 🟡 "파라미터 7종"이 검증 불가

ver4 §3-7:

### 조치
- 7종 목록과 각각의 기본값·허용범위를 문서에 명시 (`SPEC` 표를 그대로 붙이면 됨)

## 9. 🟡 M1 용어 사전 — 성과 주장과 자기 판정이 상충

문서 세 곳의 서술이 서로 안 맞는다.

| 위치 | 서술 |
|---|---|
| §3-1 | "오분류 10건 중 **설명만 보여주면 5건 해소** / 되묻기가 필요한 건 0건" |
| §4-2 | 용어 사전 ⚠️ "배선만, **발동 0건**" |
| §7-4 | "조사 결과 실제 오분류가 **업무 경계**에서 발생" → 축 재정의 후보 4순위 |

**발동이 0건인데 5건 해소를 어떻게 측정했나.** 오프라인 수기 판정이라면 그렇게 명시해야 한다. 실행 경로가 없는 상태에서 나온 수치를 "측정 결과"라고 쓰면 §8의 "숫자 없이 머지하지 않는다"·"유리한 방향으로 틀린 측정은 안 한 것보다 나쁘다"와 충돌한다.

그리고 §5 인용 주의 표는 "용어 사전 = **구현 완료**라고 쓰지 마라"만 걸어 뒀고, **"5건 해소"에는 캐비앗이 없다.** 발표에서 인용될 위험이 가장 큰 수치인데 보호가 안 걸려 있다.

### 우리 쪽 접점

§7-4의 "업무 경계"는 우리 `KDIC_소관경계_정리.md`의 R1~R7 판정 규칙과 같은 대상이다. 특히 §3-3이 다중의도 근거로 든 **"새마을금고·우체국은 예금자보호 비대상이지만 착오송금 반환지원에서는 대상"**은 우리 R2와 동일한 발견이다(독립 도출 → 상호검증).

M1을 폐기할 게 아니라 **축을 용어 쌍에서 업무 경계로 갈아끼우면** 소관정리 문서가 그대로 재료가 된다.

## 10. 🟡 오발동 수치가 문서 안에서 세 번 다르다

| 위치 | 서술 |

| §3-5 | "결과. 오발동 **6/6 → 2/12**" |
| §3-6 | "`찾` 토큰을 어절 단위로 조였다 → 오발동 **0건**" |

## 11. 🟡 §3-3 다중의도 절이 미검증 설계인데 구현처럼 읽힌다

§3-3은 다중 의도 처리를 대표 예시로 상세히 서술한다.

> "착오송금 신청했는데 그 은행이 파산하면 내 돈은?"
> → `[착오송금 반환 신청] [예금자보호 한도]` 분리 제시

그런데 §5 말미:
> **현행 문턱에서 미발동한다.** 문턱을 낮추면 잡히지만 오발동이 같이 늘어서 낮추지 않았다.

즉 **§3-3의 예시가 실제로는 작동하지 않는다.** 그리고 §4-2 층별 완성도 표에 **다중의도 항목이 아예 없다** — ✅도 ⚠️도 ⛔도 없다.

절 전체가 "이번에 만든 것" 아래에 있으므로 읽는 사람은 구현된 기능으로 받아들인다. §5의 캐비앗은 20줄 뒤 다른 절에 있다.

### 조치
- §4-2 층별 완성도 표에 "다중의도 분리 — ⚠️ 설계 완료, 현행 문턱 미발동" 행 추가
- §3-3 서두에 미발동 사실 명기

## 12. 🟡 자기 설계 원칙을 위반한 구역이 있다

§3-3 메모리 패널의 설계 원칙:
> **화면에 값은 보이는데 실제로는 안 먹는 상태가 최악이다.** 그래서 각 항목마다 "고치면 무엇이 바뀌는가"를 명시하고, **바뀌는 게 없으면 회색으로 표시**한다.

그런데 §4-2:
> 큐 처리 액션 ⚠️ **표시·편집만, 클릭 후속 미구현**

패널 3구역 중 "**대기 중인 용건**"이 정확히 그 상태다 — 화면에 뜨고 편집도 되는데 클릭해도 아무 일이 없다. 회색 표시 규칙이 이 구역에 적용됐는지 문서에 없다.

§8 배운 것 3("만들어 놓고 안 닿는 경로가 제일 위험하다")과도 같은 지적이다. **자기가 세운 두 원칙에 자기 산출물이 걸린다.**

### 조치
- 큐 구역을 회색 처리했는지 확인. 안 했으면 데모 전에 처리하거나 구역을 숨김

## 13. 🟡 발동률 2.0%의 절대 수준을 캐비앗하지 않았다

§5는 "2.0% → 4.2%"의 **분모 이동 함정**은 정확히 짚었다. 그러나 **2.0%(9/84) 자체가 낮다는 점**은 어디에도 언급이 없다.

착오송금 질의 84건 중 **75건(89%)에서 큐폼은 아무 일도 하지 않는다.**

발표에서 "큐폼 도입"의 근거로 발동률을 쓰면 이 숫자가 역효과를 낸다. 대안은 **발동했을 때의 좁힘 폭**인데, 그건 §5 첫 행이 "22건 → 1~4건은 파일 엔트리 기준, 중복 제거하면 11건 → 1~2건대"라고 이미 반쪽을 깎아 놓았다.

즉 **발표에 쓸 수 있는 강한 수치가 현재 없다.** §7-5(평가셋 개정 후 재측정)가 대기 중이므로, 그 전까지는 큐폼을 "성능 개선"이 아니라 **"UX 개선 + 무해 증명 완료"**로만 포지셔닝하는 게 안전하다.
