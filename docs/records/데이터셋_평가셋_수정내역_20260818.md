**`882`를 독립 셋으로 쓰면 안 되는 이유** — 실측 구성이 이렇다.

```
882 = VAL505 전체 505건 (100%)  +  TEST450 중 377건 (83.8%)
882 밖의 신규 문항: 0건
```

VAL을 100% 삼키고 TEST의 대부분을 삼킨다. 882 수치는 VAL·TEST 어느 쪽의 일반화도 증명하지 못한다. **`and` 라벨 교차검증** 용도로만 썼다(882의 v9 라벨이 TEST의 `and` 41건을 독립적으로 어떻게 라벨했는지 확인 — 41/41 일치).

**VAL ∩ TEST = 0** — `id` 기준 0건, `question` 기준 0건. 두 셋은 실제로 분리돼 있다.

## 3. 파생 계보 — 원본 무수정 원칙

**원본 파일은 어떤 경우에도 in-place 수정하지 않는다.** 모든 변경은 접미사가 붙은 새 파일로 나가고, 원본은 그대로 남아 sha256으로 대조 가능하다.

```
gt_natural505_val.jsonl (505)
  └─ [make_val_split.py] answerable==True 355건
     └─ gt_natural355.jsonl (355)
        └─ [fill_anchors.py] 앵커 +14 / 14문항
           └─ gt_natural355_anchored.jsonl (355)

gt_natural450.jsonl (450)
  └─ [filter_anchored.py --mode has-anchor] 앵커 결측 20건 제외
     └─ gt_natural430.jsonl (430)
        └─ [fill_anchors.py] 앵커 +131 / 75문항
           └─ gt_natural430_anchored.jsonl (430)
```

| 파일 | 행수 | sha256 (앞 8) | 파생 | answerable |
|---|---:|---|---|---|
| `gt_natural505_val.jsonl` | 505 | `750c56ae` | 원본 | T 355 / F 150 |
| `gt_natural355.jsonl` | 355 | `c4e4a309` | 505에서 필터 | T 355 |
| `gt_natural355_anchored.jsonl` | 355 | `044a54e0` | 355 + 앵커 | T 355 |
| `gt_natural450.jsonl` | 450 | `d92fbc51` | 원본 | T 448 / F 2 |
| `gt_natural430.jsonl` | 430 | `4ad4cad0` | 450에서 필터 | T 430 |
| `gt_natural430_anchored.jsonl` | 430 | `c86b7d13` | 430 + 앵커 | T 430 |
| `gt_natural882.jsonl` | 882 | `aeab60c6` | 원본 (합집합) | T 732 / F 150 |
| `gt_natural400.jsonl` | 400 | `c8db58d4` | 원본 (오염) | T 262 / F 138 |

`_anchored` 파일은 `id` 집합이 부모와 **완전히 동일**하다(문항 추가·삭제 없음, 앵커 필드만 늘어남). 확인 완료.

### 필터가 무엇을 뺐는가

- **505 → 355**: `answerable == False` 150건. unanswerable은 gold 청크가 없어 hit@k 분모에 들어갈 수 없다. 평가기가 알아서 빼주긴 하지만, **"이 파일의 행수 = 분모"가 성립해야** 인용할 때 혼동이 없다.
- **450 → 430**: 앵커(`gt_anchors`/`gt_anchor_span`)가 하나도 없는 20건. `relation` 분포가 `single 376/and 69/or 5` → `single 370/and 55/or 5`으로 바뀐다 — **빠진 20건 중 14건이 `and`다.** `and` 문항에 앵커 결측이 몰려 있었다는 신호이고, §5의 수기 보강으로 이어졌다.

> ⚠️ **430과 450의 절대 수치를 나란히 비교하지 말 것.** 구성이 다르다(`and` 비중 12.2% vs 15.3%). 각각의 시계열로만 본다.

## 4. 스키마 변경

### 4.1 `gt_anchors` 승격 (복수 앵커)

**문제** — 기존 스키마는 `gt_anchor_span` 단수 문자열 하나였다. `and` 문항은 gold 청크가 2~4개인데 근거 스팬을 하나만 적을 수 있어 구조적으로 표현이 안 됐다.

**변경** — `gt_anchors: list[str]`를 1급 필드로 승격. 평가기는 `gt_anchors` → 없으면 `gt_anchor_span` 순으로 읽는다(`_get_gt_anchors`). **기존 파일 무수정 호환** — 단수 필드만 있는 셋도 그대로 채점된다.

**적용** — `promote_gt_anchors.py`가 단수 → 복수 승격을 수행. 400/450/882 세 셋에서 정상 동작 확인.

### 4.2 `chunk_relation` alias 확장

**문제** — VAL 505의 relation 라벨 어휘가 TEST와 달랐다. 실측 분포:

| 셋 | 라벨 어휘 |
|---|---|
| TEST 450 | `single` 376 · `and` 69 · `or` 5 |
| VAL 505 | (미기재) 456 · `near_dup` 35 · `duplicate` 12 · `contained` 2 |

`near_dup`/`duplicate`/`contained`는 평가기가 모르는 라벨이라 `ValueError`로 죽었다.

**변경** — 판정 규약에 alias를 정의했다.

```python
RELATION_ANY = {"single", "or", "near_dup", "duplicate", "contained"}  # gold 중 하나면 적중
RELATION_ALL = {"and"}                                                 # gold 전부 필요
# 그 밖의 라벨 → ValueError (조용히 ANY로 떨어지지 않게)
```

**설계 근거** — `near_dup`/`duplicate`/`contained`는 "같은 내용이 여러 청크에 있다"는 뜻이므로 하나만 찾아도 답할 수 있다 = ANY. 미기재는 `single`로 취급. **알 수 없는 라벨은 예외를 던진다** — 새 라벨이 조용히 관대하게 채점되면 지표가 부풀기 때문이다.

**보고용은 원본 유지** — `_get_relation_label()`(원본 라벨, 리포트용)과 `_get_relation()`(정규화, 채점용)을 분리했다. relation별 분해 표에는 `near_dup`이 `near_dup`으로 찍힌다.

### 4.3 판정 규약 (참고)

```
hit@k =
  anchors ANY:  ∃ chunk ∈ topk : normalize(anchor) ⊂ normalize(chunk.text)
  anchors ALL:  ∀ anchor : ∃ chunk ∈ topk : ...
  + 앵커가 덮지 않는 gold는 chunk_id 폴백으로 요구 (하이브리드)
  + 코퍼스에 없는 gold(stale)는 조건에서 제외, n_stale_gold로 별도 계상
```

`normalize` = NFKC + 공백 제거. `--score {chunk_id|anchor|both}`, 기본 `both`.

## 5. 라벨 보강 — 수기 앵커 38개

**이건 자동화 파이프라인이 아니다.** 사람이 청크 원문을 읽고 근거 스팬을 고른 작업이고, `docs/앵커텍스트_정답라벨링_파이프라인.md`의 자동 경로에 포함시키지 않는다.

**대상 선정** — `audit_anchors.py`가 미앵커 gold 청크를 집계하고, 코퍼스 전체에서 **그 청크에만 존재하는 줄** 중 가장 짧은 것을 후보로 제시한다(결정론적, 창작 없음). 사람이 그중 실제 근거를 골랐다.

**산출물** — `crawler/data/anchor_fill_430.json` · 38개 스팬 · 키는 옛 gold `chunk_id`.

**2단 검증** — 스팬 하나가 여러 문항에 걸리므로 38개가 430셋에서 앵커 131개(75문항)로 펼쳐진다.

| 검증 | 결과 |
|---|---|
| 옛 gold 청크 안에 verbatim 존재 | **38 / 38** |
| 새 181청크 코퍼스 안에 verbatim 존재 | **38 / 38** |

**효과** — 앵커 커버리지가 이렇게 변했다. `gold쌍 = 앵커커버 + id폴백 + stale`.

| 셋 | 문항 | 앵커 수 | gold쌍 | 앵커커버 | id폴백 | stale | id폴백 문항 |
|---|---:|---:|---:|---:|---:|---:|---:|
| `430` | 430 | 430 | 519 | 361 (69.6%) | 51 | 107 | 48 (11.2%) |
| `430_anchored` | 430 | **561** | 519 | **390 (75.1%)** | **22** | 107 | **22 (5.1%)** |
| `355` | 355 | 355 | 405 | 356 (87.9%) | 14 | 35 | 13 (3.7%) |
| `355_anchored` | 355 | **369** | 405 | **358 (88.4%)** | **12** | 35 | **12 (3.4%)** |

지표 이득은 작다(TEST hit@5 `+.003`). **얻은 것은 라벨 내구성**이다 — id 폴백은 재청킹하면 깨지는 판정이고, 그 비율이 TEST에서 11.2% → 5.1%로 절반 이하가 됐다.

**한계 (문서화 필수)** — 표 청크에서 고른 스팬은 '최소 근거 문장'이 아니라 해당 행을 특정하는 **locator**에 가깝다. 표에는 근거 문장이라 할 단위가 없기 때문이다. `anchor_fill_430.json`의 `_note` 필드에 같은 내용을 남겼다. 근본 해결은 P2 표→markdown 파싱이다. (`HOLES` H30)

## 6. `stale gold` — 재청킹이 남긴 것

표 원자성 수정으로 코퍼스가 215 → 181청크가 되면서 **gold `chunk_id` 107쌍(430셋)·35쌍(355셋)이 코퍼스에서 사라졌다.**

- **GT를 고쳐서 맞추지 않았다.** 새 청킹에 맞춰 gold id를 다시 매기면 검색이 좋아진 게 아니라 채점을 고친 것이 된다.
- **평가기가 처리한다.** 코퍼스에 없는 gold는 판정 조건에서 빼고 `n_stale_gold`로 별도 계상한다. 감추지 않기 위해 세는 것이다.
- **앵커 판정이 이걸 견딘다.** 앵커는 텍스트 포함 관계라 청크 경계가 바뀌어도 살아남는다 — 실측 305/305 잔존. `chunk_id` 판정은 107쌍을 잃었다.

이것이 §4.1 앵커 승격의 실질적 정당화다. **`chunk_id`는 좌표이고 앵커는 근거다.**

## 7. 인용 시 주의

1. **앵커 지표는 `_anchored` 파일로.** `gt_natural430_anchored` / `gt_natural355_anchored`. 원본으로 재면 id 폴백 비율이 높아 리랭킹·재청킹 효과가 라벨 결측에 묻힌다.
2. **VAL·TEST 절대 수치를 나란히 놓고 회귀를 판단하지 말 것.** VAL 355는 `and` 0건, TEST 430은 `and` 55건이다. 구성이 달라 절대값 비교가 무의미하다. 각각의 시계열로만 본다.
3. **882·400은 인용하지 않는다.** 882는 합집합, 400은 라우터 학습셋과 99.8% 중복.
4. **주지표는 `single`.** 판정 구조가 재청킹에 불변인 문항군이라 순수 검색 변화를 본다. 전체 hit@5는 부지표.
5. **지표에서 QFORM 27건을 분리해야 한다** (미해결). 착오송금 `and` 27건은 `qform_combos_msdr.csv` 14조합이 슬롯 채움으로 좁히는 대상이고, 검색 hit@5로 평가할 성질이 아니다. 지금은 섞여 있어 검색을 실제보다 나쁘게 보이게 한다.
