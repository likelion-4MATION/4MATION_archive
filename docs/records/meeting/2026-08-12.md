## 2. 실제 진행 내용

### GT 스키마 재정립 방향 논의 — "5개 개념 분리"
기존 평가셋이 `question → answerable → gt_chunk_id`로 지나치게 단순하게 묶여 있어, 데이터셋 오류와 검색 시스템 오류가 서로 구분되지 않는 문제를 확인.

| 개념 | 질문 |
|---|---|
| **Scope** | KDIC 소관 질문인가? |
| **Corpus Support** | 현재 코퍼스에 직접 근거가 있는가? |
| **Answerable** | 사용자에게 안전하고 유효한 응답이 가능한가? |
| **Answer Mode** | 어떤 방식으로 답변 가능한가? |
| **Retrieval GT** | 검색기가 찾아야 할 명시적 근거 청크가 있는가? |

- 핵심 원칙: **`Corpus Support ≠ Answerable ≠ Retrieval GT`** — 코퍼스에 직접 근거가 없어도(`corpus_support=absent`) 안전한 안내(`guided`)가 가능하면 `answerable=true`로 처리하고, 이 경우 GT 청크를 억지로 만들지 않음
- **Answer Mode 5종** 정의: `direct`(직접 답변, GT 필요) / `multi_evidence`(복수 청크 조합, GT 필요) / `guided`(안전 안내, GT 없을 수 있음) / `judgment`(맞다/아니다 판단, 외부지식 사용 금지) / `unanswerable`(안전한 응답 불가). 되묻기(`clarification`)는 큐폼 영역이라 이 스키마에서 제외
- **Judgment 유형의 제약**: 코퍼스에 판단 근거가 없으면 추측하지 않고 "현재 자료만으로는 확인할 수 없습니다"로 답하되, 이것도 무조건 `answerable=false`가 아니라 유효한 응답으로 인정
- **Retrieval 평가 대상 한정**: 전체 질문 중 `direct`/`multi_evidence`만 GT 청크 평가 대상으로 좁히고, `guided`/`judgment`/`unanswerable`은 평가 대상에서 분리
- **Gold 판정 4단계**: `KEEP`(기존 GT가 실제 근거) / `REPLACE`(다른 청크가 근거) / `MULTI`(여러 청크 필요 또는 복수 정당 근거) / `DROP`(평가 대상 부적절)
- **오류 3계층 분류 확정**: DATASET(Scope/Answerability/GT/Multi-Gold/품질 오류) / CORPUS(코퍼스 갭) / RETRIEVAL(랭킹 실패/검색 미스/청킹 이슈) — 이 구분으로 recall이 낮다고 무조건 임베딩·리랭커 문제로 결론짓지 않도록 함
- 핵심 원칙 재확인: **검색기를 보고 GT를 수정하지 않는다.** GT가 먼저 확정돼야 retrieval 평가가 독립성을 가짐 → 이후 전수 검수·dataset freeze로 이어질 예정

### 검색 개선 로드맵 논의 — "파라미터 튜닝보다 표현 개선 우선"
핵심 진단: 평가 기준은 이미 chunk-level GT로 전환됐고, 병목은 **업무 자체를 못 찾는 게 아니라 동일 업무 내 유사 청크 간 정답 변별 실패**임을 재확인. 이 진단에 따라 RRF·BF·embedding 파라미터를 반복 튜닝하는 대신, 데이터 표현(청크가 스스로를 어떻게 나타내는지) 자체를 먼저 개선하는 방법.

| 순서 | 확정 방향 |
|---|---|
| 1. Metadata | 필드를 무작정 늘리지 않고, `business_function + topic/section + content`로 청크의 semantic identity를 최소 보강해서 정확히 표현 |
| 2. Anchor-Text | LLM으로 질의마다 앵커를 생성하지 않음(과설계로 판단) — 기존 metadata와 문서 구조에서 **결정론적(deterministic)으로** 앵커를 생성. 예: `[착오송금 반환지원] [신청 구비서류] + 본문` |
| 3. Retriever | 기존 Dense + BM25 + RRF 구조 우선 유지 — 데이터 표현 개선과 검색 알고리즘 변경을 분리 |
| 4. MMR/cap | cap(동일 문서 독점 방지)은 즉시 제거하지 않고, 필요 시 cap/MMR/cap+MMR을 비교 실험. MMR은 근본 해결책이 아니라 랭킹 보조 수단으로 위치시킴 |
| 5. Freshness | 구버전 정보(예: 보호한도 5천만원 잔존) 문제는 의미(semantic) 문제와 분리해, 향후 `effective_date/is_current/superseded_by` 필드로 별도 처리 |
| 6. 평가 | `answerable → gt_chunk → gt_anchor_span` 관계를 고정하고, 이미 확인한 GT 문제를 반복 진단하지 않음 |

- **핵심 원칙**: 검색 알고리즘을 계속 튜닝하기보다 검색 대상 청크 자체를 정확한 의미 단위로 표현하는 것을 우선하며, 실험은 방향을 결정하는 수단이 아니라 **확정한 구조의 효과를 검증하는 용도로만** 사용

### 문제 확인 — 형제 청크 변별 실패
- 같은 업무(business_function) 내에서 내용이 미세하게 다른 "형제 청크"들끼리 검색이 거의 구분을 못 하는 문제를 회의에서 재확인 — 이는 위 검색 개선 로드맵의 metadata·anchor-text 방향이 겨냥하는 핵심 문제와 동일함
- **리랭킹 시도했으나 효과 없음 확인**: 1,651건 라벨링 자체의 품질 문제(정확한 GT가 아직 확정되지 않은 상태)로 인해 리랭킹을 적용해도 효과가 제대로 측정되지 않는 것으로 확인됨 

## 3. 논의사항 (결론 미확정 — 다음 논의로 이월)
- **메타데이터를 크롤링 단계에서 청크마다 부착하는 방식**이 제안됐으나, 질문만 보고 메타데이터를 정확히 찾아내는 게 실제로 가능한지에 대한 확신이 부족한 상태로 논의 지속 필요
- **근접 청크 확장 시 부모 문서 전체 반환에 가까워지는 부작용** 우려 제기 — 형제 청크 구분 문제를 해결하려다 오히려 문서 단위 반환으로 회귀할 수 있다는 우려로, 대책 논의 필요
- **큐폼 트리거 범위**: "착오송금 신청은 어떤 경우에 가능한가요?" 같이 실제로는 여러 갈래로 나뉘지 않는 질문에도 큐폼이 트리거되는 문제 사례 제기. 큐폼이 버튼 선택 방식이라 "LLM다운 유연함이 부족하다"는 지적도 함께 나옴
- **큐폼 형식 확장안**: 트리거 조건을 완화해 더 다양한 질문에도 큐폼을 적용하되, 슬롯이 일부만 채워져도 바로 임베딩 검색으로 넘기는 방식이 제안됐으나 결론 없음
- **메타데이터 기반 큐폼 매칭 아이디어**: LLM이 큐폼에서 메타데이터 형식에 맞게 슬롯을 채우면 임베딩 검색 없이도 빠르게 매칭될 수 있다는 아이디어가 나왔으나, "메타데이터 생성 과정 자체의 신뢰도가 낮아 보인다"는 우려 제기 
- **BF 키워드 분류를 계층적으로 쌓는 방안**: 키워드를 단순히 더 추가하는 대신 계층 구조로 쌓아 형제 문서 분류 개선을 기대한다는 아이디어가 나왔으나 구체적 설계는 없는 상태

## 4. 이슈 정리

## 이슈 1. 형제 청크(같은 업무 내 유사 청크) 변별 실패

**문제**
동일 업무 안에서 내용이 미세하게 다른 청크들을 검색기가 거의 구분하지 못하는 문제가 핵심 병목으로 재확인됨. 리랭킹을 시도했으나 GT 라벨링 품질 문제로 효과 자체가 측정되지 않음.

**건의/조치**
검색 알고리즘 튜닝보다 청크의 의미 표현(metadata·anchor-text)을 먼저 정교화하는 방향으로 로드맵을 논의. GT 고정을 최우선 선행 작업으로 재확인.

## 이슈 2. 1,651건 GT 라벨링 품질 미확정으로 실험 신뢰도 저하

**문제**
GT가 아직 최종 확정(freeze)되지 않은 상태에서 리랭킹 등 실험을 진행해, 실험 결과가 검색 성능 때문인지 라벨 품질 때문인지 구분되지 않음.

**건의/조치**
GT 재정립 방향(Scope/Corpus Support/Answerable/Answer Mode/Retrieval GT 분리)에 따라 전수 검수 후 dataset freeze를 먼저 완료하고, 그 이후에 검색 실험 결과를 신뢰할 수 있는 것으로 취급하기로 확정.

## 이슈 3. 큐폼 트리거 범위의 과민 반응

**문제**
실제로는 슬롯 분기가 필요 없는 질문에도 큐폼이 발동하는 사례가 확인됨. 현재 되묻기가 버튼(선택지) 방식이라 자연어 질의의 뉘앙스를 못 살린다는 지적도 있음.

**건의/조치**
결론 미도출 — 트리거 조건 완화안과 메타데이터 기반 매칭안 두 방향이 제안됐으나 신뢰도 문제로 확정되지 않아 다음 논의로 이월.
