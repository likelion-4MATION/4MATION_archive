### 트랙 A — 검색 정확도 개선 (`방법론_정확도개선_결론_20260818.md`, `DECISIONS.md`)

**표 청킹 문제 발견**
- `split_generic()`이 표(`|` 라인) 블록을 만나면 크기와 무관하게 무조건 독립 청크로 끊어버리는 문제를 확인 — 텍스트 블록처럼 `CHUNK_SIZE`(800자)까지 인접 블록과 합치는 로직이 없었음
- 원인: 표 셀 안 `<br>` 다항목이 파이프 없는 줄로 직렬화되며 "연속 파이프 줄 = 표" 휴리스틱이 끊김. 보호대상 금융상품 표(2,330자)가 10청크, 착오송금 구비서류가 20청크(중앙 120자)로 흩어져 있었음
- **수정**: `TABLE_GAP_MAX=12` 도입 — 파이프 줄 사이 비-파이프 줄을 셀 연속으로 흡수. 코퍼스 실측상 그런 구간 37개의 최장이 11줄이고 전부 실제 셀 내용이라(산문 오흡수 0건) 신규 문서의 "표→산문→표"만 막음
- **재청킹 결과**: 기존 청크 215건 → **181건**으로 수집. `single`(주지표) hit@5가 TEST `.8946→.9081`, VAL `.8268→.8333`로 두 셋 모두 상승(전이 확인). LLM 입력은 +19%(1,571→1,871토큰)로 HCX-003 한도의 52%, 초과율 0%

**파라미터 재튜닝**
- 청킹이 바뀌면 최적 파라미터도 옮겨간다는 원칙에 따라 `tune_params_v2.py`(임의 코퍼스 대응)로 8,064 config 재스윕
- **채택**: `RRF_K` 1→4, `BF_BOOST` 0.12→0.06, `FACET_BOOST` 0.15→0.05 (`RRF_ALPHA` 0.65·`BF_DOC_CAP` 5는 불변)
- 이유: 표가 합쳐져 청크가 자기완결적이 되면서 메타 기반 부스트(business_function·sub_category)의 상대 기여가 줄었음 — "메타는 본문이 빈약할 때의 대용품, 본문이 채워지면 물러나야 한다"는 원칙 확인

**평가기 버그 발견 및 수정**
- 표 원자성 수정 직후 정본 수치가 예상(.8977)보다 크게 낮은 `.828`로 나옴 → `_split_gold_by_anchor`가 재청킹으로 사라진 gold id(430셋 중 107쌍)를 여전히 그 id 안에서만 찾도록 되어 있어, 앵커를 채워도 영원히 "미앵커"로 남는 구조적 버그 확인
- 수정: 코퍼스에 없는 gold는 조건에서 빼고 `n_stale_gold`로 별도 계상 → TEST hit@5 `.828 → .888`

**앵커 라벨 수기 보강**
- `and` 관계 문항에서 앵커 커버리지가 40%(single은 100%)에 그치는 문제 확인 → 옛 gold 청크 원문에서 근거 스팬 **38개**를 수기로 선정, 2단 검증(옛 gold 청크 verbatim 38/38, 새 코퍼스 verbatim 38/38)
- 효과: TEST hit@5 `.888 → .891`(+.003), id 의존도 11.2% → **5.1%**. 지표 이득은 작지만 재청킹에 견디는 라벨 비율이 69.6%→75.1%로 상승 — "지표보다 라벨 내구성이 실질"로 정리

**최종 수치 (앵커 채점, TEST 430 / VAL 355)**

|---|---:|---:|
| hit@1 | .470 | .513 |
| hit@3 | .772 | .797 |
| **hit@5** | **.891** | **.896** |
| hit@10 | .953 | .961 |

시작점(215청크·구파라미터·chunk_id 판정) 대비 TEST hit@5 `.765 → .891`. **일곱 처방 중 다섯은 검색기를 건드리지 않았다** — 측정 오류를 고치자 이미 있던 성능이 드러난 것으로 결론

**리랭커 재검토(v1→v2)**
- v1(215청크·구파라미터): 주지표 hit@5 TEST flat(−.002), VAL만 개선(+.082) → 두 셋 전이 실패로 미채택
- v2(181청크·앵커보강 GT·실경로 기준): TEST hit@5 최대 +.0047(2문항), VAL +.0563. 절단 가설 기각(ml=512로 충분), `and`는 완전 무반응
- **결론 유지: 주지표 기준 미채택**. 단 top-1 노출 UI라면 채택 가치 있음(TEST hit@1 +.061, VAL +.1127) — 판단은 UI 방향 결정에 연동

**라우터 355셋 오분류 분해**
- VAL 355에서 라우터 질의분류 일치율이 71.0%(450셋 100%와 큰 격차)로 나타나 원인 분해
- 78건 중 **76%(59건)가 실제 라우터 오분류**로 확인 — 실제 오분류율은 355셋 기준 16.6%
- 혼동은 인접 업무 쌍에 집중(예금자보호제도↔예금보험금 안내 12건, 예금보험금 안내↔미수령금 9건). 어휘 신호 없는 질문(구어체·맥락 의존)에서 특히 취약
- MSP는 이번에도 무력함을 재확인(오분류 78건 중 43건이 MSP .99 이상) — "틀릴 때 가장 확신한다"는 기존 진단(H28) 재현

### 트랙 C — OOS 처리 로직 설계 (`OOS_처리로직_계획서.md`)

**2층 구조 설계**
- L0(게이트, 기존 로직 유지) + L1(OOS 세분류 신규) 구조로 확장 — L0이 놓쳐도 생성단 프롬프트 규칙이 2차 방어
- IN_SCOPE 판정 기준을 "예보 소관인가"(기관 지식)에서 **"코퍼스에 답이 있을 것으로 기대되는가"**(코퍼스 존재 여부)로 전면 재정의 — 기존 실패 사례(퇴직연금 오차단)가 분류 프롬프트의 파라메트릭 지식 오염 때문이었음을 확인

**핵심 발견 — SCOPE_OOS 대부분은 "답변 가능한 OOS"**
- 제시된 SCOPE_OOS 7개 하위 항목 중 6개가 코퍼스에 안내 근거가 실존 — 즉 "모른다"가 아니라 "예보 소관이 아니며 ○○○이 담당한다"를 원문 근거로 답할 수 있음
- 정책 결론: SCOPE_OOS는 거절(reject)이 아니라 **안내(link)**로 처리 — 소관 진술 + 안내처 제시 + 인접 업무 안내(선택)의 3부 구조
- 안내처 URL·전화번호는 LLM이 생성하지 않고 사전(referral registry)에서만 조립 — 휴면예금 안내 기관명이 프롬프트와 코퍼스 원문 간 불일치했던 사례를 발견해 즉시 시정 필요 항목으로 등록

**6대 택소노미 정의**: DOMAIN_OOS(reject) / SCOPE_OOS(link) / HUMAN_HANDOFF(handoff) / BUG_REPORT(handoff+로깅) / CASUAL(casual) / INVALID·ADVERSARIAL(reject+로깅), 다중 라벨 충돌 시 우선순위 규정

**리스크 식별**: 분류 실패 시 안전 기본값이 "정상"이라 프롬프트 인젝션이 분류기 출력을 깨뜨리면 게이트 우회 가능 — L-1 룰 프리필터로 인젝션 시그니처를 0콜 선차단하는 방향 권고

- **용어 판별 사전(M1)**: 지급금 5종·채무조정 5종 혼동(실측 오분류 10건) 대응 — `qform_terms_v0.csv` 신설. 설명만 보여줘도 5건 해소되고 되묻기가 필요한 건 0건이라, 되묻기 기능은 구현하지 않기로 결정

- **설정 배선(M8)**: `app.py`에 설정 주입 코드가 아예 없어 파라미터 7종이 전부 모듈 기본값에 묶여 있던 것을 발견·수정 — 관리자 콘솔의 전제조건이었음
- **스코프 기본값은 여전히 착오송금 단일 유지** — 측정상 확장 준비는 끝났으나(신규 발동 10건 전부 타당, 오발동 0건), 검증 하니스(`verify_qform_e2e.py`)가 "예금보험금 질문은 소관 밖"을 하드코딩해둔 상태라 동결 원칙에 따라 하니스 개정을 먼저 처리하기로 결정 — 다음 스프린트 1순위로 이월

## 4. 이슈 정리

## 이슈 1. 표 청킹이 원자성을 깨고 있었음

**문제**
`split_generic()`이 표 블록을 크기와 무관하게 무조건 독립 청크로 끊어, 표 셀 내 `<br>` 다항목이 만드는 비-파이프 줄에서 표가 여러 조각으로 쪼개짐. 착오송금 구비서류 문서가 20청크로 흩어져 있었음.

**건의/조치**
`TABLE_GAP_MAX=12`로 비-파이프 줄을 셀 연속으로 흡수하도록 수정. 재청킹(215→181청크) 후 파라미터 재튜닝까지 완료해 TEST hit@5가 `.765→.891`로 상승.

## 이슈 2. 평가셋이 라우터 학습셋과 최대 100% 중복

**문제**
라우터 정확도 81.2%로 보고했던 평가셋이 실제로는 라우터 학습 데이터와 100% 겹쳐 있었음(`gt_schema_v6.jsonl` vs `router_trainset_v2`).

**건의/조치**
`gt_natural450`(교집합 0 확인) 계열만 라우터 개입 평가에 인용하도록 역할 규약을 확정. VAL(505/355)·TEST(450/430)로 분리 확정, 882·400 인용 금지.

## 이슈 3. 평가기가 사라진 gold 좌표를 필수 조건으로 요구

**문제**
재청킹으로 사라진 gold chunk_id에 대해 `_split_gold_by_anchor`가 그 id 안에서만 앵커를 찾도록 되어 있어, 앵커를 채워도 영원히 "미앵커"로 남는 판정 버그가 있었음.

**건의/조치**
코퍼스에 없는 gold는 판정 조건에서 제외하고 `n_stale_gold`로 별도 계상하도록 수정. TEST hit@5가 `.828→.888`로 즉시 회복.

## 이슈 4. 안내 기관명이 프롬프트와 코퍼스 원문 간 불일치

**문제**
현행 분류 프롬프트는 "휴면예금은 서민금융진흥원"이라 서술하지만, 코퍼스 원문은 "전국은행연합회 휴면계좌통합조회시스템(sleepmoney.or.kr)"이라고 명시 — 분류기가 코퍼스와 다른 기관을 파라메트릭 지식으로 말하고 있었음.

**건의/조치**
안내처 정보는 프롬프트가 아니라 코퍼스 원문에서만 채우는 안내 사전(referral registry)으로 일원화하기로 결정. OOS 처리 로직 계획서 §9 다음 단계 1순위로 지정.
