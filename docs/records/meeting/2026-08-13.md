### 검색 논의
1. **미수령금 FAQ 라우팅**: 미수령금 관련 FAQ 게시판 청크 중 실제로 미수령금 도메인에 해당하는 건 3개뿐이고 나머지는 다른 도메인 — FAQ만 별도로 라우터에 넣어 분류하는 방식 논의
2. **미수령금 신청 구비서류 태깅 문제**: 내용이 예금보험금과 사실상 같아서 예금보험금으로 분류(태깅)되어 넘어가는 문제 — 단일 BF 필드로는 이런 준용관계를 표현할 수 없어, 필드를 나눠 관리하는 방향 논의
3. **BF 키워드 세분화**: 지금은 키워드가 크게(포괄적으로) 잡혀 있어 세분화가 더 필요하다는 의견이 나왔으나, 세분화하면 오히려 키워드 하나만 보고 확신해 다른 질문에 대해 오답을 내는 위험이 커질 수 있다는 트레이드오프도 함께 확인

### 착오송금 반환신청 미적중 Root-cause 분석 (`gt_natural450_v7` × hybrid_bf 기준)
착오송금 반환 신청 84건 중 미적중 56건을 정밀 분석함.

- **완전 미회수 vs 순위 밀림**: 미적중 56건 중 94.6%는 완전히 놓친 게 아니라 순위 밀림 문제로 확인
  - top4~10위: 48건(85.7%)
  - top11~30위: 5건(8.9%)
  - top50에도 없음(완전 미회수): 3건(5.4%, 이 중 2건은 and 관계 다중청크, 1건은 별도 조사 필요)
- **순위 밀림 56건의 두 갈래 원인**
  - **`and`(다중청크 전부 필요) 관계: 31건(55%)** — 정답 청크(평균 3개)가 전부 `MsdrprPossDcmntGudn`(구비서류 안내) 한 문서 안에 `#01~#16`으로 조각조각 쪼개져 있어, top-3 안에 3~4개를 동시에 넣는 게 구조적으로 거의 불가능. **검색기 튜닝 문제가 아니라 청킹/문서구조 문제**로 판정
  - **`single`/`or`인데 밀린 것: 25건(45%)** — 다른 업무 혼입이 아니라 전부 같은 "착오송금 반환 신청" 업무 내에서, 신청대상(`kmrsItrdAplyTrgt`)·반환지원절차(`MtrsGvbkSprtProc`) 같은 **포괄적/일반적 문서가 구체적 질문보다 계속 상위를 차지**하는 문제. FACET_RULES 키워드 사전이 구어체 변형("방법으로 하면" 등)을 못 잡아내고, "제도란"(개요) 카테고리 자체가 FACET_RULES에 아예 없는 것이 원인으로 확인
- **결론**: 이 업무의 미적중은 리랭커가 필요한 문제가 아니라 **① 멀티청크 문서 쪼개짐(로드맵 4-2 대상)**과 **② FACET_RULES 키워드 사전 커버리지 부족(로드맵 3-3 대상)** 두 가지가 원인. 리랭커는 ①은 후보 자체가 부족해 못 고치고, ②는 도움이 될 수도 있는 지점으로 정리

### 검색개선 아이디어 문서 감사(`검색개선_문제와아이디어.md`)
- **결론**: 방향은 대체로 타당하나, 지금은 구조를 바꿀 단계가 아니라 **"미스 원인 확정 → 저비용 실험 → 필요 시 구조 변경"** 순서가 맞다고 판단
- **가장 타당한 지적으로 인정한 부분**: BF를 업무 내 변별축으로 쓰는 데 한계가 있다는 점(BF는 라우팅용, topic이 변별축이어야 함), GT가 불안정한 상태에서 개선을 진행하면 위험하다는 점, `answerable=false`를 F1~F4로 세분화해야 한다는 점, 준용관계 표현을 위한 `bf_relations` 같은 별도 관계층 필요성, BM25/dense 텍스트 채널 분리 필요성
- **우선순위 확정**: 미스 구성비 확정 → Topic Oracle/BF 계수 실험 → 평가셋 정리 → 구조 개선
- **채택 여부 정리**
  | 제안 | 판정 |
  |---|---|
  | I2 Topic Oracle | 즉시 실행 |
  | I3 구조화 계수 튜닝 | 즉시 실행 |
  | I4 셋 A/B 병존 · I5 평가셋 층 분리 · I6 F1~F4 | 채택 |
  | I7 BF×Topic matrix | 진단용 채택 |
  | I9 `bf_map` | 후순위 |
  | I10 FAQ 자동태깅 | 조건부 |
  | I11 `bf_relations` | 장기적으로 채택 |
  | I12 관계 5건 | 후보로 유지, 확정 금지 |
  | I13 관계 자동발견 | 후순위 |
  | I8 응답 사다리 | 검색 개선과 분리 |
- **지금 하면 안 되는 것으로 명시**: parser/chunker 수정, topic 재청킹, contextual prefix 도입, `bf_map` 전환, 관계 자동화, 검색 구조 대개편

### 검색 성능 리포트 산출(`eval_report_450.md`)
- **평가 대상**: `gt_natural450_v7.jsonl` 450건 중 answerable=true 448건(제외 2건). relation 분포: single 374건(83.5%)/and 69건(15.4%)/or 5건(1.1%)
- **전체 성능**: Hit@1=0.350, Hit@3=0.618, Hit@5=0.754, Hit@10=0.848, MRR=0.513 / MacroRecall@3=0.665, @5=0.801, @10=0.890
- **relation별**: `and` 관계가 압도적으로 취약(Hit@1=0.000, Hit@3=0.072, MacroRecall@10=0.676) — `single`(0.928)·`or`(1.000) 대비 크게 낮아 위 root-cause 분석 결과와 일치
- **업무별 미적중률**: 착오송금 반환 신청이 가장 취약(56/84=66.7%) → 예금자보호제도(36/84=42.9%) → 고객 미수령금 신청(29/75=38.7%) → 은닉재산 신고(17/62=27.4%) → 채무조정 안내(20/78=25.6%) → 예금보험금 안내(13/65=20.0%, 가장 양호)
- **오류 원인 분포**: 미적중 171/448건(38.2%) 중 93.6%는 정분류(업무 내 랭킹·청킹 문제), 6.4%만 오분류(다른 업무 청크 혼입)
- **혼입 1순위 청크 식별**: 예금보험금 안내 도메인의 `DpsmIbamtAplyPossDcmnt-selectScrn#02` 청크가 다른 업무 질문의 top-3를 12회 잠식 — 업무 분류/부스트 파라미터 재검토 1순위 후보로 지목
- **문서 단위 대비 거품 재확인**: hit@1 +23.9pp, hit@3 +28.3pp, hit@5 +20.8pp, recall@10 +13.1pp, mrr +23.2pp — 청크 단위 전환의 효과를 다시 한 번 정량 확인

## 3. 논의사항
- BF 키워드 세분화 여부 — 세분화 시 정밀도는 올라가지만 다른 질문에 대한 과확신 오답 위험도 커지는 트레이드오프, 결론 미도출
- 미수령금 도메인의 구비서류 준용관계(예금보험금과 겹침)를 어떤 필드 구조로 분리 관리할지 — `bf_relations` 계층 도입을 장기 과제로만 확정, 구체 설계는 미정
- 착오송금 반환신청의 멀티청크(and) 미적중 문제를 해결할 재청킹 방향(로드맵 4-2)이 아직 구체화되지 않음

## 4. 이슈 정리

## 이슈 1. `and` 관계(멀티청크) 검색 성능이 압도적으로 낮음

**문제**
전체 relation 중 `and`(다중 청크 전부 필요) 관계의 Hit@1이 0.000, Hit@3도 0.072에 불과해 `single`(0.717)·`or`(0.800) 대비 극단적으로 낮음. 착오송금 반환신청의 미적중 56건 중 55%가 이 유형.

**건의/조치**
Root-cause 분석 결과 원인은 리랭커가 아니라 `MsdrprPossDcmntGudn` 한 문서가 정답 청크를 `#01~#16`으로 과도하게 쪼개고 있는 문서 구조 문제로 특정. 로드맵 4-2(멀티청크 대응 청킹 재검토)로 이관.

## 이슈 2. FACET_RULES 키워드 사전의 구어체 커버리지 부족

**문제**
착오송금 반환신청에서 같은 업무 내 포괄적 문서(신청대상, 절차 개요)가 구체적 질문보다 계속 상위를 차지하는 미적중 25건(45%) 확인. "방법으로 하면" 같은 구어체 표현이 facet 키워드 사전에 없고, "제도란"(개요) 카테고리 자체가 FACET_RULES에 없음.

**건의/조치**
로드맵 3-3(큐폼/facet 소프트부스트 재조정, FACET_RULES 키워드 확장)으로 우선순위 지정.

## 이슈 3. 예금보험금 안내 특정 청크의 반복 혼입

**문제**
`DpsmIbamtAplyPossDcmnt-selectScrn#02` 청크가 다른 업무 질문의 top-3에 12회나 잘못 등장해 미적중을 유발.

**건의/조치**
업무 분류/부스트 파라미터 재검토 1순위 대상으로 식별 — 구체적 조치는 다음 실험에서 진행 예정.
