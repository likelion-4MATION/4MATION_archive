## 1. 오늘 할 일 (오전 스탠드업 기준)
아래 사항들에 대해 역할 분담 및 진행 방향 결정
- **큐폼**: 멀티턴으로 본인/대리인·상황·업무 등 슬롯 채우는 구조 실장 / 민원 처리(상담원 연결, 오류·버그 신고 등) 관련 질의를 OOS로 볼지 큐폼으로 처리할지 결정 후 반영
- **테스트셋 앵커-텍스트 반영**: 청크별 정답 구절 라벨링 / 동일 구절 다수 위치 시 중복 라벨 처리 대응 / 원문 사이트 동적 변경 시 정답 구절 소실 한계에 대한 보완 방법 검토
- **발표 준비**: 중간발표(금) 대비 진행 상황 정리 및 자료 준비

## 2. 실제 진행 내용

### 큐폼 구조 변경 — 트리 → 테이블
- 기존에는 트리 구조로 설계하려 했으나 한계를 확인하고 **테이블 구조로 전환**
- 경우의 수가 42개 정도로 크지 않아(열 데이터 42개, 행도 많지 않음) 테이블로 다뤄도 부담 없다고 판단
- 원래 트리를 고려한 이유는 "열 데이터가 필요 없는 부분이 많아서"였는데, 그 이점보다 트리 구조의 한계가 더 크다고 결론

### 라우팅 모델(6개 분류) ↔ 큐폼 연계 방식
- 라우팅에서 나온 6개 업무 분류 결과를 큐폼에 **가중치로만** 반영할지 논의 — 하드 필터가 아니라 기존 soft-boost 원칙을 유지하는 방향으로 정리
- 큐폼 슬롯을 채우는 작업 자체는 **LLM에 맡기는 게 낫다**고 정리
- 큐폼 작성이 필요한 질의인지 판단하는 라우팅 과정은 약 **0.1초** 수준으로 가볍게 처리됨

### 큐폼 적용 범위 및 원칙 재확인
- 모든 질의에 큐폼을 적용하지는 않을 것 — **신청서가 필요하거나 상황을 묘사해야 하는 질의에만** 큐폼을 넣어 정확도를 높이는 방향
- 큐폼이 트리거된다는 것 자체가 복잡한 질의라는 의미이므로, 응답 시간이 길어져도 괜찮다고 판단
- **큐폼은 보조 장치**이고 답변의 본체는 LLM — 큐폼 없이도 답변이 잘 되는 게 기본 전제, 큐폼은 정확도를 더 끌어올리는 역할
- 남은 결정 사항: 큐폼을 어느 정도까지 채워야 하는지 / 어떤 질의에 큐폼이 필요한지 기준 정교화 필요
- 멀티턴은 넣되 **최소화**하는 방향, UI 차원에서도 적용 가능하도록 고려

### 큐폼 문항 구성 원칙
- 큐폼 문항 구성 시 **business_function(bf)은 반드시 포함**되어야 함을 확정
- **큐폼-텍스트앵커-첨부문서 흐름**: 첨부문서 매칭은 큐폼이 나와야 가능한 구조 — 큐폼이 상황을 특정해야 첨부를 하나로 확정할 수 있음

## 4. 이슈 정리

## 이슈 1. 큐폼 저장 구조 — 트리의 한계

**문제**
트리 구조로 큐폼을 설계하려 했으나, 실제로 구현하는 과정에서 한계가 확인됨(분기가 늘어날수록 구조가 비대해지고 관리가 어려워지는 문제로 추정).

**건의/조치**
테이블 구조로 전환. 실제 조합 경우의 수가 42개 수준으로 크지 않아 테이블로 다뤄도 성능·관리 부담이 없다고 판단.

## 이슈 2. 라우팅 결과와 큐폼의 결합 방식

**문제**
라우팅 모델이 산출한 6개 업무 분류 결과를 큐폼에 어떤 식으로 반영할지(하드 필터 vs 가중치) 결정 필요.

**건의/조치**
기존 소프트부스트 원칙을 유지 — 라우팅 결과는 큐폼 슬롯에 가중치로만 반영하고 하드 필터로 쓰지 않기로 결정. 슬롯 채우기 자체는 LLM에 위임.

## 이슈 3. 큐폼 정합성 검사 아웃풋 단위(문서 vs 청크)

**문제**
유상님이 진행한 큐폼 정합성 검사 결과, 아웃풋이 문서 단위로 태깅되어 있어 세밀한 검증이 어려움.

**건의/조치**
문서 단위 태깅을 청크 단위로 전환할 수 있는지 가능성을 확인함 — 전환 자체는 가능한 것으로 파악, 실제 적용 여부는 추후 결정.
