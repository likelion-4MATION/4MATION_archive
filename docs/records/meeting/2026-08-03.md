## 2. 실제 진행 내용

### 오전
- 멘토링 보고서 작성
- 6개 업무 도메인 분기점 조사 진행 — 사이트맵 기준 진입 경로 외에도, 실제 사용자 질문으로 진입했을 때 여러 갈래로 흩어지는 경로가 있어 이 부분도 함께 조사함

### 오후
- 구조적 개편 관련해서 바로 작업 가능한 항목들 진행

### 주요 논의 및 결정사항
1. **분기점 조사 → 청크별 첨부문서 태깅** 진행 (담당: 유상님)
2. **큐폼 설계**: 짧은 질의는 큐폼만으로 대응이 어려워 개념형/요구형 질문을 구분 → 이 판단은 별도 라우팅보다 LLM이 직접 처리하거나 가볍고 빠른 로컬 모델로 분리 (라우팅 모델 조사: 규남님, ELECTRA 금융 도메인 파인튜닝 검토 / 큐폼 설계: 현욱님)
3. **큐폼 방식 전환**: 큐폼을 룰베이스로 그대로 쓰는 것보다, 청크 메타데이터에 대해 **soft-boost(가중치) 방식**으로 전환하는 방식 논의 — 기존에 임베딩+BF로 나눠 키워드를 추출해 넣던 방식과 유사한 접근
4. **멀티턴 적용 범위**: 분기가 많은 예금보험금·미수령금 등 복잡한 도메인(3개)에서만, 자연어로 상황을 되묻는 방식으로 적용(설문형 노출 지양)
5. **애매한 케이스**: 용어 자체가 어려운 경우가 많아 LLM으로 처리하는 방향으로 논의 → 토글로 개념 설명을 붙여 사용자가 필요할 때 확인할 수 있게 구성
6. **관리자 UI 실험 환경**: RRF 파라미터 3종 + 청크 사이즈 + 오버랩 = 총 5개 파라미터 조정 가능하도록 구축 진행 중. 추가로 넣을 만한 파라미터를 검색 시점과 적재시점으로 나누어 조사완료, 임베딩 모델과 같은 모델 부분은 추가 필요(경은님)

## 3. 논의사항
- 현재 테스트셋(400건)은 업무 관련 질문으로만 구성되어 있어, **공용 테스트셋 1,000건**으로 확장 계획 — 복잡한 질문 + 업무 외 질문을 섞어 관할/비관할 구분 능력을 검증할 예정
- 현재는 "부적합" 질문만 라우팅에서 걸러지고 있어, **애매한 질문(소관 여부 불분명)** 에 대한 처리가 부족한 상태
- 큐폼에서 LLM으로 정보가 전달되는 구체적인 방식은 아직 미정

## 4. 이슈 정리


## 이슈 1. 첨부문서 반환·청크 단위 답변 vs 페이지 단위 정답 불일치

**문제**
현재 핵심 문제는 검색 정확도 자체가 아니라 첨부문서 반환과 청크 단위 답변 추출임. 정답 데이터셋은 페이지 단위로 라벨링되어 있어, 답변이 다른 청크에서 나와도 같은 문서(페이지)면 정답으로 인정되는 평가 구조와 실제 청크 기반 응답 방식이 어긋남.

**건의/조치**
분기점 조사 결과를 반영해 청크별 첨부문서를 하나씩 태깅. 예: 신청서 관련 질의가 들어오면 LLM이 질문(개인/법인 여부 등)을 읽고 정리(포맷)한 뒤 해당 양식과 매칭.
→ 검색 구조 자체의 개편이 필요하다는 결론.


## 이슈 2. 사용자 상황 정보를 어떻게 수집할 것인가 (큐폼 설계)

**문제**
상황 설명이 필요한 복잡한 질의에 큐폼(정형 질문)이 유효하지만, 처음부터 모든 항목을 채우게 하면 기존 시나리오형 챗봇("예솜이")과 차별점이 없어짐. 또한 큐폼을 그대로 룰베이스로 적용하면 슬롯 오추출 시 정답 문서가 배제되는 문제 발생.

**시도된 방향들**
- 개념 질문 vs 요구 질문을 먼저 구분하려 했으나, 이를 별도 라우팅 단계로 두면 시간 비용이 기존 방식과 비슷해짐
- 큐폼을 설문 형태로 노출하지 않고, 자연어로 되묻는 방식("상황을 설명해주세요", "당사자분의 상황을 설명해주세요" 등)으로 전환

**최종 확립**
- 큐폼은 사용자에게 노출하지 않고 자연어 반문으로 자연스럽게 정보 유도
- 청크 메타데이터에는 하드 필터가 아니라 **soft-boost(가중치)** 방식으로 반영 → 룰베이스 문제 해소 (기존 임베딩+BF 키워드 추출 방식과 유사한 접근)
- 적용 범위는 분기가 많은 도메인 3개(예: 착오송금반환 청구, 예금보험금 안내, 고객 미수령금 청구)로 한정
- 큐폼 항목: party, 본인/대리인, BF, 미성년자/군인 등 특수신분, 인터넷/방문 등. 어려운 용어는 토글로 개념 설명 제공, LLM 질문 문장도 쉬운 표현 사용
- 질문 생성은 하드코딩이 아니라 LLM이 큐폼 스키마를 참고해 부족한 부분만 반문
- 시나리오 리프 노드는 42개(항목별 충족 여부 조합에 따라 더 늘어날 수 있음)

**미해결**
- 큐폼에 채워진 정보가 LLM에게 어떤 방식으로 전달되어야 하는지 결정 안 됨
- "적합 + 복잡한 상황" 케이스의 세부 처리 흐름 미정



## 이슈 3. 질문 유형 판단(라우팅) 비용 문제

**문제**
LLM으로 질문 유형(개념/요구)을 매번 판단하면 비용·시간이 들고, 별도 라우팅 단계를 둬도 절감 효과가 크지 않을 수 있음.

**건의/조치**
라우팅을 가볍고 빠른 로컬 모델로 분리 — ELECTRA 계열 모델을 금융 데이터로 파인튜닝하는 방안 검토.
초기 라우팅 구조 자체는 기존처럼 **모호/적합/부적합 3단계**로 유지하되, 그중 정보가 채워지지 않은 항목에 대해서만 동적으로 질문을 생성(룰베이스 아님 — 사용자가 어떤 정보를 이미 줬는지 사전에 알 수 없어 매번 판단 필요).


## 이슈 4. 평가셋(테스트셋)의 커버리지 부족

**문제**
현재 테스트셋 400건은 업무 관련 질문으로만 구성되어 있어 관할/비관할(우리 소관 여부) 구분 능력을 검증하지 못함. 현재는 "부적합" 질문만 라우팅에서 걸러지고, 소관이 애매한 질문에 대한 처리가 미흡함.

**건의/조치**
공용 테스트셋을 1,000건으로 확장.
- 키워드 포함 질문
- 키워드 미포함 질문
- 소관 아닌 질문(애매한 케이스)
을 나누어 검증 예정.
