## 3. 실제 진행 내용

### OOS 처리 로직 — 3안 비교 후 최종 확정

**query unit 분해안 제시**
```
사용자 Query → [0] Input Guard(injection/invalid→reject) → [1] Intent Router(casual/handoff/bug/information)
→ [2] Query Decomposition → IN/LINK/OOS 분기 → RAG/Registry/reject → Response Composer
```
핵심은 route를 질문 전체에 하나만 부여하지 않는 것, LLM 역할을 최소화하는 것. LLM은 의도/질문 단위 분해만, Retrieval은 실제 코퍼스 근거 확인, Registry는 타기관 안내처 결정, Code는 최종 route 결정, Generation은 IN_SCOPE 답변만 담당. 수정 핵심 3가지: ① L0이 "코퍼스에 있나"를 자기 지식으로 판단하지 않게 할 것 ② 복합질의를 단일 route가 아니라 query unit 단위로 처리할 것 ③ LLM은 label만 결정하고 실제 route는 registry/retrieval 기반 코드가 결정할 것

**룰 기반 L1 + 태그 분리 상세 설계**

컴포넌트 5개로 구성: [1] L-1 룰 프리필터(HANDOFF/BUG 고신뢰 패턴을 여기로 승격, L0 콜 자체 스킵) [2] L0 게이트(프롬프트 한 줄만 추가, 기존 유지) [3] 레퍼럴 태거(신규 — 형태소 토큰 오버랩 매칭, `negative_context`로 오탐 방지, `top_n=3` 상한) [4] 라우팅 조합기(신규, LLM 콜 없는 순수 로직) [5] 응답 조립기(신규 — 안내처 URL·전화번호는 LLM이 생성하지 않고 사전 값을 문자열로만 치환)
- 콜 수 비교: 원안(L1=LLM)이 OOS 문항마다 +1콜인 데 비해 B안은 handoff/bug 강신호 문항에서 오히려 -1콜(L0까지 스킵)
- 추가 결정: `OOS_처리로직_계획서.md` §7-1의 안전 기본값을 "정상"에서 "모호"로 변경하는 게 좋겠다는 의견 정리
- dev 기준 `hit@3`로 되어 있던 것을 `hit@5`로 변경 — 관리자 UI에서도 조절 가능해야 하는 부분이라 함께 반영

**최종 결정사항 반영 및 확정 (`복합질의_라우팅_3안비교.md`)**
- **결론: 2안(라벨을 "라우팅"과 "태그"로 분리, 질의는 절대 쪼개지 않음) 채택** — 콜 0, 계약 유지. 1안에서는 지시어 결정론 재작성 1조각만 차용, 3안은 목표 아키텍처로 보류
- 채택 근거: ① 콜 0(라우터 GPU 서빙이 막혀 있는 상태에서 콜을 더 얹지 않음) ② "질문이 몇 개냐"를 판정할 필요 자체가 없음("미수령금은 무엇인가요, 그리고 어떻게 신청하나요"는 나눌 기준이 없음) ③ 450/1150셋이 즉시 회귀 테스트로 재사용 가능 ④ 계약 4필드 무변경(`route` 단일값 유지, 복합 여부는 `_meta.referral_tags`) ⑤ URL·전화번호를 LLM이 한 글자도 생성하지 않음
- 인정한 구멍 2개: 레지스트리 커버리지가 곧 안전 커버리지라는 한계, top-k 확대(5→8~10) 자체는 생성이 top-3만 읽는 한 효과 없음(리랭킹·생성 k 확대와 묶어야 의미)
- 라벨 분기 트리를 8건(C1~C8) 수정 — 예: SCOPE_OOS의 "기타 타 기관 소관 업무" catch-all 삭제(사전 미등록 시 DOMAIN_OOS로 강등), 외국 예금보호제도 별도 하위 신설, "보호한도 초과분"·"비보호 금융기관"을 SCOPE_OOS에서 IN_SCOPE로 이동 등
- LLM 호출 경계 원칙 확립: "출력이 검증 가능한 라벨·ID면 LLM에 맡긴다. 출력이 자유 텍스트인데 그 안에 코퍼스 밖 고유명사(기관명·URL·전화번호)가 들어가면 조립한다"

**경은 vs 유상 2자 GT 비교 (`머지방향_경은_vs_유상_20260820.md`)**
- 가장 중요한 실측: 경은 `gt_natural430_curated`와 유상 `gt_natural430_anchored`가 **id 집합 완전 동일, relation 동일, gold 청크 총계 519로 동일** — 두 사람이 독립적으로 작업해 소수점까지 같은 결과에 도달, GT 정본 다툼이 아니라 필드 규약만 통일하면 되는 병합임을 확인
- 11개 설계 쟁점 중 8개는 이미 합의(판정 기준·스팬 다중화·`TABLE_GAP_MAX`·라벨 보강 방식·stale gold 되살리기·실험 채택 기준·GT 계보·파일 정리)
- 갈린 3개: 필드명 정합(`gt_anchors`+`gt_anchor_spans` 병기 — 경은 채택), 추론형(inferable) 처리(유상의 gold 단위 하이브리드 채택), 질의 분류기(라우터-키워드-PRF 3단 계층으로 양립)
- 파라미터가 BF 소스에 종속됨을 발견 — `BF_BOOST`가 라우터 전제(0.06)와 키워드+PRF 전제(0.04)에서 다르게 최적화되어 있어, 라우터 미착륙 상태로 클론하면 폴백 시 오분류가 12배 증폭될 위험 확인

**3자(경은·유상·규남) 머지 판정 (`merge_판정_3자.md`)**
- 세 사람의 GT가 하나의 계보임을 확인 — 공통 430건 중 스팬 428건이 겹침(완전 불일치 2건)
- 규남 GT는 위로 넓고(추가 20건이 `inferable` 18건+`answerable=false` 2건), 옆으로 부풀어 있음(gold 총계가 930으로 519의 1.79배 — 중복게재 청크를 gold에 보강한 결과)
- 필드가 4중명으로 늘어남(`gt_anchors`/`gt_anchor_spans`/`gt_anchor_span`)을 확인, 규남 평가기가 `chunk_relation`을 읽지 않아 `and` 관계가 전부 ANY로 채점되는 문제(경은·유상 규칙 대비 hit@5 기준 +3.1pp 부풀림) 발견

## 4. 논의사항
- **복합질의(한 질의 안에 2가지 쿼리) 처리**: 질문을 나누기보다 서로 연관되어 있으므로 LLM에게 맡기는 방향으로 논의 — 질문이 2개라고 판단되면 top-10으로 넓히는 방안 검토했으나, OOS 질문만 걸러내는 게 어려울 것 같고 애초에 질문을 2개로 나누는 기준 자체가 모호한 사례가 있음("미수령금은 무엇인가요, 그리고 이것은 어떻게 신청하나요"는 나눌 수 없음)
- 해결 방법 후보 2가지 논의만 진행, 결론 미도출: ① MOAI 학습 ② 멀티턴과 비슷한 방법으로 해결
- 버그 관련 문의는 관련 창을 띄우는 방식, 상담사 연결·casual 질의는 별도 분기로 처리하는 방향 논의
- OOS handler — 임베딩 모델을 쓰지 않으면 키워드 범위가 너무 많아지는 문제 확인, 결론 미도출
