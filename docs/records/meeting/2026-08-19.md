## 3. 실제 진행 내용

### OOS 처리로직 계획서 문제 파악
어제 산출한 `OOS_처리로직_계획서.md`(2층 구조·6대 택소노미)를 리뷰해 우선순위별 문제를 정리함.

**🔴 핵심 문제**
- **L0과 검색기의 역할 중복**: L0이 "코퍼스에 답이 있는가"를 판단하는데, 이는 검색기가 해야 할 판단과 겹침. L0이 코퍼스 정보를 충분히 알지 못하면 오판 가능하며, 검색을 먼저 하면 L0이 불필요해질 수 있음
- **L1을 LLM으로 처리하는 것은 과도함**: OOS 판정 이후 link/handoff/bug/casual/reject는 대부분 규칙으로 결정 가능한데 불필요한 LLM 1콜이 추가되어 지연시간·비용·비결정성 증가
- **단일 라벨 구조가 복합질의를 처리하지 못함**: "보호한도+워크아웃"처럼 IN_SCOPE와 SCOPE_OOS가 섞인 질문을 하나의 라벨로 표현하기 어려워 결국 별도의 질의 분해 로직이 필요해짐
- **IN_SCOPE = 코퍼스 존재 정의가 너무 넓음**: "예보 소관이 아니다"라는 안내문이 존재하는 경우와 실제 답변 근거가 존재하는 경우를 동일하게 취급할 위험

**🟠 운영/안정성 문제**
- 분류 실패 → "정상" 기본값 → RAG fallback: 공격/오류 상황에서 게이트가 우회될 수 있어, 최소한 `classification_failed` 상태는 별도 보존 필요
- SCOPE_OOS → link 자동 연결이 과도하게 단순함(복합질의·세부업무에서 잘못된 referral 선택 가능)
- Referral Registry가 새로운 유지보수 지점을 만듦(코퍼스 변경 시 안내처 갱신 필요 — 이미 휴면계좌 안내처 불일치 사례 있었음)
- 택소노미 경계 불안정(DOMAIN_OOS↔SCOPE_OOS, HUMAN_HANDOFF↔BUG_REPORT)

**🟡 평가/성능 검증 문제**
- 20문항 트랩셋은 held-out 아니고 26개 하위 유형을 충분히 커버 못함
- L1 추가 비용 추정(OOS 60%→평균 +0.6콜)이 현재 트랩셋 기준일 뿐 실제 분포와 다를 수 있음
- OOS 개선과 RAG 문제(구정보 확인형 등)의 경계를 명확히 유지해야 함

**우선순위 요약**: 반드시 수정 검토(L0 코퍼스 판단 방식·L1 LLM 제거 가능성·복합질의 처리 방식·분류 실패 fallback) → 구현 전 검증(SCOPE_OOS 매핑·registry 갱신·택소노미 경계·실사용 분포 콜/지연) → 평가 단계 보완(held-out 트랩셋·26개 유형 커버리지·OOS/검색생성 책임 경계). **핵심 결론: L0→L1 LLM 구조를 그대로 구현하기 전에 구조를 한 번 더 줄이는 것이 좋다.**


### 관리자 UI 파라미터 조사
전체 파라미터를 "파라미터를 바꾸면 벡터·청크 텍스트 자체가 달라지는가"를 기준으로 재분류.

**검색시점(즉시 반영, 재적재 불필요)**
- Top-K, `RRF_ALPHA`, `RRF_K`, `BF_BOOST`, `FACET_BOOST`(누락돼 있던 항목 발견), `BF_DOC_CAP`(문서당 청크 cap — A/B 비교가 가장 필요한 값), `BF_MODE`(soft/hard), `QBF_MIN_SCORE`/`QBF_MARGIN`, 검색 mode(dense/bm25/hybrid/hybrid_bf), 후보 pool 크기, 리랭커(미구현)

**적재시점(재청킹·재적재 필요)**
- `CHUNK_SIZE`, `OVERLAP`, 임베딩 모델(`MODEL_NAME`), `MIN_CHUNK`, `FAQ_MARGIN`/`FAQ_RETAG_GATE`(텍스트·임베딩은 안 바뀌지만 business_function 메타데이터가 바뀌어 재청킹은 필요하되 재임베딩은 불필요 — 비용이 다른 두 그룹으로 나뉨)

## 4. 논의사항
- **큐폼-앵커텍스트 연결**: 앵커 텍스트를 직접 연결할 필요가 있음을 확인 — 청크 사이즈는 동적 대응이 가능하지만 사이트 내용이 바뀌면 정답 텍스트 자체가 바뀌는 문제가 있어, 큐폼 값을 임베딩에 넘기고 슬롯 분기에 맞춰 큐폼을 설계하는 방향으로 논의. 문서 반환도 큐폼으로 해소하는 방향
  - 큐폼으로 들어올 때 키워드가 앵커텍스트와 합쳐지면 키워드가 과도하게 늘어나는 문제 확인 — 키워드 분기가 아니라 값이 입력된 자리에 실제 입력을 넣는 방식(예: "본인" 키워드가 그 자리에 들어가야 함)으로 정리했으나, 청크 아이디를 그대로 넣으면 정확도가 지나치게 높아져(오탐 위험) 청크 아이디로는 처리할 수 없다는 결론
  - 키워드 분류기는 여전히 필요한 것으로 판단됨
- 브랜치 통합 방향은 오늘 착수만 하고 세부 방안은 결론 미도출
- 관리자 UI 파라미터는 위 조사를 바탕으로 상세 사양서·목업까지 이어졌으나, 실제 콘솔 구현·배선은 다음 단계로 이월
