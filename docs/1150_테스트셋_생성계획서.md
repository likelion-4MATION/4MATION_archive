# 1,150 테스트셋 생성 계획서 — 라우팅 평가 (B안 연동)

**작성 배경:** 라우터 평가셋 핸드오프 + `routing_model_review.md` B안 검토 반영
**대상:** 4MATION — 초기 라우팅 held-out 평가셋
**상태:** 설계 승인 계승 — §11 미결정 사항 팀 확인 후 생성 착수

---

## 0. 이 문서의 역할 및 관계

이 1,150문항은 **순수 held-out 평가셋**이다. 파인튜닝 학습 데이터(`testset_natural_400` 등)와 무관하며 지금 생성하지 않는다. 스키마 `usage` 필드를 `held_out_eval`로 고정해 학습 혼입을 스키마 레벨에서 차단한다.

**작업계획서(B안)와의 짝:** B안이 "학습 방법", 이 셋이 "평가"다. 특히 이 셋의 **G5a/G5b가 작업계획서 §5의 far-OOD/near-OOD 분리 AUROC를 그대로 측정**한다 — 원 문서 §7-5가 요구한 "토픽 단위·기관 분리 OOS 평가셋"이 바로 이것이다.

**절대 원칙 계승:** 근거주의(추측 금지) · 기존 파일 불가침(신규 파일로만) · §11 미결정 사항 임의 결정 금지.

---

## 1. B안 평가에서 이 셋의 역할 (신규 — 반드시 이해)

B안은 **6분류 argmax(도메인) + MSP 임계(in/out)**를 한다. 이 셋의 각 그룹이 무엇을 검증하는지 매핑한다.

| 그룹 | 라우팅(in/out) 관점 | 도메인(6-class) 관점 | B안에서의 쓸모 |
|---|---|---|---|
| G1·G2 | in-scope, 高 MSP 기대 | 정답 도메인 | 명확 케이스 회귀 확인 |
| G3 Hard Negative | 모두 in-scope | **도메인 경계 예리함** | 통합 모델이면 도메인 오분류 측정 |
| G4 복합/중의성 | in-scope, 高 MSP | 다중의도 | 高 MSP 유지 확인 |
| **G5a 완전무관** | **OOS, 低 MSP 기대** | — | **far-OOD AUROC (쉬움)** |
| **G5b 금융연관** | **OOS, near-OOD** | — | **near-OOD AUROC — 진짜 승부처** |
| G6 저신뢰 경계 | 임계 튜닝 | — | 모호 임계 캘리브레이션 |

**핵심:** 라우팅 평가의 심장은 **G5a vs G5b의 AUROC 격차**다. 이 격차가 크면 MSP가 금융연관을 못 거른다는 신호다(작업계획서 §5-4).

> **참고 — 수량 재배분 판단:** 이전에 "순수 이진 라우터면 G3/G4를 줄이라"고 논의했으나, **B안(6-class)에서는 G3/G4가 도메인 경계 학습·평가에 기여**하므로 원 핸드오프 구조를 대체로 유지한다. 대신 **G5b(near-OOD)의 기관 다양성·표본 견고성**을 최우선으로 확보한다(§6). 통합 vs 분리 아키텍처가 확정되면 최종 조정.

## 2. 도메인 체계 (7-class)

| 코드 | 도메인 | 정의 |
|---|---|---|
| D1 | 예금보험금 신청·안내 | 예금보호한도·보험금 지급 |
| D2 | 미수령금 통합조회/신청 | 미수령 자산 조회·신청 |
| D3 | 착오송금 반환지원 | 잘못 송금한 돈 반환 |
| D4 | 채무조정 재기지원 | KDIC 자체 프로그램 |
| D5 | 파산금융회사 관리·배당 | 정리·파산배당금 |
| D6 | 증명서 발급·신고 | 증명서·신고 접수 |
| OOS | 소관 외 | 위 6개 밖 |

**퇴직연금 판별:** 예금보호(한도·보험금) 관련이면 D1, 그 외(중도인출 세제·체불임금·사업장 미납 등 근로복지공단 실무)는 OOS. §7 최소대조쌍으로 구체화.

## 3. 그룹 구조 및 수량 (총 1,150)

| 그룹 | 성격 | 도메인당 | 합계 |
|---|---|---|---|
| G1 | 키워드 포함·쉬운 문장 | 10 | 60 |
| G2 | 키워드 미포함·구어체 | 15 | 90 |
| G3 | Hard Negative (인접 오인) | 40 | 240 |

| 그룹 | 성격 | 합계 |
|---|---|---|
| G4 | 복합/중의성 (도메인 간 우선순위) | 210 |
| G5a | OOS — 완전 무관 | 150 |
| **G5b** | **OOS — 금융연관·타기관 소관** | **270** |
| G6 | 저신뢰 경계 (임계 튜닝) | 130 |

**검증:** 60+90+240(도메인반복 390) + 210 + 150 + 270 + 130 = **1,150** ✓

### G5a 세부 (150)
- 일상 잡담(날씨·맛집·취미): 100
- 챗봇/시스템 메타("너 뭐야", "상담원 연결"): 50

### G5b 세부 (270) — near-OOD, 최우선 관리
- 타업권 상품(카드/증권/일반보험): 80
- 타기관 실제 소관(국세청·금감원·신용회복위): 80
- 일반 금융상식(개념 설명): 50
- 퇴직연금-OOS 대조쌍(근로복지공단 소관): 60

## 5. 퇴직연금 최소대조쌍 (id19 직접 대응)

동일 "퇴직연금" 표면 키워드를 공유하되 **보호/보장 여부로만** 라벨이 갈리게 짝을 맞춘다.

| 배치 | 예시 | 라벨 |
|---|---|---|
| D1-G3 내 12문항 | "퇴직연금도 예금자보호 한도 적용되나요?", "IRP도 5천만원까지 보호돼요?" | D1 |
| G5b-OOS 내 12문항 | "퇴직연금 중도인출하면 세금 얼마나?", "회사가 퇴직연금 안 넣어줬는데 어디 신고?" | OOS |

**신용회복위 개인워크아웃 ↔ D4 대조쌍도 동일 원리로 배치:** G5b 타기관 소관 80건 중 최소 20건을 이 유형으로, D4의 G3 Hard Negative에 대응 쌍 배치.

## 6. G5b 설계 강화 — 기관 단위 분리 (원 §7-5 연결) ⭐

**near-OOD 평가의 타당성은 건수가 아니라 토픽(기관) 수가 좌우한다.** 표현만 늘려 270건을 채우면 "몇 개 기관만 아는 분류기"가 통과한다.

- **설계 기준:** 기관/토픽 N개 × 표현 2~3개 (표현 복제로 건수 부풀리기 금지)
- **학습·평가 토픽을 기관 단위로 분리** — 표현만 나누면 토픽 누수(자기참조 편향 재현)
- **기관 목록은 사람이 먼저 나열** (정부24 민원 카테고리 참고) 후 토픽당 표현 생성 — LLM 단독 생성은 분포가 좁아진다
- **경계 케이스 별도 확보:** 퇴직연금·연금저축(id19 계열), 파산절차 vs 법원, 신용회복 vs 신복위
- **더 나은 소스:** 예솜24 챗봇 로그(확보 시 "작성"이 "라벨링"으로 바뀌고 대표성↑) → 클라비 문의

## 7. 라벨 스키마 v2

```json
{
  "id": "D1-G3-014",
  "text": "질의 원문",
  "domain": "D1",
  "is_oos": false,
  "group": "G3",
  "difficulty": "hard",
  "ambiguity_type": "lexical_overlap",
  "secondary_domain": null,
  "priority_rationale": null,
  "confidence_tier": "high",
  "source": "seed_human",
  "seed_id": null,
  "annotator_note": "퇴직연금 예금보호 문의 — OOS 대조쌍",
  "usage": "held_out_eval"
}
```

| 필드 | 값 | 근거/용도 |
|---|---|---|
| `is_oos` | true/false | CLINC150 방식 — 도메인 오분류율·OOS 탐지율 독립 측정 |
| `difficulty` | easy/medium/hard/adversarial | ANLI 난이도 티어링 |
| `ambiguity_type` | lexical_overlap / multi_domain / **jurisdiction_boundary** / null | 오류 원인 유형화. **near-OOD는 jurisdiction_boundary로 태깅** |
| `secondary_domain` | G4 전용 | 다중의도 표시 |
| `priority_rationale` | G4 전용 | 우선순위 판단 근거 (검수자용) |
| `confidence_tier` | high / low(G6) | MSP 임계 튜닝용 |
| `source` | seed_human / llm_augment | Self-Instruct provenance — 근접중복 방지 |
| `seed_id` | augment 시 원본 id | 계보 추적 |
| `usage` | held_out_eval 고정 | 학습 혼입 차단 |

**설계 프레임워크:** CheckList 행동 테스트 대응 — G1/G2=MFT, G3=Invariance+Hard Negative, G4=Directional Expectation, G5=CLINC150 OOS, G6=MSP baseline.

## 8. 생성 방법론 — 근접중복 방지 (착오송금 22건 재발 방지)

1. **Seed 우선:** 도메인×그룹당 3~5개 seed 먼저 작성 (`source: seed_human`)
2. **Paraphrase 증강:** 나머지는 문장 구조·어투·길이를 의도적으로 분산 (`source: llm_augment`, `seed_id` 연결)
3. **템플릿 반복 금지:** 고정틀 대량 복제 금지. 같은 seed 내에서도 길이·격식/구어·질문/평서 혼합
4. **근접중복 자체 점검:** 생성 후 문항 간 유사도(자카드 또는 임베딩 코사인) 상위 쌍을 훑어 임계 이상이면 재작성

## 10. 생성 후 자체 검증 체크리스트

- [ ] 총 문항 = 1,150 (그룹별 목표와 정확히 일치)
- [ ] domain/is_oos/group 조합이 §3 표와 100% 일치
- [ ] **G5b가 기관 단위로 분리됐고, 표현 복제 부풀리기가 아닌지** (§6)
- [ ] **`jurisdiction_boundary` 태그가 near-OOD 케이스에 부여됐는지** (far/near AUROC 분리 측정 전제)
- [ ] G4의 `secondary_domain`+`priority_rationale` 전부 채움
- [ ] G6 `confidence_tier: low` 정확히 130건
- [ ] `usage` 예외 없이 `held_out_eval`
- [ ] 퇴직연금 대조쌍(D1 12 + OOS 12) 존재 + annotator_note에 대조 관계 명시
- [ ] 신용회복위 개인워크아웃 ↔ D4 Hard Negative 포함
- [ ] 근접중복 점검 수행·결과 요약

## 11. 미결정 사항 — 팀 확인 필요

1. **아키텍처(통합 vs 분리)** 확정 후 G3/G4 수량 최종 조정 여부 — 작업계획서 §3과 연동.
2. 산출물 경로 — 실제 레포 구조 확인 후.
3. G4 저빈도 조합(D5–D6 등) 유지/재배분 — 도메인 지식 검수 필요.
4. **G4/G6 gold 라벨 검수 프로토콜** — 정답이 논쟁적인 340건(전체 30%)에 2인 라벨링+불일치 조정을 적용할지, 팀 눈 검수로 갈지.
5. 예솜24 로그 확보 시 G5b 일부를 로그 라벨링으로 대체할지 — 클라비 문의 결과에 따라.
6. 파인튜닝 학습 데이터 확보는 이 작업 범위 밖 — 별도 진행, 혼동 금지.
