## 0. 현재 지점 & 이 문서의 역할

데모 챗봇(분류 라우팅 → 하이브리드 검색 → 생성 → 검증 + 첨부 반환)까지 동작 확인. 이제부터는 정확도·자원·구조를 개선하는 단계다. 아래는 팀이 나열한 14개 과제를 **의존성과 순서**에 맞춰 워크스트림·페이즈로 재구성한 마일스톤이다.

세부 설계가 이미 별도 문서로 존재하는 항목은 링크로 연결한다:
- **항목 9(표=청크 다량 반환)** → `plan_attachment_party_scoping.md`
- **항목 5·14 일부(입도 불일치·평가)** → `plan_eval_granularity_mismatch.md`

## 1. 확인된 사실 (착수 전 정정)

- **항목 13(bge-m3 ko)**: base `BAAI/bge-m3`는 **이미 적용 중**이고 RRF 파라미터(`RRF_ALPHA=0.6`, `RRF_K=5`)도 bge-m3 기준 재튜닝 완료. → 항목 13은 "**한국어 파인튜닝 변형** 비교·교체 검토"로 재정의.
- **항목 1(lxml)**: 파서는 이미 `lxml` 우선 → 실패 시 `html.parser` 폴백 구조(`parser.py:parse_html`). → 항목 1은 "**lxml 시도를 건너뛰고 html.parser로 직행**"으로 정정.
- **항목 12(하이브리드 비중)**: 현재 가중 RRF(dense 0.6). 재조절 대상.

## 3. 페이즈 마일스톤 (의존성 기반 순서)

### Phase 0 — 측정 기반 확립 (WS-A) · **선행 필수**
> 이유: 지금 평가셋은 관점에 따라 validation, RRF 관점에선 train set이라 **지표 낙관편향**. 이후 모든 정확도 개선(11·12·13)의 신뢰 기준이 여기서 나온다. 측정이 흔들리면 튜닝은 자기기만이 된다.

- **M0.1 — held-out 테스트셋 구축 (항목 14)**: 현 평가셋과 분리된 독립 검증셋. 튜닝에 절대 노출 금지. 완료: 문항 세트 + 분리 원칙 문서화.
- **M0.2 — evidence-span 태깅 & 이중 지표 (항목 5 평가측)**: `gt_docs`(문서) 유지 + `gt_evidence`(청크 근거 문구) 추가, doc-hit@k와 evidence-hit@k 병행 리포트. 재청킹 내성 확보. 완료: 두 입도 지표 + **doc–evidence 격차** 산출. (상세: `plan_eval_granularity_mismatch.md`)

### Phase 1 — 데이터/수집 품질 (WS-B) · **정확도의 상류(上流)**
> 이유: garbage-in 방지. 검색·생성을 튜닝하기 전에 코퍼스 정합성을 먼저 확보해야 개선이 진짜 개선으로 측정된다.

- **M1.1 — 파서 html.parser 직행 (항목 1)**: lxml 시도 제거, 처음부터 `html.parser`. 완료: 파싱 결과 동일성 회귀 확인 + 파싱 시간 단축 측정.
- **M1.2 — 구정보(stale) 처리 (항목 2)**: 사이트 내 과거/폐지 정보 식별·태깅·필터 정책. 완료: 구정보 목록화 + 검색 노출 정책 결정.
- **M1.3 — 퇴직연금 소관 커버리지 (항목 3)**: 소관 관리 미흡 구간 보강(수집 범위/분류/거절 경계). 완료: 퇴직연금 질의 셋에서 소관 판정·근거 확보.
- **M1.4 — 근접중복 문서군 정리 (항목 4)**: 착오송금 구비서류 22건(본인/대리인/미성년자/군복무자/법인/비법인단체/국외거주 × 송금인/수취인 × 인터넷/방문)의 근접중복 구조화. 완료: 중복 축(당사자/신청경로) 메타 정의 — **항목 9의 section-scoping과 축 공유**.
- **M1.5 — bf 분류 키워드 확장·재검증 (항목 11)**: `chunk.py` `BF_KEYWORDS` 확장, 게이트 재검증. 완료: Phase 0 지표로 재태깅 정확도 개선 확인, 오분류 회귀 0.

### Phase 2 — 검색·인덱싱 정확도 (WS-C) · **핵심 개선**
> 이유: Phase 0 지표 위에서만 유의미. 청킹 구조(7·9·5)를 먼저 확정하고, 그 위에서 검색 파라미터(12·13)를 튜닝한다. 청킹을 바꾸면 인덱스·chunk_id가 무효화되므로 순서가 중요.

- **M2.1 — 청킹 단위 재설계 (항목 7)**: CHUNK_SIZE/경계 정책 재검토(청크 크기별 증감 기실측 반영). 완료: 후보안 A/B를 Phase 0 지표로 비교, 최적 경계 확정.
- **M2.2 — 표=청크 다량 반환 해소 (항목 9)**: 표 내 당사자(송금인/수취인 등) section-scoping + 질문 당사자 필터 + 집계 상한. 완료: 첨부 정밀도↑, 재현율(누락) 0. (상세: `plan_attachment_party_scoping.md`)
- **M2.3 — 부모-자식 반환 전략 (항목 5 생성측)**: 청크 vs 페이지 반환 트레이드오프 — whole-doc는 정보량 급증·오염 위험. **bounded parent(이웃/섹션 확장, FAQ 확장 금지)**로 결정. 완료: doc–evidence 격차 기반 확장범위 결정 + 토큰예산 내 검증. (상세: `plan_eval_granularity_mismatch.md`)
- **M2.4 — 하이브리드 비중 조절 (항목 12)**: `RRF_ALPHA`/`RRF_K` 재스윕. **held-out에서** 최적값 선택(과적합 방지). 완료: held-out 지표로 확정.
- **M2.5 — 한국어 파인튜닝 임베딩 비교 (항목 13)**: bge-m3 한국어 파인튜닝 변형 후보 조사·벤치. 완료: held-out에서 base bge-m3 대비 유의 개선 시에만 교체(EMB_DIM/인덱스 갱신 포함).

### Phase 3 — 비용/지연 최적화 (WS-D)
> 이유: 정확도가 안정된 뒤 자원을 줄인다. 교체가 품질 회귀를 부르지 않는지 Phase 0 지표로 가드.

- **M3.1 — 라우팅 주체 교체 검토 (항목 6)**: 초기 라우팅(현재 HCX 1콜)을 경량 대안(결정론 키워드/임베딩 분류기 등)으로 대체 가능성 평가. 완료: 분류 정확도·지연·비용 3지표로 LLM 대비 비교, 회귀 없으면 교체.

### Phase 4 — 제품/경험 (WS-E)
> 이유: 코어(검색·생성·비용)가 안정된 후 사용자 경험을 확장.

- **M4.1 — 멀티턴 적용 (항목 8)**: 대화 맥락 유지 설계(질의 재작성/맥락 병합), 계약 4필드·라우팅과의 정합. 완료: 멀티턴 시나리오 셋 통과.
- **M4.2 — UI 방향 결정 (항목 10)**: 멘토링 기반 — ① 기존 챗봇 답습 vs ② 포트폴리오용 독자 UI. 완료: 방향 확정 + 범위 정의. *(의사결정 항목 — 팀 합의 필요)*

## 5. 핵심 순서 원칙 (요약)

1. **측정부터(P0)**: held-out + evidence 태깅 없이는 이후 모든 개선이 낙관편향. 차단요소로 취급.
2. **상류→하류**: 데이터 품질(P1) → 인덱싱/청킹 구조(P2 전반) → 검색 파라미터(P2 후반) → 비용(P3) → 경험(P4).
3. **청킹 먼저, 파라미터 나중**: 7·9·5로 청크 구조 확정 후 12·13 튜닝(재청킹이 인덱스·chunk_id·gt를 무효화).
4. **튜닝은 held-out에서 확정**: 12·13은 반드시 독립셋 지표로. 현 평가셋 과적합 금지.
5. **축 공유**: 근접중복(4)·표 반환(9)·부모자식(5)의 섹션/당사자/신청경로 축을 **하나로 통일**해 중복작업·오염을 방지.

## 6. 미해결 결정 사항 (팀 합의 필요)

- **항목 10 UI 방향**: 기존 답습 vs 독자 UI — 리소스·포트폴리오 목적에 따라 상충. 조기 결정 권장(P4 범위 좌우).
- **항목 13 교체 임계**: 파인튜닝 변형이 base 대비 얼마 이상 개선해야 교체할지(인덱스 재구축 비용 대비) 기준 사전 합의.
- **항목 2 구정보 정책**: 필터로 숨길지, 시점 라벨로 노출할지 — 정책 결정 후 구현.
