# 평가 수합 (eval / GT handoff)

각자 브랜치에 흩어진 **평가 스크립트와 GT(정답셋)** 중 가장 정확한 버전을 골라
하나로 합치기 위한 제출 디렉토리.

---

## 파일명 규약 — **1인 1파일**

```
docs/handoff/eval_<이름>.md      # 예: eval_유상.md · eval_규남.md · eval_경은.md · eval_현욱.md
```

**공용 파일 하나를 여러 명이 고치지 않는다.** 각자 자기 브랜치에서 자기 이름 파일만
만들면 병합 시 충돌이 0이다(서로 다른 파일이므로). 공용 파일에 모두가 쓰면
브랜치를 합칠 때마다 같은 줄에서 충돌한다.

## 작성 절차

1. `eval_TEMPLATE.md`를 복사 → `eval_<본인이름>.md`
2. **자기 브랜치에서** 부록 A의 명령을 그대로 실행해 값을 채운다
3. 커밋 → 푸시 (커밋은 각자 직접)
4. 수합 담당이 모든 제출서를 모아 **파일 단위로** 정본을 판정한다

## 채우는 사람이 지킬 것

- **실행해서 채운다.** 기억·추정으로 쓴 수치는 수합에서 기각된다.
- **모르면 `미측정` / `미확인`으로 쓴다.** 빈칸은 0으로 읽힐 수 있다.
- **폐기한 파일도 적는다.** 다른 사람이 같은 파일명을 정본이라 주장할 수 있다.
- **캐비앗(§6)을 비우지 않는다.** 낙관편향을 숨기면 수합이 잘못된 정본을 고른다.
- **부록 B(수합 판정 규칙)는 수정하지 않는다.**

## 왜 코퍼스 지문을 매번 적는가

`chunks.jsonl`은 관리자 UI에서 크롤링·재청킹이 계속 돌면서 **움직이는 자산**이다.
청크 수가 다른 브랜치끼리는 hit@k를 직접 비교할 수 없다 —
같은 셋이라도 코퍼스가 다르면 다른 수치가 나온다.
그래서 **모든 수치에 청크 수 + 파일 해시를 붙인다.** 지문이 다르면 비교 대상이 아니라
재측정 대상이다.

## 산출물

수합 담당이 제출서들을 읽고 만드는 것:

- 파일 단위 정본 판정표 (GT / eval 스크립트 / 파라미터 세트)
- 동일 지문 재측정이 필요한 항목 목록
- 각 제출서 §8 미결 사항의 통합 결정 목록
