# FAQ 도메인 분류 — 라우팅 모델 연결

> **범위**: FAQ 청크의 BF 태깅을 부모 문서 상속에서 라우팅 모델로 전환.
> **이 단계에서 하지 않는 것**: 라우터 정확도 측정, 임계값 튜닝, 검색 파라미터 조정, 일반 청크 확장, 청킹 로직 변경.
> **작성**: 2026-08-14

---

## 0. 이 문서의 핵심 원칙

**개별 청크의 BF 값을 손으로 고치지 않는다. 결정론 로직만 고친다.**

결과가 이상하면 그 청크의 값을 바꾸는 게 아니라, 그런 결과가 나온 **규칙**을 찾아 고치고 전체를 재실행한다.

| | 허용 | 금지 |
|---|---|---|
| 수정 대상 | 질문 추출 규칙, 정규화 규칙, `is_board()` 필터 조건, MSP 임계값 | 개별 청크의 `bf` 값 |
| 결과 | 재실행하면 같은 값이 나옴 | 재크롤 시 재현 불가 |

`_nramtaply_bf(i)`가 만들어진 경로가 후자다. 사람의 개별 판단이 코드에 박혀서, 신규 FAQ가 생기면 다시 사람이 손대야 하는 구조가 됐다. 같은 실수를 `bf_map`에서 반복하지 않는다.

**`source: manual` 값은 이 단계에서 생성하지 않는다.**

---

## 1. 문제

### P1. 부모 태그 상속이 게시판에서 틀림

FAQ 청크의 BF는 breadcrumb·URL 규칙으로 부모 문서 태그를 상속받는다. 통합 게시판(`-cm-bbs-`)은 한 페이지에 여러 업무 Q&A가 섞이므로 문서 단위 태그가 맞을 수 없다.

### P2. 게이트가 오류를 보존함

`FAQ_MARGIN` / `FAQ_RETAG_GATE`는 키워드 재태깅에 확신이 없으면 원 태그로 롤백한다. 원 태그가 틀린 값이므로, 게이트가 보호하는 것은 정확도가 아니라 오류다.

### P3. `FAQ_BF_OVERRIDE`가 청크 순번에 조인돼 있음

```python
def _nramtaply_bf(i):
    if i <= 5: return "예금자보호제도"
    return "예금보험금 안내"
```

`split_faq()`는 Q&A 단위로 자르므로 FAQ 항목이 하나 추가·삭제되면 경계가 통째로 밀린다. 에러 없이, 재크롤마다, 조용히 틀린다.

### P4. 사람의 판단이 코드에 박혀 있음

수작업 태깅이 함수로 들어가 있어, 신규 FAQ가 생기면 코드를 고쳐야 한다. 관리자 파이프라인 자동화 원칙과 충돌한다.

---

## 2. 아이디어

### I1. FAQ에만 라우터 적용

FAQ 청크는 질문 문장을 보유하므로 라우터 학습 분포(질문 → 업무)와 일치한다. 일반 청크는 본문뿐이라 도메인 시프트가 발생하므로 제외한다. 대상은 `is_board()` 판정 청크로 한정.

### I2. 조인 키는 순번이 아니라 질문 정규화 hash

`qhash = hash(normalize(질문문장))`.

질문 텍스트가 유지되면 순번이 밀려도 매핑이 따라오고, 질문이 수정되면 hash가 바뀌어 미매핑으로 드러난다. P3의 무성 오류가 사라진다.

### I3. BF를 코퍼스에서 분리

```
청킹 → chunks.jsonl        (결정론, 소스 무수정)
          ↓ qhash 조인
       bf_map.jsonl         (라우터 산출, 커밋 대상)
```

`doc_attachments.json` · `link_registry`와 같은 패턴. `chunks.jsonl`을 건드리지 않으므로 청킹 파이프라인이 그대로 유지된다.

### I4. 저신뢰는 `null`, 부모 태그로 롤백하지 않음

MSP가 낮으면 `bf = null`. 부모 태그는 틀렸다고 이미 아는 값이므로 되돌릴 이유가 없다. BF는 soft 부스트라 null이면 부스트를 못 받을 뿐 검색에서 배제되지 않는다. 질의측 `classify_query_bf()`가 마진 미달 시 `None`을 반환하는 규약과 대칭.

### I5. 재현성은 버전 기록으로 확보

`bf_map`에 `model`·`msp`·`labeled_at`을 함께 기록하고 산출물을 커밋한다. 재크롤 시 `content_hash`가 불변이면 재추론하지 않고 기존 값을 재사용하므로, 정상 재크롤에서 사람 개입이 발생하지 않는다. 모델을 교체할 때만 전체 재라벨 + diff.

## 3. 구현 범위

**변경**

- `bf_map.jsonl` 생성 (신규 산출물)
- 검색 단계에서 FAQ 청크의 BF를 `bf_map` 조인으로 조회

**미변경**

- `chunk.py` 청킹 로직, `CHUNK_SIZE` / `OVERLAP`
- `chunks.jsonl` 스키마 및 내용
- 일반(비게시판) 청크의 BF
- `search()` 시그니처, RRF·부스트 계수
- GT 파일

**후속 (이 단계 아님)**

- `FAQ_MARGIN` / `FAQ_RETAG_GATE` / `FAQ_BF_OVERRIDE` 제거
- 라우터 정확도 측정, θ 결정
- 일반 청크 확장

## 4. 입출력

**입력**: `chunks.jsonl`, 라우터 체크포인트(로컬)

**출력**: `bf_map.jsonl`

```jsonl
{"qhash":"...", "chunk_id":"...", "question":"...",
 "bf":"예금보험금 안내", "msp":0.94,
 "model":"...", "source":"router", "labeled_at":"..."}
```

`bf`는 6개 BF 중 하나 또는 `null`. `source`는 이 단계에서 항상 `router`.

---

## 5. 처리 순서

1. `is_board()` 청크 필터
2. 각 청크에서 질문 문장 추출 → `qhash`
3. 질문 문장을 라우터에 입력 → 예측 BF + MSP
4. MSP 미달 시 `bf = null`
5. `bf_map.jsonl` 기록

질문 추출이 실패한 청크는 `bf_map`에 넣지 않고 목록으로 남긴다. 추측으로 채우지 않는다.

## 6. 검증 — 파이프라인이 도는지만 본다

라우터 예측값의 옳고 그름을 판정하는 단계가 아니다. 아래 항목만 확인한다.

| # | 확인 | 이상 시 고칠 대상 |
|---|---|---|
| V1 | 라우터 라벨 표기가 6개 BF 명칭과 매핑되는가 | 라벨 매핑 테이블. **불일치 시 중단** |
| V2 | 질문 문장이 제대로 뽑히는가 | 질문 추출 규칙 |
| V3 | 추출 실패 청크가 몇 건인가 | 추출 규칙 폴백 |
| V4 | `qhash` 충돌이 있는가 | 정규화 규칙 |
| V5 | 대상 청크 수가 `is_board()` 예상과 맞는가 | 필터 조건 |
| V6 | 한 문서에서 청크마다 BF가 다르게 나오는가 | — (**정상 동작**) |
| V7 | `null` 비율이 과도하지 않은가 | MSP 임계값 |

**V6은 실패가 아니다.** `selectFaqNramtAply`가 그 사례이며, 문서 단위로 통일하려 해서는 안 된다.

## 7. 주의

- **라벨 매핑 오류는 조용히 틀리는 유형이다.** 매핑이 확인되지 않으면 진행하지 않고 중단한다.
- **질문 문장만 입력한다.** 청크 전문을 넣으면 분포가 달라져 라우터 성능 근거가 사라진다.
- **`chunks.jsonl`을 수정하지 않는다.** BF는 별도 레이어에만 기록한다.
- **개별 청크 값을 고치지 않는다.** 0절 원칙. 이상하면 규칙을 고쳐 전체 재실행한다.

## 9. 이 단계가 선행조건인 이유

- **미수령금 recall 0.532의 원인 규명** — 청크 부재인지 태깅 오류인지 지금은 구분되지 않는다.
- **셋 B(청크 역생성 GT) 생성보다 앞서야 한다** — 셋 B는 청크 메타를 근거로 라벨을 확정하므로, 태깅이 틀리면 틀린 라벨이 대량 생산된다.
