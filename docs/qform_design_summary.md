## 0. 왜 이 작업을 하는가 — 지난 대화와의 연결

이전 대화에서 짚었던 문제(§ `docs/mentoring_01_followup_plan.md`)를 다시 떠올리면: 지금 평가셋(`gt_docs`)은 **문서 단위**로 정답을 인정하는데, 실제 검색·답변은 **청크 단위**로 이루어져서 "같은 문서 안 엉뚱한 청크가 뽑혀도 정답 처리"되는 간극이 있었다. `qform_v1_리뷰시트.html`의 표현을 빌리면 이건 결국 **"슬롯(분기 조건)을 못 채우면 엉뚱한 청크가 뽑힌다"**는 문제이기도 하다. 오늘 논의는 이 간극을 메우기 위해 "질문에서 어떤 조건을 놓치면 답이 틀리는가"를 예솜24라는 실제 서비스형 챗봇을 직접 만져보며 역으로 알아내는 작업이었다.

## 1. 예솜24 분기 트리 분석 — 무엇을 관찰했나

### 1-1. 조사 방법
예솜24(`https://pubkbot.kdic.or.kr/chatbot.html`)를 **버튼을 안 누르고 자연어 질문만으로** 검색했다. 챗봇이 "질문하신 의도가 명확하지 않았어요"로 실패하면 유사어·챗봇이 제안한 문구로 재검색했다. `yesom_qa.jsonl`의 실제 이동 경로(`yesom_path`) + `chunks.jsonl`의 FAQ 데이터 + 라이브 응답을 교차 검증했다.

### 1-2. 핵심 동작 방식
예솜24는 버튼 클릭에 분기가 달린 게 아니라, **질문의 의미를 검색해 특정 노드로 이동한 뒤, 그 노드가 답변 말미에 보여주는 "관련 칩(chip)"이 곧 하위 분기**가 되는 구조다. 즉 칩 목록 = 그 시점에서 시스템이 알고 싶어하는 다음 조건.

### 1-3. 정답을 정확히 내기 위한 4가지 분기 축

| 축 | 정의 | 값(예) |
|---|---|---|
| ① 업무성 분기 | 업무의 세부 갈래 | 안내/종류/신청, 이자시기, 신고방법 등 |
| ② 자격 분기 | 신청 자격 | **본인 → 대리인** |
| ③ 주체(주어) 분기 | 신청 주체(당사자) | 송금인 본인·대리인·미성년자(→친권자)·군인·사망 송금인·국외거주/외국인·법인단체(→대표/직원)·비법인단체(→대표/직원) |
| ④ 조건 분기(8절에서 추가 확인) | 절차와 무관한 **자격·한도 조건** | 대상금액·신청기한·제외사유·수수료·종류·신고자격 등 |

대부분 업무에 ③ 아래로 **신청수단 분기**(인터넷/방문/우편/이메일)도 따로 존재한다.

**2계층 구조**: 모든 업무는 `[구조 분기: 업무·자격·주체·수단]` + `[조건 분기: 자격·금액·기한·종류 등]`의 2계층으로 나뉜다. 앞으로 나올 슬롯 스키마도 이 2계층 구분을 그대로 따른다.

### 1-4. 업무별 트리 (분기 최다 → 최소 순)

**① 착오송금 반환 청구 — 분기가 가장 많음**
```
착오송금 반환 청구
├─ [주체] 착오송금인(송금인) → [수단] 인터넷/방문/청구서류 → [자격] 본인→대리인
│                                    → [주체] 대리인일 때: 미성년자·군복무자·국외거주/외국인·
│                                       법인단체 대표·법인단체 직원·비법인단체 대표·비법인단체 직원
├─ [주체] 착오송금수취인(잘못 받은 사람) → 이의제기 / 이체오류수수료환급 (각각 인터넷·방문)
└─ 착오송금반환지원 절차
```
실측: "보낸 사람인데 반환받고 싶어요" → 칩 `인터넷 청구` `방문 청구` `청구 서류`. "대리인이 청구할 때 서류" → 칩 7종(위 대리인 목록).

**② 예금보험금 안내**
```
예금보험금 안내
├─ 지급되는 경우
├─ [업무] 종류 → 가지급금 / 개산지급금
└─ [업무] 청구 → [수단] 인터넷/방문/청구서류
                     → [주체] 청구서류: 예금자본인·대리인·미성년자·군복무자·사망예금자·국외거주/외국인·법인단체
```

**③ 고객 미수령금 청구**
```
고객 미수령금 청구
└─ [수단] 인터넷/방문/청구서류
      → [주체] 예금자본인·대리인·미성년자(→친권자 확인증명/합의서)·사망예금자·국외거주/외국인·군인·법인단체
```

**④ 예금자보호제도**
```
예금자보호제도
├─ 보호 대상 금융회사
├─ 보호 대상 금융상품 → [권역] 보호O/X × 은행·보험사·저축은행·종금사·투자매매중개업
└─ 보호 한도 (1인당 1억원)
```

**⑤ 숨은보험금 신고**
```
숨은보험금 신고
├─ [수단] 신고방법 → 이메일/인터넷/우편/방문
├─ 처리절차 · 포상금(최고 30억, 회수기여금 5~20% 차등) · 신원 비밀보장 · 정보취득경위
```

**⑥ 채무조정 안내**
```
채무조정 안내
└─ [업무] 채무조정 금액 / 채무 확인 방법 / 청구 부가 사유 / 청구 종류
```

### 1-5. 실패 로그가 알려주는 것 (가장 중요한 인사이트)

챗봇은 **노드가 존재해도 표현이 다르면 실패**한다("질문하신 의도가 명확하지 않았어요"). 이게 답변 정확도의 최대 병목이다.

| 실패한 질문(표현) | 결과 | 성공한 재검색 표현 |
|---|---|---|
| "숨은보험금 이메일 신고" | 실패 | "숨은보험금 어떻게 신고하나요" |
| "채무조정 금액" | 실패 | "채무 조정이란?" |
| "채무조정 청구 부가 사유" | 실패 | "채무 조정 청구 부가능한 경우는?"(챗봇이 직접 제안) |
| "착오송금 잘못 받은 사람" | 실행만 반환 | "착오송금 수취인 이의제기" |

시사점:
1. **직접 노드형 "~~이란?/~~안내" 표현**을 선호 — 실제 개인이도 칩(하위분기)으로 바로 내려간다.
2. **실패 시 재질문 제안 문구가 곧 정답 노드의 표준 표현** — 학습데이터 사전 구축에 재사용 가능.
3. **주체(대리인 포함)·수단 분기는 명시적 칩 메뉴** — "본인/대리인 + 주체 + 수단" 3중 슬롯을 채워야 최소 답(리프)에 도달.
4. 리프 노드 답변에는 **양식 파일 다운로드 링크**가 함께 제공된다.

### 1-6. 조건 분기 확장(8절) — 절차와 무관한 자격·한도 조건

1~6절은 "어떻게 신청하는가"의 구조 분기다. 이와 별도로 "신청할 자격이 되는가/얼마까지인가" 같은 조건 분기가 있는데, 이건 **칩 메뉴에 노출되지 않고 자연어로만 도달**한다.

| 업무 | 조건 분기 핵심 |
|---|---|
| 착오송금 | 대상금액 5만원~1억원(시행일별 상이), 청구기한 착오송금일로부터 **1년 이내**, 보이스피싱 제외, 계좌송금만 인정(연락처송금 제외) |
| 예금보험금 | 종류 5가지(예금보험금/가지급금/개산지급금/파산배당금/개산지급금의연금), 예금+대출 상계(시효), 보증채무 해소 후 청구, 사망 시 상속인 방문청구 |
| 고객 미수령금 | 종류 3가지, **소멸시효가 종류별로 다름**(가지급금·개산지급금=지급종료일 / 보험금=지급개시일부터 5년 / 배당금 등=통산 10년). ⚠️ `chunks.jsonl`에 미수령금 FAQ가 **0건** — 챗봇엔 있는데 크롤 데이터에 없음(가장 자주 반복되는 액션아이템, §7 참고) |
| 숨은보험금 | 실명 원칙(익명·가명은 포상금 미지급), 신고자격 제한 없음(재외국민·외국인도 가능) |
| 채무조정 | 기존 4항목 외에 **사후 재산조사**(연 1회 이상) 존재 |
| 예금자보호 | 개인/법인 유형, 상품별 별도한도(퇴직연금·연금저축·사고보험금=별도 1억), 명의분산·회사합산 각각 1억, 외화예금/보험해약환급금 등 상품 특성 |

**챗봇 라우팅 실패 = RAG의 기회**: FAQ에는 답이 있는데 예솜24가 라우팅에 실패하는 지점들 — 예금자보호(여러계좌 합산·예금대출상계·인수/인가), 채무조정("신청 되나요?" 재질문 유도, 인증서 오류 등 기술 FAQ). 우리 시스템이 이 지점을 커버하면 바로 우위를 보일 수 있다.

## 2. RAG 설계 해결안 — 관찰을 아키텍처로 옮기기

### 2-1. 기존 결론에 대한 재평가

기존 설계 문서(`RAG_설계_논의_요약.md`)의 방향(**LLM Query Understanding + Metadata-aware Hybrid RAG, 멀티턴은 보조**) 자체는 유효하다고 재확인했다. 아래 4가지는 폐기가 아니라 **구체화·수정**이다.

| # | 기존 우려/결론 | 보강·수정 방향 |
|---|---|---|
| 1 | 룰베이스로 보일까 우려 | "실패 시 임베딩 폴백이 존재한다"로 관점 전환 |
| 2 | 슬롯 스키마가 표면적(applicant_type/role/proxy 정도) | 업무별로 슬롯을 분리 + 2단계 라우팅 |
| 3 | "항상 멀티턴은 아니다"는 원칙만 있음 | 질문을 유형별로 명문화(단정형/조건형/절차형/요구형) |
| 4 | Metadata Filtering + "슬롯 추출 가능" | 하드필터는 최소화, 소프트부스트+리랭커 위주로 전환 |

### 2-2. "룰베이스처럼 보인다" 우려에 대한 답

비교 기준을 "메타필터를 쓰는가"가 아니라 **"분기를 누가 설계하는가"**로 바꿔서 봐야 한다.

- 예솜24는 **사람이 미리 짜둔 시나리오 노드 + NLU 인텐트**다. 표현이 조금만 벗어나면 완전히 실패한다(1-5절 실패 로그).
- 우리 시스템은 분기(슬롯)를 **크롤 데이터에서 자동 도출**하고, LLM이 슬롯을 채우되 **슬롯이 비거나 틀려도 시맨틱 검색으로 우아하게 대체(degrade)**된다.

즉 진짜 방어선은 "룰베이스냐 아니냐"가 아니라 **"실패했을 때 무너지는가, 완만하게 저하되는가"**다. 예솜24의 실패 로그가 곧 우리 프로젝트가 우위를 증명할 1차 증거다.

### 2-3. 슬롯 스키마를 업무별로 분리 + 2단계 라우팅 (가장 중요한 결정)

단일 평면 슬롯으로는 안 된다. 1절에서 봤듯 업무마다 축이 다르다(착오송금엔 party/qualification/subject 축이 있지만 예금자보호엔 본인/대리인 축 자체가 없음). 그래서:

1. **1단계 분류**: `business_function`(어느 업무인지) + `question_type`(질문 유형)만 먼저 판별.
2. **2단계 슬롯 채움**: 1단계 결과에 맞는 **업무 전용 슬롯 스키마**를 로드해서 필요한 슬롯만 채운다.

`yesom24_분기점_트리분석.md`(1절)가 이 업무별 슬롯 정의의 원재료 역할을 한다.

### 2-4. 슬롯·멀티턴은 "절차형/요구형" 질문에만 — 질문유형 게이트

멀티턴(되묻기)을 질문 유형으로 걸러야 매번 예솜24 같은 시나리오 챗봇처럼 보이지 않는다.

| 질문유형 | 예시 | 처리 |
|---|---|---|
| 단정형 | "예금보험금이 뭔가요?" | 슬롯 0 → 바로 검색, 되묻지 않음 |
| 조건형 | "보호한도 얼마?", "보이스피싱도 되나요?" | 슬롯 0 → 바로 검색, 되묻지 않음 |
| 절차형·요구형 | "착오송금 서류 뭐 필요해?" | subject/method 슬롯이 비면 **1회만** 되물음 |

핵심: **되묻기는 절차형·요구형에서 슬롯이 실제로 비었을 때만** 발동한다. 조건형·단정형은 절대 되묻지 않는다.

### 2-5. 메타데이터는 "하드 필터" 최소화 → 소프트부스트 + 리랭커

슬롯 추출이 틀렸을 때 하드 필터를 걸면 정답 문서 자체가 통째로 배제된다. 그래서:

- **하드 필터**는 신뢰도가 가장 높은 `business_function`에만 건다.
- `subject`/`method`/`condition` 같은 나머지 슬롯은 필터가 아니라 **리랭커 가중치(소프트부스트)**로만 반영한다(일치 시 점수 가산).
- 슬롯 신뢰도가 낮으면 **필터 없이 검색 → 리랭커가 나중에 정리**하는 폴백 경로를 둔다.
- **조건형 질문엔 Cross-encoder 리랭커가 사실상 필수**다 — 규정 예외조항은 메타데이터로 못 잡고 본문에만 있기 때문에, 벡터 검색 + 리랭커 조합이 잡아줘야 한다.

### 2-6. 첨부문서 반환 — Qform과는 별개 문제, 이미 인덱싱 설계로 해결됨

"한 청크에 여러 첨부가 달려서 대량 반환"되는 문제의 원인은 크롤 단위가 **페이지(`parent_doc_id`)**라 여러 서식이 한 문서에 뭉쳐 있어서다. 이건 Query Understanding(Qform)이 아니라 **인덱싱(태깅) 설계**로 푼다.

- 첨부는 **임베딩하지 않는다**(빈 어순 검색에 헛 소환되는 걸 방지) → `attachment_id`를 부여한 별도 계층(**Tier B**)로 관리.
- 반환은 벡터 유사도가 아니라 **해석된 슬롯(subject/method/condition)과 메타데이터를 JOIN**해서 결정한다.
- **공통 서식**(신청서·동의서 등)은 `subject=공통` 와일드카드로 항상 포함.
- **표 데이터**(부보금융회사 목록 등)만 본문처럼 임베딩(**Tier A**, 주기적 갱신).

(세부 스키마는 `attachment_tagging_schema.md` / `attachment_tagging_template.csv` 참조 — 이번 문서 범위 밖)

### 2-7. 최종 권장 아키텍처

```
사용자 질문
   ↓
[1] LLM Query Understanding
     ├─ business_function 분류
     └─ 질문유형(단정형/조건형/절차형/요구형) 판별
   ↓
[2] 업무별 Structured Output (Qform 슬롯 채움)
   ↓
[3] (절차형·요구형 & 슬롯 미결정 시에만) 최소 멀티턴 1회
   ↓
[4] Retrieval
     ├─ 하드 필터: business_function (고신뢰만)
     ├─ Hybrid: Vector + BM25
     └─ 소프트 부스트: subject/method/condition (리랭커 가중)
   ↓
[5] Cross-encoder 리랭커 (조건형 질문엔 사실상 필수)
   ↓
[6] 첨부 JOIN: 해석된 슬롯 → attachment_index (공통 와일드카드 포함)
   ↓
[7] LLM 답변 생성 (본문 + 필요한 첨부만)
```

풀어서 읽으면: **①질문이 들어오면 먼저 "무슨 업무고 어떤 종류의 질문인지"만 빠르게 판정한다 → ②그 업무에 맞는 질문지(Qform)를 꺼내 LLM이 질문 안에서 알아낼 수 있는 만큼 자동으로 채운다 → ③꼭 필요한데 못 채운 항목이 있고, 그게 "어떻게/뭐가 필요해"류 질문일 때만 딱 한 번 되묻는다 → ④검색은 업무만 확실히 걸러내고(하드필터), 나머지 정보는 순위를 살짝 조정하는 데만 쓴다(소프트부스트) — 그래야 슬롯이 틀려도 정답이 아예 사라지지 않는다 → ⑤조건이 까다로운 질문은 리랭커가 한 번 더 정밀하게 훑는다 → ⑥첨부파일은 벡터 검색이 아니라 "이 사람이 어떤 서류가 필요한 상황인지" 해석된 슬롯 값으로 목록을 조인해서 결정한다 → ⑦마지막에 LLM이 본문과 필요한 첨부만 골라 답한다.**

### 2-8. 차별점과 검증 계획

- **진짜 moat(경쟁우위)**: 크롤 → 정제 → **태깅 자동화** → 하이브리드 파이프라인 → API RAG. 멀티턴은 부속 기능일 뿐 핵심이 아니다.
- **정량 비교 명제**: "예솜24가 실패하는 조건 질문을 우리는 커버한다." 실측 실패 사례 — 예금자보호(여러계좌 합산·예금대출상계·인수/인가), 채무조정("신청 되나요?" 재질문 유도, 인증서/시스템 기술 질문).
- **평가**: 기존 `testset_natural_*.jsonl`의 `gt_docs`로 Retrieval 정확도(Recall@k) 측정. 슬롯 스키마는 통합 트리를 정답 라벨 삼아 검증.
- **우선순위**: ①미수령금 FAQ 크롤 보강(현재 0건) ②예금자보호·채무조정 실패질문 커버 ③착오송금 사후관리 4종(철회·해지·계좌변경·대리인변경) 노출.

## 3. Qform 스키마 — 실제로 무엇을 채우는가

**Qform**은 "검색 전에 LLM이 질문을 분석해서 채우는 Structured Output 슬롯 모음"이다. 예솜24 분기 트리(1절)를 근거로 설계했고, **2단계 구조**다: (Stage1) 공통 라우터 슬롯으로 업무·질문유형만 먼저 판별 → (Stage2) 그 업무 전용 슬롯 스키마를 로드해서 세부 항목을 채운다.

### 3-1. 슬롯 공통 속성 5가지

모든 슬롯은 다음 속성을 가지며, 이 속성값이 검색 단계에서 실제로 무엇을 하는지를 결정한다.

| 속성 | 값 | 의미 |
|---|---|---|
| `cardinality` | single / multi | 하나만 고를 수 있는지, 여러 개 가능한지 |
| `role` | routing / hard_filter / soft_boost / **condition_retrieval** | 아래 §3-2 참고 |
| `nullable` | true / false | 못 채워도 되는지 |
| `ask_if_missing` | true / false | 비었을 때 되물을지 (**절차형·요구형에서만 발동**) |
| `maps_to` | 메타데이터 필드명 | 청크/첨부 태깅 필드와의 조인 키 |

### 3-2. `role`의 실제 의미 — JSON 스키마 기준 4가지

`qform_schema.json`에는 산문 설계 문서(`Qform_메타데이터_설계.md`)에 없던 4번째 role이 명시돼 있다: `condition_retrieval`.

- **`hard_filter`**: `business_function` **딱 하나만**. 검색 공간을 아예 좁힌다 — 틀리면 정답이 통째로 사라지므로 가장 신뢰도 높은 슬롯에만 허용.
- **`soft_boost`**: 나머지 대부분(qualification/subject/method 등). 필터링이 아니라 리랭커 가중치로만 반영 — 슬롯이 틀려도 정답이 사라지지 않는다.
- **`routing`**: `question_type`, `sub_task` 등. 검색 자체보다 "다음에 뭘 할지"(되물을지, 어느 업무 스키마를 쓸지)를 결정.
- **`condition_retrieval`**(신설): `eligibility`/`condition`/`limit_condition` 등 금액·기한·제외사유류 슬롯. **필터도 부스트도 아니고, 본문(청크 텍스트) 검색 대상**일 뿐이다 — 즉 이 값들은 슬롯으로 뽑아서 "판정"하는 데 쓰지 않고, 그냥 관련 청크를 찾는 검색어 성격으로만 쓴다(§3-6, §4-3에서 이유 설명).

원칙: **`hard_filter`는 `business_function`뿐**. 되묻기(`ask_if_missing=true`)는 절차형·요구형의 결정 슬롯에만 건다.

### 3-3. Stage 1 — 공통 라우터

```json
{
  "business_function": null,   // enum, hard_filter, nullable=false
  "question_type":     null,   // enum, routing
  "sub_task":          null    // enum(업무별), routing
}
```

- `business_function` 후보: 착오송금 반환 청구 / 예금보험금 안내 / 고객 미수령금 청구 / 예금자보호제도 / 숨은보험금 신고 / 채무조정 안내 (6종)
- `question_type` 후보 4종:

| 유형 | 예시 | 처리 |
|---|---|---|
| 단정형 | "~~이 뭔가요" | 슬롯 0, 바로 검색, 안 되물음 |
| 조건형 | "~~는 되나요/얼마" | 슬롯 0, 바로 검색, 안 되물음 |
| 절차형 | "어떻게 청구하나요" | 수단/자격 슬롯 비면 결정 시 1회 되물음 |
| 요구형 | "서류 뭐 필요해요" | 주체/수단 슬롯 비면 결정 시 1회 되물음 |

(§2-4의 3분류를 여기서 절차형/요구형 두 개로 더 세분화한 것 — 동작은 거의 같지만 채우는 슬롯 종류가 다르다.)

### 3-4. 공통 재사용 슬롯 (여러 업무가 같이 씀)

| 슬롯 | cardinality | 후보 |
|---|---|---|
| `qualification` | single | 본인 / 대리인 |
| `subject` | multi | 본인·대리인·미성년자·군복무자·사망예금자·국외거주/외국인·법인및단체·비법인단체·**공통(와일드카드)** |
| `subject_role` | single | 대표 / 직원 (법인·비법인단체일 때만) |
| `method` | multi | 인터넷(온라인) / 방문 / 우편 / 이메일 |

### 3-5. Stage 2 — 업무별 슬롯 (6개 업무)

**착오송금 반환 청구**: `party`(송금인/수취인) · `sub_task`(반환청구/이의제기/이체오류수수료환급/청구철회/매매계약해서/수령계좌변경/대리인변경) · 공통슬롯(qualification/subject/subject_role/method) · `eligibility`(**condition_retrieval**: amount_krw, days_since_remit, remit_channel, exclusion)

**예금보험금 안내**: `sub_task`(지급되는경우/종류/청구) · `payment_kind`(가지급금/개산지급금) · 공통슬롯 · `condition`(**condition_retrieval**: has_loan, has_guarantee)

**고객 미수령금 청구**: `sub_task`(종류/청구/청구서류) · `money_kind`(예금보험금/파산배당금/개산지급금의연금) · `claim_period_kind`(소멸시효 조회) · 공통슬롯

**예금자보호제도** (청구 절차가 없어 qualification/method 미사용): `sub_task`(보호대상금융회사/보호대상금융상품/보호한도) · `depositor_type`(개인/법인/제외기관) · `product_domain`(은행/보험사/저축은행/종금사/투자매매중개업) · `product`(일반예금/외화예금/퇴직연금/연금저축/사고보험금/해약환급금/펀드류) · `limit_condition`(**condition_retrieval**: 일반한도/별도한도/명의분산/회사합산/여러계좌합산/예금대출상계/인수인가) — ⚠️ 여러계좌합산·예금대출상계·인수인가는 예솜24 실패 지점(1-6절)이라 RAG가 커버해야 할 우선 대상.

**숨은보험금 신고**: `sub_task`(신고방법/처리절차/포상금/비밀보장/정보취득경위/제외) · `report_method`(이메일/인터넷/우편/방문) · `reporter_type`(내국인/재외국민/외국인, 자격 제한 없음) · `anonymity`(실명/익명·가명)

**채무조정 안내**: `sub_task`(금액/확인방법/청구부가사유/청구종류/사후재산조사/부채증명) · `qualification`(본인/대리인) · `method`(방문 — 부채증명서 발급은 방문만)

### 3-6. Qform → 메타데이터 조인

| Qform 슬롯 | 청크/첨부 메타 필드 | Retrieval 역할 |
|---|---|---|
| `business_function` | `business_function` | hard_filter |
| `sub_task` | `sub_category` | routing + soft_boost |
| `qualification` | `qualification`(신설 예정) | soft_boost |
| `subject`(+role) | `subject`(+`subject_role`, 신설 예정) | soft_boost, 공통 와일드카드 |
| `method` | `method`(신설 예정) | soft_boost |
| `eligibility`/`condition`/`limit_condition` | `condition`(신설 예정) | **필터 아님** — Tier A 본문 검색 대상 |
| (첨부 반환) | `attachment_id`, `retrieval_tier=B` | 슬롯 해석 결과로 JOIN |

### 3-7. 채움 예시

**Q. "법인 직원이 착오송금 반환 인터넷으로 청구하려면 서류 뭐 필요해?"**
```json
{
  "business_function": "착오송금 반환 청구", "question_type": "요구형",
  "party": "송금인", "sub_task": "반환청구", "qualification": "대리인",
  "subject": ["법인 및 단체"], "subject_role": "직원", "method": ["인터넷"]
}
```
→ 슬롯이 충분히 채워짐 → 되묻지 않음 → `subject=법인 및 단체` + 공통(와일드카드) 첨부를 JOIN해서 반환.

**Q. "예금 보호한도 세금 빼기 전 기준이야?"** (예솜24가 실패하던 질문)
```json
{
  "business_function": "예금자보호제도", "question_type": "조건형",
  "sub_task": "보호한도", "limit_condition": "세전 세후"
}
```
→ 조건형이라 슬롯 없이 바로 시맨틱 검색(본문 세부조항) + 리랭커로 처리.

### 3-8. 설계 요약

- `hard_filter`는 `business_function`뿐, 나머지는 `soft_boost` → 슬롯을 잘못 뽑아도 정답이 배제되지 않는다.
- 조건형·단정형은 아예 안 되묻는다(슬롯 0). 절차형·요구형만 결정 슬롯을 1회 되묻는다.
- `eligibility`/`limit_condition` 같은 조건 슬롯은 필터가 아니라 **본문(Tier A) 검색 대상** — 세부 조항은 임베딩이 담당한다.
- 첨부는 슬롯 JOIN으로만 반환하고, 벡터검색 대상이 아니다. `subject=공통` 와일드카드로 공통양식은 항상 포함.

## 4. 리뷰 시트 — 이 설계에서 뭐가 검증됐고 뭐가 안 됐나 (현재 가장 중요한 파트)

`qform_v1_리뷰시트.html`은 위 Qform 설계(3절)를 팀원 두 명의 독립 초안(`qform_schema.json` + 동료의 `qform_문항설계_v0`)을 합쳐 검토한 문서다. 상단에 이렇게 못박혀 있다:

> **착안점 측정 3종(M1·M2·M3) 미완 → 구현 착수 보류**

즉 지금 시점의 공식 입장은 **"설계는 있지만, 아직 만들면 안 된다"**다. 판정 원칙은 단순하다: **근거 없으면 슬롯 없다.**

### 4-1. 슬롯을 세 레인으로 나눠서 판정

| 레인 | 의미 |
|---|---|
| **GATE** | 진입·되묻기 여부만 제어. 검색의 주역이 아님 |
| **RETRIEVAL** | 청크 메타 조인·부스트 변경 — **되묻는 가치가 검색 지표(hit@3)로 직접 측정되는 슬롯** |
| **CONTEXT** | 생성 프롬프트에만 주입 — 되물어도 검색 결과는 동일하고, 효과는 생성 단계에서만 나타남(그래서 지표를 검색/생성으로 분리해서 봐야 함, `mentoring_01_followup_plan.md` §2-6과 같은 문제의식) |

### 4-2. 슬롯별 현재 검증 상태 — "현재 분기점"의 실제 모습

| 슬롯 | 레인 | 상태 | 근거 |
|---|---|---|---|
| `business_function` | RETRIEVAL | **verified** | `classify_query_bf` 커버리지 71% · 정확도 99.1%. 미적중 22건 중 **8건**이 이 슬롯("불명" 처리) 관련 |
| `sub_task` | RETRIEVAL | **verified** | `FACET_BOOST` 실측: 0.00→hit@3 .935, **0.03→.945**(착오송금 .833→.889). 0.08은 부스트가 검색신호를 지배해 기각됨(rag.py:101과 일치하는 현재 운영값) |
| `party`(착오송금 전용) | RETRIEVAL | **verified** | 동일 `page_title`("유의사항")이 송금인·수취인 두 문서에 중복 존재해 제목만으론 구분 불가 → 이 슬롯이 실제로 문서를 갈라내는 근거 확인됨 |
| `method` | RETRIEVAL | **provisional** | `sub_category`가 인터넷/방문/우편/이메일을 문서 단위로 실제로 갈라내는지 미확인. `sub_task`와 같은 필드에 조인되므로 부스트 중복가산 여부 미결 |
| `qualification` | RETRIEVAL | **provisional** | "대리인"은 `MsdrprPossDcmntGudn`(대리인 전용 서류안내 문서)이 따로 있어 변별력 있지만, "본인"은 기본 문서와 동일해 변별력이 없는 **비대칭 슬롯** — 한쪽만 부스트할지 판단 필요 |
| `applicant_type`(미성년자/군복무자 등 8종) | CONTEXT | **unverified — 가장 중요한 미확인 항목** | 38개 문서 코퍼스에서 8종이 각각 별도 문서일 가능성은 낮음. 검증 없이 구현하면 "되묻는데 hit@3 무변동"이 되어 되묻기의 가치가 0으로 나올 위험 → **M3 게이트** |
| `question_type` | GATE | **provisional** | 미적중 22건을 4유형으로 분류할 근거가 아직 없음. 조건형 비중이 높으면 되묻기가 미적중에 도달하지 못해 Qform이 정확도 기능이 아닌 UX 기능이 됨 → **M2 게이트** |
| `trigger`(Qform 진입 여부) | GATE | **확정** | 진입 판단은 **하드코딩(버튼/키워드)만** 사용, LLM 판단은 그 이후 단계. 기존 `CLS_PROMPT`의 "모호" 라벨이 이미 이 역할을 겸하고 있어(`chain.py`), 신규 분류기를 얹으면 질문당 LLM 콜이 3회로 늘고 과거 LLM 분류기 오분류 전례(로그 id 19)도 있음 |
| `free_text` | CONTEXT | **확정** | 폼 마지막 자유입력 문항, 비워도 됨. 생성 프롬프트에서만 사용 — **검색 쿼리로 직렬화하는 것은 금지**(노이즈가 부스트를 훼손) |

### 4-3. 스키마에서 아예 배제한 항목 — "결론을 계산해야 하는" 조건

조건에 대해 시스템이 스스로 판정을 내려야 하는 축은 슬롯으로 받지 않기로 했다. 문서에 있는 결론 산식(예: "1억 초과니까 대상 아님")을 시스템이 대신 계산하면, 생성 프롬프트 규칙 1("참고문서에 없는 내용은 답하지 않는다")을 위반하게 된다.

- **착오송금 `eligibility` 필드**(amount_krw/days_since_remit/remit_channel/exclusion): 금액·경과일을 슬롯으로 받아 시스템이 판정하지 않는다. 조건 자체는 Qform을 거치지 않고 기존 `hybrid_bf` + (리랭커 확보 시) cross-encoder로 처리한다.
- **예금자보호제도 조건 슬롯 전체**(여러계좌합산/예금대출상계/세전세후/명의분산/회사합산): 실체적 판정이 필요해서 위험도가 높다. 예솜24가 실패하는 지점이라 데모 가치는 크지만, Qform이 아니라 검색·생성 품질 자체로 커버해야 한다. 개별사례 고정 문구·결정론 계산함수·`answer_checks` 정합체크 같은 안전장치가 먼저 갖춰져야 한다.

### 4-4. 착오송금 문항 흐름 예시 — 되묻기가 실제로 어떻게 생겼는가

슬롯을 단순히 곱하면 112리프로 폭발한다(subject 8종 × qualification 2 × method 4 × ...). 조기 종료와 조건부 활성화로 실제 리프를 15개 이하로 유지해야 한다는 게 원칙이다(**업무당 실질 리프 15개 초과 = 슬롯 축을 줄이라는 신호**).

| 문항 | 질문 | 선택지 | 노출 조건 |
|---|---|---|---|
| Q1 | 어떤 내용이 궁금하신가요? | 안내 / 반환청구 / 이의제기 / 이체오류수수료환급 | 안내→즉시 검색 종료, 이의제기·환급→당사자=수취인 고정, Q2 종료 |
| Q2 | 어느 쪽이세요? | 돈을 잘못 보낸 분(송금인) / 돈을 잘못 받은 분(수취인) | Q1=반환청구일 때만 |
| Q3 | 어떻게 청구하실 예정이신가요? | 인터넷청구/방문청구/청구서류가 궁금해요/아직 모르겠어요 | Q2=송금인 경로만 |
| Q4 | 누가 청구하시나요? | 본인 / 대리인 | Q2=송금인 경로만 |
| Q5 | 어떤 대리인이세요? | 미성년자/군복무자/국외거주·외국인/법인단체대표/법인단체직원/비법인단체대표/비법인단체직원 | Q4=대리인일 때만. **CONTEXT 레인이라 검색 지표에 반영 안 됨** |
| Q6 | 그 밖에 알려주실 내용이 있나요? | 자유입력, 비워도 됨 | 항상 마지막 |

**문항 설계 원칙 — 확인형("~ 맞죠?") 절대 금지, 선택형만 사용.** 되묻기는 본질적으로 확인 문장이라, 사용자가 무심코 "네"라고 답하면 틀린 슬롯이 사용자 승인까지 받은 채로 검색에 들어간다. 과거 로그(id 16)에서 "확인형 문구가 롤렛(단순 선택형)보다 위험하다"는 교훈이 나온 적이 있는데, 이게 되묻기 UI에도 그대로 적용된다.

### 4-5. 구현 전 필수 측정 — M1~M5 (전부 0콜, 무료)

착안점을 모른 채 구현하면 "이미 실측 데이터가 있는 리랭커(hit@1 .567→.707 개선 확인됨)보다 Qform을 먼저 할 이유"를 댈 근거가 없다. 그래서 세 측정을 통과한 뒤에만 구현에 들어가기로 했다.

| 측정 | 방법 | 게이트(통과 못하면?) |
|---|---|---|
| **M1** | 오라클 상태 확인 — 미적중 22건의 retrieval 슬롯(업무·세부주제·당사자·수단)을 **정답으로 직접 채워** 넣고 부스트를 적용했을 때 hit@3이 얼마나 오르는지 상한을 뽑는다 | 상한이 유의미하게 안 오르면 Qform은 검색 기능이 아니다 → 리랭커에 우선순위를 양보 |
| **M2** | 미적중 22건을 단정형/조건형/절차형/요구형으로 수동 분류 | 절차형·요구형 비중이 낮으면 되묻기가 애초에 미적중 문항에 도달하지 못함 → Qform을 UX·생성 기능으로 재포지셔닝 |
| **M3** | `applicant_type` 8개 값을 각각 검색어로 넣어봐서 `parent_doc_id`가 실제로 갈리는지 확인 | 안 갈리면 이 슬롯은 RETRIEVAL이 아니라 CONTEXT로 확정하고, 효과는 생성 단계 실측으로만 계속 본다 |
| M4 (구현 후) | 400건 회귀 테스트 — 게이트를 적용해 실행 후 오분류 지표와 hit@3 무변동 여부 확인 | 400건은 전부 단정형·단일 해석이라 **Qform의 이슥(가치)을 애초에 측정할 수 없음** — 회귀 안전망 역할만 담당 |
| M5 (유료) | 착오송금 5~10문항으로 새로 실제 시나리오 실행(hit@3 없이 정성 확인) | held-out이 아니면 낙관 편향을 명시해야 함(`HOLES.md` H12 — 평가셋 self-referential 문제와 동일 유형). **슬롯 스키마를 예솜24 트리로 채운 뒤, 그 트리로 다시 평가하는 것은 자기참조라 금지** — H12의 대칭 사례 |

### 4-6. 아직 사람이 판단해야 하는 것들

- **채움 주체**: 어디까지 LLM 추출(Structured Output)로 하고 어디부터 사용자가 폼에서 직접 고르게 할지, 슬롯별 `fill` 속성은 나눠뒀지만 기본값이 미정.
- **확인된 슬롯의 부스트 강도**: 사용자가 직접 답한 슬롯을 기존 0.03 그대로 둘지, 올릴지, 아예 하드필터로 승격할지. (0.08은 이미 기각된 값이라 무작정 올릴 수 없음)
- **부스트 중복 가산**: `sub_task`와 `method`가 같은 `sub_category` 필드에 조인될 때 부스트를 겹쳐 더할지.
- **슬롯 도출 방향**: 슬롯은 원래 코퍼스 메타데이터에서 도출해야 하고, 예솜24 트리는 슬롯 "정의서"가 아니라 **커버리지 갭 체크리스트**로만 써야 한다는 원칙 — 트리에서 그대로 슬롯을 뽑으면 트리에 있는 구멍(빠진 케이스)까지 그대로 상속하게 된다.
- **되묻기 문장 생성 방식**: 슬롯별 고정 템플릿 vs LLM 생성. 지연·콜 비용 차이가 있음(현재 RAG 평균 응답 5.0초, 되묻기가 2회 추가되면 체감이 크게 달라짐).
- **사실 확인 필요**: "미수령금 FAQ 크롤 0건"이 진짜 누락이 아니라 재태깅 로직의 결과일 가능성이 있다(`selectFaqNramtAply` 문서: 공통2·안내4·예금보험32로 재태깅됨, 미수령금으로 남은 게 0건). 재수집 전에 `chunks.jsonl` 실측 카운트를 다시 확인해야 한다.

## 5. 오늘 팀 논의 흐름 (시간순 — 아래로 갈수록 최근/확립)

원문 메모를 시간 순서 그대로 정리했다. 뒤로 갈수록 더 확정된 내용이다.

1. **분기점 조사 → 청크별 첨부문서 태깅** 아이디어로 시작: 신청서류처럼 개인이 던지는 질문을 LLM이 읽고 "회사/본인" 등으로 정리(포맷)한 뒤 맞는 양식을 찾아준다는 구상.
2. **상황 설명형 질의는 짧으면 Qform이 어려울 수 있다**는 우려 → 그래서 "개념 질문이냐 요구 질문이냐"부터 나누자는 아이디어가 나옴(이게 나중에 `question_type` 4분류로 발전). 이 판단을 라우팅으로 처리하면 시간 비용이 LLM으로 직접 처리하는 것과 비슷할 수 있어, **가볍고 빠른 로컬 모델로 라우팅을 분리**하자는 논의로 이어짐(→ 8번 ELECTRA 아이디어).
3. **관리자 UI 파라미터 실험 환경** 논의(이전 대화에서 다룬 내용과 동일선상): RRF 3가지 + 청크사이즈 + 오버랩 5가지에 "여러 모델"도 추가로 넣을 수 있을지 조사하자는 합의.
4. **담당자 배정**: 유상님 — 분기점 반영 청크별 첨부문서 태깅 / 규남님 — 라우팅 모델 조사 / 현욱님 — Qform.
5. **멀티턴으로 빈칸을 채우는 방식이 핵심**이라는 합의 — "처음부터 다 채우게 하면 예솜이(예솜24)와 다를 게 없다." 즉 한 번에 설문조사처럼 다 받는 게 아니라, 대화를 통해 부족한 것만 채워나가야 차별점이 생긴다.
6. **메타데이터 수집은 자연어 유사도가 아니라 직접 질문**하는 형태 — "이 정보가 뭔지" 구조화해서 물어보는 부분은 임베딩이 필요 없다는 확인.
7. **테스트 결과 재확인**: 400건 테스트셋에서 리랭킹 없이 22건 빼고 다 맞춤(정답 라벨링 오류를 고치면 더 오를 가능성) → 그래서 **테스트셋 난이도를 올리고 라우팅 모델도 먼저 실험**해보는 게 우선순위로 판단됨(4절 M1·M2와 직결).
8. **핵심 문제 재확인**: 정확도 자체보다 "첨부문서 반환"과 "청크 단위로 답을 뽑는데 정답은 페이지 기준으로 인정되는" 구조적 문제가 크다 → 검색 구조 개편이 필요하고, 그 개편에 Qform(우리에게 필요한 정보를 정리하는 틀)이 필요하다는 결론. 다만 **도입 시 초기 버전은 룰베이스**로 시작.
9. **UX 방향 확정**: Qform을 설문조사(체크박스·드롭다운) 형태로 사용자에게 그대로 노출하지 않는다. 대신 **자연어로 반문**한다("상황을 설명해주세요", "당사자분의 상황을 설명해주세요" 같은 형태).
10. **적용 범위 좁힘**: 이 상황설명형 되묻기는 간단한 질문이 아니라 복잡한 질문에서, 그리고 예금보험 안내나 미수령금 안내처럼 **분기가 많은 업무 몇 개에서만** 작동시킨다. 어느 도메인까지 커버할지는 아직 확정 전.
11. **초기 라우팅 카테고리 재검토**: 업무/업무 외에 더해 "적합한데 Qform 필요"와 "적합한데 Qform 불필요"를 나누는 방향이 논의됨.
12. **최종 정리**: 초기 라우팅(모호/적합/부적합)은 지금 구조를 그대로 두고, **안 채워진 슬롯에 대해서만 질문을 생성**한다. 다만 이건 순수 룰베이스로는 안 된다 — 사용자가 처음 질문에 이미 어떤 정보를 넣었는지 시스템이 모르는 채로는 "뭐가 비었는지" 판단할 수 없기 때문(→ LLM 추출이 필요한 이유).
13. **분기 규모 재확인**: 시나리오 슬롯 7개 중 몇 개가 채워졌는지에 따라 리프가 42개(더 늘 수도 있음) — 4절의 "리프 15개 이하 유지" 원칙과 대비되는 실측치로, 슬롯을 더 줄여야 함을 시사.
14. **질문 생성 방식 확정**: 하드코딩 템플릿이 아니라, Qform 스키마(슬롯·후보군)만 작성해두고 **LLM이 채우는 것도 LLM, 부족한 부분을 되묻는 것도 LLM**이 담당. 슬롯 예시로 party, 본인/대리인, business_function, 미성년자/군인 등 subject, 인터넷/방문 등 method가 거론됨. **개념 설명은 토글로 제공**하고, LLM이 되물을 때도 쉬운 문장을 쓰기로 함.
15. **액션아이템**: 모든 조건 분기를 한 번 더 더블 체크(4-5절 M1과 직결).
16. **열린 질문**: Qform에서 LLM으로 전달되는 방식 자체가 아직 미정.
17. **라우팅 모델 구체화**: ELECTRA 모델을 금융 데이터로 파인튜닝해서 라우팅에 쓰는 방향(2번 항목의 "가벼운 로컬 모델" 아이디어가 구체적인 모델로 확정).
18. **테스트셋 확장 계획**: 공용 테스트셋을 400건→**1000건**으로 확장. 지금 400건은 업무 관련 질문으로만 채워져 있어 복잡한 질문과 업무 외 질문이 섞인 게 없음 → 관할/비관할 질문을 분리해서 채워 넣기로 함. **내일(8/4) 계획**: 100건(키워드 포함 질문) + 100건(키워드 미포함 질문) + 200건(소관 아닌 것 구분 — 애매한 질문) 순서로 확장. 현재는 "부적합" 카테고리만 비어있는 상태.
19. **Qform 반영 방식 재확인**: 청크 메타데이터에 붙는 Qform 슬롯은 룰베이스(하드필터)로 주면 안 된다는 문제의식을 다시 확인 — **가중치(소프트부스트) 방식**으로 전환해야 하고, 이는 이미 `business_function`을 키워드로 추출해 부스트에 넣었던 기존 방식(`rag.py`의 `BF_BOOST`/`FACET_BOOST`)과 같은 패턴을 그대로 확장하는 것.

## 6. 지금 상태 한눈에 보기

### 6-1. 확정된 것

- Qform은 사용자에게 설문조사로 노출하지 않고 **자연어 반문**으로 감싼다.
- 슬롯 채움과 되묻기 문장 생성 모두 **LLM이 담당**(하드코딩 템플릿 아님).
- `hard_filter`는 `business_function`뿐, 나머지는 `soft_boost`.
- 되묻기는 **절차형·요구형 + 슬롯 미충족**일 때만, 확인형("~맞죠?") 문구는 금지.
- 조건 계산이 필요한 축(금액·기한·상계 등)은 슬롯으로 안 받고 본문 검색+생성 검증으로 처리.
- Qform 적용 범위는 복잡한 질문 + 분기 많은 일부 업무로 한정(전체 6업무 아님).
- 라우팅은 ELECTRA 기반 경량 로컬 모델로 분리 검토(규남님 담당).
- 첨부문서 태깅은 청크 단위로, 분기점 반영해 재작업(유상님 담당).
- 테스트셋을 400→1000건으로 확장하고 관할/비관할·키워드유무를 나눠 8/4부터 순차 구축.

### 6-2. 아직 보류/미결인 것

- **구현 자체가 보류**: M1(오라클 상한)·M2(질문유형 분포)·M3(applicant_type 문서 변별력) 세 가지 무료 측정을 통과해야 착수.
- `method`/`qualification` 슬롯의 실제 문서 변별력 — provisional 상태.
- `applicant_type` 8종이 RETRIEVAL(검색에 영향)인지 CONTEXT(생성에만 영향)인지 — 가장 중요한 미확인.
- Qform 값이 LLM에 전달되는 정확한 방식/포맷.
- 부스트 강도 재조정(현재 0.03) 및 중복 가산 처리.
- Qform을 어느 업무(몇 개)까지 적용할지 최종 범위.
- 미수령금 FAQ 크롤 0건이 진짜 누락인지 재태깅 부산물인지 — 재확인 필요.

### 6-3. 담당·다음 스텝

| 담당 | 작업 |
|---|---|
| 유상 | 분기점 반영해 청크별 첨부문서 태깅 재작업 |
| 규남 | ELECTRA 기반 라우팅 모델 조사·금융데이터 파인튜닝 |
| 현욱 | Qform 스키마 정교화 — M1·M2·M3 측정 설계 포함 |
| 공통 | 8/4: 테스트셋 100(키워드 포함)+100(키워드 미포함)+200(소관外 구분) 구축, 관리자 UI 파라미터 실험 환경에 넣을 추가 파라미터/모델 조사(이전 대화 답변 참고) |

**순서 원칙**: M1·M2·M3 측정(무료, 0콜) → 게이트 통과한 슬롯만 실제 구현 → 400건 회귀로 안전망 확인 → 유료 시나리오 테스트(M5)는 held-out 원칙 지키며 마지막에.

## 7. 용어 정리

| 용어 | 의미 |
|---|---|
| **Qform** | 검색 전에 LLM이 질문을 분석해 채우는 Structured Output 슬롯 모음. 사용자에게는 노출하지 않고 자연어 반문으로 감싼다. |
| **분기점(Branching Point)** | 예솜24 챗봇이 답을 좁혀가기 위해 사용자에게 추가로 물어보는 지점(칩 메뉴). Qform 슬롯 설계의 원재료. |
| **슬롯(slot)** | Qform 안의 개별 항목(예: `party`, `qualification`, `method`). 각각 cardinality/role/nullable/ask_if_missing/maps_to 속성을 가짐. |
| **`hard_filter`** | 검색 공간을 아예 좁히는 필터. 틀리면 정답이 통째로 사라짐 — `business_function`에만 허용. |
| **`soft_boost`** | 필터링 없이 순위만 살짝 올리는 방식. 슬롯이 틀려도 정답이 사라지지 않음 — 대부분의 슬롯이 여기 해당. |
| **`routing`** | 검색이 아니라 "다음에 뭘 할지"(업무 스키마 선택, 되묻기 여부)를 결정하는 슬롯 역할. |
| **`condition_retrieval`** | 금액·기한 등 판정이 필요한 조건 슬롯의 역할. 필터·부스트가 아니라 본문 검색 대상으로만 쓴다. |
| **GATE / RETRIEVAL / CONTEXT 레인** | 슬롯을 "언제 어디에 영향을 주는가"로 나눈 3분류. GATE=진입·되묻기 제어, RETRIEVAL=검색 지표(hit@3)로 직접 측정 가능, CONTEXT=생성 단계에만 영향(검색 지표로는 안 잡힘). |
| **오라클(Oracle) 상태 확인(M1)** | 슬롯을 "정답으로 직접" 채워 넣었을 때 지표가 얼마나 오르는지 상한을 재보는 측정. 상한이 안 오르면 그 슬롯은 만들 가치가 없다는 뜻. |
| **리프(leaf)** | 분기 트리의 최종 도달 노드(더 이상 안 갈라지는 답변 지점). 슬롯 조합 수만큼 리프가 생기며, 많을수록 UX가 복잡해짐. |
| **Tier A / Tier B** | 인덱싱 계층 구분. Tier A=본문처럼 임베딩해서 검색되는 대상(표 데이터 포함), Tier B=임베딩하지 않고 슬롯 JOIN으로만 반환되는 첨부파일. |
| **`condition` 축 / `variant` 필드** | 청크 메타데이터에 조건 분기(금액·기한 등)를 담기 위해 신설 예정인 필드. 현재 `variant`는 비어있는 필드로, 이 용도로 재활용 후보. |
| **자기참조(Self-referential) 편향** | 슬롯 스키마를 만든 원천(예솜24 트리)으로 그 슬롯의 효과를 다시 평가하면, 트리에 있던 편향이 평가에도 그대로 스며드는 문제. `crawler/HOLES.md`의 **H12**(평가셋이 정답 문서에서 추출한 질문이라 어휘가 겹쳐 지표가 실제보다 후하게 나오는 문제)와 같은 유형. |
| **ELECTRA** | 라우팅에 검토 중인 경량 로컬 분류 모델. 현재는 HCX(LLM) 1콜로 분류하는데, 이를 대체할 가볍고 빠른 대안으로 검토. |
