## 0. 문제 정의

하나의 사용자 질의에 **복수의 질문**이 들어올 수 있다(`IN+IN`, `IN+OOS`, `OOS+IN`).
특히 후속 질문이 `이것/그것/이건/그럼` 등 **지시어**로만 구성되면 단독으로는 대상 파악이 불가능하다.

현행은 전체 질의를 **하나의 라우팅 대상**으로 처리한다(`chain._route()` → `rag`/`reject` 단일값).
따라서 두 가지 실패가 성립한다.

| # | 실패 경로 | 결과 |
|---|---|---|
| F1 | 앞의 IN 질문이 라우팅을 끌어당김 | 뒤의 OOS 질문까지 IN으로 통과 |
| F2 | 통과한 질의가 그대로 검색으로 감 | BGE-M3가 앞 질문 키워드로 문서를 찾아 **OOS 파트에도 근거가 있는 것처럼** 답변 |

F2가 이 프로젝트에서 특히 위험한 이유: 도메인이 돈과 법이고,
목표가 "그럴듯한 답"이 아니라 **"근거 있는 답"**이다(`CONTEXT.md` §1).

## 1. 세 안 요약

### 1안 — Query Structure 단계 신설
`Routing → Slot Filling → Trigger → RAG` 앞에 복수질문·지시어 판정 단계를 둔다.
복수로 판정되면 Sub-query로 **분리**하고, 슬롯·이전 문맥으로 지시어를 실대상 질의로 **Context Resolution**한다.
정규화된 각 Sub-query를 라우팅에 **개별 투입**해 IN/OOS를 독립 판정하고, OOS는 검색을 차단한다.

### 2안 — 라벨을 "라우팅"과 "태그"로 분리 (질의 분할 안 함)
쿼리 문자열을 **절대 쪼개지 않는다.** L0는 원문 전체로 단일 라우팅 라벨만 결정(현행 유지).
이와 **병렬로** 룰 기반 레퍼럴 태거가 원문 전체에 `link_registry` 키워드 매칭을 돌린다(비배타·0~N개).

| L0 | 태그 | 처리 |
|---|---|---|
| IN_SCOPE / 모호 | 없음 | `rag` (현행과 동일) |
| IN_SCOPE / 모호 | 있음 | `rag` 생성 후, 태그별 안내사전 항목을 템플릿 렌더링해 **답변 뒤 후첨** |
| OOS | 있음 | `link` (템플릿만, LLM 생성 없음) |
| OOS | 없음 | `reject` (DOMAIN_OOS) |

`route`는 여전히 단일값(계약 유지), 복합 여부는 `_meta.referral_tags`로만 남긴다.
태그 2개 이상이면 top-k를 5→8~10으로 넓혀 특정 서브토픽 쏠림을 완화한다.

### 3안 — query unit 단위 재설계
`[0] Input Guard → [1] Intent Router(casual/handoff/bug/information) → [2] Query Decomposition
→ IN/LINK/OOS 분기 → RAG/Registry/reject → Response Composer`.
route를 질의 전체에 하나만 부여하지 않는다. LLM은 **label만** 결정하고
실제 route는 registry/retrieval 기반 **코드**가 결정한다. 생성은 IN_SCOPE 답변만 담당.

## 3. 채택 권고 — 2안 + 1안의 1조각

### 3-1. 2안을 고르는 근거

1. **콜 0.** 라우터 교체(G1)가 GPU 상시 서빙 때문에 막혀 있는 상태에서
   1·3안은 그 위에 콜을 더 얹는다. 2안은 이미 있는 `link_registry` 키워드로 돌아간다.
2. **"질문이 몇 개냐"를 판정하지 않는다.** "미수령금은 무엇인가요, 그리고 어떻게 신청하나요"는
   나눌 기준 자체가 없다. 관련된 두 부분을 억지로 쪼개면 검색 품질이 오히려 깎인다.
   2안은 그 판정을 **아예 요구하지 않는** 유일한 구조다.
3. **평가 단일축·no-numbers-no-merge 규율이 산다.** 450/1150셋이 즉시 회귀 테스트로 재사용된다.
4. **계약 4필드 무변경.** `route` 단일값 유지, 복합 여부는 `_meta.referral_tags`.
5. URL·전화번호를 LLM이 한 글자도 생성하지 않는다. 후첨 블록은 **문자열 조립**이다.

### 3-2. 2안의 인정해야 할 구멍 2개

- **레지스트리 커버리지 = 안전 커버리지.**
  `L0=IN_SCOPE + 태그 없음`에 "보호한도 알려주고, 그럼 여권은 어디서 만들어요?"가 들어오면
  여전히 앞 질문 키워드로 검색이 돌고 OOS 파트가 조용히 답변된다.
  2안은 이 케이스를 **해결하지 않고 L0 프롬프트로 넘긴다**
  (`OOS_처리로직_계획서` §7-1 안전기본값 `"정상"` 리스크와 직결).
  → H7(공란 2건) 해소 + 레지스트리 확장이 이 안의 실질 작업량이며, 여기가 정직한 한계선이다.
- **top-k 5→8~10은 그 자체로 효과가 없다.**
  생성이 읽는 창은 top-3이다(`QFORM_ARCH` §6 "생성 window 목표").
  회수만 늘리면 지표만 좋아지고 답은 그대로다. **리랭킹 또는 생성 k 확대와 묶어서만** 의미가 있고,
  G13(부스트된 쿼리로 `rag.search`가 업무를 재분류)과 상호작용하므로
  패널의 `⚠ 업무 갈림` 건수를 함께 봐야 한다.

### 3-3. 1안에서 가져올 한 조각 — 지시어, LLM 없이

2안이 못 잡는 것은 `이것/그것/그럼`이다. 여기에 1안의 LLM Context Resolution을 붙이면 콜 0이 깨진다.
대신 **결정론 재작성**으로 충분하다.

- 큐폼이 이미 직전 턴의 `business_function`·`sub_task`를 세션 확정값으로 들고 있다.
- 지시어만으로 된 짧은 질의(길이 임계 + 지시어 사전)일 때, 확정 슬롯을 **문자열로 앞에 붙여**
  L0·검색에 넘긴다.
- 콜 0, 문자열 조립, 되돌리기 1줄. LLM 코어퍼런스 해소는 M4.1(Phase 4)로 미룬다.

### 3-4. 3안의 처분 — 목표로 남긴다

"LLM은 label만, route는 코드가 결정"은 옳고, 이미 `route`를 코드(`_route()`)가 정하므로 방향은 일치한다.
다만 Input Guard·handoff(G5)·Composer 신규 + 1150셋 라벨 재설계가 동시에 걸려 데모 일정과 정면 충돌한다.
3안의 저비용 부분(Intent Router의 casual/handoff/bug 분기)은 **2안의 태거와 같은 자리**에
룰 프리필터로 얹을 수 있다 → **2안이 3안으로 가는 경로를 막지 않는다.**

### 5-2. 우선순위와 태거의 관계 — 2안의 핵심 접합부

`OOS_처리로직_계획서` §5-3 우선순위 스택(`ADVERSARIAL > BUG > HANDOFF > IN_SCOPE >
SCOPE_OOS > DOMAIN_OOS > CASUAL`)은 **L0의 단일 라벨을 정하는 데만** 쓴다.

그런데 이 스택의 `IN_SCOPE > SCOPE_OOS` 규칙이 바로 §0의 F1/F2를 만든다 —
"보호한도랑 워크아웃 알려줘"는 IN_SCOPE로 삼켜지고, 워크아웃 파트는 근거 없이 답변된다.
**태거가 정확히 이 지점을 구제한다.** 우선순위는 그대로 두고, 삼켜진 SCOPE_OOS 파트를
비배타 태그로 **따로 건져 후첨**한다.

| L0 라벨 | 태그 | 최종 처리 |
|---|---|---|
| IN_SCOPE / 모호 | 없음 | `rag` (현행) |
| IN_SCOPE / 모호 | 있음 | `rag` + 태그별 안내 템플릿 **후첨** ← **복합질의 케이스** |
| SCOPE_OOS | 있음 | `link` (템플릿만) |
| SCOPE_OOS | 없음 | **`reject`로 강등** (사전 미등록 = 안내 불가) |
| DOMAIN_OOS | — | `reject` |
| HANDOFF / BUG | — | `handoff` (+로깅) · 태그 무시 |
| INVALID | — | `reject` (+로깅) · L-1에서 이미 종결 |
| CASUAL | — | `casual` |

### 5-3. 원안에서 수정한 것 — 이유

| # | 원안 | 수정 | 이유 |
|---|---|---|---|
| C1 | SCOPE_OOS > "기타 타 기관 소관 업무" | **catch-all 삭제**, 사전 등록 개별 항목만 | SCOPE_OOS 판정 = "안내 사전에 항목이 있다"와 1:1이어야 한다. catch-all을 두면 사전에 없는데 SCOPE_OOS로 판정되어 **빈 안내문**이 나간다. 미등록 건은 DOMAIN_OOS로 강등 |
| C2 | DOMAIN_OOS > 타 기관 금융제도 안에 외국 제도 혼재 | **외국 예금보호제도 별도 하위 신설** | 트랩 20문항 중 5문항이 이 유형이고 "해외 수치 혼입 0건" 검증축과 직결. 별도 노드여야 회귀 측정이 된다 |
| C3 | SCOPE_OOS > **보호한도 초과분** | **IN_SCOPE로 이동** (+ 파산배당·개산지급금 태그) | 개산지급금·파산배당 참여는 **예보 소관 업무**이고 코퍼스에 답이 실재한다. SCOPE_OOS로 두면 답할 수 있는 것을 link로 넘긴다 |
| C4 | SCOPE_OOS > **비보호 금융기관 예금보호** | **IN_SCOPE로 이동** (판단 필요 — §7-3 참조) | "우체국 예금 보호되나요?"의 답("예보 비보호·자체기금")이 코퍼스 원문에 있고, Qform은 이미 이걸 `institution_type` **슬롯 값**으로 편입했다(`QFORM_DECISIONS_HOLES` A-3 #1). 현행 두 문서가 **서로 다르게 취급하고 있다** |
| C5 | CASUAL > 챗봇 기능 문의 | **시스템 메타로 분리** | 1150셋 G5a가 "챗봇/시스템 메타 50건"을 별도로 세고 있어 라벨을 맞춰야 집계가 어긋나지 않는다. 또한 자기소개 문구는 **코퍼스 밖 하드코딩**이라 규칙 1 예외 결정이 걸린다(`qform_기획서_v1` §9) |
| C6 | HUMAN_HANDOFF · BUG_REPORT | **route 신설 대상으로 명시** | 현재 `_route()`는 `rag`/`reject`만 반환한다(G5 미구현). 트리에 그려두고 구현이 없으면 이 두 분기는 조용히 rag로 흘러간다 — **갭임을 트리에 표기** |
| C7 | 휴면계좌 안내처 | **사전(referral registry)에서만 인출** | 현행 `CLS_PROMPT`는 "서민금융진흥원"이라 하고 코퍼스 원문은 "전국은행연합회 sleepmoney.or.kr"다. 분류 프롬프트에 기관명을 쓰면 파라메트릭 지식 오염이 재발한다 |
| C8 | INVALID / ADVERSARIAL을 OOS 하위로 배치 | **L-1 룰 프리필터로 승격** | OOS 분류의 결과가 아니라 **LLM 콜 이전**에 끝내야 하는 층이다. 인젝션을 LLM에 먹인 뒤 라벨을 받는 순서는 위험하고, 콜도 낭비다 (3안 Input Guard가 정확히 이 자리) |

### 5-4. LLM 호출 경계 — "무엇인지"는 LLM, "무슨 말을 할지"는 사전

논의 끝에 정리된 단일 기준이다. **OOS냐 아니냐가 기준이 아니다.**

> **출력이 검증 가능한 라벨·ID면 LLM에 맡긴다. 출력이 자유 텍스트인데 그 안에
> 코퍼스 밖 고유명사(기관명·URL·전화번호·금액)가 들어가면 조립한다.**

근거는 실측 2건이다. ① 현행 `CLS_PROMPT`가 "휴면예금=서민금융진흥원"이라 서술하는데
코퍼스는 "전국은행연합회 sleepmoney.or.kr"다(§5-3 C7). ② 전야 Q3에서 컨텍스트에 정답이
있는 상태에서도 `fss.or.kr` 출처와 맨몸 가짜 kdic URL을 생성했다(→ 규칙 2).
즉 **가이드라인을 프롬프트에 적는 것으로는 통제되지 않는다.** 라벨·ID는 유효값 검사로
100% 폴백이 되지만, 자유 텍스트 안의 고유명사는 검사할 기준이 없다.

| 층 | 담당 | 출력 형태 | 검증 |
|---|---|---|---|
| 라우팅 라벨 (6개 중 1개) | **LLM (L0, 기존 1콜)** | enum | 3값 검증 실패 시 안전기본값 |
| SCOPE_OOS 행 선택 (7행 중 1개) | **LLM (L0 콜에 합침, 권장)** 또는 임베딩 최근접 | `row_id` | 유효 ID 아니면 태그 없음 처리 |
| 안내 내용 (기관명·URL·번호) | **사전 조립** | 템플릿 | 구조적으로 날조 불가 |
| 문장 다듬기 | LLM (옵션) | 자유 텍스트 | ⓑ 모드 가드 8종 → 위반 시 100% 템플릿 폴백 |
| 민원 요약 (HANDOFF/BUG) | **LLM** | 자유 텍스트 | 재료가 **사용자 발화**라 외부 사실 날조 위험 없음 |

**변형 흡수는 L0가 담당한다.** `안녕/헬로/hi/하이루/방가방가`는 표현이 무한하지만 CASUAL의
출력은 고정 1개라 **어느 변형인지 알아낼 필요가 없다.** 사전에 행을 만들 일도 없다.
세부 판별이 필요한 것은 **SCOPE_OOS 7행 중 택1** 하나뿐이다.

| 라벨 | 표현 변형 | 필요 출력 수 | 세부 판별 |
|---|---|---|---|
| CASUAL / DOMAIN_OOS / INVALID | 무한 | 각 1개 (고정) | **없음** — 라벨만 맞으면 끝 |
| HUMAN_HANDOFF / BUG_REPORT | 많음 | 각 1개 (+요약) | 없음 |
| **SCOPE_OOS** | 많음 | **7개 중 1개** | **필요** ← 태거의 일 |

### 5-5. 레퍼럴 태거 상세 (2안의 실체)

#### (1) 위치와 실행 시점
L0와 **병렬**로 돈다. L0의 HCX 응답을 기다리는 동안 CPU에서 끝나므로 **지연 추가가 0**이다.
질의를 **분할하지 않고 원문 전체**에 대해 돈다(§3-1 근거 2). 입력은 §3-3 지시어 재작성을 거친 문자열.

#### (2) 사전(referral registry) 행 구조
```
row_id        : scope_oos_workout            ← combo/템플릿이 참조하는 키
label         : 워크아웃 / 신용회복
keywords[]    : 워크아웃, 신용회복, 채무감면, 신복위
anchor_text   : (코퍼스 원문 한 줄 — 임베딩 대상)
guide_block   : { org: 신용회복위원회, link_key: ccrs, tel: 1600-5500, note: 신청비 5만원 }
evidence      : chunk_id (근거 앵커)
```
- **URL은 넣지 않고 `link_key`로 참조**한다(`QFORM_ARCH` §4-2). URL 변경 시 레지스트리 한 곳만 고친다.
- `guide_block` 값은 **코퍼스 원문에서만** 채운다. 프롬프트·모델 지식에서 가져오지 않는다(C7).
- 편집 주체는 관리자 콘솔. 편집 이력(audit log) + 링크 헬스체크 대상(§4-3).

#### (3) 매칭 파이프라인
```
질의(원문)
 → [0] 정규화 (공백·조사 제거, 영문 소문자화)
 → [1] 키워드 매칭        ── 히트 → 태그 확정 (match_by=keyword)   · 콜 0 · 수 ms
 → [2] 행 선택 (키워드 미스 시)
        ├─ (권장) L0 콜에 행 목록을 선택지로 동봉 → row_id 회수   · 추가 콜 0
        └─ (대안) anchor_text 임베딩 최근접 + 임계 τ              · 콜 0 · 수십 ms
 → [3] 임계 미달 / 유효 ID 아님 → **태그 없음**
 → 출력: tags = [{row_id, match_by, score}, ...]   (0~N개, 비배타)
```
- **비배타인 이유**: 복합질의는 토픽이 동시에 걸린다("보호한도랑 워크아웃"). 반면 `route`는
  계약상 단일값이어야 하므로, **라벨은 1개 / 태그는 N개**로 축을 분리한다. 이것이 2안의 전부다.
- **과소태깅이 안전한 방향**이다. 태그가 없으면 §5-2대로 reject로 강등된다.
  빈 안내문이 나가는 것보다 거절이 낫다.

#### (4) 태거가 우선순위 스택을 구제하는 방식
`§5-3`의 우선순위는 `IN_SCOPE > SCOPE_OOS`다. 즉 "보호한도랑 워크아웃 알려줘"는
**IN_SCOPE로 삼켜지고 워크아웃 파트가 근거 없이 답변된다**(= §0의 F1·F2).
태거는 우선순위를 건드리지 않고, 삼켜진 파트를 태그로 따로 건져 후첨한다.

#### (5) 후첨 블록 렌더링 (LLM 0)
```
[rag 생성 답변 — 출처 표기 포함]

──
말씀하신 「{label}」은 예금보험공사 소관이 아닙니다.
{org} 에서 안내받으실 수 있습니다.
· 홈페이지: {link_key → 현재 URL}
· 전화: {tel}
{note}
```
- 문자열 조립이다. **LLM이 한 글자도 생성하지 않는다**(P3/규칙 2 유지).
- **후첨 최대 2개**로 제한한다. 태그 3개 이상이면 상위 2개만 렌더링하고 나머지는
  대표번호 안내 한 줄로 접는다(문장 폭주 방지).
- `answer_checks`의 "출처 번호 미표기" 오탐 대상이다 — `_is_rejection()`과 같은 성질의
  예외 처리가 필요하다(§7-2 미결).

#### (6) 태거가 하지 **않는** 것
질의 분할 · `route` 결정 · 기관명 생성 · IN/OOS 판정. 전부 다른 층의 일이다.

#### (7) 임계 τ와 평가
1150셋 G5b의 **타기관 실제 소관 80건 + 퇴직연금 대조쌍 60건 = 140건**이 이 판별의 평가셋이다.
단 현재 in/out 라벨만 붙어 있어 **행(분야) 라벨 추가가 필요**할 수 있다 — 이 트랙의 유일한 라벨링 비용.
450셋에서는 **태그 발동률 = 오발동 지표**로 쓰고 hit@3 무변동을 확인한다.

### 5-6. HUMAN_HANDOFF 응답 구성

"답답하니깐 사람 연결해줘" 류. **필요한 사실은 대표번호 1588-0037 하나이고 코퍼스 실재가
확인됐다**(`answer_checks` 검증 기록). 검색·생성 없이 사전 인출로 끝난다.

| 구성 | 출처 | LLM |
|---|---|---|
| 연락처 안내 | 사전 (`tel`, 운영시간) | 없음 |
| 공감 한 줄 | **코퍼스 밖** → 규칙 1 예외. 하드코딩 시 `DECISIONS` 명시 기록 대상 | 없음(또는 ⓑ 가드) |
| 민원 요약 (옵션) | **사용자 발화** — 외부 사실 없음 | **있음** |
| 불만족 로깅 | — | — |

- 민원 요약은 규칙 1과 충돌하지 않는다. 사용자가 방금 한 말을 정리해 돌려주는 것이라
  날조할 외부 사실이 없다. 실제 접수 시스템 연동은 PoC 범위 밖.
- **"답답하니깐"은 앞 턴 답변이 실패했다는 신호다.** 이 로깅이 실사용 실패 질의 수집원이 되며,
  H12/H18("평가셋이 self-referential이라 수치는 상한 추정")을 깨는 재료다.
- ⚠️ **현행은 이 질의가 `rag`로 흘러간다**(G5 미구현). 사람을 불러달라는 사용자에게
  검색을 돌려 문서를 읽어준다. C6의 실제 증상.

### 5-7. 예상 응답 시간

실측 기준선(`route_e2e_report.md` · `demo_report.md`): **reject 평균 1,318ms · rag 평균 4,956ms**
(RAG 생성 평균 5.2s/최대 7.9s, 맨몸 생성 평균 3.0s/최대 5.1s).

| 경로 | 구성 | 예상 지연 | 근거 |
|---|---|---|---|
| INVALID | L-1 룰만, 콜 0 | **< 100ms** | 즉답 |
| CASUAL / DOMAIN_OOS → reject | L0 1콜 + 고정 문구 | **≈ 1.3s** | 실측 1,318ms |
| SCOPE_OOS → link | L0 1콜(+행 선택 동봉) + 템플릿 조립 | **≈ 1.3s** | 행 선택을 같은 콜에 합치므로 추가 0 |
| SCOPE_OOS → link (행 선택 임베딩) | L0 1콜 + 임베딩 최근접 | **≈ 1.4s** | +수십ms |
| HANDOFF (연락처만) | L0 1콜 + 사전 인출 | **≈ 1.3s** | — |
| HANDOFF (민원 요약) | L0 1콜 + 요약 1콜 | **≈ 4.3s** *(추정)* | 1.3s + 맨몸 생성 3.0s |
| **IN_SCOPE → rag** (현행) | L0 + 검색 + 생성 | **≈ 5.0s** | 실측 4,956ms |
| **IN_SCOPE + 태그 → rag + 후첨** | 위 + 문자열 조립 | **≈ 5.0s** | **후첨은 조립이라 +0** · 태거는 L0와 병렬 |
| IN_SCOPE + 태그 + top-k 확대 | 위 + 컨텍스트 증가 | **≈ 5.5~6.5s** *(추정)* | 컨텍스트 길이가 지연에 영향(demo_report §68). 검색 pool 확대 자체는 수십ms |

**읽을 점 세 가지**

1. **복합질의 처리(2안 핵심 경로)는 지연이 늘지 않는다.** 태거는 L0와 병렬, 후첨은 문자열 조립이다.
2. **지연을 늘리는 건 태깅이 아니라 top-k 확대**다(+0.5~1.5s 추정). §3-2대로 이건 별건 A/B이며,
   생성 창을 안 늘리면 효과가 없으므로 **지연을 내주고 얻는 것이 있는지 먼저 측정**한다.
3. OOS 경로는 rag의 1/4이다. **소관밖 즉답이 UX 부수효과**로 남는다 — 여기에 생성 콜을 붙이면
   그 이점이 사라지므로, 민원 요약(4.3s)은 HANDOFF에만 국한한다.

> 추정치는 *(추정)* 로 표기했다. **no-numbers-no-merge** — 머지 판정에는 실측으로 대체한다.

## 6. 트리에서 **빼야 하는** 것 — 검색·생성단 책임

OOS 분기 트리에 넣고 싶어지지만 넣으면 **과차단**이 생기는 항목들이다.
분류기가 이걸 잡으려 하면 IN_SCOPE 질문이 거절된다.

| 항목 | 왜 트리 밖인가 | 담당 |
|---|---|---|
| **구정보 확인형** ("보호한도 5천만 맞죠?") | IN_SCOPE이고 rag로 가야 한다. 위험은 OOS 미차단이 아니라 **오정보 승인**이다 | 검색(BF 부스팅) + 생성 프롬프트 규칙 4 · 최신성 가드 |
| **근접 용어 혼동** (개산지급금 vs 예금보험금, 채무조정 5종) | 전부 IN_SCOPE 안에서의 오지목. 오분류 9건의 실제 원인 | 큐폼 `sub_task` 되묻기 + D 용어판별 사전(G8) |
| **보호한도 초과분 · 비보호 기관** (C3·C4) | 코퍼스에 답이 있는 IN_SCOPE. OOS로 보내면 답변 가능한 것을 포기 | rag + 후첨 태그 |
| **지시어 후속 질문** ("그럼 그건요?") | 라벨이 아니라 **입력이 불완전한 상태**다. 라벨을 붙이려 하면 무엇을 붙여도 틀린다 | 전처리 재작성 (§3-3) |
| **표/첨부 다량 반환, 부모-자식 입도** | 라우팅과 무관 | Phase 2 (M2.2 · M2.3) |

> 원칙: **트리는 "답할 수 없는 것"만 가른다.** "답할 수 있는데 틀리게 답하는 것"은
> 전부 검색·생성단 문제이고, 트리에 올리면 과차단으로 되돌아온다.

## 7. 미결 사항 (팀 확인 필요)

1. `_meta.referral_tags` 추가가 계약 변경 승인 대상인지 (`OOS_처리로직_계획서` §7-6 연결).
2. 후첨 블록이 `answer_checks`의 출처 미표기 오탐을 유발하는지 (§6-4 충돌과 동일 성질).
3. top-k 확대의 판정 기준 — 생성 top-k를 올릴지, 리랭킹으로 갈지.
4. 지시어 사전의 범위(`이것/그것/그럼/이건` 외) 및 길이 임계값.
5. `L0=IN_SCOPE + 태그 없음`의 잔여 위험을 L0 프롬프트 강화로만 덮을지, 별도 장치를 둘지.
6. **C3·C4 — "보호한도 초과분"·"비보호 금융기관"을 SCOPE_OOS(link)로 볼지 IN_SCOPE(rag)로 볼지.**
   `OOS_처리로직_계획서` §4는 link, `QFORM_DECISIONS_HOLES` A-3은 슬롯 값(=IN_SCOPE)으로
   서로 다르게 취급하고 있다. 둘 중 하나로 정렬해야 트랩 라벨과 큐폼 조합 테이블이 어긋나지 않는다.
7. C5 — "시스템 메타"를 CASUAL 하위로 둘지 별도 라벨로 둘지 (1150셋 G5a 집계 정합).
8. C6 — `handoff` route 신설 시점. 신설 전까지 HUMAN_HANDOFF·BUG_REPORT는 rag로 흘러간다는 것을
   알려진 갭으로 기록할지, 임시 고정 문구로 막을지.
9. C8 — L-1 룰 프리필터의 인젝션 패턴 사전을 어디까지 채울지(과차단 위험 vs 방어 범위).
10. **SCOPE_OOS 행 선택 방식** — L0 콜에 선택지 동봉(권장, 추가 콜 0) vs 임베딩 최근접(콜 0, 임계 τ 필요).
    전자는 프롬프트 길이가 늘고, 후자는 τ 스윕이 필요하다.
11. 1150셋 G5b 140건에 **행(분야) 라벨 추가** 여부 — 태거 정밀도 측정의 전제.
12. 후첨 블록의 `answer_checks` 예외 처리 — `_is_rejection()`과 같은 패턴으로 갈지.
13. HANDOFF 공감 한 줄의 규칙 1 예외 승인 + 민원 요약 채택 여부(연락처만 vs 요약 생성).
