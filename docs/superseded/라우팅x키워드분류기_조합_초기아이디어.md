# 라우팅 모델 × 키워드 분류기 조합 — 초기 아이디어

> **상태**: 초기 아이디어(제안) · 미착수
> **레이어**: 검색 전 업무(도메인) 신호 생성 — `chain.py`(라우팅), `rag.py`(소프트부스트)
> **한 줄**: 라우팅이 정확할 때, 결정론 키워드 분류기와 LLM 라우팅 모델의 도메인 판정을 **비율 파라미터**로 섞어 업무 신호를 만든다.

---

## 1. 배경 — 지금은 두 신호가 따로 논다

현재 파이프라인에는 업무/도메인을 판정하는 **두 개의 독립 신호**가 있다.

| 신호 | 위치 | 방식 | 산출 |
|---|---|---|---|
| 키워드 분류기(소프트부스트) | `rag.py` `classify_query_bf` → `BF_BOOST` | 결정론 키워드 매칭 | 6대 업무 중 1개 or 불명(None) → 같은 업무 청크에 RRF `+0.005` 가산 |
| 라우팅 모델(도메인 분류기) | `chain.py` `classify()` | LLM 분류 | 정상 / 모호 / 소관밖 (in-scope 라우팅) |

- 키워드 분류기는 **검색 랭킹**에, 라우팅 모델은 **소관 여부 게이트**에 각자 쓰인다.
- 둘 다 "이 질문이 어느 업무인가"라는 **같은 판단의 다른 버전**을 내부적으로 갖는데, 지금은 서로 참조하지 않는다.

---

## 2. 문제 — 키워드 분류기 단독의 천장

소프트부스트 채택 기록(2026-07-22)에서 드러난 한계:

| 버킷 | 규모(400셋) | 성격 |
|---|---|---|
| **불명(None)** | 120건(30%) | 키워드 미검출 → 부스트 미개입(순수 하이브리드) → **커버리지 천장** |
| **오분류** | 9건 | 확신을 갖고 틀림 → 소프트부스트가 **틀린 업무를 부스트** → 정답을 오히려 묻음 |
| 정분류 | 나머지 | 정상 동작 |

- **불명 30%**: 결정론 키워드는 구어체·신조어·긴 문장에서 쉽게 놓친다. 키워드 확장은 **테스트셋 문구 암기(오버핏)** 위험이라 지양.
- **오분류**: 키워드로는 못 고침. **의미 이해가 있는 신호**가 필요.

> LLM 라우팅 모델은 의미 기반이라 이 두 버킷(특히 불명)을 메울 잠재력이 있다. 단, LLM도 틀릴 수 있으니 **키워드를 버리지 않고 섞는다.**

---

## 3. 아이디어 — 두 도메인 신호를 비율로 조합

라우팅 모델이 판정한 도메인과 키워드 분류기의 도메인을 **가중 혼합**해 최종 업무 신호(소프트부스트 대상·강도)를 만든다.

```
질의
 ├─ 키워드 분류기 → bf_kw (or None)         [결정론·정밀·저커버]
 └─ 라우팅 모델   → bf_route (+ 소관 판정)   [의미·고커버·오류가능]
                     │
          [라우팅 정확/확신 게이트]
                     │
      combine(bf_kw, bf_route; ratio=λ) → 최종 업무 신호 → soft boost
```

### 3.1 조합 비율 λ (파라미터)
- `λ` = 라우팅 모델 도메인 신호의 반영 비중(0=키워드 단독=현행, 1=라우팅 단독).
- 부스트 강도/대상 결정에 `λ`로 두 신호를 섞음. 예: 두 신호 일치 → 강하게, 불일치 → 약하게 또는 라우팅 우선(λ 높을 때).
- **불명 구제**: `bf_kw=None`이고 라우팅이 확신하면 → 라우팅 도메인으로 부스트(현행이면 무개입이던 30% 구간을 커버).

### 3.2 게이트 — "라우팅이 정확할 경우"에만
- 라우팅 모델의 도메인 신호는 **정확/확신 조건을 통과할 때만** 반영(사용자 요구).
- 확신 판단 근거 후보: 라우팅 라벨(정상 vs 모호), 분류 사유, 파싱 성공 여부, (가능 시) 확신도.
- 라우팅이 불확실하면 → **키워드 단독으로 폴백**(현행 동작 보존, graceful degradation).

---

## 4. 설계 파라미터(초안)

| 파라미터 | 의미 | 초기값 방향 |
|---|---|---|
| `λ` (조합 비율) | 라우팅 도메인 신호 반영 비중 | 스윕 대상(0=현행부터) |
| 게이트 조건 | 라우팅 신호를 신뢰할 임계 | 정상 라벨 + 파싱성공 등 보수적으로 시작 |
| 불일치 정책 | kw≠route일 때 처리 | λ 가중 or 라우팅 우선 or 부스트 약화 |
| 부스트 강도 연동 | 두 신호 일치 시 가산 여부 | `BF_BOOST` 기반 소량 가산 |

- **소프트 원칙 유지**: 조합 결과도 **제외가 아니라 가산**. 틀려도 정답을 후보에서 배제하지 않음(리랭킹 토대 보존).

## 5. 고려할 점 / 리스크

| # | 이슈 | 방향 |
|---|---|---|
| R1 | **추가 LLM 콜 비용** | 라우팅 분류는 이미 `chain.classify()`에서 수행 → **재사용**(추가 콜 0 목표). 검색이 라우팅 뒤에 오도록 순서 확인 |
| R2 | **라우팅 오류가 부스트를 오염** | 게이트(확신 조건)로 차단 + 소프트라 배제 없음 + 불일치 시 λ 완화 |
| R3 | **오버핏 회피** | 라우팅은 의미 기반이라 키워드 확장식 오버핏과 다름. 단 게이트·λ 튜닝이 400셋 과적합 안 되게 실트래픽 검증 |
| R4 | **평가 방법** | `eval_TF.py`로 λ 스윕 A/B(현행 λ=0 sanity 포함). 불명 120·오분류 9 버킷의 회복/퇴행을 개별 추적 |
| R5 | **도메인 라벨 정합** | 라우팅의 도메인 표현 ↔ 6대 `business_function` 매핑 명확화(소관밖·모호 라벨의 취급) |

---

## 6. 다음 단계

1. `chain.classify()`가 **도메인(업무) 후보**까지 산출하는지 확인 — 없으면 라우팅 프롬프트에 업무 라벨 추가(콜 재사용).
2. 검색이 라우팅 판정 **이후**에 실행되도록 순서 확정(추가 콜 0).
3. `combine(bf_kw, bf_route; λ)` 프로토타입 + 게이트 → `rag.hybrid_soft` 부스트 결정부에 주입.
4. `eval_TF.py` λ 스윕 A/B: λ=0(현행)부터 → **불명·오분류 버킷별** 회복/퇴행 추적.
5. 게이트·λ 확정 → 실트래픽 강건성 모니터링(소프트라 안전판).

---

## 7. 한 줄 요약

> 키워드 소프트부스트는 30% 불명·9건 오분류가 천장이고, LLM 라우팅 모델은 의미 이해로 이를 메울 수 있으나 자체 오류가 있다. **라우팅이 확신할 때만** 두 도메인 신호를 **비율 λ로 조합**해 소프트부스트에 반영한다 — 제외가 아닌 가산 원칙을 지켜 틀려도 정답을 배제하지 않고, 라우팅 콜은 재사용해 추가 비용 0을 목표로 한다.
