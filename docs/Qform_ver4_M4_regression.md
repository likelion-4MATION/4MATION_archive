## §0. 이 문서가 주장하지 않는 것

**이번 스프린트는 성능 개선을 주장하지 않는다(K8).**
"큐폼 확장으로 검색 성능이 올랐다"는 **주장하지 않으므로 재지 않았다.**
여기서 재는 것은 **"확장이 기존 동작을 망가뜨리지 않았다"** 하나다. **무해 증명이지 개선 주장이 아니다.**

쿼리 부스트는 **기본 OFF 유지**다. G13(검색측 업무 재분류 갈림 13건)이 미해결이고
해소하려면 `rag.py` 를 건드려야 하는데 동결이다.

## §3. A4-3 — 발동률 변동 원인 분해

**변동이 없다(Δ +0건).** 그래도 축 분해를 남긴다 — 다음에 움직였을 때 비교 기준이 필요하다.

| 축 | 분해 |
|---|---|
| 업무 | 착오송금 반환 신청 **9건 / 9건** · 나머지 5업무 **0건** |
| 슬롯 | `qualification` **6건** · `subject` **3건** · `party`·`sub_task`·`method` **0건** |
| 발동 질의 | M0 §3-5 의 9건과 **동일**(`nat450-0087·0100·0101·0113·0132·0223·0225·0228·0232`) |

**늘어난 업무·슬롯이 없다.** 예금보험금 조합(DPIN 9행)을 추가했는데도 발동률이 안 움직인 이유는
§5 에 있다 — 추출기 스코프가 아직 착오송금 단일이라 DPIN 행이 자연어 경로에서 생존 판정에 들어가지 않는다.

## §4. A4-4 — `is_definitional()` 발동 건수 재측정

§9-4 가 "지금 발동 0건 = 검증 공백. **6업무 확장에서 처음 물린다**"고 예측한 자리다.

| 지표 | 실측 |
|---|---|
| `is_definitional()` **True** | **23건 / 450 = 5.1%** |
| 그중 착오송금 반환 신청 | **0건** |
| 되묻기 발동 9건과의 **교집합** | **0건** |
| **우회가 실제로 되묻기를 막은 건수** | **0건** |
| 업무 분포 | 채무조정 7 · 예금자보호 5 · 미수령금 5 · 예금보험금 4 · 은닉재산 2 |

**예측은 아직 실현되지 않았다.** 정의형 어휘를 가진 질의는 23건 있지만 전부 착오송금 밖이고,
추출기 스코프가 착오송금 단일이라 그 23건은 애초에 슬롯이 0개다 → 되묻기가 발동할 일이 없다
→ 우회가 막을 것도 없다. **`is_definitional()` 은 여전히 "오늘 고치는 버그가 없는 방어 장치"** 이며
ver3 D9 의 판단이 그대로 유지된다. **성과로 계상하지 않는다.**
