## 1. 한 줄 요약

상황 설정형 질의를 **구조화 입력(큐폼)** 으로 받되, 큐폼은 답을 직접 결정하지 않고 **기존 검색 파이프라인의 입력을 풍부하게 만드는 역할**만 한다.

---

## 2. 배경 — 왜 큐폼인가

| 현재 문제 | 큐폼이 하는 일 |
|---|---|
| 질의 분류기 불명 30% | 사용자가 직접 선택 → 커버리지 100% |
| 오분류 9건(개산지급금 → 예금보험금) | 소멸 |
| 분류기 키워드 확장 = 테스트셋 오버핏 위험 | 튜닝 노브 자체가 사라짐 |
| 시나리오형 질의를 받을 구조 부재 | 조건을 슬롯으로 명시적 수집 |

**한계도 같이 기록한다.** 미적중 ~22건은 착오송금 형제문서 계열로 **전부 동일 업무**다. 업무 슬롯(S1)만으로는 하나도 안 풀린다. id 16(구정보 확인형)은 생성·코퍼스 층위라 큐폼과 무관하다.

## 3. 노선 결정 — (나) 검색 입력 강화

두 노선이 있었고 **(나)로 확정**한다.

| | (가) 큐폼이 검색을 대체 | **(나) 큐폼이 검색 입력을 강화** ✅ |
|---|---|---|
| 리프에 `gt_docs` | 박는다 | **박지 않는다** |
| 문서 선택 주체 | 테이블 조회(결정론) | 기존 하이브리드 검색 |
| 문항 설계 기준 | 리프를 **유일하게 특정**하는 축 | **검색 쿼리를 풍부하게** 만드는 축 |
| 커버 안 되는 경로 | 트리에서 제거 필요(**차단요소**) | 검색이 처리, 최악이 기존 거절 경로(**참고사항**) |
| hit@3 해석 | 구조상 1.0 = 라벨링 품질 | 기존 지표와 동일 축에서 비교 가능 |

### (나)를 고른 이유

1. **기존 자산이 그대로 산다.** 하이브리드·RRF·소프트부스트·평가 방법론이 계속 주인공이다. (가)는 이것들을 큐폼 경로에서 무력화한다.
2. **평가가 한 축으로 유지된다.** (가)는 큐폼 경로와 일반 경로가 서로 다른 지표로 측정돼 "우리 시스템 성능은 X"를 한 숫자로 말할 수 없게 만든다.
3. **선행 작업이 사라진다.** (가)는 "모든 리프 경로가 38문서 안에서 gt를 가져야 함"이 착수 전 필수였다. fins `/cm/bbs/` FAQ 5건 robots 차단(H5)이 이 검증에 직접 걸려 있었는데, (나)에서는 차단요소가 아니게 된다.
4. **구현이 더 싸다.** §7 참조.

## 4. 전체 구조

> ⚠️ **rev.3(`QFORM_ARCH_설계스펙.md`)이 이 절을 대체한다.** 아래 `[게이트]` 전제는 D1으로 **폐기**됐다 — 큐폼은 게이트 없이 모든 질의에 슬롯 추출기를 돌린다.

```
질의 유입
  │
  ├─ 일반 질문(개념·단순) ──────────────→ 기존 파이프라인 → 답변
  │
  └─ 상황 설정형 ── [게이트] ──→ 큐폼
                                 │
                    자연어에서 슬롯 프리필(추가 콜 0)
                                 │
                    남은 슬롯을 챗에서 **한 개씩 순차 질문**
                                 │
                    확인 화면("작성 내용을 확인해주세요")
                                 │
                    슬롯 → 쿼리 직렬화 + 부스트 → 기존 검색 → 생성 → 답변
```

**게이트 방식**(멘토링 반영). 단 잠금은 아니며 탈출구를 상시 노출한다 — "그냥 물어볼게요" / "상담원 연결".

## 5. UI — 순차형(챗) 슬롯 채우기

> ⚠️ **rev.3(`QFORM_ARCH_설계스펙.md`)이 이 절을 대체한다.** "순차형 슬롯 채우기 폼" 전제는 D1으로 무효 — 되묻기는 `sub_task`가 잡혔는데 행이 안 좁혀질 때만 최대 2턴(예시 제시형)이다. 슬롯 스킵 가능 원칙은 유지된다.

한 화면 폼이 아니라 챗에서 한 슬롯씩 묻는다. 상태는 `session_state`에 `qform` dict + `cursor` 하나.

순차형이라서 추가로 필요한 것 세 가지:

| 항목 | 내용 |
|---|---|
| **확인 화면 필수** | 순차형은 3번째 답하다 1번을 되돌릴 수 없다. 마지막 확인·수정 화면이 선택이 아니라 **필수 구성요소**다 |
| **프리필 값어치 상승** | 한 화면에서는 "미리 선택됨"이지만 순차에서는 **질문 통째 생략 = 턴 수 직접 감소** |
| **자유입력은 별도 질문 없음** | 어느 턴에서든 선택지 대신 타이핑하면 `free_text`에 누적. "잘 모르겠어요"도 이 경로로 처리 |

### 설계 원칙 (불변 조건)

> **모든 슬롯은 건너뛸 수 있다.**

큐폼은 기관 신청서 메타포에서 왔지만, **사람들이 챗봇을 쓰는 이유가 신청서가 어려워서**다. "비법인단체 직원이신가요?"에 자신이 해당하는지 모르는 사용자가 다수이며, 착오송금은 특히 급한 사용자가 유입되는 업무다. 미선택(`null`)은 결함이 아니라 정상 입력으로 취급한다. 현행 소프트부스트가 `None`을 "부스트 미적용, 풀 유지"로 처리하므로 설계가 이미 호환된다.

선택지마다 한 줄 설명을 붙이고, "잘 모르겠어요"를 상시 노출한다.

## 6. 저장 구조 — 중첩 트리 대신 조합 테이블

### 왜 트리를 버리나

중첩 트리는 **순회 순서가 구조에 박혀 있다.** 사용자가 자연어로 "인터넷으로 신청하려는데요"만 말한 경우(= 상위 슬롯을 건너뛰고 하위 슬롯만 들어온 경우) 트리로는 표현이 안 된다.

### 조합 테이블

| combo_id | S2 세부주제 | S3 역할 | S4 자격 | S5 유형 | S6 채널 |
|---|---|---|---|---|---|
| C01 | 신청 | 송금인 | 본인 | * | 인터넷 |
| C02 | 신청 | 송금인 | 대리인 | 미성년자 | 방문 |
| C07 | 이의제기 | 수취인 | * | * | * |

`*` = 무관. **`gt_docs` 컬럼은 없다** — (나) 노선의 핵심.

### 이 구조가 주는 것

1. **어느 슬롯이 먼저 들어와도 동작.** 들어온 값으로 행을 좁히면 된다.
2. **활성화 규칙이 자동 도출.** 08-03 스펙에 손으로 적었던 `S5 활성: S4=대리인`, `Q1=제도안내 → Q2~Q5 스킵` 같은 규칙을 **유지보수할 필요가 없어진다.** 남은 행에서 어떤 슬롯의 값이 하나뿐이면 묻지 않고 채우고, 값이 전부 `*`면 묻지 않는다.
3. **다음 질문을 계산 가능.** 남은 행을 가장 고르게 쪼개는 슬롯을 고른다.
4. **관리자 콘솔 편집 자산이 중첩 JSON이 아니라 표.** 종합 단계 "폼 스키마 편집" 대상으로 적합.

**단, 질문 순서에 브레이크가 필요하다.** 정보이득만 따르면 사용자에게 순서가 이상하게 느껴질 수 있다("왜 이걸 먼저 물어?"). 사람이 정한 선호 순서를 기본으로 두고, **턴을 실제로 아낄 때만 재정렬**한다.

### 테이블 작성 원칙 — bottom-up

논리적으로 예쁜 조합을 top-down으로 짜면 문서에 근거가 없는 조합이 생긴다. 문서의 **"대상 / 제외 / 요건"** 서술에서 실제 분기 조건을 추출해 행을 만든다.

**경고등**: 업무당 실질 조합 15개 초과 시 슬롯 축이 잘못 잡힌 신호로 본다.

## 7. 자연어 프리필 — 가지치기 아님

들어온 자연어에서 슬롯을 추출해 미리 채운다. **단, 추출 결과로 행을 삭제하지 않는다.**

### 왜 삭제하면 안 되나

자연어 → 슬롯 추출은 결정론이 아니다. 잘못 추출되면 **정답 조합을 사용자가 보기도 전에 지운다.**

이건 이미 겪은 실패 구조다. 하드필터 → 소프트부스트 전환 때 정확히 같은 문제였다 — 분류기가 틀리면 정답 문서가 후보에서 아예 배제됐고, 부스트로 바꿔 graceful degradation을 얻었다(hit@1 +1.0pp, 퇴행 2건). **검색 층에서 배운 것을 폼 층에서 반복하지 않는다.**

### 규칙

| | 방침 |
|---|---|
| 행 처리 | **삭제 금지, 정렬만.** 확신 낮은 슬롯은 후순위로 미룰 뿐 후보에서 빼지 않음 |
| 사용자 노출 | 채워진 슬롯은 확인 화면에서 **보이고 고칠 수 있게.** 조용히 반영 금지 |
| 질문 생략 | 확실한 경우만 생략, 애매하면 "이거 맞나요?" 확인 |

### 추출 주체 — 결정론부터

슬롯 값이 전부 닫힌 enum이고 어휘가 좁다("인터넷/온라인/홈페이지" → 인터넷, "위임/대신/맡겨" → 대리인). 키워드 매핑으로 상당 부분 커버될 가능성이 높고 **콜 0, 실패면 증가 없음**이다.

관통 단계는 결정론으로 간다. LLM 추출은 결정론 커버리지를 측정한 뒤 붙일지 판단한다.

**S1(업무)은 이미 무료다.** MOAI 라우터가 D1~D6 도메인 분류를 하므로 추가 콜 없이 항상 프리필된다.

### 기대치 조정

"자연어에서 뭐가 잡히든 이득"이 아니다. **잡히는 슬롯이 무엇이냐에 따라 이득 편차가 크다.**

- S2(제도안내/신청/이의제기/수수료환급) — 한 방에 대부분 제거, 가지치기 능력 높음
- S6(채널) — 대부분 조합이 인터넷·방문 둘 다 허용하면 가지치기 능력 거의 없음

조합 테이블을 채우면 **슬롯별 가지치기 능력이 숫자로 바로 나온다**(값별 생존 행 수). 그 결과를 보고 자연어 추출을 어느 슬롯에 우선 걸지 정한다.

## 8. 구현 층 — 난이도와 스코프

| 층 | 하는 일 | 난이도 | 이번 스코프 |
|---|---|---|---|
| ① 쿼리 직렬화 | 슬롯 값 문자열 이어붙여 검색 | 반나절 | ✅ |
| ② S1 부스트 | 업무 슬롯 → 소프트부스트 입력 | 몇 줄 | ✅ |
| ③ 나머지 슬롯 부스트 | S3~S6 → 메타데이터 매칭 | **비쌈** | ⏸ 조건부 |
| ④ B-1 조건 필터링 | 슬롯 → 생성 프롬프트 조건 블록 | 중간 | ✅ |

### ①② 는 사실상 공짜

현행 `hybrid_bf`가 하는 일이 "질의 → 업무 분류 → 부스트"다. 큐폼은 **분류 단계를 사용자 선택으로 갈아끼우는 것**뿐이다. 분류기 불명 30%·오분류 9건이 이 두 줄에서 사라진다.

### ③ 이 조건부인 이유

청크 스키마 14필드 중 부스트 가능한 축은 `business_function` / `sub_category` / `page_type` / `coverage` / `variant`다. **S1은 대응되지만 S3(송금인/수취인)·S4·S5(대리인 유형)·S6(채널)은 대응 필드가 없다.** 제대로 하려면 청크 재태깅 + 인덱스 재구축이 필요하다.

대안: ③을 건너뛰고 해당 슬롯은 ①(쿼리 문자열)로만 흘린다. 공짜지만 효과가 BM25/dense 어휘 매칭에 좌우돼 **문서 본문에 그 표현이 실재해야** 한다. 가능성은 높다 — 미적중 22건의 형제문서 축이 정확히 `본인/대리인/미성년자/… × 송금인/수취인 × 인터넷/방문`으로, **슬롯 축과 동일**하다.

### ④ 에 실제 값어치가 몰려 있을 가능성

08-03 확인 사항: 대리인 7종 리프가 실제로는 **`MsdrprPossDcmntGudn` 문서 하나 안에** 다 들어있다.

- **검색 관점**: S5를 뭘로 채우든 같은 문서로 수렴 → hit@3 안 움직임
- **답변 관점**: "미성년자면 친권자 확인 증명서 + 친권자 합의서"만 뽑아줘야 함 → ④의 일

④는 **B-1(조건 필터링)** 이므로 프롬프트 규칙 1("참고문서에 없는 내용 답하지 마라")과 충돌하지 않는다. 문서에 있는 항목 중 해당분을 고르는 행위이기 때문이다.

> **B-2(조건 판정)는 이번 스코프 제외.** 예금자보호 한도 계산만 해당하며, 문서에 없는 결론을 생성하므로 규칙 1과 정면 충돌한다. 개별심사 고정문구 · 결정론 계산함수 · `answer_checks` 정합체크 세트가 갖춰진 뒤 별건으로 진행한다.

### 착수 전 필수 — 오라클 실험 (콜 0, 반나절)

400셋에 `business_function`이 이미 라벨돼 있다. 이를 **"사용자가 완벽하게 고른 S1"** 으로 간주하고 부스트를 확정 적용해 돌린다. 이것이 **②의 상한선**이다.

| 결과 | 해석 |
|---|---|
| +1pp 수준 | 큐폼의 값어치는 검색이 아니라 UX·접근성. **③에 투자할 이유 없음** |
| +5pp 수준 | ③ 재태깅 비용 정당화 가능 |

숫자 없이 ③까지 계획을 세우면 **"no numbers, no merge" 위반**이다.

## 9. 민원 처리 — 액션 리프 (어제 이월 안건)

### 결론: OOS 아님, 큐폼으로 처리

지금 조합 테이블의 종착점은 두 종류다 — **정보**(문서 인용), **서류**(양식 첨부). 여기에 **액션**(상담원 연결 · 민원 접수)을 추가한다.

**액션 리프는 `gt_docs`가 없어도 되는 유일한 종착점**이다. 따라서 "답할 문서가 없는 경로"의 착지점이 생기며, fins FAQ robots 차단(H5)이 만드는 커버리지 구멍의 안전망 역할도 한다.

### OOS로 보내면 안 되는 이유

1. **출력이 근본적으로 다르다.** OOS = "저희 소관이 아닙니다"(타 기관 안내). 민원 = **소관 안**이며 "접수를 도와드리겠습니다".
2. **라우터 설계와 충돌.** OOS는 학습이 아니라 open-set 스코어로 잡는 구조다(학습셋에서 OOS 700 기각). 민원을 OOS 라벨에 얹으면 OOS의 의미가 "예보 소관 아님"에서 "문서로 답 못함"으로 바뀌고, G5b AUROC이 무엇을 재는 지표인지 흐려진다.

### 구현 — 라우터 스키마 무변경

결정론적 프리필터로 `handoff` 분기를 만든다. 민원 어휘는 좁다(상담원·전화·연결·신고·접수·오류·버그). 라우터 모델은 건드리지 않는다.

```
rag / reject(OOS) / handoff(민원·큐폼)
```

### 미결 — 액션 리프의 산출물이 무엇인가

**"상담원 연결"을 안내만 할 거라면 슬롯을 채울 이유가 없다.** 번호만 알려주면 끝이며 큐폼을 거칠 필요가 없다.

큐폼으로 처리하는 것이 의미를 가지려면 **정리된 민원 내용을 생성하는 것**까지 가야 한다 — 사용자가 그대로 복사해 접수하거나 상담원에게 전달할 수 있는 요약. 슬롯이 그 요약의 필드가 된다. 실제 접수 시스템 연동은 PoC 범위 밖이다.

**결정 필요**: 액션 리프 산출물 = (i) 연락처 안내만 (ii) 구조화된 민원 요약문 생성

### 규칙 1 예외 여부 확인

대표번호(1588-0037)는 코퍼스 실재가 확인됐다(`answer_checks` 검증 기록). **오류·버그 신고 경로는 별개이며 미확인**이다. 코퍼스에 없다면 응답 문구를 코퍼스 밖에서 하드코딩해야 하는데, 이는 프롬프트 규칙 1의 예외를 여는 행위다. **명시적 결정 + DECISIONS 기록 대상**이며 암묵적으로 넣지 않는다.
