## 2. 표 청킹 수정 — 모든 수치의 전제

이 작업의 모든 측정은 아래 청킹 위에서 이뤄졌다. 다른 수치와 비교할 때 반드시 같은 청킹인지 확인해야 한다.

**문제** — `chunk.py`의 `_blocks()`는 "연속된 파이프(`|`) 줄 = 표"로 표를 잡는데, 표 셀 안의
`<br>` 다항목이 파이프 없는 줄을 만들면 거기서 표가 끊긴다. 보호대상 금융상품 표(2,330자)가
10청크로, 착오송금 구비서류가 20청크로 흩어져 조각마다 어느 업권·어느 행인지 알 수 없었다.

**해결** — 파이프 줄 사이의 비-파이프 줄을 셀 연속으로 흡수하는 유예값을 뒀다.

```python
CHUNK_SIZE = 800
OVERLAP = 100        # docstring과 실제 값이 어긋나 있던 드리프트 수정
MIN_CHUNK = 60       # 표 사이 낀 짧은 헤딩/라인 파편 병합 임계
TABLE_GAP_MAX = 12   # 표 안 파이프 없는 구간 흡수 유예. 0=엄격, None=무제한
```

```python
while i < len(lines):
    if "|" in lines[i]:
        last_pipe = i
        j = i + 1
        while j < len(lines):
            if "|" in lines[j]:
                last_pipe = j; j += 1
            elif TABLE_GAP_MAX is None or (j - last_pipe) <= TABLE_GAP_MAX:
                j += 1          # 셀 안 <br> 다항목 → 표의 일부로 흡수
            else:
                break
        out.append(("table", "\n".join(lines[i:last_pipe + 1])))
        i = last_pipe + 1
```

**결과** — 청크 `215 → 181`. 표가 쪼개지지 않도록 `CHUNK_SIZE` 초과를 허용하므로 최대 청크가
800자에서 **2,613자**가 된다. 이건 부작용이 아니라 "표는 분할하지 않는다"는 원칙의 귀결이다.

**주의 — 코드만 바꾸면 인덱스가 조용히 낡는다.** `pipeline.py`의 스킵 판정은 원본 HTML의
`content_hash` 기준이라 청킹 코드 변경을 감지하지 못한다. 같은 `chunk_id`가 다른 내용을 가리키게
되므로 청킹 코드를 고치면 **반드시** 재구축해야 한다.

```bash
python pipeline.py --rebuild
```

## 3. GT 스키마 정비 — 다중 스팬

### 3.1 무엇이 문제였나

기존 스키마의 근거 필드는 단수 문자열(`gt_anchor_span`) 하나였다. 그런데

- `and` — 한 질문의 답이 **두 개 이상의 청크를 합쳐야** 나오는 경우. gold 청크가 2~4개다.
- `or` — 한 질문의 답이 **두 청크 모두에** 있는 경우. 하나만 찾아도 답할 수 있다.

`and` 문항은 근거가 2~4개인데 스팬을 하나밖에 못 적으니 구조적으로 표현이 안 됐다.

### 3.2 스키마

`gt_anchors: list[str]`를 1급 필드로 올리고, gold 청크마다 스팬을 하나씩 대응시켰다.
`single`은 기존 단일 앵커를 1원소 리스트로 옮기기만 한다.

```json
{
  "id": "nat450-0107",
  "chunk_relation": "and",
  "gt_chunk_ids": ["...#02", "...#09", "...#11"],
  "gt_anchors":      ["스팬A", "스팬B", "스팬C"],
  "gt_anchor_spans": ["스팬A", "스팬B", "스팬C"]
}
```

`gt_anchors`와 `gt_anchor_spans`를 **둘 다 같은 값으로** 쓴다. 전자는 GT 생성 파이프라인
(`filter_anchored.py`)의 관례 필드이고, 후자는 채점기가 실제로 읽는 필드다. §5의 사고 이후
두 이름이 어긋나지 않도록 항상 함께 기록한다.

### 3.3 판정 규약

```
hit@k =
  and  : ∀ span : ∃ chunk ∈ top-k, normalize(span) ⊂ normalize(chunk.text)   (전부 필요)
  or   : ∃ span : ∃ chunk ∈ top-k, ...                                        (하나면 충분)
  single: 스팬 1개 (or과 동일)

normalize(s) = 공백 전부 제거
```

`chunk_id` 일치가 아니라 **본문 텍스트 포함 관계**로 판정한다. 재청킹으로 청크 경계가 바뀌어도
판정이 살아남는다 — `chunk_id`는 특정 청킹에 대한 좌표일 뿐이고 근거는 텍스트다.

### 3.4 라벨 보강은 정확도를 올리지 못한다 — 먼저 알아둘 것

작업 중 실증된 사실이라 앞에 둔다. **채점이 청크 단위 포함관계이므로, 같은 청크 안에서 어떤
문장을 스팬으로 고르든 hit/miss가 바뀌지 않는다.** 스팬을 청크 전체에서 짧은 문장으로 바꿔도,
자동 선택과 사람이 원문을 읽고 고른 선택을 비교해도 — 결과가 **소수점까지 동일**했다.

라벨이 수치를 움직이는 경우는 둘뿐이다.

1. **깨졌거나 불가능한 라벨을 고칠 때** — 스팬이 현재 코퍼스에 없으면 그 문항은 검색이 아무리
   잘 돼도 영원히 못 맞힌다.
2. **`and`가 요구하는 청크 개수를 바꿀 때** — 이건 정확히 '채점을 고치는' 행위다. 하면 안 된다.

**따라서 수기 라벨링에 시간을 쓸 수 없어도 정확도 손해는 없다.** 라벨 보강의 가치는 수치가
아니라 **라벨이 진짜 근거를 담고 있다는 신뢰성**에 있다.

### 3.5 부족한 근거를 직접 채웠다

**대상 선정** — `filter_anchored.py`로 만든 430 중, and/or 문항의 gold 청크마다 기존 앵커가
실제로 verbatim 커버하는지 확인했다. 60건(113슬롯)이 부족했는데, 겹치는 청크가 많아
**고유 청크 40개**만 채우면 전부 해결되는 구조였다(청크 하나가 여러 문항에 재사용됨 — 예:
착오송금 구비서류 표의 한 행이 "미성년자", "법인", "대리인" 등 여러 질문에 공통 근거로 쓰임).

**방법** — 재청킹으로 사라진 청크는 재청킹 이전 218청크 스냅샷에서 원문을 조회했다. 40개
청크 원문과, 그 청크를 필요로 하는 모든 질문을 함께 놓고 원문을 직접 읽어 질문에 실제로
답이 되는 문장을 그대로 발췌했다(청크 전체를 쓰거나 임의로 자르지 않음, 창작 없음).

**검증** — 골라낸 40개 스팬 전부에 대해 (a) 원 출처(현재 또는 구버전 청크) 원문에 정말
있는지, (b) 현재 181청크 코퍼스 어딘가에 verbatim으로 있는지(재청킹에서 살아남았는지) 둘 다
자동 확인했다. **전부 통과** — and/or 60건 전부 필요한 만큼 앵커가 채워졌다(커버리지 100%).

```bash
python data/curate_anchors_450.py
```

### 3.6 추론형 문항은 스팬을 만들지 않는다

`evidence_type=inferable`(계산·추론이 필요해 정답 문장이 원문에 없는 유형)은 근거 스팬이
구조적으로 존재할 수 없다. 여기에 스팬을 합성하면 '근거'가 아니라 청크를 가리키는
**locator**를 만들어 chunk_id 채점을 스팬 채점으로 위장하게 된다. 그래서 이 유형은 스팬을
만들지 않고, `filter_anchored.py`가 앵커 없는 문항으로 걸러 430 밖에 둔다.

전부 포함해 채점하려면(스팬이 없는 문항을 gold `chunk_id` 등장 여부로 대체 판정) 채점기의
`--id-fallback` 옵션을 쓴다(§4.1).

### 3.7 재청킹으로 사라진 gold — 되살리는 쪽을 택했다

표 원자성 수정으로 215→181 병합되며 사라진 gold `chunk_id`가 있다. 이 gold를 그냥 두면
스팬을 만들 원문이 없다.

경계해야 할 원칙이 있다 — **새 청킹에 맞춰 gold를 다시 매기면 검색이 좋아진 게 아니라 채점을
고친 것이 된다.** 이 작업이 거기 해당하는지 따져봤고, 아니라고 판단한 근거는 셋이다.

1. **`gt_chunk_ids`를 바꾸지 않았다.** 어떤 청크가 정답인지는 원본 그대로다. 바꾼 것은 그 gold가
   담고 있던 **근거 텍스트를 청킹 독립적인 형태로 표현**한 것뿐이다.
2. **방향이 반대다.** 위험한 것은 채점이 *쉬워지는* 쪽인데, 이 방식은 오히려 엄격하다 — 제외하면
   `and`의 요구 개수가 줄어 공짜 적중이 생기고, 되살리면 요구 개수가 그대로 보존된다.
3. **근거가 사라진 게 아니라 담는 그릇이 커진 것이다.** 표 병합으로 옛 청크의 내용은 새 청크
   안에 그대로 있다(내용 손실 0 확인). 옛 스냅샷을 보는 것은 *라벨이 무엇을 가리켰는지*를 읽는
   행위이지 채점 기준을 조정하는 행위가 아니다.

## 4. 채점 로직

정본 채점기는 `eval_anchor_span_multi.py`다.

```python
def _relation_mode(item):
    return "and" if item.get("chunk_relation") == "and" else "any"

def _item_metrics(item, retrieved_ids, chunk_text, id_fallback=False):
    spans_norm = [_norm(s) for s in _get_gt_spans(item)]
    ranks = [_rank_of_span_hit(s, retrieved_ids, chunk_text, RETRIEVAL_DEPTH) for s in spans_norm]
    for k in KS:
        found_at_k = [r for r in ranks if 0 < r <= k]
        if mode == "and":
            hits[f"hit@{k}"] = bool(ranks) and len(found_at_k) == len(ranks)
        else:
            hits[f"hit@{k}"] = bool(found_at_k)
```

`and`의 MRR은 "모든 스팬이 다 등장한 시점"이므로 `1/max(ranks)`를 쓴다.

### 4.1 스팬이 없는 문항 — `--id-fallback`

`evidence_type=inferable`은 스팬이 구조적으로 존재할 수 없다(§3.6). 스팬 0개를 그대로 두면
무조건 미적중이 되는데, 이건 검색 실패가 아니라 측정 결함이다. 이 경우에만 gold `chunk_id`
등장 여부로 대체 판정하는 옵션을 넣었다.

```bash
python eval_anchor_span_multi.py --gt data/gt_natural430_curated.jsonl --id-fallback
```

**기본은 꺼져 있다** — 기존 리포트가 그대로 재현되도록 하기 위해서다. `gt_natural430_curated.jsonl`은
and/or 커버리지가 100%라 이 옵션이 실제로 발동할 일이 거의 없다.

### 4.2 알려진 갭 (미조치)

`_relation_mode()`는 `and`가 아닌 모든 라벨을 조용히 ANY로 처리한다. 지금 쓰는 라벨
(`single`/`or`/`near_dup`/`duplicate`/`contained`)은 의도와 우연히 일치하지만, **새 라벨이
들어오면 경고 없이 관대하게 채점돼 지표가 부풀 수 있다.** 알 수 없는 라벨에 예외를 던지는
가드를 넣는 것이 안전하다.

## 5. 발견한 사고 — `and` 채점이 작동한 적이 없었다

**증상** — `and` 문항의 스팬을 1개에서 2~4개로 전부 채워 넣고 다시 채점했는데, 리포트가 GT 경로
한 줄을 빼고 **완전히 동일**했다.

**원인** — 채점기가 읽는 필드는 `gt_anchor_spans`(복수형)인데, GT 생성 파이프라인이 쓰는 필드는
`gt_anchors`였다. 채점기는 `gt_anchors`를 모르므로 매번 `None`으로 떨어졌고, 그 아래 폴백인
`gt_anchor_span`(단수 문자열 1개)으로만 채점되고 있었다.

```python
def _get_gt_spans(item):
    spans = item.get("gt_anchor_spans")      # 채점기가 읽는 필드
    if spans is None:
        spans = item.get("gt_anchor_span")   # 단수 폴백 — 여기로 계속 떨어지고 있었다
```

즉 스팬을 아무리 채워도 **`and`의 ALL 판정이 실제로는 한 번도 수행된 적이 없었다.**
4개 중 1개만 맞아도 적중으로 처리되고 있었다.

**영향** — 필드를 맞춰 진짜 ALL 판정을 하자 `and` Hit@5가 **0.927 → 0.709**로 떨어졌다.
성능이 나빠진 게 아니라, 과대평가돼 있던 수치가 제자리를 찾은 것이다.

**교훈** — 라벨을 보강했는데 지표가 **정확히 그대로**면 개선이 없는 게 아니라 반영이 안 된
것일 수 있다. 보강 전후로 채점기가 실제로 읽은 스팬 개수를 찍어 확인해야 한다.

```python
lens = [len(m._get_gt_spans(x)) for x in and_items]
Counter(lens)   # {2: 33, 3: 15, 4: 7}  ← gt_chunk_ids 개수와 일치해야 정상
```

## 6. 검색 개선 실험 — 4건 실측, 1건 채택

### 6.1 실패 구조 진단

`and` 문항 실패를 뜯어보니 패턴이 뚜렷했다 — 대부분 "완전 미회수"가 아니라 **간발의 차**였다
(한 스팬은 top-5 안인데 나머지가 6~10위로 경계 밖). 필요 청크가 같은 문서인 경우와 다른
문서인 경우가 반반이었다. 이걸 회수하는 방향으로 가설 셋을 세워 실측했다.

### 6.2 채택/기각

모든 실험은 **TEST 430(`gt_natural430_curated.jsonl`)·VAL 355 두 셋 모두에서 개선되는
값만 채택**한다는 규율로 판정했다. 한쪽만 좋아지는 값은 그 셋의 특성을 학습한 것이라
일반화되지 않는다.

| 처방 | 착안 | 실측 | 판정 |
|---|---|---|---|
| **1차 결과로 업무 역추론** | 키워드 분류기 기권 구간에 업무 부스트가 안 걸린다 | TEST `.872→.877` · VAL `.839→.842` · 기권구간 `.843→.860` | **채택** (§6.3) |
| 형제 청크 점수 전파 | `and` 필요 청크가 같은 문서인 경우가 절반 | 두 셋 모두 λ>0에서 단조 하락. 주지표 `single`이 밀려남 | 기각 |
| MMR 다양성 재랭킹 | top-5가 중복으로 차서 상보 청크가 밀린다 | hit@5는 어떤 β에서도 개선 없음. **단 hit@3은 β=0.8에서 두 셋 모두 개선**(TEST `.756→.770`, VAL `.761→.772`) | 기각(hit@5 기준) |
| 복합질의 분해 | 실패 질문 다수가 "A는? B는?" 형태 | 실제로 분해된 질의가 TEST 430건 중 **11건(2.6%)**뿐이라 효과 없음 | 기각 |

**형제 전파와 MMR은 정반대 방향의 처방**이다. 전자는 같은 문서 청크를 끌어올리고 후자는 중복을
덜어낸다. 둘 다 hit@5를 못 올렸다는 건, 현재 top-5 구성이 이미 균형점에 가깝다는 뜻이다.

**복합질의 분해가 안 먹힌 이유**는 분해기가 물음표(`?`)와 접속어만 보기 때문이다. 실패 질문
상당수는 물음표가 하나뿐인 복합문이다.

> "회사 명의로 안 찾아간 돈이 있는데 법인은 **뭘 준비해서 어디로 가야** 하죠?"

의문사 2개(`뭘`/`어디로`)를 인식하는 절 단위 분해기로 개선하면 적용 범위가 넓어질 수 있다.
현재 구현은 `eval_query_decomp.py`에 남겨뒀다.

> **라벨 누수 금지.** 분해 여부를 `chunk_relation`으로 정하면 정답을 보고 검색 전략을 바꾸는
> 것이라 평가가 무의미해진다. 오직 질문 문자열의 형태만 보고 결정했고, 따라서 `single` 문항에도
> 동일하게 적용된다. 형제 전파·MMR도 같은 원칙으로 정답을 참조하지 않는다.

### 6.3 채택 — 1차 검색 결과로 업무 역추론

키워드 분류기 `classify_query_bf()`는 점수·마진 임계에 못 미치면 `None`을 반환하고, 그러면
업무 부스트가 통째로 안 걸린다. 기권 구간을 뜯어보니 대부분 '모호'가 아니라 **사전에 걸리는
말이 아예 없는 경우**였다. 임계값 조정이나 사전 확장으로는 근본 해결이 안 된다.

**키워드에 없을 뿐 dense 검색기는 이미 그 질의를 의미적으로 이해하고 있다.** 신호가 사전이
아니라 1차 검색 결과에 있다는 착안으로, 의사 적합성 피드백(pseudo-relevance feedback)을 썼다.

```
1) 부스트 없이 1차 융합 → 상위 N개
2) 그 N개의 business_function을 순위 가중 투표(1/rank) → 우세 업무 득표 비중이 임계 이상이면 채택
3) 그 업무로 부스트를 걸어 2차 랭킹
```

키워드가 확신할 때는 그대로 쓰고 기권할 때만 역추론값을 쓴다. 정답 `business_function`을
참조하지 않고 검색 결과에서만 추론하므로 실배포 경로에서 그대로 동작한다(라벨 누수 없음).

`crawler/rag.py`에 반영:

```python
QBF_PRF_TOPN = 5          # 투표에 쓸 1차 상위 개수
QBF_PRF_MIN_SHARE = 0.40  # 1위 업무 득표 비중이 이 값 이상일 때만 채택. None이면 비활성
```

| | TEST 430 | VAL 355 |
|---|---:|---:|
| 적용 전 | 0.872 | 0.839 |
| 적용 후 | **0.877** | **0.842** |
| 기권 구간만 | 0.843 → 0.860 | 0.810 → 0.816 |

TEST·VAL 두 셋 모두에서 개선되는 것을 확인하고 채택했다. **한계** — VAL의 `hit@1`은 소폭
손해다(`.493→.482`). `hit@5`가 목표 지표라 채택했지만 top-1만 노출하는 UI라면 재검토해야
한다. 끄려면 `QBF_PRF_TOPN = None`.

### 6.4 파라미터

4축(`RRF_ALPHA`, `BF_BOOST`, `FACET_BOOST`, `BF_DOC_CAP`)을 다시 스윕한 결과 **현재값이
이미 최적**이라 바꾸지 않았다. `BF_DOC_CAP`은 cap=5와 무제한을 비교해도 결과가 완전히
동일해, 현재 코퍼스·K에서는 사실상 발동하지 않는 상수임도 확인했다.

```python
RRF_ALPHA   = 0.6
RRF_K       = 5
BF_BOOST    = 0.04
FACET_BOOST = 0.05
BF_DOC_CAP  = 5
```

> **파라미터는 청킹·질의분류기와 한 세트다.** 청킹이나 분류기가 바뀌면 반드시 다시 스윕해야 하고,
> 다른 조건에서 뽑힌 값을 그대로 가져오면 안 된다.

## 7. 남은 개선 여지 — 질의 분류기

§6에서 기권 구간을 일부 메웠지만, 질의 분류는 여전히 가장 큰 단일 레버다. 상한을 오라클
(정답 `business_function` 주입)로 쟀다.

| 경로 | TEST 430 Hit@5 | `and` |
|---|---:|---:|
| 현재(키워드 + 역추론) | 0.877 | 0.745 |
| **오라클(완벽한 분류)** | **0.888** | 0.764 |
| 남은 상한 이득 | **+0.011** | +0.019 |

즉 분류를 완벽하게 만들어도 `+0.011`이 천장이다. **현재 검색 파이프라인에서 짜낼 수 있는
여지는 여기까지**라는 뜻이기도 하다.

학습 모델로 교체한다면 저장소의 `router_electra/`, `router_moai/` 노트북이 출발점이다.
체크포인트는 용량이 커서 `.gitignore` 대상이므로 **부재 시 키워드로 폴백하는 현재 구조를
유지**해야 한다. 분류기는 어휘 신호가 없는 질의에서 무너지기 쉬우므로 TEST·VAL 양쪽에서
반드시 확인해야 하고, 역추론(§6)이 이미 그 구간을 일부 가져갔으므로 **역추론 대비 증분**으로
평가해야 한다.

### 그 밖에 남은 것

- **`고객 미수령금 신청` 업무** Hit@5 0.814로 가장 취약한 축에 속한다. top-5를 잠식하는 청크가
  소수 문서에 몰려 있다. 업무 내부 문서들이 주제가 겹쳐 랭킹 경쟁이 심한 구조적 문제라 전역
  파라미터로는 안전하게 못 고친다.
- **미지 relation 라벨 가드** (§4.2)
- **stale gold 처리 방식 재검토** (§3.7) — 현재는 되살려 요구하는 엄격한 쪽.
