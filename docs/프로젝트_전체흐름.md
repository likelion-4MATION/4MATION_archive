# 4MATION — 프로젝트 전체 흐름

예금보험공사(KDIC) 공개 웹사이트의 안내 데이터를 모아, **자연어로 물으면 근거와 함께
답하는 챗봇**을 만드는 기술 검증(PoC) 프로젝트다.
`2026-07-10 ~ 2026-09-02` · LikeLion AI/NLP 5기 · 클라비 기업 연계.

---

## 1. 무엇을 만들었나 — 세 덩어리

```
    ┌─────────────────────────────────────────────────────────────┐
    │ ① 데이터 파이프라인                                          │
    │   예보 웹사이트 38페이지 → 본문만 추출 → 조각내기 → 검색용 색인 │
    └────────────────────────┬────────────────────────────────────┘
                             ↓  코퍼스 181조각 + 색인
    ┌─────────────────────────────────────────────────────────────┐
    │ ② 챗봇                                                       │
    │   질문 → 소관 판정 → 업무 분류 → 조각 검색 → LLM이 근거로 답변  │
    │          (되물을 게 있으면 되묻고, 소관 밖이면 안내처를 알려줌)  │
    └────────────────────────┬────────────────────────────────────┘
                             ↓
    ┌─────────────────────────────────────────────────────────────┐
    │ ③ 관리자 콘솔                                                │
    │   비전공자가 코드 없이 파라미터 조정·재수집·성능 측정·안내처 관리 │
    └─────────────────────────────────────────────────────────────┘
```

**왜 이렇게 나눴나** — 챗봇의 답이 틀리면 원인이 셋 중 하나다. ①에서 원문을 잘못 잘랐거나,
②에서 엉뚱한 조각을 찾았거나, LLM 이 근거를 벗어났다. 세 층을 갈라 두면 **어디가 틀렸는지
따로 잴 수 있다.**

## 2. 챗봇이 질문 하나를 처리하는 순서

```
사용자: "착오송금 반환 신청 서류가 뭐예요?"
   │
   ├─ ① 절 나누기        한 문장에 용건이 여러 개면 쪼갠다
   │
   ├─ ② 업무 분류        6개 업무 중 무엇인가? (로컬 AI 모델 — 65ms, 무료)
   │     └─ 못 고르면 → 소관 밖 처리 → 타기관 안내처 or 유선 상담 안내
   │
   ├─ ③ 되묻기 판정      본인/대리인? 개인/법인? 온라인/방문?
   │                     서류가 갈리는데 정보가 없으면 **최대 2번** 되묻는다
   │
   ├─ ④ 조각 검색        181조각 중 관련된 5개를 찾는다
   │                     (의미 검색 + 키워드 검색을 합치고, 업무 가산점을 얹는다)
   │
   ├─ ⑤ 답변 생성        찾은 조각만 근거로 LLM(HCX)이 답한다
   │                     "참고문서에 없으면 답하지 마라 · URL을 새로 만들지 마라"
   │
   └─ ⑥ 검증·첨부        생성된 답의 URL·숫자를 규칙으로 점검, 근거 문서 첨부
```

**핵심 원칙 하나** — LLM 은 **찾아준 조각 안에서만** 답한다. 모델이 아는 지식으로
보충하지 않는다. 그래서 "그럴듯한 답"이 아니라 **"근거 있는 답"** 이 된다.

## 3. 용어 사전 — 이 프로젝트에서 계속 나오는 말

### 3-1. 데이터 다루는 말

| 용어 | 뜻 | 왜 중요한가 |
|---|---|---|
| **코퍼스** | 챗봇이 볼 수 있는 문서 전체. 여기서는 예보 웹사이트 38페이지 | 코퍼스에 없는 건 답할 수 없다 |
| **청킹 / 조각** | 긴 페이지를 검색 단위로 자르는 것. 현재 **181조각** | 너무 크면 관련 없는 내용이 섞이고, 너무 작으면 문맥이 끊긴다 |
| **청크** | 자른 조각 하나. 800자 목표, 문단·섹션 경계 우선 | — |
| **표 원자성** | 표는 중간에서 자르지 않는다는 규칙 | 표를 자르면 "어느 업권의 어느 행"인지 알 수 없어진다. 지키지 않으면 업권 비교 질문 정확도가 0.82 → 0.31 로 떨어졌다 |
| **첨부** | 페이지에 걸린 PDF·HWP 서식 파일 | 답변에 "이 서식을 쓰세요"를 붙이려면 필요 |
| **doc_id / chunk_id** | 문서·조각의 고유 이름 | `chunk_id` 는 **자를 때마다 바뀐다** — 그래서 평가 기준으로 쓰면 안 된다(§5-2) |

### 3-2. 검색하는 말

| 용어 | 뜻 | 비유 |
|---|---|---|
| **임베딩** | 문장을 숫자 목록(1024개)으로 바꾸는 것. 뜻이 비슷하면 숫자도 비슷해진다 | 문장마다 좌표를 주는 것 |
| **의미 검색 (dense)** | 임베딩 좌표가 가까운 조각을 찾는다 | "잘못 보낸 돈" ↔ "착오송금" 을 같은 뜻으로 본다 |
| **키워드 검색 (BM25)** | 단어가 실제로 겹치는 조각을 찾는다 | 고유명사·숫자에 강하다 |
| **하이브리드 / RRF** | 위 두 결과의 **순위**를 합치는 방법 | 둘 다 상위에 올린 조각을 신뢰한다 |
| **BF (business function)** | 6개 업무 분류. 아래 §4 | 질문이 어느 업무인지 알면 그 업무 문서에 가산점을 줄 수 있다 |
| **소프트부스트** | 같은 업무 문서에 점수를 **더한다**(배제하지 않는다) | 분류가 틀려도 정답이 후보에서 사라지지 않는다 |
| **doc cap** | 한 문서에서 뽑을 조각 수 상한(5개) | 긴 문서가 상위를 독점하는 것을 막는다 |
| **PRF** | 1차 검색 결과로 업무를 거꾸로 추정하는 것 | 분류기가 기권했을 때의 마지막 수단 |

### 3-3. 챗봇 동작하는 말

| 용어 | 뜻 |
|---|---|
| **RAG** | Retrieval-Augmented Generation. **찾아서(Retrieval) 그걸 근거로 답하기(Generation)** |
| **Qform (큐폼)** | 되묻기 장치. 서류가 갈리는 조건(본인/대리인 등)을 슬롯으로 채우고, 안 채워지면 되묻는다 |
| **슬롯** | 되묻기가 채우는 항목 5개 — `party`(본인/대리인) · `sub_task`(무슨 일) · `qualification`(개인/법인) · `subject`(대상) · `method`(온라인/방문) |
| **조합 테이블** | 슬롯 조합별로 어떤 서류가 필요한지 적은 표. **답변 값은 이 표에서만 온다** |
| **OOS (Out Of Scope)** | 소관 밖 질문. "날씨 어때요" 또는 "금감원 민원 넣는 법" |
| **라우팅** | 질문을 어디로 보낼지 정하는 것. 이 프로젝트에서 **두 층**이다 — §4-2 |
| **오케스트레이터** | 절 나누기 → 라우팅 → Qform/RAG 또는 OOS 로 흘려보내는 최상위 조율기 |
| **HCX** | 네이버 CLOVA Studio 의 LLM. 답변 생성과 OOS 세부분류에 쓴다 |

### 3-4. 측정하는 말 — 여기가 제일 헷갈린다

| 지표 | 뜻 | 읽는 법 |
|---|---|---|
| **hit@k** | 정답 근거가 **상위 k개 안에 들었는가**의 비율 | `hit@5 = 0.89` → 100번 물으면 89번은 정답 근거가 top-5 안에 있다 |
| **MRR@10** | 정답이 **몇 등**으로 나왔는지의 평균(역수). 1등이면 1.0, 2등이면 0.5 | 높을수록 정답이 위쪽에 온다 |
| **Recall@k** | 정답 근거가 **여러 개일 때 몇 개나** 회수했는가 | 복합 근거 질문용 |
| **앵커텍스트 판정** | 정답을 "이 조각 번호"가 아니라 **"이 구절이 들어있는가"** 로 판정 | 조각을 다시 자르더라도 판정이 유지된다. 현재 **정본 판정 방식** |
| **AUROC** | 두 집단(소관 안/밖)의 점수를 얼마나 잘 **갈라내는가**. 0.5 = 동전 던지기, 1.0 = 완벽 | `0.83` = 무작위로 뽑은 소관밖 질문이 소관내 질문보다 높은 점수를 받을 확률 83% |
| **MSP** | 모델이 고른 답에 대한 확신도(0~1). Max Softmax Probability | 높으면 확신. 다만 §5-4 참조 — 이 모델은 near-OOD 에서도 확신한다 |
| **Energy** | 확신도의 다른 계산법(`-logsumexp`). **낮을수록 소관 안** | 이 모델에서는 MSP 보다 잘 가른다(AUROC 0.860 vs 0.806) |
| **오차단 (FPR)** | 소관 **안**인 질문을 잘못 막은 비율 | 이게 커지면 챗봇이 쓸모없어진다 |
| **σ (표준편차)** | 같은 조건을 여러 번 돌렸을 때 결과가 흔들리는 폭 | **σ 의 2배보다 작은 개선은 개선이라 말할 수 없다** — §5-5 |
| **held-out** | 학습에 쓰지 않고 평가에만 쓰는 데이터 | 학습에 쓴 데이터로 평가하면 점수가 부풀려진다 |

## 4. 6개 업무와 두 층의 라우팅

### 4-1. 6개 업무 (BF)

이 프로젝트의 모든 분류가 이 6종을 쓴다. 정의의 출처는 `crawler/crawl_manifest.csv` —
**코퍼스 38페이지가 실제로 어느 업무로 태깅돼 있는지**가 조작적 정의다.

| 업무 | 무엇에 답하나 | 코퍼스 |
|---|---|---:|
| **예금자보호제도** | 보호 한도(1억), 보호 대상 금융회사·상품 | 6페이지 |
| **예금보험금 안내** | 금융회사가 문 닫았을 때 받는 돈, 신청 절차·서류 | 3페이지 |
| **고객 미수령금 신청** | 안 찾아간 돈(파산배당금·개산지급금 정산금), 상속인 조회 | 4페이지 |
| **착오송금 반환 신청** | 잘못 보낸 돈 되찾기. 절차·구비서류·유의사항 | 12페이지 |
| **채무조정 안내** | 빚 조정, 신용회복·개인회생·파산면책, **부채증명원 발급** | 8페이지 |
| **은닉재산 신고** | 부실관련자 숨긴 재산 제보, 포상금 | 4페이지 |

> **주의** `부채증명원/금융거래정보신청` 페이지는 **채무조정 안내** 밑에 있다. "증명서 발급"
> 질문이 착오송금(구비서류 페이지가 많다)으로 오분류되는 원인이 이 어휘 중첩이다.

### 4-2. 라우팅 두 층 — 대체 관계가 아니다

| | **업무 6분류** | **소관 판정 (OOS)** |
|---|---|---|
| 무엇으로 | 로컬 AI 모델(MoAI 0.6B) | 같은 모델의 **기권**으로 판정 |
| 판정 | 6개 중 하나 | 기권(확신 < 0.70)하면 소관 밖 |
| 쓰임 | 검색 가산점 · 되묻기 범위 | 소관밖은 검색·생성 없이 안내처로 닫음 |
| 비용 | 65ms, LLM 콜 0 | 같음 |
| 모델이 없으면 | 키워드 규칙으로 폴백 | 폴백도 기권 규칙을 그대로 씀 |

**소관 밖으로 판정되면** LLM(HCX)이 5개 중 하나를 고른다 —
`BOT_FEEDBACK`(챗봇 오류 신고) · `REFERRAL`(등록된 타기관 안내) · `CASUAL`(인사) ·
`FAR_OOS`(명백히 무관) · `PHONE_GUIDE`(불확실하면 유선 상담). **기관명·연락처는 관리자가
등록·검증한 값만** 쓴다 — 모델이 URL·전화번호를 만들지 못하게 하는 장치다.

## 5. 이 프로젝트가 배운 것 — 다섯 가지

### 5-1. "잘 되는 것 같다"와 "잰 것"은 다르다

자연어로 몇 개 물어보면 소관밖 처리가 잘 되는 것처럼 보인다. 그런데 1,150문항으로 재면
**금융 인접 질문(near-OOD)은 4개 중 3개가 통과한다.**

| 집단 | 라우터가 막는 비율 |
|---|---:|
| 완전 무관 (날씨·여권) | 47.5% |
| **금융 인접 (금감원·신복위·보이스피싱)** | **25.0%** |
| 경계 (애매한 것) | 6.0% |

**그럼에도 실사용이 괜찮은 이유** — 신복위·보이스피싱 같은 질문은 **코퍼스에 "그건 저희
소관이 아니고 ○○○ 담당입니다"가 실제로 적혀 있어서** RAG 가 그걸 찾아 답한다.
라우터가 막은 게 아니라 코퍼스가 답한 것이다. 이건 좋은 동작이고 설계 의도이기도 하다
("거절보다 안내"). **다만 공로를 잘못 돌리면 다음 개선을 엉뚱한 데 한다.**

→ `records/router_판정경계_측정_20260825.md`

### 5-2. 평가 기준이 흔들리면 개선을 못 잰다

정답을 "이 조각 번호"로 적어두면, 조각 크기를 바꿀 때마다 번호가 달라져 **성능이 아니라
판정 방식 때문에 수치가 움직인다.** 그래서 정답을 **구절(앵커텍스트)** 로 바꿨다.
조각을 다시 잘라도 그 구절을 따라가면 된다.

효과는 두 가지였다 — hit@5 가 `.765 → .828` 로 올랐고(같은 검색기인데 판정이 정확해진 것),
더 중요하게는 **재라벨링 없이 청킹 실험을 할 수 있게** 됐다.

### 5-3. 파라미터와 코퍼스는 한 세트다

표 원자성을 고쳐 코퍼스가 215 → 181조각이 되자, 기존 파라미터가 8,064개 조합 중
**883등**이 됐다. 조각이 자기완결적이 되면서 "메타데이터 가산점"의 상대 기여가 줄었기
때문이다 — **메타는 본문이 빈약할 때의 대용품**이고, 본문이 채워지면 물러나야 한다.

→ 재튜닝했다: `RRF_K` 1→4 · `BF_BOOST` .12→.06 · `FACET_BOOST` .15→.05.
**옛 청킹에서 새 파라미터를 쓰면 성능이 떨어진다. 따로 인용하면 안 된다.**

### 5-4. 확신도가 높은 것과 맞는 것은 다르다

라우터에게 "신용회복위원회 개인워크아웃 신청은 어디서 하나요"를 물으면 **확신도 0.9999** 로
`채무조정 안내` 라고 답한다. 소관 밖인데 확신한다. 반면 "금융감독원에 민원 넣으려면"은
0.5526 으로 기권한다.

**어휘를 공유하는 소관밖 질문(near-OOD)은 모델이 자신 있게 틀린다.** 이건 설계 단계에서
예측했던 사각지대이고(`plans/작업계획서_초기라우팅_B안채택.md` §5-1), 그래서 평가를
far/near 로 쪼개 놓았다. 예측이 맞았다.

### 5-5. 같은 조건을 세 번 돌려야 개선인지 알 수 있다

라우터 성능(G5b AUROC)을 같은 설정으로 시드만 바꿔 3번 돌리면 **0.790 ~ 0.827** 로
흔들린다(σ = 0.015). 그런데 08-06 실험은 **시드 1개**로 0.830 을 보고했고, 그 값이
이후 모든 비교의 기준이 됐다.

**즉 기준값 자체가 운 좋은 한 번이었다.** 정직한 기대값은 **0.809 ± 0.015** 다.
학습 데이터를 4배로 늘리고 증강을 두 방향으로 넣어도 개선 폭이 이 흔들림(2σ = 0.03) 안에
들어와, **개선했다고 말할 수 없었다.**

→ 규칙: **σ 를 붙여서 인용한다. 2σ 를 넘지 않으면 개선이 아니다.**
