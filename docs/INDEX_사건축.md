## 1. 평가셋이 검색기를 따라다녔다 → 앵커텍스트 전환

**문제** 정답이 **문서 단위**로 라벨링돼 있어, 실제 답변 근거가 아닌 청크가 검색돼도
정답 처리됐다(Parent-Child 문제). 청크 단위로 바꾸면 청킹 파라미터를 만질 때마다
전체 재라벨링이 필요했다.

**원인** `gt_chunk_ids` 는 **특정 청킹에 대한 좌표**다. 재청킹하면 일부 id 가 사라지고,
사라진 id 를 필수 조건으로 남기면 `and` 문항이 영구 불가능해진다.

**해결** 청크마다 **정답 구절(앵커텍스트) 자체**를 라벨로 저장한다. 청크 사이즈가
바뀌어도 구절을 따라가며 자동 매칭되므로 재라벨링이 없다. 동일 구절이 여러 곳에 있으면
중복 라벨로 대응한다. 08-05 회의에서 대안 2개(청크 단위 재라벨링 · 문서 전체 LLM 전달)를
기각하고 최종 채택했다.

**효과** TEST hit@5 **.765 → .828**. 부수 효과가 더 크다 — 재청킹으로 `chunk_id` 가
밀려도 판정이 유지된다(앵커 305/305 잔존).

**근거**
`superseded/앵커텍스트_정답라벨링_초기아이디어.md` → `records/앵커텍스트_정답라벨링_파이프라인.md`

## 2. 업무 필터가 정답을 배제했다 → 하드필터 → 소프트부스트

**문제** 질의 업무(BF)로 검색 후보를 **하드 필터**하면, 업무 분류가 틀린 순간 정답이
후보에서 아예 사라진다.

**원인** 분류 오류가 검색 실패로 증폭된다. 오분류 1건 = 정답 회수 불가 1건.

**해결** 필터가 아니라 **가산점**(`BF_MODE="soft"`, `BF_BOOST`)으로 바꿨다. 같은 업무
문서에 점수를 더할 뿐 다른 업무를 배제하지 않는다. 08-06 회의에서 "라우팅 결과를 큐폼에도
**가중치로만** 반영" 으로 같은 원칙을 확장했다.

**근거** `records/진행도_2607/진행도_하드필터_공백정규화_20260721_1551.md` ·

## 4. 표가 조각나 업권 비교가 깨졌다 → 표 원자성

**문제** 보호대상 금융상품 표(2,330자)가 **10청크**로, 착오송금 구비서류가 **20청크**로
흩어졌다. 조각마다 어느 업권·어느 행인지 본문만으로 알 수 없어, 여러 업권을 비교하는
질문의 정확도가 0.82 → 0.31 로 떨어졌다.

**원인** `_blocks()` 의 "연속 파이프 줄 = 표" 휴리스틱이, **셀 안 `<br>` 다항목**이 만든
파이프 없는 줄에서 끊긴다. `crawler/HOLES.md` 상태 요약표 H13 행이 이미 등재한 홀이었다.

**해결** `TABLE_GAP_MAX=12` — '표 → 설명 → 표' 구조에서 몇 줄까지 함께 묶을지 정한다.
코퍼스가 215 → **181청크**로 줄었다(청크가 자기완결적이 됐다).

**연쇄 효과** 청크가 자기완결적이 되면서 메타 기반 부스트의 상대 기여가 줄어
파라미터를 재튜닝해야 했다 — `RRF_K` 1→4 · `BF_BOOST` .12→.06 · `FACET_BOOST` .15→.05.
**파라미터와 청킹은 한 세트다.** 옛 청킹(215)에서 `RRF_K=4` 를 쓰면 성능이 떨어진다.

**근거** `records/방법론_정확도개선_결론_20260818.md` §04·§05 · `crawler/HOLES.md` H13 ·
코드 `crawler/chunk.py:TABLE_GAP_MAX` · `crawler/rag.py` 파라미터 주석

## 5. 질의 업무 분류기가 43%를 기권했다 → 라우터 교체

**문제** 키워드 분류기의 실패는 '오답'이 아니라 **'침묵'** 이었다 —
정답 54.6% · 오답 2.0% · **기권 43.4%**. 기권하면 BF 부스트가 아예 안 걸린다.

**해결 경로**
1. **08-04** A안(OOS 이진 직접 학습) vs B안(6업무 분류 + 스코어 임계) → **B안 채택.**
   A안은 소수 기관 음성만 학습하면 "소관밖" 대신 "그 기관 토픽"을 배워 첫 대면 질의를
   통과시킨다. B안은 음성 데이터 0건으로 그 함정을 우회한다.
2. **08-05** 후보 4종(KR-electra · Kcelectra · finance-kcelectra · MOAI) 파인튜닝 비교
   → **MOAI 채택.** 속도(약 4배 느림)보다 정확도 우위 우선. OOS 학습셋 700건은 **기각**.
3. **08-06** MoAI vs kf-deberta — near-OOD(G5b) AUROC **0.830 vs 0.720**
4. **08-14** `classify_query_bf` 를 라우터 6분류로 교체. 시그니처 불변이라 호출부 무수정

**효과** 기권 361문항에서 hit@5 **.535 → .609**.

## 6. 소관밖 질의에도 LLM 콜이 나갔다 → 라우터 기반 OOS

**문제** 소관밖 질의에도 HCX 분류 콜 1회(평균 1,318ms)가 나갔다. 그리고 LLM 세계지식
오류로 오차단이 생겼다 — id19 "퇴직연금 5천만원까지만 별도 보호 맞나요?" 가
*"퇴직연금은 근로복지공단 담당"* 으로 차단됐다.

**해결** 절별 라우터 판정으로 옮겼다. `route_clause()` → `rag.classify_query_bf(clause)`
→ **기권(MSP < 0.70)이면 OOS** → `oos_policy.classify_oos()` 가 5개 action 중 하나로 닫는다
(`BOT_FEEDBACK` · `REFERRAL` · `CASUAL` · `FAR_OOS` · `PHONE_GUIDE`).
기관명·URL·전화번호는 **관리자 레지스트리의 게시·검증된 값만** 쓴다.

**⚠ 상태: 부분** 실사용 체감은 좋지만 지표는 다르다. dev 1,150 기준 —

| 집단 | 차단율 |
|---|---:|
| far-OOD (G5a) | 47.5% |
| **near-OOD (G5b)** | **25.0%** |
| 경계 (G6) | 6.0% |
| in-scope 오차단 | 5.76% |

신복위·보이스피싱·전세보증 질의는 **라우터를 통과한다**(MSP 0.9999·0.9964·0.9998).
그럼에도 잘 처리되는 것은 **코퍼스에 타기관 안내가 실재해 RAG 가 답하기 때문**이다
(`OOS_처리로직_계획서` §4 의 "답변 가능한 OOS", P6 "거절보다 안내").
위험 구간은 **코퍼스에 안내 근거가 없는 near-OOD** 다.

**근거** `plans/OOS_처리로직_계획서.md` · `current/OOS_구현_운영가이드.md` ·
**`records/router_판정경계_측정_20260825.md`**(수치화) · `current/KDIC_소관경계_정리.md` ·

## 7. 복잡한 질의를 한 번에 못 받았다 → Qform

**문제** "착오송금 반환 신청 서류 알려주세요" 하나로는 답이 안 나온다 — 본인/대리인,
개인/법인, 온라인/방문에 따라 구비서류가 갈린다.

**첫 설계가 무효화됐다** 기획서 v1 은 **객관식 폼 + 게이트**(상황설정형 질의만 진입)를

**해결** 설계스펙 rev.3 **D1 에서 게이트를 폐기**하고, Qform = **슬롯 추출기 + 조건부
되묻기**로 재정의했다. 모든 질의에 결정론 추출기를 돌리되 `sub_task` 가 잡히고도 조합이
안 좁혀질 때만 되묻는다. 되묻기 발동률 **2.0%** — 오발동을 막았다.

**핵심 원칙** 되묻기 선택지 값은 **조합 테이블 생존 행에서만** 온다. v1 에서 부연 4개가

도 따로. 수치의 출처가 갈렸다.

**해결** `crawler/eval.py` 하나에 서브커맨드 3개로 합쳤다 —
`chunk`(정본) · `span`(다중 span AND) · `gold`(앵커-host + Wilson CI·nDCG·McNemar).
**등가성 회귀 테스트**(`crawler/tests/test_eval_equivalence.py`)로 판정이 같은지 못박았다 —
구 평가기와 반환 dict·리포트 바이트까지 비교한다.

**뒤이어** 판정 기준을 **앵커텍스트 전용**으로 고정했다(`--score` 기본 `anchor`).
`gt_chunk_ids` 는 청킹 좌표라 재청킹하면 수치가 판정 방식 때문에 움직인다.

**근거** `DECISIONS` D13 · `records/handoff/eval_유상.md` · `archive/README.md`(은퇴 19개) ·
코드 `crawler/eval.py` · `crawler/tests/test_eval_equivalence.py`

## 10. 파라미터를 바꿀 사람이 코드를 못 만졌다 → 관리자 콘솔

**문제** 검색 5축·청킹 4축·생성 파라미터를 조정하려면 파일을 고쳐야 했다. 비전공자

③ 잣대가 다른 두 수치를 나란히 빼지 않는다(앵커 hit@5 vs 청크 hit@k)

## 11. 체크포인트 2.38GB 를 git 에 넣을 수 없었다 → HF 프라이빗 repo

**문제** `pytorch_model.bin` 2.38GB. GitHub 단일 파일 100MB 상한, Release 에셋도 2GB 상한.

**해결** 임베딩 모델이 런타임에 HF 에서 받아 캐시하는 것과 **같은 패턴**으로 라우터도
HF 프라이빗 repo(`us788/moai_yebo_ft`)에서 받는다. `crawler/router_source.py` 가
`ROUTER_PATH`(env) → 로컬 디렉토리(크기 일치) → `hf_repo` → `None`(키워드 폴백) 순으로
해석한다. **예외를 던지지 않는다** — 체크포인트가 없어도 검색은 돌아야 한다.
단 `chatbot/chain.py`·`admin/jobs.py` 는 `HF_HUB_OFFLINE=1` 로 돌기 때문에 챗봇·콘솔 경로에서는
자동 다운로드가 일어나지 않는다 — `scripts/download_router_hf.py` 로 미리 받는다(`SETUP.md` §7).

**함정** 재학습하면 **매니페스트도 갱신해야 한다.** 안 하면 `resolve()` 가 새 로컬 파일을
"크기 불일치"로 보고 HF 의 옛 가중치를 받아온다 — 조용히 다른 모델을 쓰게 되는 최악의 실패.

**근거** `current/router_checkpoint.md` · 코드 `crawler/router_source.py` ·
`scripts/upload_router_hf.py` · `scripts/download_router_hf.py`
