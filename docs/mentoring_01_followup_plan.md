## 0. 먼저 확인할 것 — 사전 자료 수치 정정

`mentoring_01_report.md` 부록이 지적한 대로, 멘토링에 들어간 사전 질의서 자체에 두 가지 오류가 있었다.

1. "bge-m3 모델 사용"이라고 썼지만 그 시점 락 걸린 베이스라인은 `jhgan/ko-sroberta-multitask`(768d)였다.

멘토가 사전 질의 5·6번(현업 수용 컷, 검색지표-답변만족도 상관)에 명확한 수치를 안 준 이유가 이 오표기 때문일 수 있다는 게 보고서의 추정이다. 2차 자료에서는 반드시 "hit@3 94.5% = 검색 성공률이지 답변 정확도가 아니다"를 먼저 정정하고 들어가야 재질의가 의미가 있다.

## 2. 실행안 — 항목별 상세

### 2-1. 정답 판정 단위 재설계: 문서 vs 청크 + cap 정책

**문제의 실체** (앞선 대화에서 코드로 확인한 내용 요약):

- `build_testset.py:8`: 정답은 `parent_doc_id`(문서) 단위로만 라벨링돼 있음.
- `eval_TF.py`의 `first_hit_rank()`는 청크의 `parent_doc_id`가 `gt_docs`에 속하기만 하면 무조건 hit 처리 → 같은 문서 안에서 엉뚱한 청크가 뽑혀도 정답으로 채점됨.
- 실서비스(`chain.py:196`, `mode="hybrid_bf"`)에서는 `rag.py`의 `BF_DOC_CAP=1`이 걸려 있어 문서당 청크를 **딱 1개**로 잘라낸다. 즉 진짜 정답 청크가 아닌, 그 문서 안에서 스코어가 가장 높았던 청크 하나만 실제로 LLM에 들어간다.
- 정리하면: **채점(문서 단위, 관대함) ↔ 실제 주입(청크 1개, 극단적으로 좁음)** 사이 간극이 지금 문제의 핵심이다.

**실행 스텝**:

1. **라벨 스키마에 `gt_evidence` 추가** — `gt_docs`는 유지하고, 문항마다 실제 근거가 되는 `chunk_id` 리스트를 새 필드로 추가한다. 이미 있는 항목을 지우는 게 아니라 옆에 병기하는 것(문서-라벨과 근거-청크-라벨을 동시에 인정 = "멀티 라벨"의 실체, §5 용어 참고).
2. **`eval_TF.py`에 evidence-hit@k를 doc-hit@k와 병행 리포트** — 지금처럼 문서 단위 지표 하나만 내지 않고, 두 지표를 나란히 낸다. 둘의 격차(doc–evidence gap)가 곧 "검색은 맞는데 근거는 틀린" 비율을 드러낸다.
3. **`BF_DOC_CAP=1` 정책 재설계** — 대안 두 가지를 팀이 이미 제시함:
   - **확장된 cap**: `BF_DOC_CAP`을 1보다 크게(예: 2~3) 올려서, 같은 문서 안에서도 여러 후보 청크가 살아남게 한다. 구현은 단순하지만 상위권이 다시 한 문서로 쏠리는 문제(cap을 두는 원래 이유)가 재발할 수 있다.
   - **MMR(Maximal Marginal Relevance)**: 정보검색의 고전적 다양성 확보 기법. 매 스텝마다 "관련성은 높은데 이미 뽑힌 것들과는 겹치지 않는" 후보를 우선 선택한다(`λ·관련성 - (1-λ)·기존 선택분과의 유사도` 최대화). 하드 cap처럼 "문서당 몇 개"를 못박지 않고, 실제로 정보가 겹치는지 여부로 다양성을 판단하므로 같은 문서 안에서도 서로 다른 정보를 담은 청크는 둘 다 살아남을 수 있다. `rag.py`의 `_cap_by_doc()`([rag.py:307](../crawler/rag.py#L307))를 대체하는 자리에 넣을 수 있다.
   - 팀 판단이 필요한 지점: MMR은 구현·튜닝 비용이 cap 확장보다 높다. 이번 주 범위에서는 **cap 확장으로 먼저 검증하고, 효과가 부족하면 MMR로 넘어가는 단계적 접근**을 권장.

### 2-2. LLM에게 넘기는 데이터 단위·구조 확정

현재 `chain.py:197`은 검색된 청크 텍스트를 그대로 이어붙이기만 한다(청크 구조 없이 flat concat). "주입 청크 3~5개(페이지 1~2개 분량)"를 결정하려면 아래 세 가지 방식 중 하나를 택해야 한다.

| 방식 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. cap 완화 + top-k 그대로** | 2-1에서 cap을 확장한 결과를 그대로 3~5개 반환 | 구현이 가장 단순, 기존 파이프라인 재사용 | 랭킹이 밀리면 페이지 내 관련 문맥이 빠질 수 있음 |
| **B. bounded parent(이웃/섹션 확장)** — `phase3_milestone.md` M2.3 | top-1 hit 청크를 중심으로 같은 문서 내 앞/뒤 이웃 청크를 강제로 몇 개 붙임 | 문맥 파편화 보완, whole-doc보다 안전 | FAQ/표처럼 이웃이 완전히 무관한 원자 청크인 경우 오염 위험 → 문서 타입별 예외처리 필요 |
| **C. 진짜 parent-child 청킹** | 원문을 child(작게, 예 400자)와 parent(크게, 예 2000자) 두 크기로 각각 슬라이스해 이중 인덱싱, 검색은 child로 하고 반환은 그 child가 속한 parent 블록 | 검색 정밀도(child)와 생성 문맥(parent)을 분리 최적화 | 중간 크기 parent 레이어를 새로 만들어야 함 — 청킹 파이프라인 재설계 비용 큼 |

멘토가 "청크 단위 vs 페이지 단위 둘 다 실험해보라"고 한 것도 이 결정과 연결된다(현장 메모: "청크 단위로도 실험해봤지만, 페이지 단위로도 같이 실험해보는 것을 추천"). **이번 주는 A(cap 완화)로 빠르게 베이스라인을 만들고, 시간이 되면 B(이웃 확장)를 표/FAQ 제외 문서에 한해 A/B 비교**하는 순서를 권장한다. C는 청킹 재설계(M2.1)와 함께 가는 게 맞아 이번 주 범위 밖으로 둔다.

### 2-3. 라우팅 경계 방향성 개편

멘토 확정 방향은 **규칙 기반 → Structured Output → 의도 분류기**의 3단계 로드맵이다. 현재 `chain.py`의 `classify()`([chain.py:143](../chatbot/chain.py#L143))는 이미 HCX(LLM) 1콜로 정상/모호/소관밖을 분류하고 있다 — 사실상 3단계 중 가장 무거운 방식을 맨 처음부터 쓰고 있는 셈이다. 멘토 권고를 따르면 순서가 거꾸로 된 상태이므로:

1. **1단계(규칙 기반)**을 먼저 붙여서, `rag.py`의 `classify_query_bf()`([rag.py:109](../crawler/rag.py#L109))처럼 이미 있는 결정론적 키워드 분류가 소관밖 판정에도 어느 정도 커버되는지 측정.
2. 규칙 기반으로 못 거르는 잔여 케이스에 한해 **Structured Output**(LLM 응답을 JSON 스키마로 강제 — 이미 `CLS_PROMPT`가 JSON 출력을 요구하고 있어 사실 이 단계에 가장 가까움, §5 참고)을 유지.
3. 마지막에 **의도 분류기**(경량 학습 모델, LLM 아님)로 대체할지는 비용·지연 데이터가 쌓인 뒤 판단(=`phase3_milestone.md` M3.1과 동일 과제).

"라우팅 경계"는 구현 방식뿐 아니라 **분류 경계 자체**(현재 정상/모호/소관밖 3분류에서 "모호"를 정상과 동일하게 rag 라우트로 보내는 `_route()`([chain.py:167](../chatbot/chain.py#L167)) 로직)도 재검토 대상으로 포함해야 한다 — 지금은 "모호"가 사실상 아무 특별 처리 없이 "정상"과 같은 경로를 타고 있다.

### 2-4. 표 청킹 — 직접 태깅 옵션 추가

기존 계획(`phase3_milestone.md` M2.2)은 표 내부 당사자(송금인/수취인 등) section-scoping을 **결정론적 규칙**으로 자동화하는 방향이었다. 8/3 팀 논의에서 나온 새 옵션은 **모든 표 문서를 사람이 직접 태깅**하는 방식이다.

- 규칙 기반의 한계: 착오송금 구비서류처럼 당사자×경로 축이 22건씩 겹치는 근접중복 표는 규칙만으로 경계를 딱 자르기 어렵다(`phase3_milestone.md` M1.4가 이미 지적한 문제와 동일 축).
- 수동 태깅의 비용: 표가 있는 문서 수만큼(전체 38건 매니페스트 중 일부) 사람이 직접 어떤 행/열이 어떤 질문에 대응하는지 표시해야 함 — 문서 재수집 때마다 재작업 필요 여부 확인 필요.
- 권장: 표 개수가 많지 않다면(38건 매니페스트 규모), **우선 수동 태깅으로 빠르게 정답을 만들고, 그 정답을 규칙 기반 자동화의 검증 기준(gold set)으로 재사용**하는 순서가 효율적이다. 규칙을 먼저 짜고 나중에 검증하는 것보다, 정답을 먼저 확보하는 편이 규칙의 정확도를 측정할 기준을 준다.

### 2-5. 임베딩 모델 ko 교체 — 완료, 결과 보고용 정리

`emb-ko` 브랜치에서 `BAAI/bge-m3` → `dragonkue/BGE-m3-ko`로 교체하고 `testset_natural_400`(400건)으로 평가를 마쳤다.

| mode | hit@1 | hit@3 | MRR |
|---|---|---|---|
| dense | 0.662 → **0.698** | 0.850 → **0.885** | 0.766 → **0.799** |
| hybrid | 0.632 → **0.672** | 0.865 → **0.892** | 0.751 → **0.786** |
| hybrid_bf(배포모드) | 0.672 → **0.718** | 0.945 → 0.945(동일) | 0.802 → **0.830** |

배포 모드 hit@3은 그대로지만 hit@1·MRR이 전 모드에서 뚜렷하게 올랐다(정답이 top-3 안에서 더 상위로 옴). 멘토의 "리트리버 모델들의 성능이 유사하다"는 발언과는 다소 배치되는 결과라, **2차 자료에서 이 표를 직접 들고 재질의할 가치가 있다** — 다만 held-out이 아닌 기존 튜닝셋(400건) 기준이라는 단서는 같이 밝혀야 한다(§2-6과 연결).

### 2-6. 테스트셋 재편: validation 100건 + 생성/검색 지표 분리

멘토 확정 방향 두 가지가 겹쳐서 하나의 작업이 된다:

1. **"train/valid/test 분리보다 난이도를 올려라"** — 지금 400건 자연어화 테스트셋은 실제로는 RRF 파라미터 튜닝(`RRF_ALPHA`, `RRF_K`)과 이번 임베딩 모델 비교(§2-5)에 **같은 세트**를 반복 사용하고 있어 `phase3_milestone.md`가 우려한 "낙관 편향" 상태 그대로다.
2. **"생성작업과 검색작업을 분리해서 평가"** — 지금 hit@3을 "정확도"로 착각한 것도 결국 이 분리가 안 됐기 때문이다(§0).

팀이 정한 **validation 100건**은 `phase3_milestone.md` M0.1(held-out 구축)의 구체적 규모로 볼 수 있다. 다음 원칙으로 만드는 걸 권장:

- 이 100건은 **어떤 파라미터 튜닝(RRF, cap, 임베딩 모델 비교)에도 쓰지 않는다** — 최종 검증 전용.
- 검색 지표(doc-hit@k, evidence-hit@k, §2-1)와 생성 지표(실제 LLM 답변이 맞았는지, `answer_checks.py` 기반 검증)를 **별개 표**로 낸다. 지금처럼 하나의 hit@3 숫자로 뭉치지 않는다.
- 구조적 개편(§2-1~2-3)이 먼저 끝나야 라벨 스키마(`gt_evidence`)와 채점 기준이 확정되므로, **validation 100건 구축은 구조적 개편 이후 순서**로 두는 게 맞다 — 팀이 이미 이 순서를 인지하고 있음("구조적 개편에 맞춰서 평가셋 재편 가능성").

### 2-7. 라벨 조정

사전 질의서 논의사항 마지막 항목("정답이어도 오답처리하는 오류 발견")과 `gt_evidence` 신설(§2-1)은 사실 같은 작업으로 묶인다.

- **기존 `gt_docs` 오태깅 재검수**: 지금 400건 중 정답 문서가 누락되었거나 잘못 들어간 항목을 먼저 골라낸다(멘토가 지적한 "정답인데 오답처리" 케이스).
- **`gt_evidence` 신규 라벨링**: §2-1에서 결정한 스키마대로 문항마다 근거 청크를 사람이 확인해 추가.
- 두 작업을 한 번에 하는 이유: 어차피 문항 하나하나를 다시 열어봐야 하는 작업이라, `gt_docs` 검수와 `gt_evidence` 부여를 같은 패스에서 처리하는 게 두 번 열어보는 것보다 효율적이다.
- **재청킹 취약성 주의**: `chunk.py`의 청킹 규칙(`CHUNK_SIZE`, `OVERLAP`)이 바뀌면 `chunk_id`가 전부 무효화된다. `gt_evidence` 라벨링은 **청킹 구조가 안정화된 뒤**(청킹 재설계가 이번 주 범위가 아니라면 지금 상태 기준으로) 진행해야 재작업을 피할 수 있다.

## 5. 용어 정리 (이번에 새로 등장한 개념)

| 용어 | 의미 |
|---|---|
| **`gt_docs`** | 테스트셋 문항의 기존 정답 라벨. 정답으로 인정하는 문서(`parent_doc_id`)들의 리스트. 문서 단위라 청크 단위 오차를 못 잡음. |
| **`gt_evidence`** (신설 예정) | `gt_docs`에 추가할 새 라벨. 문항마다 실제 근거가 되는 정확한 `chunk_id` 리스트. 여러 개일 수 있음(멀티 라벨). |
| **doc-hit@k / evidence-hit@k** | `gt_docs` 기준 채점(느슨) / `gt_evidence` 기준 채점(엄격)을 병행하는 이중 지표. 둘의 격차가 클수록 "문서는 맞았지만 근거는 틀린" 비율이 높다는 뜻. |
| **멀티 라벨(multi-label)** | 정답으로 인정하는 단위(문서든 청크든)를 1개로 고정하지 않고, 있는 만큼 리스트로 인정하는 라벨링 방식. `gt_docs`가 이미 여러 문서를 허용했던 것처럼 `gt_evidence`도 여러 청크를 허용. |
| **`parent_doc_id`** | 청크 하나하나에 붙는 메타데이터 필드. "이 청크가 어느 원본 문서에서 나왔는가"를 가리키는 구조적 정보일 뿐, 그 자체로 정답 여부를 뜻하지 않음. |
| **`BF_DOC_CAP`** | `rag.py`의 하이브리드 검색(`hybrid_bf`)에서 한 문서가 top-k 결과를 독점하지 못하게 문서당 반환 청크 수를 제한하는 파라미터. 현재 1로 고정. |
| **MMR (Maximal Marginal Relevance)** | 검색 결과 재정렬 기법. "관련성은 높지만 이미 뽑힌 결과들과는 정보가 겹치지 않는" 후보를 우선 선택해 다양성을 확보. 하드 cap과 달리 문서당 개수를 못박지 않고 실제 정보 중복 여부로 판단. |
| **Bounded parent (이웃/섹션 확장)** | 검색된 청크를 중심으로 같은 문서 내 이웃 청크 몇 개를 추가로 붙여 반환하는 전략. 문서 전체(whole-doc)를 통째로 반환하는 것보다 안전하지만, 진짜 parent-child 인덱싱과 달리 별도 저장 없이 기존 청크를 재사용. |
| **Parent-child 청킹** | 원문을 child(작은 단위, 검색용)와 parent(큰 단위, 생성용) 두 가지 크기로 각각 슬라이스해 이중으로 인덱싱하는 전통적 RAG 패턴. 검색은 정밀한 child로, 반환은 문맥이 풍부한 parent로 한다. |
| **Structured Output** | LLM 응답을 정해진 JSON 스키마 형식으로만 강제하는 기능. 대부분의 최신 LLM이 지원하며, 자유 서술형 응답보다 파싱이 안정적이라 "약한 분류기" 용도로 쓸 수 있음. |
| **TTFT (Time To First Token)** | 사용자가 질문한 뒤 챗봇이 응답을 시작하기까지 걸리는 시간. 멘토 권고 목표치는 3~5초. |
| **낙관 편향 (Optimistic Bias)** | 파라미터 튜닝에 썼던 데이터로 그 파라미터의 성능을 다시 평가할 때 생기는 착시. 같은 세트를 반복 사용하면 실제 일반화 성능보다 지표가 좋게 나옴. |
| **Held-out / Validation set** | 튜닝에 전혀 노출되지 않은 독립 평가 세트. `phase3_milestone.md` M0.1이 요구하던 것과 동일 개념, 이번에 100건 규모로 구체화됨. |
| **리랭커 (Reranker)** | 1차 검색 결과 상위 후보를 다시 정밀하게 재정렬하는 2단계 모델. 멘토는 hit@1과 hit@50~100 격차가 크면(정답이 상위권 밖에는 있지만 최상위는 아님) 투입 시점이라고 언급. |
