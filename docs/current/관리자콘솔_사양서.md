## 0. 설계 원칙 — 왜 숫자를 그대로 보여주지 않는가

검색 5축(`RRF_ALPHA` `RRF_K` `BF_BOOST` `FACET_BOOST` `BF_DOC_CAP`)은 **8,064개 조합을 전수 탐색해서 고른 한 점**이다. `rag.py` 주석에 명시돼 있다.

> **이 값들은 181청크 코퍼스와 한 세트다.** 옛 청킹(215)에서 `RRF_K=4`를 쓰면 single이 .8946 → .865로 떨어진다.

개별 슬라이더를 주면 검증된 적 없는 조합이 즉시 만들어진다. 실제로 그리드 결과를 보면 **한 축만 바꿔도 성능이 무너지는 조합이 존재**한다(예: 430셋 단독 최적 `bf=0.18`은 355셋을 .8254 → .8028로 깎음).

그래서 **프리셋 3단계**로 묶는다. 각 프리셋은 그리드에서 실측된 조합만 쓴다.

### 정직한 경고 — "정확도 ↔ 속도"는 검색 5축에 없다

관리자가 기대하는 "느리지만 정확 ↔ 빠르지만 대략" 트레이드오프는 **검색 파라미터에 존재하지 않는다.** 5축은 전부 순위 계산 방식이라 계산량이 사실상 같다.

응답시간을 실제로 움직이는 레버는 따로 있다.

| 레버 | 실측 효과 |
|---|---|
| OOS 조기차단 | reject 경로 **1,318ms** vs rag 경로 **4,956ms** (약 1/4) |
| 참고문서 개수 `k` | k↑ → 프롬프트 길이↑ → 생성 시간·토큰 비용↑ |
| 큐폼 되묻기 상한 | 되묻기 1턴 = 왕복 1회 추가 (템플릿 모드는 LLM 콜 0) |
| 큐폼 문구 모드 | ⓐ템플릿 = 0콜 / ⓑLLM = 턴당 +1콜 |

콘솔 UI는 이 둘을 **다른 탭**으로 분리한다. 섞으면 관리자가 검색 프리셋을 바꾸고 속도가 안 변한다고 혼란스러워한다.

## 2. 사이드 고정 패널 — 변경 사항 추적 (전 탭 공통)

설정이 7개 탭에 흩어져 있으면 **관리자가 무엇을 바꿨는지 잊는다.** 그래서 우측에 항상 붙어 있는(sticky) 패널 하나가 **탭과 무관하게** 미저장 변경분과 예상 결과를 보여준다.

### 2-1. 구성

```
┌ 변경 사항            [3건 변경 · 미적용] ┐
│ 참고문서 수 (①번 탭)                    │
│   3 → 5                                │
│ 겹치는 분량 (⑦번 탭)                    │
│   100자 → 200자   [재빌드 필요]          │
├────────────────────────────────────────┤
│ 지표          현재      변경 후          │
│ 정확도 hit@5  0.9081    ?      [미측정]  │
│ LLM 콜/질의   1.72      1.72   [계산]    │
│ 평균 응답시간  4.0초     4.0초   [계산]   │
│ 비용/질의     ₩9.7      ₩9.7   [추정]    │
├────────────────────────────────────────┤
│ ⚠ 재빌드가 필요한 변경 1건 …             │
│           [되돌리기]  [저장 (재빌드 필요)] │
└────────────────────────────────────────┘
```

각 변경 항목에 **어느 탭에서 바꾼 값인지** 병기한다. 되돌아가서 확인하는 동선을 줄인다.

### 2-2. 지표별 산출 방식과 신뢰 등급

값 옆에 **등급 배지**를 붙여 어디까지가 실측인지 드러낸다. 이게 없으면 관리자가 추정치를 실측으로 오해한다.

| 지표 | 등급 | 산출 |
|---|---|---|
| 정확도 (hit@5) | **측정** / 복합 / 미측정 | 실제 A/B를 돌린 조합의 값만 표시 |
| LLM 콜 / 질의 | **계산** | 경로 비중 × 경로별 콜 수(reject 1콜 / rag 2콜) + 되묻기 LLM 모드 발동분 |
| 평균 응답시간 | **계산** | 경로 비중 × 경로별 실측(reject 1.32초 / rag 4.96초) |
| 비용 / 질의 | **추정** | 콜 수 × 답변 길이 계수 |

### 2-3. ⚠️ 정확도는 지어내지 않는다

정확도에 영향을 주는 축은 셋이다 — **검색 프리셋 · 참고문서 수 `k` · 문서 처리(청크)**. 실측이 있는 지점만 숫자를 낸다.

| 상황 | 표시 | 배지 |
|---|---|---|
| 변경 없음 | 현재값 | 측정 |
| 한 축만 변경 + 그 값이 측정된 지점 | 실측값 | **측정** |
| 한 축만 변경 + 미측정 지점 | `?` | **미측정** |
| **두 축 이상 동시 변경** | `?` | **복합** |

**두 축을 같이 바꾸면 효과가 곱해지지 않는다.** 예컨대 "프리셋을 균형으로 + `k`를 5로"의 결과는 두 실측치로 계산할 수 없다. 이 경우 안내 문구를 띄운다 — *"정확도에 영향을 주는 항목을 두 가지 이상 동시에 바꿨습니다. 조합 효과는 곱해지지 않으므로 예측할 수 없습니다 — A/B 평가가 필요합니다."*

실측 보유 지점:

| 축 | 측정된 값 |
|---|---|
| 검색 프리셋 | 정확도 우선 .9054 · 균형 .8946 · 다양성 .8892 (TEST 430) |
| 참고문서 수 `k` | **k=3 → .8108 · k=5 → .9081** (181청크). k=1·2·4는 미측정 |
| 문서 처리 | §9-9의 4개 조합만 |

### 2-4. 재빌드 변경의 분리

`CHUNK_SIZE`·`OVERLAP`·`MIN_CHUNK`·`TABLE_GAP_MAX`·`원문 재수집`은 변경 목록에 **`재빌드 필요`** 태그가 붙고, 저장 버튼이 `저장 (재빌드 필요)`로 바뀐다. 이 상태에서 저장을 누르면 즉시 반영하지 않고 **⑦ 문서 처리 탭으로 안내**한다 — A/B 평가를 거치지 않은 재빌드를 막기 위해서다.

### 2-5. 요구사항 요약

| # | 요구사항 |
|---|---|
| 1 | 우측 상단 **sticky** — 모든 탭에서 스크롤과 무관하게 보인다 |
| 2 | 변경 항목마다 **소속 탭 번호** 병기 |
| 3 | 지표마다 **측정 / 계산 / 추정 / 미측정** 배지 |
| 4 | 미측정·복합 변경은 **숫자를 비운다** (`?`) |
| 5 | 재빌드 변경은 태그로 분리하고 저장 경로를 다르게 |
| 6 | 변경 없으면 되돌리기·저장 **비활성** |
| 7 | 정확도 하락 시 경고 박스 (현재값 → 변경값 명시) |

## 6. 탭 ④ 최신성 가드 — 관리자 정정 규칙

### 6-1. 왜 필요한가

크롤링 원문은 **수정하지 않는다**는 것이 이 프로젝트의 불변 규칙이다. 그런데 법령·수치는 바뀌고, 홈페이지가 항상 즉시 갱신되지도 않는다. 실제로 우리 코퍼스 안에 **구값이 남아 있다.**

| 위치 | 원문에 남은 값 | 현행 |
|---|---|---|
| 상속인 금융거래조회 (`ProtSystHrpeHistInq`) | "상속인의 예금과 합산하여 **5천만원** 한도 여부를 판단" | 1억원 (2025-09-01~) |
| 착오송금 웹툰 (`MtrsGvbkSprtProc#01~02`) | "5만 원에서 **5천만 원** 사이" / "1천만원 초과 **5천만원** 이하" | 5만원 ~ **1억원** |

실측 사고도 있다. 트랩 문항 **"예금자 보호 한도가 5천만원 맞죠?"** 에 챗봇이 **"네, 5천만원입니다"**로 답했다. 검색이 구값 청크를 물었고, 인용 청크에 실제로 5천만원이 있어서 검증기도 통과했다. **확인형 질문은 사용자의 오정보를 승인하기 때문에 롤렛보다 위험하다.**

이 층은 신규 발명이 아니다. `QFORM_DECISIONS_HOLES.md`에 이미 원칙으로 적혀 있다.

> **소스 원문 무수정** — 최신성 보정은 답변 레이어(`global_guards`)에서만. outcome에 stale 수치 하드코딩 금지(H17).

이 탭은 그 `global_guards`를 **관리자 UI로 노출**하는 것이다.

### 6-2. ⚠️ 핵심 제약 — 자유 서술을 그대로 프롬프트에 넣으면 안 된다

관리자가 빈 텍스트 상자에 아무 문장이나 적고 그것이 프롬프트에 들어가면 **네 가지가 동시에 깨진다.**

| # | 깨지는 것 | 이유 |
|---|---|---|
| 1 | 생성 프롬프트 규칙 1 | "참고문서에 없는 내용은 답하지 마라"와 정면 충돌 |
| 2 | `answer_checks.check_numbers` | 관리자가 넣은 "1억원"이 컨텍스트에 없으므로 **전건 경고**로 잡힌다 |
| 3 | 출처 표기 | `[출처N]`을 붙일 대상이 없다 |
| 4 | 인젝션 표면 | 관리자가 악의 없이 쓴 "그리고 무조건 …라고 답해"가 시스템 지시로 먹힌다 |

그래서 **자유 서술이 아니라 구조화된 폼**으로 받는다.

### 6-3. 가드 항목 구조

| 필드 | 입력 방식 | 필수 | 설명 |
|---|---|---|---|
| `제목` | 텍스트 (40자) | ✅ | 목록에서 식별용. 예: "예금보호한도 1억원 상향" |
| `유형` | 선택 3택 | ✅ | **정정 / 보충 / 금지** (§6-4) |
| `발동 조건` | 키워드 다중 입력 | ✅ | 이 단어가 질문·참고문서에 있을 때만 적용. 예: `보호한도` `5천만원` |
| `적용 업무` | 업무 6종 다중선택 | ✅ | 전체 또는 특정 업무만. 좁힐수록 안전 |
| `기존 값` | 텍스트 (30자) | 정정형만 | 코퍼스에 남아 있는 낡은 값. 예: `5천만원` |
| `정정 값` | 텍스트 (30자) | 정정형만 | 예: `1억원` |
| `안내 문장` | 텍스트 (2문장·200자) | ✅ | 답변에 그대로 들어갈 문장 |
| `근거` | 텍스트 (60자) | ✅ | 예: "예금자보호법 시행령 개정(2025-09-01)". **답변에 출처로 표기됨** |
| `적용 시작일` | 날짜 | ✅ | |
| `적용 종료일` | 날짜 | — | 비우면 무기한. 지나면 자동 비활성 + 알림 |
| `우선순위` | 0~100 | — | 가드끼리 충돌할 때 높은 쪽이 이김 |
| `승인 상태` | 초안 / 승인됨 | ✅ | **초안은 실서비스에 반영되지 않는다** |

작성자·수정일시는 자동 기록(감사·롤백용).

### 6-4. 유형 3종

| 유형 | 쓰는 상황 | 답변에서의 동작 |
|---|---|---|
| **정정** (override) | 코퍼스에 낡은 값이 남아 있음 | 새 값으로 답하고, 문서에 구값이 있으면 **"안내 문서 일부에 이전 기준이 남아 있을 수 있습니다"**를 덧붙인다 |
| **보충** (append) | 문서에 아직 없는 사실 | 문서 근거 답변 뒤에 별도 문단으로 덧붙인다 |
| **금지** (block) | 답하면 안 되는 주제 | 답변 생성을 건너뛰고 상담 연결 문구로 대체 |

**정정형이 가장 중요하고 가장 많이 쓰인다.** 우리 실제 사례가 전부 정정형이다.

### 6-5. 답변에 어떻게 나타나는가 (예시)

관리자 입력:

```
제목      : 예금보호한도 1억원 상향
유형      : 정정
발동 조건 : 보호한도, 5천만원, 예금자보호
적용 업무 : 예금자보호제도, 예금보험금 안내, 고객 미수령금 신청
기존 값   : 5천만원
정정 값   : 1억원
안내 문장 : 예금보호한도는 2025년 9월 1일부터 1인당 1억원입니다.
근거      : 예금자보호법 시행령 개정 (2025-09-01 시행)
```

사용자: **"예금자 보호 한도가 5천만원 맞죠?"**

```
아닙니다. 예금보호한도는 2025년 9월 1일부터 1인당 1억원입니다. [관리자 정정]
원금과 소정이자를 합하여 금융회사별로 1인당 1억원까지 보호됩니다. [출처1]

※ 안내 문서 일부에 이전 기준(5천만원)이 남아 있을 수 있습니다.
근거: 예금자보호법 시행령 개정 (2025-09-01 시행)
```

**`[관리자 정정]` 마커를 `[출처N]`과 분리한다.** 문서 근거와 관리자 주입 사실을 사용자가 구분할 수 있어야 하고, 검증기도 두 가지를 다르게 취급해야 한다.

### 6-8. 비용·성능 영향

| 항목 | 영향 |
|---|---|

| 대시보드 지표 | **가드 발동률** · 가드별 발동 건수 · 가드 적용 답변의 👎 비율 |

## 9. 탭 ⑦ 문서 처리 — 청크 크기·오버랩 (재빌드 필요)

### 9-1. ⚠️ 이 탭만 성격이 다르다

①~⑦ 중 **이 탭의 값만 저장 즉시 반영되지 않는다.** 바꾸면 문서를 다시 잘라 임베딩을 전부 새로 계산해야 하고, **연쇄로 세 가지가 무효화된다.**

| 연쇄 | 내용 |
|---|---|
| 1 | **검색 프리셋 전부 무효** — `rag.py` 명시: "이 값들은 181청크 코퍼스와 한 세트다. 옛 청킹(215)에서 `RRF_K=4`를 쓰면 single이 .8946 → .865로 떨어진다" |
| 2 | **인덱스 전체 재생성** — FAISS·BM25·임베딩(1024차원) 재계산 |
| 3 | **큐폼 조합 테이블 근거 무효** — 청크 ID가 바뀐다. 실제로 215→181 재청킹으로 MSDR 14행 중 **11행**의 근거가 이미 끊겼다 |

그래서 UI는 **슬라이더가 아니라 "재빌드 마법사"** 여야 한다.

```
값 변경 → [미리보기: 청크 수·길이 분포 변화] → [A/B 평가 실행]
        → 결과 확인 → [적용 & 재빌드] → 검색 프리셋 재튜닝 안내
```

**적용 버튼은 A/B 평가를 돌리기 전에는 비활성**으로 둔다.

### 9-2. 파라미터 4종 + 실행 옵션

| 파라미터 | 현재값 | 범위 | 의미 |
|---|---|---|---|
| `CHUNK_SIZE` | **800자** | 400 ~ 1200 | 한 조각의 **목표 상한**. 문단·섹션 경계를 우선하므로 고정 크기가 아니다 |
| `OVERLAP` | **100자** | 0 ~ 300 | 조각 사이에 겹쳐 넣는 분량. 문장이 경계에서 잘리는 것을 완화 |
| `MIN_CHUNK` | **60자** | 20 ~ 150 | 이보다 짧은 파편은 앞 조각에 병합 |
| `TABLE_GAP_MAX` | **12** | 0 ~ 30 / 무제한 | 표를 쪼개지 않고 통째로 유지할 때, 표 사이 산문을 몇 줄까지 흡수할지 |
| (실행 옵션) `원문 재수집` | **끔** | 켬/끔 | 켜면 KDIC 홈페이지에서 원문을 새로 받아온다 (§9-7) |

### 9-3. 현행 코퍼스 실측

```
청크 181개 · 평균 387자 · 중앙값 283자 · 최대 2,613자 · 최소 64자
800자 초과 3개 · 60자 미만 0개
```

**최대 청크가 2,613자로 상한 800을 크게 넘는다.** 버그가 아니라 의도다 — 표는 쪼개면 의미가 깨지므로 `TABLE_GAP_MAX` 규칙이 통째로 유지한다(§9-5). 즉 `CHUNK_SIZE`는 **표가 아닌 산문에만 적용되는 상한**이다.

### 9-4. 오버랩 A/B 실측 — 늘리면 오히려 나빠진다

`eval_overlap.py` · GT 무수정 · 215청크 기준

| OVERLAP | 청크 수 | K5 single | K3 single | K10 single | 판정 |
|---:|---:|---:|---:|---:|---|
| **100** | 215 | **0.8946** | **0.7973** | 0.9541 | ✅ **현행 채택** |
| 200 | 218 | 0.8892 | 0.7811 | 0.9514 | −0.5%p |
| 300 | 222 | 0.8811 | 0.7730 | 0.9622 | −1.4%p |

관리자에게 전달할 요지: **"겹치는 분량을 늘리면 더 정확해질 것 같지만, 실제로는 반대다."** 중복 내용이 늘면 서로 다른 조각이 같은 문장으로 경쟁해 순위가 흐려진다. 조각 수만 늘어(215→222) 저장·검색 비용도 올라간다.

### 9-5. 표 처리가 가장 큰 레버다

`eval_tablefix.py` — 표를 쪼갤지 통째로 둘지의 A/B

| 설정 | 청크 수 | 최대 길이 | K5 전체 | K5 **single** | K5 **and** |
|---|---:|---:|---:|---:|---:|
| 표 분할 (구) | 215 | 800자 | 0.8209 | 0.8946 | **0.3091** |
| **표 유지 (현행, gap≤12)** | **181** | **2,613자** | **0.8977** | **0.9081** | **0.8182** |

**복합 조건 질문(`and`)에서 0.309 → 0.818, +51%p.** 이 프로젝트에서 단일 변경으로 가장 큰 개선이었다. 보호대상 금융상품표처럼 "은행 / 보험 / 저축은행"이 한 표에 있는 문서는 쪼개는 순간 답이 조각나기 때문이다.

부수 효과도 컸다 — 청크가 자기완결적이 되면서 메타 부스트 의존이 줄어 `BF_BOOST 0.12→0.06`, `FACET_BOOST 0.15→0.05`로 재튜닝됐다. `rag.py` 주석: **"메타는 본문이 빈약할 때의 대용품이고 본문이 채워지면 물러나야 한다."**

### 9-7. 실행 방식 — 재청킹 vs 재수집

적용 버튼은 **두 가지 작업 중 하나**를 돌린다. 관리자가 토글로 고른다.

| 구분 | 무엇을 하나 | 홈페이지 접속 | 예상 소요 | 언제 쓰나 |
|---|---|---|---|---|
| **재청킹** (기본) | 저장된 원문(`data/parsed/`)으로 다시 자르고 다시 계산 | ❌ 없음 | 약 2분 | 파라미터만 바꿀 때 |
| **재수집 + 재청킹** | KDIC 홈페이지에서 원문을 새로 받아온 뒤 전 과정 | ✅ 있음 | 약 8~12분 | 원문이 바뀌었을 때 (부보금융회사 명단 분기 갱신 등) |

**파라미터 변경만으로는 홈페이지에 접속할 필요가 없다.** 이 구분을 화면에 명시하지 않으면 관리자가 매번 재수집을 돌려 불필요한 부하가 걸린다.

### 9-8. 진행 상태 알림 (필수 요구사항)

재빌드는 수 분이 걸리므로 **버튼을 누른 뒤 아무 표시가 없으면 관리자가 중복 실행**한다. 세 단계로 알린다.

**① 실행 전 확인 모달**

```
저장된 원문으로 문서를 다시 자르고 전체를 재계산합니다.

예상 2분. 진행 중에도 챗봇은 기존 설정으로 정상 동작합니다.

계속할까요?          [취소]  [실행]
```

재수집을 켠 경우에는 "KDIC 홈페이지에서 원문을 다시 수집한 뒤…" + "예상 8~12분"으로 문구가 바뀐다.

**② 진행 중 배너** — 화면 상단 고정. 단계별 진행 표시.

| 재청킹 | 재수집 + 재청킹 |
|---|---|
| 문서 다시 자르기 → 임베딩 재계산 → 검색 인덱스 빌드 → 평가셋 검증 | 홈페이지 수집 → 문서 파싱 → 문서 다시 자르기 → 임베딩 재계산 → 검색 인덱스 빌드 → 평가셋 검증 |

배너에 반드시 포함할 문구: **"진행 중에도 챗봇 서비스는 기존 인덱스로 정상 동작합니다."** 이게 없으면 관리자가 서비스 중단으로 오해한다. 진행 중에는 다른 탭의 저장을 잠근다.

**③ 완료 알림 + 남은 작업 안내**

```
재빌드가 완료됐습니다.

다음 작업이 남아 있습니다:
· 검색 프리셋 재튜닝            (개발자)
· 되묻기 조합 테이블 근거 재매핑  (개발자)
· 최신성 가드 재검토            (관리자)
```

### 9-9. 비교 패널 — 파라미터 옆에 평가셋 결과를 즉시 표시

값을 움직이면 **바로 옆 패널에 현재 설정과의 비교**가 뜬다. 평가셋 TEST 430문항 · 지표는 앵커 hit@5.

| 항목 | 현재 | 변경 후 | 차이 |
|---|---:|---:|---:|
| 조각 수 | 181 | 215 | +34 |
| 전체 정확도 | 0.8977 | 0.8209 | −0.0768 |
| 단일 조건 질문 | 0.9081 | 0.8946 | −0.0135 |
| 복합 조건 질문 | 0.8182 | **0.3091** | **−0.5091** |

**핵심 원칙 — 측정하지 않은 조합에 숫자를 지어내지 않는다.** 실제로 A/B를 돌려본 조합은 4개뿐이다.

| 조합 (크기·겹침·표유지) | 조각 | 전체 | 단일 | 복합 | 출처 |
|---|---:|---:|---:|---:|---|
| 800 · 100 · ON | 181 | .8977 | .9081 | .8182 | `eval_tablefix` (현행) |
| 800 · 100 · OFF | 215 | .8209 | .8946 | .3091 | `eval_tablefix` |
| 800 · 200 · OFF | 218 | .8163 | .8892 | .3091 | `eval_overlap` |
| 800 · 300 · OFF | 222 | .8116 | .8811 | .3273 | `eval_overlap` |

그 외 조합을 고르면 배지가 **"미측정 조합"**으로 바뀌고 수치 자리에 `?`가 뜬다. 안내 문구: *"이 조합은 아직 평가한 적이 없습니다. [A/B 평가 실행]을 눌러 실제 수치를 확인한 뒤 적용하세요."*

측정된 조합인데 현재보다 나쁘면 경고 박스가 뜬다 — 예: *"이 조합은 현재보다 나쁩니다. 전체 정확도 0.8977 → 0.8209, 복합 조건 질문은 0.8182 → 0.3091로 크게 떨어집니다."*

**적용 버튼은 A/B 평가를 돌리기 전까지 비활성**이다. 미측정 조합을 근거 없이 적용하는 경로를 UI 차원에서 막는다.

### 9-10. 재빌드 체크리스트 (화면에 그대로 표시)

```
□ 1. A/B 평가 실행 후 결과 확인   (필수 — 미실행 시 적용 불가)
□ 2. 인덱스 재생성                (임베딩 재계산)
□ 3. 검색 프리셋 재튜닝           ← 개발자 작업. 기존 프리셋 3종은 무효
□ 4. 큐폼 조합 테이블 근거 재매핑  ← 청크 ID가 바뀜
□ 5. 대시보드 "코퍼스 버전" 갱신
□ 6. 최신성 가드 재검토           ← 정정 대상 구값이 사라졌을 수 있음
```

### 9-11. 비용·소요

| 항목 | 현재 규모 기준 |
|---|---|
| 임베딩 재계산 | 181청크 × 1024차원 — 로컬 모델이라 **LLM 비용 0** |
| A/B 평가 | 검색만 재실행 — **LLM 비용 0** |
| 소요 시간 | 재청킹 + 인덱스 빌드 수 분 · 파라미터 재튜닝(8,064 config)은 별도 |

**청크 파라미터 변경에는 LLM 비용이 들지 않는다.** 로컬 임베딩 모델(`dragonkue/BGE-m3-ko`)을 쓰기 때문이다. 관리자가 부담 없이 A/B를 돌려볼 수 있다는 뜻이라, 화면에 명시하는 편이 좋다.
