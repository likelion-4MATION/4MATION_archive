# 앵커 텍스트 기반 정답 라벨링 — 초기 아이디어

> **상태**: 초기 아이디어(제안) · 미착수
> **레이어**: 평가 / 정답(GT) 라벨링 — `eval_TF.py`, `testset*.jsonl`
> **핵심 원칙**: 청킹·인덱싱 파이프라인 **무수정**. 정답을 청크가 아니라 **내용(앵커 텍스트)** 에 건다.
> **한 줄**: 정답을 청크 경계가 아니라 안정적 내용 스팬에 라벨 → 재청킹해도 라벨이 안 깨진다.

---

## 1. 문제의 방향 — 왜 앵커 텍스트에 도달했나 (결정 흐름)

```
[시작]  문서 단위 정답 체크 + 청크 단위 반환
          └→ 같은 문서 안의 '다른 청크'가 정답으로 계산됨 (오탐)
          └→ 정확도(hit@k) 상한 과대추정  ── 문제 발생
                     │
                     ▼
[후보 1]  청크 단위로 정답까지 라벨링
          └→ 오탐은 잡힘
          └→ 그러나: 관리자 UI로 청킹 단위를 조절할 예정
          └→ 청크 경계가 바뀌면 라벨을 전부 다시 매겨야 함  ── 취약
                     │
                     ▼
[채택]   앵커 텍스트 방식
          └→ 정답을 '내용 스팬'에 건다 (청크 ID에 안 묶임)
          └→ 청크 단위가 바뀌어도 라벨 그대로  ── 재라벨링 0
```

### 1.1 시작 — 문서 단위 정답 + 청크 단위 반환의 오탐

현재 `hit@k` 판정은 **검색된 청크의 `parent_doc_id`가 `gt_docs`에 있으면 적중**으로 센다(`eval_TF.py`의 `_tag`: `chunk["parent_doc_id"] in gt` → ✅정답).

- 하지만 LLM은 **개별 청크**를 받는다.
- 정답 문서의 **엉뚱한 청크**(정답 스팬이 없는 청크)가 검색돼도 "적중"으로 계산된다.
- → 검색은 맞은 것처럼 보이나 실제 근거는 빠진 **오탐(false positive)**. `hit@k`가 실사용보다 후하게 나오는 상한 과대추정(기존 캐비앗 H12 "평가셋 self-referential → 수치는 상한 추정"과 같은 방향의 결).

| 상황 | 문서 단위 판정 | 실제 |
|---|---|---|
| 정답 문서의 정답 청크가 top-k | ✅ 적중 | ✅ 맞음 |
| 정답 문서의 **다른** 청크가 top-k, 정답 청크는 밖 | ✅ 적중(오탐) | ❌ 근거 누락 |

### 1.2 후보 1 — 청크 단위 정답 라벨링 (기각)

정답을 청크 단위(`gt_chunk_ids`)로 라벨하면 오탐은 사라진다. 하지만:

- **관리자 UI로 청킹 단위(크기·오버랩·규칙)를 조절하는 기능이 예정**돼 있다.
- 재청킹하면 `chunk_id`가 전부 바뀐다 → **라벨 전량 무효** → 매번 재라벨링.
- 청크 단위 GT 라벨링은 비용이 크다고 이미 플래그된 사안.
- → 청크 경계에 묶인 라벨은 근본적으로 **가변 기준에 정답을 매다는 셈**이라 취약.

### 1.3 채택 — 앵커 텍스트 방식

정답을 **청크가 아니라 '앵커 텍스트'(정답이 담긴 안정적 내용 스팬)** 에 건다.

- 평가 시: top-k 청크 중 하나라도 그 **앵커 스팬을 포함**하면 적중.
- 청크 경계가 어떻게 바뀌든 앵커 스팬은 **내용**이라 어느 청크엔가 그대로 존재.
- → **라벨 불변, 재라벨링 0.** 오탐 문제와 재청킹 취약성을 **동시에** 해소.

---

## 2. 앵커 텍스트 방식이란

정답의 위치를 "이 청크"가 아니라 "이 문장/구절이 든 곳"으로 표현한다.

| 항목 | 문서 단위(현행) | 청크 단위(후보1) | 앵커 텍스트(채택) |
|---|---|---|---|
| 라벨 기준 | `doc_id` | `chunk_id` | 내용 스팬(앵커) |
| 오탐 제거 | ✗ | ○ | ○ |
| 재청킹 견고성 | ○(문서는 안 바뀜) | ✗ (chunk_id 변동) | ○ (내용은 불변) |
| 재라벨링 비용 | 낮음 | 높음(매 재청킹) | 없음 |

**판정 로직(초안)**: `hit@k = ∃ chunk ∈ topk : gt_anchor ⊂ chunk.text` (문서 일치 조건은 병용 가능 — anchor + doc_id AND).

---

## 3. 왜 재청킹에 강한가 (핵심 근거)

- 청크 경계는 **가변 파라미터**(크기·오버랩·표 분할 규칙)의 산물 → 관리자 UI가 건드릴 대상.
- 앵커 텍스트는 **소스 원문에서 나온 불변 내용** → 파라미터와 무관.
- 검색이 "다 저장하고 낼 때 고른다"이듯, 평가도 "**내용에 정답을 걸고, 청킹이 바뀌어도 그 내용을 담은 청크를 찾으면 적중**"으로 대칭을 맞춘다.
- 소스 원문 무수정 가드레일과도 정합적(라벨이 소스 내용에서 파생, 청킹 산출물에 의존 안 함).

## 4. 접점 — 최소 변경

| 파일 | 변경 | 비고 |
|---|---|---|
| `testset*.jsonl` | 정답에 `gt_anchors`(앵커 스팬 리스트) 추가 | 기존 `gt_docs` 병존 — 점진 전환 |
| `eval_TF.py` | 판정 `parent_doc_id in gt` → **앵커 포함 여부**(+선택적 doc AND) | `_tag`/`first_doc_rank` 계열 판정부만 교체 |
| 청킹·인덱싱·검색 | **변경 없음** | 원칙 준수 |

- `hit@1/hit@3/MRR` 지표 정의는 유지, "적중"의 판정 기준만 앵커 포함으로 교체.
- 전환 시 **같은 평가셋으로 문서단위 vs 앵커 두 판정을 나란히 산출** → 오탐이 얼마였는지 정량화(문서단위 대비 앵커 판정의 hit@k 하락폭 = 오탐 규모).

## 5. 라벨 스키마 초안

```jsonc
{
  "question": "...",
  "business_function": "...",
  "gt_docs": ["kdic-...-selectScrn"],          // 기존 유지(병용)
  "gt_anchors": ["착오송금 반환요구에 대한 이의 제기서 양식"]  // 신규: 정답 내용 스팬
}
```

- 앵커는 **정답을 유일하게 특정하는 최소 스팬**(짧고 변별력 있게).
- 정규화(공백·줄바꿈)는 검색 토큰화와 동일 규칙으로 맞춰 포함 판정 안정화.

## 6. 착수 전 필수 검증 — 앵커가 "유일·안정" 신호인가

| 검증 | 확인할 것 |
|---|---|
| 유일성 | 앵커 스팬이 정답 문서 내 **정답 청크에만** 등장(다른 청크·다른 문서 중복 없음) |
| 포함성 | 현재 청킹에서 앵커가 **한 청크에 온전히** 들어감(경계에 잘려 두 청크로 쪼개지지 않음) |
| 재청킹 시뮬 | 크기·오버랩을 바꿔 재청킹 후에도 앵커가 여전히 **어느 한 청크에 온전히** 잔존 |
| 정규화 일치 | 라벨 앵커와 청크 텍스트의 공백/특수문자 정규화가 동일 |

> 포함성이 깨지는 앵커(경계에 잘림)가 있으면, 앵커를 더 짧게 잡거나 표 청크 무분할 규칙과의 상호작용을 함께 점검.

## 7. 리스크·오픈 이슈

| # | 이슈 | 대응 방향 |
|---|---|---|
| R1 | 앵커가 여러 청크·문서에 중복 등장 → 오적중 | 유일성 검증에서 걸러 더 변별적인 스팬으로 교체 |
| R2 | 앵커가 청크 경계에 잘림 → 포함 판정 실패 | 앵커 축소 / 정규화 통일 / 표 무분할 규칙 확인 |
| R3 | 라벨링 손이 여전히 든다(앵커 선정) | 청크 재라벨링 대비 **1회성** — 재청킹에도 재사용되므로 총비용은 낮음 |
| R4 | 부분일치 vs 완전포함 기준 모호 | 초기엔 완전포함(엄격) → 필요 시 정규화 후 포함으로 완화 |

## 9. 한 줄 요약

> 문서 단위 정답은 같은 문서의 엉뚱한 청크를 적중으로 세어 정확도를 부풀리고, 청크 단위 정답은 관리자 UI 재청킹 때마다 라벨이 깨진다. **정답을 청크가 아니라 앵커 텍스트(안정적 내용 스팬)에 걸면** 오탐도 잡고 재청킹에도 라벨이 그대로 살아남는다. 청킹·인덱싱은 손대지 않고 평가 판정 기준만 "앵커 포함"으로 바꾼다.
