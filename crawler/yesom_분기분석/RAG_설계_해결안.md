# 공공기관 RAG 챗봇 설계 — 해결안

기존 논의(`RAG_설계_논의_요약.md`)에 대한 검토 및 구체화. 결론 방향(**LLM Query Understanding + Metadata-aware Hybrid RAG, 멀티턴은 보조**)은 유효하며, 예솜24 챗봇 실측 + KDIC 크롤 데이터 분석에서 확인한 내용을 근거로 4가지를 보강한다.

- 작성일: 2026-08-03
- 근거: 예솜24 백엔드 실측(`/chat/message` 시나리오 노드 방식), 분기 트리(`yesom24_통합분기트리.md`), 첨부 태깅 스키마(`attachment_tagging_schema.md`)

---

## 0. 기존 결론 평가

기존 문서의 결론과 권장 파이프라인은 타당하다. 특히 "본문/첨부 분리 저장", "Structured Output ≠ 룰베이스", "임베딩은 역할이 달라질 뿐 필요하다"는 판단은 맞다. 아래 4개 항목은 이를 **폐기가 아니라 구체화·수정**하는 것이다.

| # | 기존 문서 | 보강/수정 |
|---|---|---|
| 1 | 룰베이스로 보일까 우려 | "임베딩 폴백"으로 반박 — 관점 전환 |
| 2 | 슬롯 예시가 평면적(applicant_type/role/proxy) | **업무별 슬롯 분리 + 2단계 라우팅** (수정) |
| 3 | "항상 멀티턴은 아님" | **질문유형 게이팅**으로 명문화 |
| 4 | Metadata Filtering + "슬롯 오추출 가능" | **소프트 부스트 위주 + 리랭커 강화** (수정) |

---

## 1. "룰베이스처럼 보인다" 우려 → 관점 전환으로 해소

비교 기준은 "멀티턴 사용 여부"가 아니라 **분기를 누가 저작하는가**이다.

- **예솜24(경쟁 시나리오 챗봇)**: `#착오송금서류` 같은 **사람이 손으로 짠 시나리오 노드 + NLU 인텐트**. 표현이 어긋나면 *"질문 의도가 명확하지 않아요"* 로 **하드 데드엔드**. (실측 실패 예: "채무조정 금액", "예금+대출 상계", "세전/세후")
- **본 프로젝트**: 분기(슬롯)를 **크롤 데이터에서 자동 도출**, LLM이 슬롯을 채우되 **슬롯이 비거나 틀려도 시맨틱 검색이 폴백**. → 우아하게 degrade.

즉 Slot Filling이 룰베이스가 아니라는 논지에 더해, 진짜 방어논리는 **"실패 시 임베딩 폴백이 존재한다"**는 점이다. 예솜24의 실패 지점들이 곧 본 프로젝트의 우위 증거다.

---

## 2. 슬롯 스키마는 "업무별"로 분리 — 2단계 라우팅 (가장 중요)

평면적 단일 슬롯은 부적합하다. 실측 트리상 업무마다 축이 다르다.

```
착오송금:  { party(송금인/수취인), sub_task, qualification(본인/대리인), subject, method, 적격조건(금액·기한) }
예금보험금: { sub_task, subject, method, 지급조건(상계·보증채무) }
예금자보호: { 예금자유형(개인/법인), 상품유형, 한도조건 }   ← 본인/대리인 축 없음
미수령금:  { 종류, subject, method, 신청기간 }
은닉재산:  { 신고수단, 신고자격, 익명여부 }
채무조정:  { sub_task(금액/확인/불가사유/서류), 사후관리 }
```

**2단계 라우팅**
1. **1단계 분류**: `business_function` + `질문유형(절차형/조건형/정의형)` 판별
2. **2단계 슬롯 채움**: 해당 업무 전용 슬롯 스키마 로드 후 필요한 슬롯만 추출

→ `yesom24_통합분기트리.md`가 곧 업무별 슬롯 정의서 역할을 한다.

---

## 3. 슬롯·멀티턴은 "절차형 질문"에만 — 질문유형 게이팅

멀티턴을 질문유형으로 게이팅하면 대부분 원턴으로 끝나 시나리오 챗봇처럼 보이지 않는다.

| 질문유형 | 예시 | 처리 |
|---|---|---|
| 정의형 | "예금보험금이 뭔가요?" | 슬롯 0 → 바로 시맨틱 검색 |
| 조건형 | "보호한도 얼마?", "보이스피싱도 대상?" | 슬롯 0 → 바로 검색 (되묻지 않음) |
| 절차형·서식형 | "착오송금 서류 뭐 필요해?" | subject/method 슬롯 비면 **1회만** 되물음 |

핵심: **되묻기는 절차형에서 슬롯이 실제로 비었을 때만** 발동. 조건형·정의형은 절대 되묻지 않는다.

---

## 4. 메타데이터는 "하드 필터" 최소화 — 소프트 부스트 + 리랭커

슬롯 오추출 시 하드 필터는 정답 문서를 통째로 배제한다. 완충 설계가 필요하다.

- **하드 필터**: 고신뢰 슬롯만 (`business_function` 수준).
- **소프트 부스트**: subject/method/condition 은 필터가 아니라 **리랭커 가중치**로. (일치 시 점수 가산)
- **폴백 경로**: 슬롯 신뢰도 낮으면 **필터 없이 검색 → 리랭커가 정리**.
- **Cross-encoder는 조건형 질문에 사실상 필수**: 규정 예외조항은 메타데이터로 못 잡고 본문에만 있으므로 벡터+리랭커가 잡아야 한다. (기존 문서 "예외는 본문에 존재"와 정합)

이 설계가 기존 문서의 "임베딩은 여전히 필요"를 실행 레벨로 구체화한다.

---

## 5. 첨부문서 반환 — 인덱싱 단에서 이미 해결됨

"한 청크에 여러 첨부" 문제의 근본 원인은 크롤 단위가 **페이지(parent_doc_id)** 라 서식 여러 개가 한 문서에 묶인 것. Query Understanding이 아니라 **인덱싱(태깅) 설계**로 푼다. (기존 문서 "추가 고려사항"의 판단이 맞음)

- 첨부는 **임베딩하지 않음** (빈 서식은 검색신호 약함) → **Tier B**, `attachment_id` 부여.
- 반환은 벡터 유사도가 아니라 **해소된 슬롯(subject/method/condition)과 메타데이터 JOIN**.
- **공통 서식**(신청서·동의서 등)은 `subject=공통` 와일드카드로 항상 포함.
- **표 데이터**(부보금융회사 목록 등)만 **Tier A**로 임베딩(자주 갱신 → 별도 주기).

→ 상세 스키마·26건 분류는 `attachment_tagging_schema.md` / `attachment_tagging_template.csv` 참조.

## 6. 최종 권장 아키텍처

```
사용자 질문
   ↓
[1] LLM Query Understanding
     ├─ business_function 분류
     └─ 질문유형(정의형/조건형/절차형) 판별
   ↓
[2] 업무별 Structured Output (슬롯 채움)
   ↓
[3] (절차형 & 슬롯 결손 시에만) 최소 멀티턴 1회
   ↓
[4] Retrieval
     ├─ 하드 필터: business_function (고신뢰만)
     ├─ Hybrid: Vector + BM25
     └─ 소프트 부스트: subject/method/condition (리랭커 가중)
   ↓
[5] Cross-encoder Re-ranker (조건형 필수)
   ↓
[6] 첨부 JOIN: 해소된 슬롯 ↔ attachment_index (공통 와일드카드 포함)
   ↓
[7] LLM 답변 생성 (본문 + 필요한 첨부만)
```

**프로젝트 정체성**: 순수 RAG도 순수 룰베이스도 아닌 **LLM 기반 Query Understanding + Metadata-aware Hybrid RAG**. 멀티턴은 검색 품질 향상을 위한 적응형 질의이해 과정. (기존 결론 유지)

## 7. 차별점 & 검증 (데모 설득 포인트)

- **진짜 moat**: 크롤 → 정제 → **태깅 자동화** → 원클릭 파이프라인 → API RAG. 멀티턴은 부수 기능.
- **정량 비교**: "예솜24가 실패하는 조건 질문을 우리는 커버한다"를 데모에 명시. 실측 실패 사례:
  - 예금자보호: 여러계좌 합산 · 예금+대출 상계 · 세전/세후
  - 채무조정: "신청 대상자는?" (되묻기 유도), 인증서/시스템 기술 질문
- **평가**: 기존 `testset_natural_*.jsonl`의 `gt_docs`로 Retrieval 정확도(Recall@k) 측정. 슬롯 스키마는 통합 트리를 정답 라벨로 검증.
- **우선순위**: ① 미수령금 FAQ 크롤 보강(현재 0건) ② 예금자보호·채무조정 실패 질문 커버 ③ 착오송금 사후관리 4종(철회·해제·계좌변경·대리인변경) 노드화.
