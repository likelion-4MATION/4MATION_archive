# KDIC 챗봇 관리자 콘솔

비전공자 관리자가 **파라미터 조절만으로** 정확도·응답시간·비용을 조정하고, 법령 변경 시 답변을
정정하며, 문서 재빌드를 실행하는 웹 콘솔. 목업 사양서(`관리자콘솔_사양서.md`)의 구현체다.

## 설치·실행

```bash
# 리포지토리 루트에서 챗봇과 같은 가상환경을 쓴다
source .venv/bin/activate
python -m pip install -r admin/requirements.txt

# 리포지토리 경로를 알려준다 (기본값: admin/ 의 상위 폴더)
export KDIC_REPO=$PWD

cd admin
python -m uvicorn main:app --reload --host 127.0.0.1 --port 8600
# → http://127.0.0.1:8600
```

챗봇(Streamlit)과 **별도 프로세스**로 뜬다. 포트만 겹치지 않으면 동시에 띄워도 된다.
`fastapi`가 없다는 오류가 나면 다른 Python으로 실행 중인 것이므로 `which python`이
리포지토리의 `.venv/bin/python`을 가리키는지 먼저 확인한다.

## 구조

```
admin/
  main.py        FastAPI 라우트 + 정적 서빙
  registry.py    파라미터 레지스트리 — 콘솔의 단일 진실 소스 (31종)
  settings.py    저장소 + 런타임 주입 + 실측 기록 (원본 코드 미수정)
  guards.py      최신성 가드 CRUD·검증·프롬프트 블록·화이트리스트
  attachments.py 첨부 표시명 오버레이 · 파일 업로드 · 레거시 링크 데이터
  runner.py      재빌드·평가·재검증 실행체 (crawler 모듈에 상수 주입)
  jobs.py        잡 관리 — runner 를 단계별로 띄우고 stdout 을 스트리밍으로 읽어 진행률 갱신
  metrics.py     대시보드 지표 + 실측 A/B 근거
  oos_store.py   OOS 안내처·유선 상담·오류 신고 SQLite 저장소와 마스킹
  static/        index.html · app.js · style.css
  data/          admin_config.json · guards.json · attachments.json · uploads/ · backup/ · jobs/
```

## 설계 원칙

**1. 원본 코드를 수정하지 않는다.** 관리자가 바꾼 값은 `data/admin_config.json` 에만 쌓이고,
`settings.apply_runtime()` 이 모듈 상수에 주입한다. `crawler/rag.py` · `chatbot/chain.py` ·
`chatbot/qform_config.py` 는 그대로 둔다. (`qform_config` 는 이미 `SPEC`/`resolve(override)`
패턴을 갖고 있어 그 관례를 따랐다.)

**2. 검증된 조합만 노출한다.** 검색 5축(`RRF_ALPHA`·`RRF_K`·`BF_BOOST`·`FACET_BOOST`·`BF_DOC_CAP`)은
8,064개 조합 그리드에서 고른 한 세트다. 일반 관리자에게는 프리셋 3종만 보이고, 개별 값은
⑥ 고급 탭을 잠금 해제해야 나온다. 직접 건드리면 헤더에 **"검증된 프리셋 아님"** 배지가 상시 표시된다.

**3. 측정하지 않은 숫자를 만들지 않는다.** 정확도 예측은 실측이 있는 지점만 값을 내고, 나머지는
`null` → 화면에 `?` + **미측정** 배지. 정확도에 영향을 주는 축(프리셋 / `k` / 청크)을 **둘 이상
동시에 바꾸면** 곱해서 추정하지 않고 **복합** 배지를 띄운다.

**3-1. 잣대가 다른 두 수치를 나란히 빼지 않는다.** 옛 A/B 표는 **앵커 hit@5**, 재빌드 실측은
**청크 hit@k** 다. 계열이 다르면(`anchor` vs `chunk`) 값을 보여 주되 "빼서 비교하지 말라"는
경고를 띄우고 차이를 계산하지 않는다.

**3-2. 실측이 상수표를 이긴다.** `accuracy_for()` 는 `settings.measured()` 를 먼저 본다.
예전에는 아무것도 안 바꿨을 때 `BASELINE["acc"]`(0.9081 — 181청크 시절 상수)를 그대로 돌려줘서
코퍼스를 바꿔도 '변경 후' 칸이 늘 **0.9081 로 굳어** 있었다. `k` 축도 마찬가지로 이제
실측 `hit@k` 를 쓴다 — 관리자가 고르는 `k` 는 답변에 넣을 문서 수이므로, `hit@k` 가 곧
"정답 근거가 그 안에 들 확률"이다(k=2·4 는 러너가 안 내므로 미측정).

**3-3. 실측은 덮어쓰지 않고 쌓는다.** `record_measured()` 는 최신 1건을 `measured` 에 두면서
같은 기록을 `measured_history` 에도 넣고, 그때 설정 스냅샷(`OPS_KEYS`)을 함께 남긴다. 덮어쓰기만
하면 **'역대 최고'를 알 수 없다** — 직전 값과만 비교되고 지난달이 더 좋았다는 사실은 사라진다.
`metrics.best_of()` 가 그 이력에서 **항목별로 따로** 최고를 고른다(정확도는 최댓값, 콜·응답시간·
비용은 최솟값). 한 시점을 통째로 최고라고 부르면 정확도가 가장 높았던 날의 비용을 최저 비용이라고
우기게 된다. 콜·응답시간·비용은 설정에서 계산되는 값이라 `_config_timeline()` 으로 변경 이력을
거꾸로 되짚어 **실제로 적용됐던 설정들**도 후보에 넣는다. `from` 이 없는 되돌리기 기록에서는
되짚기를 멈춘다 — 그 지점부터는 복원이 아니라 창작이다.

**3-4. 잣대가 다르면 변화율을 내지 않는다.** `k` 를 바꾸면 hit@5 ↔ hit@3 으로 지표 자체가
달라진다. 이때 결과창은 세 숫자를 나란히 보여주되 변화율 칸에 **'잣대 다름'** 을 띄우고 '최고 경신'
판정도 하지 않는다. 나란히 보여주는 것까지가 정직한 한계다.

**3-5. 응답시간·콜·비용은 실제 스위치에 물린다.** `_ops()` 가 폐기된 `earlyBlock` 키를 읽는
바람에 조기차단 비중이 늘 0 이었다 — 응답시간이 무엇을 바꿔도 4.96초에 굳고, 콜 수는 1.72 가
아니라 2.00, 비용은 ₩9.7 이 아니라 ₩11.3 으로 나왔다(`BASELINE` 과 계산이 서로 어긋난 상태).
조기차단은 **토글이 아니라 확정 정책**이므로(`chain._route()` · `orchestrator._process()`)
`FAST_SHARE` 를 조건 없이 적용한다. 이 숫자를 실제로 움직이는 스위치는 셋 — 답변 길이 상한
(`maxTokens`), 되묻기 문구 생성 방식(`askMode`), 되묻기 횟수·적용 업무. 길이 계수(`GEN_SHARE`)는
응답시간과 비용이 **같은 함수**(`_length_factor()`)를 쓰게 해 두 숫자가 어긋나지 않게 하고,
계수가 걸리는 순간 응답시간 등급은 '계산'에서 **'추정'** 으로 내려간다.

**4. 재빌드 변경은 격리한다.** 청크 파라미터는 저장해도 `pending` 에만 들어가고 서비스에 반영되지
않는다. 재빌드가 성공해야 `override` 로 승격된다(`settings.commit_pending()`).

**6. 실행은 한 자리에서.** 검증·재빌드 버튼은 탭 안이 아니라 **좌측 사이드 패널**에 있다. 어느 탭에서
무엇을 바꾸든 거기서 검증 → 빌드 → 재검증까지 이어진다. 잡은 저장된 값(`override + pending`)만
읽으므로 실행 직전에 **미저장 초안을 자동 저장**한다(그러지 않으면 화면 값과 실행 값이 어긋난다).

**5. 값이 보이는데 안 먹는 상태를 만들지 않는다.** 잠긴 항목은 비활성으로 표시하고, `pending`
상태는 토스트와 배지로 계속 알린다.

화면은 **왼쪽 사이드(탐색·조작) + 오른쪽 상단 고정 결과창(읽기)** 으로 나뉜다. 보는 자리와
누르는 자리를 섞지 않는다 — 예전에는 결과·실행 패널이 우측에 세로로 길게 붙어 신선도·질의 분포
같은 우측 정보 카드를 가렸다. 끝난 잡 블록은 한 줄로 접혀 결과창이 화면을 덜 먹는다.

결과창은 머리의 **[접기]** 로 줄일 수 있다. 접으면 **정확도 한 줄만** 남고 나머지 지표·근거·실행
진행 상황은 숨는다. 선택은 `localStorage` 에 남아 새로고침해도 유지되지만, **잡이 새로 돌기
시작하면 자동으로 펼친다** — 진행 상황을 접힌 채로 숨기지 않기 위해서다(저장된 선택은 그대로 둔다).

**색은 예금보험공사 사이트에서 가져왔다.** 크롤 원문(`crawler/data/raw/*.html`)에 인라인으로 남아
있는 kdic.or.kr 스타일시트의 값을 그대로 쓴다 — `.cBlue #1a3370`(브랜드 네이비) · `.cRed #d41024` ·
GNB 현재메뉴 `#d71d30` · 섹션 배경 `#f6f6f6` · progress 트랙 `#dbdbdb` · 본문 `#333` / 보조 `#666`.
상태 배경은 알파가 아니라 **불투명 틴트**(`--ok-bg` 등)로 둔다 — 흰 카드와 회색 섹션 위에서 같은
알파가 다른 색으로 보이기 때문이다.

### 기준 설정으로 되돌리기 (초기화)

고정 패널의 [기준 설정으로 되돌리기]는 `registry.GOLDEN` 으로 되돌린다 — 기본값 + `k=5`
(같은 코퍼스에서 hit@3 0.8108 < hit@5 0.9081 이라 근거 포함률이 높은 쪽).

곧바로 실행하지 않고 **초안으로만 채운다.** 무엇이 바뀌는지 변경 목록에서 보고 나서 저장하거나
[한 번에 실행]을 누르게 하기 위해서다. 버튼에는 다른 항목 수가 표시되고, 같으면 비활성이 된다.

> 이 0.9081은 **앵커 hit@5 · 181청크** 기준이라 지금 대시보드의 **청크 hit@5** 와 직접
> 비교되지 않는다. 되돌린 뒤 [한 번에 실행]으로 같은 잣대의 수치를 다시 재야 한다.
> 확인창에도 이 경고가 그대로 나온다.

고정 패널의 버튼:

| 버튼 | 하는 일 | 홈페이지 접속 | 서비스 영향 |
|---|---|---|---|
| **한 번에 실행** | 청크 설정 변경 여부를 보고 **경로를 스스로 고른다** | 안 함 | 재빌드 경로일 때만 교체 |
| **원문 재수집** | KDIC 홈페이지에서 원문을 새로 받아 재빌드 → 재검증 | **함 (약 10분)** | 교체 |
| ① 테스트셋 검증 | 샌드박스에서만 재청킹·평가 | 안 함 | **없음** |
| ② 적용 & 재빌드 | 실제 인덱스 교체 | 안 함 | 교체 |
| ③ 재검증 | 지금 인덱스를 그대로 평가 | 안 함 | **없음 (읽기 전용)** |

## 챗봇 연동 상태

OOS 안내처와 오류 신고는 현재 챗봇에 연결돼 있다. 아래 두 항목은 기존 관리자 설정과
최신성 가드에 남아 있는 별도 배선 작업이다.

### ① 챗봇 기동 시 설정 로드 (필수)

`chatbot/app.py` 상단에 두 줄:

```python
sys.path.insert(0, str(ROOT / "admin"))
import settings as admin_settings; admin_settings.apply_runtime()
```

콘솔과 챗봇이 다른 프로세스이므로, 챗봇은 **기동 시 1회** 읽는다. 저장 즉시 반영이 필요하면
`answer()` 진입부에서 `apply_runtime()` 을 호출하거나 파일 mtime 을 감시하면 된다.

### ② 최신성 가드를 프롬프트에 주입 (필수)

`chatbot/chain.py` 의 `answer()` 에서 컨텍스트를 만든 뒤:

```python
import guards                                   # admin/ 을 sys.path 에 추가한 상태
gs = guards.match(query, context, business=label)   # 발동 조건이 맞을 때만
if gs:
    block = guards.prompt_block(gs)                 # 프롬프트에 별도 블록으로
    allow = guards.numeric_whitelist(gs)            # ← answer_checks 에 넘길 허용 수치
    guards.bump_fired([g["id"] for g in gs])        # 발동 카운트
```

**`allow` 를 `answer_checks` 에 넘기지 않으면 가드를 켜는 순간 수치 경고가 전건 발생한다.**
`check_numbers()` 가 컨텍스트에 없는 금액을 잡기 때문이다. `answer_checks.run_all()` 에
`extra_allowed: set[str] = frozenset()` 파라미터를 추가하고 `_amount_in()` 비교에 합치면 된다.

### OOS 안내처·오류 신고 (연결 완료)

`chatbot/orchestrator.py`가 비-BF 절을 `chatbot/oos_policy.py`로 보내고,
`admin/oos_store.py`의 게시·활성·링크 정상 안내처만 고정 응답에 사용한다. ⑤ 첨부 탭의
옛 링크 데이터는 이 경로에서 사용하지 않는다. 사용자 오류 신고는 같은 저장소에 마스킹 후
30일 보관되며 ⑨ 오류 신고함에서 처리한다.

> **`chunk.py` 패치는 더 이상 필요 없다.** 초기 설계는 환경변수 4줄을 요구했지만,
> `runner.py` 가 모듈 상수를 직접 주입하는 방식으로 바뀌어 원본 무수정으로 동작한다.

## 재빌드·평가가 실제로 하는 일

`runner.py` 가 crawler 모듈을 **import 해서 상수를 주입한 뒤** 그대로 호출한다.
`pipeline.py` 가 `import chunk as chunk_mod` 로 같은 모듈 객체를 쓰기 때문에,
`chunk.py` 를 고치지 않고도 청크 파라미터가 먹는다(`settings.apply_runtime()` 과 같은 방식).

파이프라인의 원자 단위는 `recollect(url) = fetch → parse → chunk → upsert` 라, **수집·파싱·청킹이
한 줄에 묶여 있다.** 러너는 기본으로 `--use-cache` 를 붙여 `data/raw/*.html` 만 읽는다 —
네트워크를 타지 않는다. `--recrawl` 일 때만 그 플래그가 빠지고 `crawler.fetch_one()` 이 실제로
kdic.or.kr 에 접속한다. 참고로 `--rebuild` 가 인덱스를 `rmtree` 하고 시작하므로 `content_hash`
스킵이 무력화돼 **매번 38개 문서를 전부 다시 임베딩**한다(그래서 재청킹 단계가 33초다).

| 러너 모드 | 인덱스 | 홈페이지 | 서비스 영향 |
|---|---|---|---|
| `eval` A/B 평가 | `data/index_eval` (샌드박스) → 끝나면 삭제 | 안 함 | **없음** — `chunks.jsonl` 은 백업에서 복원 |
| `rebuild` 재빌드 | `data/index` (실제) | 안 함 | 교체. 실패하면 백업에서 자동 복원 |
| `verify` 재검증 | `data/index` 를 **읽기만** | 안 함 | **없음** — 백업조차 뜨지 않는다 |
| `rebuild --recrawl` | 위와 동일 | **함** | 교체 |
| `files` 첨부 받기 | 안 건드림 (`data/files` · `data/parsed` 만) | **함** | 재청킹 전까지 없음 |

실측 소요(2026-08-19 잡 기록): 재청킹+인덱싱 **33초**, 평가셋 448문항 **33초**.

### `recrawl` 은 파라미터가 아니라 버튼이다

한때 재빌드 파라미터(`_p("recrawl", ...)`)였는데, 재빌드가 성공하면 `commit_pending()` 이
`pending → override` 로 승격시켜 **그 뒤 모든 재빌드가 계속 홈페이지에 접속**했다. 관리자가
직접 끄기 전까지 매번 10분이 붙는다. `CHUNK_SIZE` 같은 **값**은 남는 게 맞지만
"이번엔 새로 받아와"는 **동작**이라 같은 자리에 두면 안 된다.

지금은 레지스트리에서 빠졌고 `jobs.start(..., recrawl=True)` 인자로만 넘어간다. 예전 설정
파일에 남은 `recrawl` 키는 `settings.load()` 가 읽을 때 걸러 낸다(파일은 안 건드리고,
다음 `save()` 때 자연히 사라진다).

### 체인(`kind="chain"`) — 경로를 스스로 고른다

`resolve_plan()` 이 `settings.current()`(= override, **지금 인덱스를 만든 값**)와
`effective()`(= override + pending, **적용하려는 값**)를 청크 키에서 비교한다.

| 조건 | 실행 | 소요 |
|---|---|---|
| 청크 키가 같고 깃발도 없다 | `verify` 하나 | **약 35초** |
| 청크 키가 다르다 | `eval → (판정) → rebuild → verify` | 약 175초 |
| `settings.dirty()` 깃발이 서 있다 | 위와 같음 (첨부 재수집 직후 등) | 약 175초 |

프리셋이나 ⑥ 고급 값만 바꾼 경우가 짧은 경로다. 러너가 `apply_search_settings()` 로 그 값을
주입해 평가하므로 **다시 자르지 않고도 효과가 지표에 잡힌다.** 어느 쪽이 돌지는 슬라이더를
움직이는 즉시 고정 패널에 미리 표시된다(`/api/project` 의 `plan`).

강제로 재빌드하고 싶으면 [② 적용 & 재빌드]가 조건 없이 돈다.

### 판정 게이트

1단계 `hit@5` 가 실행 전 실측 기준선(`settings.measured()`)보다 낮으면 재빌드로 넘어가지 않고
잡을 `awaiting` 으로 세워 둔 뒤 `resume()` 신호를 기다린다.

- 대기 상태는 **서버에 있다.** 브라우저를 닫았다 다시 열어도 그대로 남아 있고, 프런트는
  폴링해서 확인 패널을 다시 그린다.
- 30분 안에 응답이 없으면 `aborted` 로 자동 종료된다. 이때 `pending` 도 `override` 도
  `measured` 도 건드리지 않는다 — **아무 일도 없었던 것과 같다.**
- 게이트는 고정 패널의 체크박스로 끌 수 있다(`guard: false`).
- `job["baseline"]` 은 **실행 전 스냅샷**이라 도중에 덮어쓰지 않는다. 완료 화면의
  "실행 전 대비" 열이 이 값을 기준으로 계산된다.

`③ 재검증`이 따로 있는 이유는 **②가 잰 수치와 실제 서비스 인덱스가 같은지 확인**하기 위해서다.
두 값이 다르면 인덱스 교체가 제대로 안 된 것이므로, 결과표에 그 해석을 함께 띄운다.

### 겹침(OVERLAP) 0 방어

`chunk.py` 는 겹침을 `cur[-OVERLAP:]` 로 잘라 붙이는데, 파이썬에서 `s[-0:]` 는 빈 문자열이
아니라 **문자열 전체**다. 따라서 0 은 "겹침 없음"이 아니라 **"직전 누적분 통째 복제"** 로
동작한다(실측: 179 → 195조각, 총 글자수 +18%, `hit@5` 0.7277 → 0.6942).

원본을 고치지 않고 세 겹으로 막는다 — ① 실행 전 preflight 경고 ② `runner.clamp_overlap()`
이 주입 시 1 로 올리고 로그·`injected._warn` 에 남김 ③ `jobs.start()` 가 저장값도 1 로
맞춰 "설정은 0, 코퍼스는 1" 인 어긋남을 막고 변경 이력에 `system` 항목으로 기록.

슬라이더는 **5자 단위**(0~300)다.

### ⚠️ 왜 샌드박스가 필요한가 (초기 구현의 버그)

`rag.Store.build_and_save()` 는 마지막에 **`data/chunks.jsonl` 을 통째로 덮어쓴다.**
평가하려고 `chunk.py` 로 새로 자른 뒤 `Store()` 를 만들면, `Store` 는 기존 인덱스 상태를
읽으므로 **새 청크를 모르는 채 옛 내용으로 `chunks.jsonl` 을 되돌려 버린다.**
초기 구현이 이 함정에 빠져 평가가 1초 만에 끝나고(임베딩을 안 했다) 코퍼스가 조용히 되돌아갔다.

지금은 ① 실행 전 `chunks.jsonl` + `data/index` 를 `data/backup/<ts>/` 에 통째로 뜨고
② 평가는 별도 인덱스 디렉터리에서 돌리고 ③ 끝나면 복원한 뒤 **sha1 로 복원 여부를 검증**한다
(`runner._verify`). 복원은 삭제 후 복사가 아니라 **덮어쓰기**다 — 지우기 권한이 없는 환경에서
`unlink()` 가 실패해 복원이 무산되는 것을 막는다.

백업 디렉터리 이름은 초 단위 타임스탬프인데 **체인은 평가 직후 재빌드를 시작해 같은 초에 두 번
백업을 뜬다.** 그대로 두면 `copytree` 가 `FileExistsError` 로 죽으므로 이름을 유일하게 만들고
`dirs_exist_ok=True` 를 준다. 단독 실행에서는 절대 재현되지 않고 체인에서만 나는 버그였다.

### ⚠️ 평가가 관리자 설정을 무시하던 문제

러너는 평가 직전에 `runner.apply_search_settings()` → `settings.apply_runtime()` 을 부른다.
**이 호출이 없던 동안 모든 평가가 `crawler/rag.py` 의 파일 기본값으로 돌았다.** 프리셋이나
⑥ 고급 값을 바꿔도 지표가 꿈쩍하지 않았고, `BF_MODE` 를 `hard` 로 저장해 둔 상태에서도 실제
측정은 `soft` 로 나갔다. `rag` 는 상수를 호출 시점에 읽으므로 setattr 주입이 그대로 먹는다
(`rag.py` 379행에 "런타임에 `rag.RRF_K` 를 바꿔도 반영되지 않아 A/B가 조용히 틀린다 —
실제로 겪음"이라는 주석이 이미 있었다).

> 이 수정 이전에 기록된 `measured` 값은 **저장된 검색 설정이 아니라 rag.py 기본값 기준**이다.
> 기준선을 다시 맞추려면 [③ 재검증]을 한 번 돌리면 된다.

지표는 콘솔 출력을 정규식으로 긁지 않고 `eval.evaluate_retrieval()`(구 `eval_anchor_v3` — 2026-08-24 통합) 을 직접 호출해
dict 로 받는다. 재빌드가 성공하면 그 값이 `settings.record_measured()` 로 저장되고,
그때부터 대시보드의 "현재 정확도"가 **추정표가 아니라 실측치**가 된다.

동시 실행은 1건으로 제한된다. 진행 상태는 `runner` 가 stdout 에 내는 `__STEP__` 마커를
`jobs.py` 가 스트리밍으로 읽어 갱신하고, 프런트가 1.5초 간격으로 폴링한다.

### 실행 환경 주의

러너는 **검색 스택(faiss·rank_bm25·numpy)이 설치된 파이썬**에서 돌아야 한다. 없으면 산출물을
건드리기 전에 멈추고 무엇이 없는지 알려준다. 챗봇과 같은 가상환경에서 콘솔을 띄우는 것이 가장 간단하다.

## 첨부문서 · 링크 관리 (⑤ 탭)

크롤링 산출물 `crawler/data/doc_attachments.json` 은 **건드리지 않는다.** 관리자 편집분은
`data/attachments.json` 에 오버레이로 쌓이고 조회 시 합쳐진다 — **재크롤링을 해도 고친 표시명이 살아남는다.**

| 기능 | 내용 |
|---|---|
| 표시명 수정 | 인라인 편집. 줄바꿈·`\|`·`※` 가 들어가면 저장 거부 |
| 일괄 정리 | 표 파싱 잔여물에 정제 제안값을 한 번에 적용. 항목별 원복 가능 |
| **내려받기** | 크롤러가 이미 받아 둔 **원본 파일**을 그대로 내려준다 (읽기 전용) |
| **교체** | 새 파일을 올려 그 자리를 대신하게 한다. 원본은 지우지 않아 언제든 되돌린다 |
| 파일 업로드 | pdf·hwp·docx·xlsx 등 · 최대 30MB. `data/uploads/` 에 저장 |
| 외부 링크 추가 | `http(s)://` 만 허용 |

### ⚠️ 첨부 다운로드는 크롤링에 포함되지 않는다

`pipeline.py` 는 `fetch_attachments.py` 도 `link_files.py` 도 부르지 않는다. **원문을 다시
수집해도 첨부 파일은 그대로다.** 원 저자가 정한 순서는

```
parser.py → fetch_attachments.py → link_files.py → chunk.py
```

인데 파이프라인은 1번과 4번만 자동화돼 있다. 그래서 ⑤ 첨부문서 탭에 **[첨부 파일 다시 받기]**
버튼을 두고 가운데 두 단계를 잡으로 돌린다(`kind="files"` → `runner --mode files`).

| 단계 | 하는 일 |
|---|---|
| 현재 상태 백업 | `data/parsed` 만 뜬다 (`link_files` 가 여기를 고쳐 쓴다) |
| 첨부 파일 내려받기 | `fetch_attachments.main()` — 폴라이트 1.5초+지터, 45건 ≈ 2분 |
| 청크 메타에 연결 | `link_files.main()` — parsed 의 첨부에 `local_path`·`sha256` 부착 |

`data/files` 는 백업하지 않는다. 파일을 더하기만 하고 `manifest.json` 은 맨 끝에 한 번에
쓰므로, 중간에 죽어도 옛 매니페스트가 남아 콘솔은 계속 동작한다.

**끝나면 재청킹이 필요하다.** `link_files` 가 `data/parsed` 를 고쳐 썼는데 청크 파라미터는
그대로라, 체인의 경로 판정만으로는 "변경 없음 → 재검증만"이 된다. 그래서 잡이 끝날 때
`settings.mark_dirty()` 로 깃발을 세우고 `resolve_plan()` 이 그 깃발을 보면 **재빌드 경로를
강제**한다. 재빌드가 성공하면 `clear_dirty()` 로 내려간다. 고정 패널의 경로 미리보기와
preflight 경고에도 그 이유가 그대로 뜬다.

### 첨부 파일은 어디에 있나

`doc_attachments.json` 의 `url` 은 **파일 주소가 아니라 원문 페이지 주소**다. 전부
`link_type: onclick_dynamic` 이라 실다운로드는 `gfn_downloadFile(encId, encName)` 토큰을
`POST /cm/file/downloadFile.do`(www) 또는 `/api/cm/file/downloadFile.do`(fins) 로 돌려보내야
받는다. 그 일은 `crawler/fetch_attachments.py` 가 이미 해 뒀다.

```
crawler/data/files/{doc_id}/{원본파일명}      실파일 46건
crawler/data/files/manifest.json             (doc_id, enc_real, enc_temp) → stored_path·sha256
```

콘솔은 이 매니페스트를 `_key(doc_id, item)` 로 조인해 **읽어서 내려주기만** 한다
(`attachments.source_path()`). 경로가 `data/files/` 밖으로 나가면 `None` 을 돌려준다.

### 교체는 삭제가 아니다

`crawler/data/files/` 는 크롤링 산출물이고 재크롤링으로 다시 받아지는 자산이라 지우지 않는다.
교체는 새 파일을 `data/uploads/` 에 올리고 오버레이에
`replace["<key>"] = {filename, note, at}` 를 기록하는 것뿐이다. [교체 취소]는 그 기록을 지우고
올렸던 파일만 정리한다 — 원본은 그대로 남아 있다.

`attachments.resolved(doc_id)` 가 **챗봇이 부를 함수**다: 숨김 제외 · 교체 반영 ·
관리자 추가분 포함한 최종 목록을 돌려준다(`GET /api/attachments/resolved/{doc_id}`).

`data/attachments.json`에 남아 있을 수 있는 옛 안내 사전 시드는 레거시 데이터다. 현재 사용자
OOS 응답은 이를 읽지 않으며, ⑧ OOS 안내처에 별도로 검증·게시한 행만 사용한다.

## 실측 근거의 출처

콘솔이 보여주는 숫자는 전부 리포지토리 실측이다. 코퍼스가 바뀌면 `metrics.py` 상단 표를 갱신해야 한다.

| 값 | 출처 |
|---|---|
| 프리셋 3종 정확도 | `crawler/data/tune_v2_summary.md` (8,064 config 그리드) |

| **지금 서비스 중인 조합** | `metrics.current_point()` — 재빌드 실측 → A/B 표 → 미측정 순 |

`current_point()` 를 따로 둔 이유: ⑦탭의 "현재" 열이 예전엔 `ACC_CHUNK["800|100|1"]` 하드코딩이라
재빌드로 코퍼스가 바뀌어도 옛 조합을 현재라고 우겼다. 지금은 `settings.current()`(= `override`,
실제로 빌드된 조합)에서 키를 만들고 `settings.measured()` 를 최우선으로 쓴다. 재빌드 실측은
전체 앵커 정확도만 내므로 단일/복합 분해는 `null` → **미측정**으로 표시하고 차이를 계산하지 않는다.
지표가 다른 두 지점을 빼서 그럴듯한 숫자를 만들지 않는다는 뜻이다.

## 알려진 제약

- **인증 없음.** 사내망 전용을 전제로 했다. 외부 노출 시 리버스 프록시에 인증을 붙일 것.
- **대시보드의 비용·질의 수는 예시값이 아니라 계산·추정값**이다. 실서비스 로그 저장소가 붙으면
  `metrics.py` 의 `business_mix()`(현재 평가셋 기준)와 비용 항목을 로그 기반으로 교체해야 한다.
- **`apply_runtime()` 은 같은 프로세스에만 즉시 반영**된다. 위 연동 ①번 참조.
- 러너는 `pipeline.main()` 과 `eval.evaluate_retrieval()`(구 `eval_anchor_v3` — 2026-08-24 통합) 의 시그니처에 의존한다.
  그쪽이 바뀌면 러너도 같이 고쳐야 한다(조용히 실패하지 않고 예외로 멈춘다).
- 업로드 파일은 `data/uploads/` 에 그대로 쌓인다. 백업·용량 관리는 운영 몫이다.
- `data/backup/` 은 최근 5개만 유지된다. 코퍼스가 크면 디스크를 확인할 것.
- **판정 게이트의 대기는 프로세스 메모리의 `threading.Event` 로 푼다.** 대기 중 서버를 재시작하면
  잡은 `awaiting` 상태의 파일로 남고 다시 이어갈 수 없다. 이때도 인덱스는 손상되지 않는다(1단계는
  샌드박스라 이미 복원됐다) — 새로 실행하면 된다.
- 체인 한 번은 청크 변경이 있을 때 **약 175초**, 없으면 **약 35초**다. 검증과 빌드가 같은 청킹을
  두 번 하는 것은 **의도된 중복**이다 — 샌드박스에서 먼저 확인하지 않으면 게이트가 성립하지 않는다.
- [원문 재수집]은 재빌드 앞에 샌드박스 검증을 두지 않는다. 바뀐 것이 **파라미터가 아니라 원문**이라
  물릴 후보 설정이 없기 때문이다. 대신 확인창에서 소요 시간과 부작용(가드의 '기존 값', 되묻기
  조합 테이블의 근거 연결이 어긋날 수 있음)을 명시한다.
